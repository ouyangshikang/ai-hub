# Java 学习：Spring 事务注解

> 系列第 39 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「事务是什么」：昨天搞定了最小用法——在 Service 方法上打一个 `@Transactional`，方法里的写库操作就被捆成了一个事务。但这个注解远不止一种写法：哪些异常要回滚？最多允许执行多久？纯查询方法要不要开事务？这些都写在注解的参数里。今天逐个拆解 @Transactional 的常用参数，并回答为什么团队规范里总要求写 `rollbackFor = Exception.class`。

## 1. 今天学什么

昨天见到的是 `@Transactional` 的裸写法，但真实项目的代码评审里你会看到各种变体：有人写 `rollbackFor`，有人写 `timeout`，还有人写 `readOnly`、`isolation`。这些不是风格偏好，每个参数都控制事务的一项具体行为，写错了就是等着出线上事故。今天逐个拆解：rollbackFor 决定哪些异常触发回滚，timeout 给事务时长装保险丝，readOnly 标记纯查询方法，isolation 决定并发事务之间互相看到什么，propagation 决定事务方法互相调用时怎么嵌套——最后这个参数值得单独一篇，今天先混个脸熟。

## 2. 前端工程师视角理解

前端里最贴切的类比是 `fetch(url, options)`：第一个参数说"做什么"，第二个配置对象说"按什么规则做"——要不要带 cookie、超时多少毫秒、遇到重定向怎么办。`@Transactional(...)` 就是打在方法上的"事务配置对象"：方法体负责做什么，注解参数负责出异常、超时、并发时按什么规则处理。

一个关键区别：fetch 的 options 是调用方每次手写，忘了写就自己承担后果；注解是在方法定义处写一次，Spring 运行时统一读取并执行。这就是声明式和命令式的差别——你只声明意图，执行细节交给框架。代价是规则藏在框架里：不知道每个参数的默认值，就会以为"默认行为 = 安全行为"，而坑恰恰出在这。

## 3. 和 JavaScript / TypeScript 的对比

**同样的配置项在 JS 里也存在，但单位和形态不同。** Prisma 里你写 `prisma.$transaction([...], { isolationLevel: 'Serializable', timeout: 5000 })`——isolationLevel 对应 Java 的 isolation，timeout 对应 timeout，但单位是毫秒；Java 的 `@Transactional(timeout = 5)` 单位是秒。前端工程师迁移肌肉记忆时，很容易写出 `timeout = 5000`，结果造出一个 5000 秒的事务。

**Java 的异常二分是 JS 里不存在的概念。** JS 想 throw 什么就 throw 什么，调用方也不被强制处理。Java 把异常分成两类：受检异常（编译器强制你声明或 catch，如 IOException）和运行时异常（RuntimeException 及其子类）。Spring 的默认回滚规则是"只有运行时异常才回滚"——这条规则是历史遗留，被吐槽了很多年，但为了兼容一直没改。TS 里没有这种分类，所以前端背景的人恰恰最容易对它毫无防备。

**TS 装饰器形似而深度不同。** NestJS 里也能往方法上打 `@UseGuards(...)`，看着和 Java 注解一样；但 Java 注解 + Spring 代理的成熟之处在于：框架会为你的 Bean 生成一个代理对象，在方法执行前后自动开事务、提交、回滚。这背后是 AOP 能力，第五阶段后面会专门讲。

## 4. 真实业务场景

**场景：门店系统的顾客退款，一个受检异常让订单集体卡在"退款中"。**

业务背景：顾客在小程序申请退款，后端 refund 方法做三步：① 把订单状态更新为"退款中"，前端立刻展示进度；② 调用风控服务校验（防止薅羊毛、盗刷退款）；③ 风控通过后执行退款并写退款记录。风控 SDK 把"校验拒绝"声明为受检异常 `RefundDeclinedException extends Exception`——这在 Java 里很常见，SDK 作者用受检异常强制调用方显式处理拒绝分支。

事故经过：refund 方法上只写了裸的 `@Transactional`，没写 rollbackFor。某天风控批量拒绝，方法纷纷抛受检异常。按 Spring 默认规则，受检异常不回滚——于是第①步的状态更新被照常提交。结果：大批订单永远停在"退款中"，钱却根本没退，客服被投诉淹没，最后靠工程师写脚本批量修数据。加上 `rollbackFor = Exception.class` 之后，风控拒绝会整体回滚，订单恢复原状态，顾客还能换个方式重试。

## 5. Java 示例代码

```java
@Service
public class RefundService {

    @Resource
    private OrderMapper orderMapper;
    @Resource
    private RefundRecordMapper refundRecordMapper;
    @Resource
    private RiskControlClient riskControlClient;

    /**
     * rollbackFor = Exception.class：受检异常、运行时异常都回滚
     * timeout = 5：超过 5 秒未完成就强制回滚，防止长事务占着连接
     */
    @Transactional(rollbackFor = Exception.class, timeout = 5)
    public void refund(Long orderId, String reason) throws RefundDeclinedException {
        // 第一步：先把状态置为"退款中"，前端立刻能看到进度
        orderMapper.updateStatus(orderId, OrderStatus.REFUNDING);

        // 第二步：风控校验，拒绝时抛受检异常。
        // 如果没写 rollbackFor，这个异常不会触发回滚，第一步会被照常提交
        riskControlClient.check(orderId);

        // 第三步：执行退款并写记录
        orderMapper.updateStatus(orderId, OrderStatus.REFUNDED);
        refundRecordMapper.insert(RefundRecord.of(orderId, reason));
    }
}
```

参数速查：

| 参数 | 默认行为 | 作用 |
|---|---|---|
| rollbackFor | 仅运行时异常回滚 | 声明哪些异常触发回滚 |
| timeout | 不限制 | 事务最长时长（单位：秒），超时强制回滚 |
| readOnly | false | 标记纯查询，便于数据源优化与路由 |
| isolation | 跟随数据库默认 | 并发事务间的隔离级别 |
| propagation | REQUIRED | 事务方法互相调用时如何嵌套（后续专篇） |

## 6. 常见坑

**坑 1：不写 rollbackFor，受检异常不回滚。** 错误理解："加了 @Transactional，出任何异常都回滚。"问题：默认只有运行时异常触发回滚，上面退款场景里受检异常一出，半截数据照常被提交，而且没有任何报错指向事务。正确做法：团队约定统一写 `rollbackFor = Exception.class`，评审时见到裸注解直接打回。

**坑 2：写方法上打了 readOnly = true。** 错误理解："readOnly 只是个优化提示，打错了也无所谓。"问题：MyBatis 确实会忽略它，但如果项目用了动态数据源或读写分离中间件，中间件会按 readOnly 把写 SQL 路由到从库——要么直接报错，要么"写成功了却查不到"。正确做法：readOnly 只打在纯查询方法上。

**坑 3：把 timeout 的单位当毫秒。** 错误写法：`@Transactional(timeout = 5000)`——这是 5000 秒，约 83 分钟，保险丝等于没装。正确做法：单位是秒，普通写事务 3~10 秒足够，确有需要放长的批量任务单独评估再放宽。

**坑 4：随手改 isolation"提升性能"。** 错误理解："READ_COMMITTED 听起来更轻量，改一下试试。"问题：MySQL InnoDB 默认 REPEATABLE_READ，不少并发安全依赖它——比如昨天下单场景那条 `UPDATE ... AND quantity >= #{quantity}` 的扣库存写法，换成 READ_COMMITTED 而不评估并发场景，超卖可能立刻冒出来。正确做法：不写 isolation（跟随数据库默认），确有需要先说清楚并发场景、评审后再改。

**坑 5：注解打了，但压根没生效。** 注解打在 private 方法上，或者被同类里的另一个方法直接调用，事务都不会生效——这比参数写错更隐蔽。展开讲就是明天的主题「事务失效场景」。

## 8. 面试 / 工作中常见问题

### 问题 1：为什么团队规范统一要求写 rollbackFor = Exception.class？

参考答案：Spring 默认只回滚运行时异常，受检异常（如 IOException、SDK 声明的业务异常）默认照常提交。业务代码很难保证抛的每个异常都是运行时异常，漏一个就是"半截数据被提交"的线上事故。统一写 `rollbackFor = Exception.class` 用一条约定消灭这一整类风险，团队行为一致，不依赖每个人记得默认规则。

### 问题 2：readOnly = true 到底有什么用？MyBatis 项目里也有效果吗？

参考答案：它是声明式提示，告诉数据源层"这个事务只读"。MyBatis / JDBC 本身不强制校验，但承接它的中间件会据此做事：动态数据源把请求路由到从库，连接池做只读优化。工程价值在路由和优化，不在校验；打错在写方法上，写 SQL 可能被发去从库，直接报错或查不到刚写的数据。

### 问题 3：不写 isolation，事务用的是什么隔离级别？

参考答案：跟随数据源连接的默认隔离级别，MySQL InnoDB 即 REPEATABLE_READ。Spring 的 isolation 默认值是 DEFAULT，含义就是"不覆盖"。只有明确遇到并发可见性问题、并确认要改成哪一级时才显式指定，且应当评审——降低隔离级别等于放弃数据库的一层并发保证。

## 9. 今日小结

- @Transactional 的参数不是风格，是行为：rollbackFor 管回滚范围，timeout 管时长，readOnly 管读写意图，isolation 管并发可见性，propagation 管嵌套。
- 默认"只有运行时异常回滚"是 Spring 最常见的坑之一，团队约定统一写 `rollbackFor = Exception.class`。
- timeout 单位是秒；readOnly 只给纯查询；isolation 默认跟随数据库（MySQL 是 RR），不要随手改。
- JS/TS 没有异常二分，前端工程师最容易以为"任何异常都会回滚"——记住默认规则恰好相反。
