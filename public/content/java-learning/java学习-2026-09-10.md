# Java 学习：日志排查

> 系列第 50 篇 · 第六阶段：工程化
> 衔接上一篇「配置管理」：昨天反复提到"生效要留痕"，今天讲留痕之后怎么用它查问题。
> **与第 34 篇的分工**：第 34 篇讲**怎么写一行有用的日志**（级别、占位符、必带主键）；今天讲**怎么把日志当证据链用**——traceId 在异步线程和 MQ 里为什么不断链、多实例怎么检索、线上怎么临时开 DEBUG，以及"搜不到日志"本身的排查法。

## 1. 今天学什么

日志排查是把第 34 篇写下的日志**用起来**的手艺：用户说下单失败、报表少了两万条，怎么在十几台机器、几亿行日志里锁定真相。四件事：① 检索三要素**锚点 → 时间窗 → 实例**，顺序错了就是大海捞针；② traceId 的**传递工程**——MDC 是 ThreadLocal，异步、定时任务、MQ 三条路径都会让它断链；③ **运行时动态调级**，不重启把某个包临时开成 DEBUG 取证；④ 反过来查"日志为什么没有"——被级别挡了、被磁盘丢了、只搜了一台机器。

它属于工程化阶段而不是语法阶段：功能 bug 只影响一次请求，查不出根因的故障会吃掉整组人半天，并直接决定事故恢复时长。

## 2. 前端工程师视角理解

前端排查线上问题你手里有**浏览器**：DevTools 一开，Network 看请求、Console 看日志、Sources 打断点，而且这台机器正是出问题的那台。后端这套全没了——服务跑在远端容器里，不能断点、没有 DevTools，**日志系统就是后端唯一的手术台**。

对应关系很整齐。Network 面板里一条请求一行、能按 Fetch/XHR 过滤、能勾 Preserve log——后端的"一行一请求 + traceId"就是它的服务端版本。而**日志的字段检索**（`level:ERROR AND storeId:8801`）更像你熟悉的**埋点**：前端埋点之所以不用自由文本，是为了能过滤、能聚合；后端结构化日志同一个理由——`log.info("订单{}成功", id)` 这种自由文本机器只能全文扫，字段化之后才是可查询的证据。

最需要一个新直觉的是**多实例**。前端一个用户一次会话只有一份运行时；后端同一个接口有 3~10 个副本对等接流量，**这次失败可能只发生在其中一台**（那台的本地缓存刚好过期、那个连接池刚好泄漏）。所以后端排查的第一课不是"搜什么关键词"，而是"我是不是把所有实例都搜了"——只搜一台机器的日志文件，是新手最常见的假阴性来源。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Spring Boot 后端 |
|---|---|---|
| 排查入口 | DevTools：本地复现 + 断点 | 只有日志/指标/链路，线上不可断点 |
| 上下文载体 | 一次会话一份运行时 | 多副本对等，需按实例聚合 |
| traceId 来源 | 自己塞请求头 `x-trace-id`，网关再传 | 入口 Filter 生成/复用，跨线程、跨 MQ 手工续 |
| 日志形态 | `console.log` 自由文本 | 占位符 + 字段化 JSON，供检索系统索引 |
| 提级调试 | 直接 `debugger` / 加 log 重跑 | 运行时改级别（actuator），但要防敏感信息与性能 |
| 关联证据 | Sentry issue + breadcrumbs | 日志 + metrics + trace 三者对齐时间轴 |

**断链这件事前端几乎碰不到。** 前端 JS 是单事件循环，`console.log` 天然属于当前这次调用，不需要"把上下文带进异步"。后端一次请求会被切成多个线程：线程池执行、`@Async`、MQ 消费者线程、定时任务线程，而 MDC 的实现是 `ThreadLocal`——**换线程即丢上下文**。所以 Java 里 traceId 能贯通，靠的不是日志框架聪明，而是每次切换线程都显式把 Map 复制过去。理解了这一条，第 42 篇 AOP 那层"环绕"和第 44 篇定时任务"没有入口请求"的困惑就都能落地。

## 4. 真实业务场景

**场景：某门店订单接口偶发下单失败，日志"看起来一切正常"。**

业务背景：门店订单服务 8 个实例，大促第二天运营反馈个别门店下单偶尔失败、重试又成功——典型的**偶发 + 局部**问题。

排查过程撞了三次墙。第一次按关键词搜"下单失败"，只捞到全局异常兜底（第 33 篇）那条 `系统异常`，几百条、没有门店维度，看不出规律。第二次登进**一台**机器 grep `SocketTimeoutException`，没有，于是判定"不是下游超时"——而失败全部集中在承接那家门店流量的两台实例上，另六台确实干净。第三次想看 SQL 耗时，但 Mapper 级别是 INFO，DEBUG 没输出；改配置发版要四十分钟，那个时段早就过去了。

根因最后是靠锚点浮出来的：入口加统一 `traceId` 响应头 → 让前端把失败请求的 traceId 报回来 → 按 traceId 检索 → 发现同一 traceId 下出现两个线程名，说明中间走了异步 → 在异步提交处补上 MDC 传递 → 完整链路最后一行是风控接口 `ReadTimeout`：超时配的是 800ms，而风控大促期 P99 是 950ms。改一个配置项（第 49 篇）+ 补一条 warn 日志，收工。

**用错的代价**：不是"多花两小时"，而是把一次**本可定位的偶发故障**熬成"用户重试就好"的口头结论——问题每天重演，且没人能证明它已经好了。

## 5. Java 示例代码

**入口：有则复用、无则生成，响应头回吐给前端——这是排查的起手式。**

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID = "traceId";
    private static final String HEADER = "X-Trace-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp,
                                    FilterChain chain) throws ServletException, IOException {
        // 复用上游（网关/调用方）的 traceId，全链路才是同一个 id
        String traceId = StringUtils.hasText(req.getHeader(HEADER))
                ? req.getHeader(HEADER) : UUID.randomUUID().toString().replace("-", "");
        MDC.put(TRACE_ID, traceId);
        resp.setHeader(HEADER, traceId);            // 前端报错截图就能带上它，锚点闭环
        try {
            chain.doFilter(req, resp);
        } finally {
            MDC.remove(TRACE_ID);                   // 线程复用，不清会串到下个请求
        }
    }
}
```

**线程池：把上下文带过去，而不是指望它自己跟过去。**

```java
@Bean("orderExecutor")
public ThreadPoolTaskExecutor orderExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(16);
    executor.setMaxPoolSize(32);
    // ★ 每次提交任务时包装 Runnable：复制提交线程的 MDC，执行完还原
    //   不配这个装饰器，异步方法里的日志 traceId 就是空的，链路断在这里
    executor.setTaskDecorator(runnable -> {
        Map<String, String> ctx = MDC.getCopyOfContextMap();
        return () -> {
            Map<String, String> previous = MDC.getCopyOfContextMap();
            if (ctx != null) MDC.setContextMap(ctx); else MDC.clear();
            try { runnable.run(); }
            finally { if (previous != null) MDC.setContextMap(previous); else MDC.clear(); }
        };
    });
    executor.initialize();
    return executor;
}
```

**MQ 消费者：traceId 要随消息体走（第 47 篇的 RabbitMQ 链路）。**

```java
// 发送侧：写进消息属性，而不是塞进业务 DTO
rabbitTemplate.convertAndSend("order-exchange", "order.paid", msg, m -> {
    m.getMessageProperties().setHeader(TraceIdFilter.TRACE_ID, MDC.get(TraceIdFilter.TRACE_ID));
    return m;
});

/**
 * 消费侧：@Header 取回，手动放进本线程的 MDC —— 消费线程与生产线程毫无关系。
 * 为聚焦链路传递，这里省略了第 47 篇的手动 ack 与 msgId 幂等，实际代码不能省。
 */
@RabbitListener(queues = "stock-order-paid")
public void onMessage(OrderPaidMsg msg,
                      @Header(AmqpHeaders.DELIVERY_TAG) long tag,
                      @Header(name = TraceIdFilter.TRACE_ID, required = false) String traceId) {
    MDC.put(TraceIdFilter.TRACE_ID,
            StringUtils.hasText(traceId) ? traceId : "orphan-" + System.nanoTime());
    try {
        stockService.deduct(msg.orderNo());
    } finally {
        MDC.clear();
    }
}
```

**运行时取证：不改代码、不发版，把某个包的级别临时打开。**

```bash
# 查当前生效级别（effectiveLevel 才是真相，configuredLevel 可能为 null 表示继承父级）
curl -s http://order-svc:8080/actuator/loggers/com.example.store.mapper
# 临时开 DEBUG 取证
curl -X POST http://order-svc:8080/actuator/loggers/com.example.store.mapper \
     -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}'
# 查完立刻关：留着既是性能开销，也可能把参数打进日志（第 37 篇脱敏）
# configuredLevel 传 null = 清除运行时级别，恢复继承父级；此设置只改内存，重启即失效
curl -X POST http://order-svc:8080/actuator/loggers/com.example.store.mapper \
     -H 'Content-Type: application/json' -d '{"configuredLevel":null}'
```

## 6. 常见坑

**坑 1：异步之后 traceId 断链，还坚持用关键词搜。** 现象：链路上半段有 traceId，进了线程池或 MQ 就没了，只能退回"按时间 + 关键词捞"，一次故障查两小时。原因：MDC 是 `ThreadLocal`，不显式复制就随线程丢失。正确做法：线程池配 `TaskDecorator`；`@Async` 与 `CompletableFuture` 走同一个装饰过的 executor；MQ 用消息头传递；定时任务没有 HTTP 入口，就在任务开始时 `MDC.put("traceId", jobId)` 自造一个。

**坑 2：只搜一台实例的日志文件就下结论。** 错误结论："代码里没有这条 error，说明没报错。" 原因：多副本对等部署下，问题可能只落在一台（本地缓存、连接池、所在节点的磁盘或网络差异）。正确做法：检索必须**按服务名聚合所有实例**，日志行固定带 `pod`/`hostname` 字段；反过来说，"只有这一台有"本身就是重要线索。

**坑 3：`loggers` 端点改完级别，重启就没了。** 现象：取证时开成 DEBUG，重启后回到 INFO，同学以为"配置丢了"。原因：actuator 改的是**运行时内存级别**，不落盘。正确做法：临时取证用它，长期策略写回配置——`logging.level.*` 由第 49 篇的配置中心下发，刷新后所有实例一致；两者别互相冒充。

**坑 4：DEBUG 常开，或级别直接压到 WARN。** 前者把日志量放大十几倍，采集管道丢弃、磁盘打满，敏感参数成批落盘；后者把 INFO 里的业务主键和状态变化丢掉，等于自己拆掉检索锚点。正确做法：**默认 INFO + 关键节点显式埋点 + 需要时按包临时提级**，并给采集链路加水位告警——日志被静默丢弃必须能发现。

- **第 34 篇「日志规范」**：那篇保证单行日志"可检索"，今天保证**一次故障可追溯**——它是弹药，今天是枪。
- **第 47 篇「消息队列基础」**：消费者线程与生产线程毫无关系，跨进程 traceId 只能靠消息头续上，这补齐了那篇漏掉的一条可观测链路。

## 8. 面试 / 工作中常见问题

### 问题 1：线上偶发报错，没有 traceId，你怎么查？

参考答案：先用**能确定的维度收窄**：时间窗（报错分钟 ±2）、接口路径、异常类名、门店/用户主键，把候选缩到几十条；再用这些行的线程名反查同线程的邻近日志。事后补两件事：入口加 traceId 响应头，让前端报错截图能带回锚点；给异步和 MQ 补上 MDC 传递。

### 问题 2：怎么在不重启的前提下临时开 DEBUG？风险是什么？

参考答案：走 actuator 的 `/actuator/loggers/{包名}` POST 改 `configuredLevel`，注意它只改内存、重启失效，且要对**所有实例**分别执行。风险有三条：日志量放大导致采集丢弃或磁盘打满；DEBUG 常打印 SQL 参数、请求体，敏感信息泄漏；改完忘记关，第二天性能莫名变差。所以要按包最小范围开、查完立刻置回 null。

### 问题 3：一次请求的日志只捞到一半，通常是什么原因？

参考答案：按概率排。① 异步/线程池/MQ 断了 traceId（最常见）；② 网关、下游服务用另一个 id 体系，没在出口把 traceId 透传下去；③ 多实例只搜了一台；④ 时间窗与时区不一致，日志按 UTC 切割、查询用本地时间（第 29 篇那个坑）；⑤ 日志级别或 appender 把该范围挡掉了。①②属于埋点缺失，③④⑤属于检索姿势问题。

## 9. 今日小结

- 检索三要素按顺序用：**锚点（traceId/主键）→ 时间窗 → 实例**，顺序颠倒就是翻日志而不是查日志。
- MDC 是 `ThreadLocal`：线程池要 `TaskDecorator`、MQ 要消息头、定时任务要自造 id，异步不接续就等于断链。
- 多实例是新的默认前提：**必须按服务聚合所有实例**，"只有这一台有"本身就是结论。
- 运行时提级是取证手段，不是配置管理：actuator 改内存、重启失效，长期策略交给配置中心下发。
- "日志没有"也是一种证据缺口：级别、采样丢弃、时区切割、只搜一台，四个方向逐个排。

原因：今天练的是"故障发生了怎么查"，更省钱的姿势是**上线前就知道它会在哪个并发度坏掉**。场景里那条根因——超时配 800ms、P99 却是 950ms——本质是个容量参数，它应该被压出来，而不是被大促压出来。第六阶段第 4 项「接口压测」接着讲：TPS/RT/P99 该盯哪个、压测数据怎么不污染生产（第 48 篇的环境边界）、线程池与连接池参数怎么调（今天的 `orderExecutor` 就是被压对象），以及怎么用今天的日志定位曲线拐点。
