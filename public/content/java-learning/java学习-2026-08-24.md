# Java 学习：事务是什么

> 系列第 38 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「数据脱敏」：那一篇给第四阶段「精度、安全与稳定性」收了尾——前面十几篇解决的都是"单次操作如何正确、如何安全"。从今天开始进入第五阶段，第一个问题来自最常见的业务动作：下单 = 扣库存 + 写订单 + 记流水，三步写库必须要么全成功、要么全失败——中间挂了怎么办？这就是事务要解决的。

## 1. 今天学什么

真实业务很少"只写一次库"：下一个订单、退一次款、调一次价，一个动作往往对应好几条 SQL。如果其中一条执行到一半失败了，数据就停在一个"做了一半"的中间状态——库存扣了，订单却没写进去。这种数据不一致比接口报错严重得多：接口报错用户刷新一下就好，数据库里的脏数据不会自己恢复。事务（Transaction）就是数据库提供的机制：把一组操作捆成一个单元，要么全部生效，要么全部回滚，像什么都没发生过。Java 后端里你基本不会手写 `BEGIN` / `COMMIT`，Spring 用 `@Transactional` 注解声明式地把整个 Service 方法包进一个事务里。

## 2. 前端工程师视角理解

你一定写过这样的代码：

```js
// 前端串联两个请求
await api.deductStock(skuId, 1);   // 第一步成功了
await api.createOrder(items);      // 第二步抛错了
```

现在问自己：第一个请求已经成功，库存已经扣了，怎么办？答案是前端没办法——请求发出去就是泼出去的水，HTTP 世界里没有"撤销"按钮。你能做的最好的补救，是再调一个"恢复库存"接口，但这个补偿请求本身也可能失败，越补越乱。

后端没有这个困境，因为数据库自带"撤销功能"，就是事务。执行三条 SQL 之前先声明：这是一个整体。全部成功，数据库才真正落盘提交；任何一步抛错，数据库把已经执行的修改全部擦掉，回到执行前的样子。关键在于：这个回滚是数据库保证的，哪怕服务器中途崩溃、断电，也不会停在半提交状态——这比你手写任何补偿逻辑都可靠。

再用前端熟悉的东西类比：你在状态管理里改三个互相关联的字段，改到一半出错了，状态停在半截，页面渲染出不一致的画面，所以你希望"要么全改、要么别改"。事务就是数据库版本的这个诉求，只是保证强度高得多。

## 3. 和 JavaScript / TypeScript 的对比

**JS 世界里没有原生"事务"这个概念。** 前端操作是一次性请求，没有回滚一说；Node.js 里最接近的是 Prisma 的 `prisma.$transaction([...])` 或 Mongoose 的 session——但注意，它们本质上是调用数据库的事务能力，不是 Node 自己有了回滚能力。事务能力始终住在数据库这一层，Java 的 `@Transactional` 只是向框架声明"这个方法请帮我用上数据库事务"。

**用法形态正好相反。** JS/TS 里事务是显式函数调用：你要手动把代码包进 `$transaction(async (tx) => { ... })`，直观，但忘了包就没有事务。Java 里是声明式的：在 Service 方法上打一个 `@Transactional`，Spring 会在方法执行前自动开启事务、正常返回时提交、抛异常时回滚，业务代码里一行事务相关的代码都不用写。好处是干净，代价是规则藏在框架里——你不了解规则，就会踩"注解不生效"的坑，后面几天会专门讲。

**为什么 Java/Spring 这么设计？** 因为 Java 后端的事务边界几乎总是和"业务方法"对齐：createOrder 这个方法整体要么成功要么失败。用注解把事务绑定到方法上，就省掉了每个方法里重复写"开启-提交-回滚"的样板代码。这是典型的 Java 思路：用声明表达意图，把执行细节交给框架。

## 4. 真实业务场景

**场景：连锁门店系统下单，一杯咖啡触发三次写库。**

业务背景：顾客在小程序下单一杯咖啡，后端要做三件事：① 在门店库存表里把这个 SKU 的库存减一；② 在订单表插入一条订单记录；③ 在库存流水表插入一条出库记录，供门店打烊对账和总部审计使用。三张表互相独立，三条 SQL 也互相独立。

最初的版本没有事务，大促期间就出事了：① 执行成功后，② 恰好因为订单号生成重复抛了异常——库存扣了，订单不存在。门店侧凭空少一杯可售库存却查不到原因，总部对账时发现几十个"库存窟窿"，只能靠工程师翻日志一条条手工修。还有反向事故：订单写成功了、扣库存失败了，造成超卖——顾客付了钱，门店却没货可做，只能退款加赠券安抚。

加上 `@Transactional` 之后，这三步写库变成一个原子操作：任何一步失败就整体回滚，顾客看到的只是"下单失败，请重试"，数据库里不留任何脏数据。

## 5. Java 示例代码

```java
@Service
public class OrderService {

    @Resource
    private StockMapper stockMapper;
    @Resource
    private OrderMapper orderMapper;
    @Resource
    private StockLogMapper stockLogMapper;

    // @Transactional 打在 Service 方法上：方法内所有数据库写操作同属一个事务
    // rollbackFor = Exception.class：任何异常都回滚（容易漏，见下面常见坑）
    @Transactional(rollbackFor = Exception.class)
    public Long createOrder(CreateOrderDTO dto) {
        // 第一步：扣库存。返回受影响行数，为 0 说明库存不足
        int rows = stockMapper.deduct(dto.getStoreId(), dto.getSkuId(), dto.getQuantity());
        if (rows == 0) {
            // 抛业务异常，事务回滚
            throw new BizException(ErrorCode.STOCK_NOT_ENOUGH, "库存不足，无法下单");
        }

        // 第二步：写订单主记录
        Order order = OrderConverter.from(dto);
        orderMapper.insert(order);

        // 第三步：写库存流水，供门店对账
        stockLogMapper.insert(StockLog.of(dto, order.getId()));

        // 三步中任何一步抛异常，Spring 都会回滚已执行的全部 SQL；
        // 只有三步全部成功，事务才提交，方法才会正常返回
        return order.getId();
    }
}
```

```java
public interface StockMapper {
    // 注意 WHERE 里的 AND quantity >= #{quantity}：
    // 让数据库在一条 UPDATE 里判断库存够不够，并发时由行锁排队，
    // 比"先在 Java 里查出来再判断"可靠——两个请求不会同时读到同一份余量
    @Update("UPDATE stock SET quantity = quantity - #{quantity} " +
            "WHERE store_id = #{storeId} AND sku_id = #{skuId} " +
            "AND quantity >= #{quantity}")
    int deduct(@Param("storeId") Long storeId,
               @Param("skuId") Long skuId,
               @Param("quantity") Integer quantity);
}
```

## 6. 常见坑

**坑 1：catch 把异常吞掉，事务以为成功了。** 错误写法：`try { orderMapper.insert(order); } catch (Exception e) { log.error("写入失败", e); }`，然后方法继续往下走、正常返回。问题：Spring 判断是否回滚，依据是"异常有没有抛出方法外"，你自己 catch 掉了，Spring 就认为方法成功，照样 commit——半截数据被提交，而且没有任何报错。正确做法：catch 之后要么重新抛出，要么显式标记回滚；不知道怎么办就抛出去，交给全局异常处理器。

**坑 2：不写 rollbackFor，checked 异常不回滚。** 错误理解："加了 @Transactional，出任何异常都会回滚。"问题：默认只有运行时异常（RuntimeException）触发回滚，如果你的代码抛的是 IOException 这类受检异常，默认行为是照常提交。正确做法：团队统一约定写 `@Transactional(rollbackFor = Exception.class)`。

**坑 3：事务里塞了耗时操作。** 错误写法：在 createOrder 里插完订单，顺手调短信接口发通知、再调积分系统的 HTTP 接口。问题：方法不结束事务就不提交，数据库连接一直被占用，相关行上的锁也不释放；第三方接口一慢，连接池被耗尽，整个下单入口跟着不可用。正确做法：事务只包"必须原子的数据库写操作"，发短信、通知积分这类动作放到事务提交之后执行。

**坑 4：以为回滚能撤销一切。** 错误理解："事务回滚了，就当什么都没发生。"问题：事务只能回滚数据库写入——已经发出去的短信、已经上传到 OSS 的文件、已经发出的 MQ 消息，都不在回滚范围内。正确做法：有外部副作用的操作放到事务提交之后；必须放在方法里的，就要想清楚"一半成功"时怎么补偿。

## 7. 和之前知识的连接

- **第 8 篇「Controller / Service / Mapper 分层」**：现在可以回答"事务为什么打在 Service 层"——Controller 只负责收参和返回结果，Mapper 只执行单条 SQL，"多条 SQL 组合成一件业务"的地方只有 Service。@Transactional 放在 Controller 太粗（把序列化也算进去了），放在 Mapper 太细（单条 SQL 不需要）。
- **第 33 篇「全局异常处理」**：事务机制和全局异常处理器是配套的一对：异常抛出方法外，先触发回滚，再被 @RestControllerAdvice 接住转成统一错误响应。当时说"异常要抛出去、不要吞掉"，今天看到了吞掉它的具体代价——事务失效。
- **第 25 篇「接口幂等性」**：事务回滚后，顾客大概率会再点一次"下单"，重试会不会产生重复订单，就看幂等设计。事务保证"失败不留脏数据"，幂等保证"重试不产生重复数据"，两件事合起来才是下单安全的完整闭环。

## 8. 面试 / 工作中常见问题

### 问题 1：用大白话解释一下什么是事务？什么场景需要它？

参考答案：事务把一组数据库操作捆成一个单元，要么全部成功提交，要么全部失败回滚，中途崩溃也不会停在半完成状态。凡是"多步写库必须同生共死"的业务都需要它：下单（扣库存 + 写订单 + 写流水）、退款、转账、结算。判断标准很简单：问自己"其中一步失败后，留在库里的数据说得通吗"，说不通就该加事务。

### 问题 2：加了 @Transactional，线上还是出现了一半成功一半失败的数据，你会排查什么？

参考答案：按概率从高到低查：① 方法内部是不是 catch 了异常没往外抛——最常见；② 抛的是不是受检异常，而没写 rollbackFor；③ 方法是不是 private，或者被同类内部调用——这都会绕过 Spring 代理，注解根本不生效；④ 数据库表引擎是否支持事务（MySQL 的 MyISAM 就不支持）。这份清单也是后两天「事务失效场景」的预告。

### 问题 3：为什么不建议在事务里调用第三方接口？

参考答案：事务从方法开始持续到方法结束，期间数据库连接一直被占用，修改过的行上的锁也不释放。第三方接口不受你控制，一旦超时或变慢，事务就被拖住，连接池迅速耗尽，整个写入口不可用——一个外部依赖拖垮自己的核心链路。正确做法是事务里只做数据库写入，短信、MQ、外部回调等放到事务提交之后。

## 9. 今日小结

- 事务让多步数据库写入"要么全成功，要么全回滚"，是数据一致性的最后一道防线。
- 前端没有回滚能力，请求串联失败只能靠补偿；数据库事务是真正的"撤销"，由数据库本身保证。
- Java 里不手写 BEGIN/COMMIT：在 Service 方法上打 `@Transactional(rollbackFor = Exception.class)`，Spring 自动开启、提交、回滚。
- 回滚依赖"异常被抛出方法外"——catch 吞异常，事务一定照样提交。
- 事务要短：只包数据库写操作，耗时调用和外部副作用一律挪到事务外。
