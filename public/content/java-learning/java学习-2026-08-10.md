# Java 学习：null 与空指针

> 系列第 30 篇 · 第四阶段：精度、安全与稳定性
> 前两天分别解决了金额和日期"有值时怎么算对"，今天处理更高频的线上事故来源——"没有值"。查不到记录的 `selectOne` 返回 null、报表 `SUM` 在没有匹配行时返回 null、用户没填的字段是 null，对这些 null 的任何一次 `.方法()` 调用，都会抛出后端闻风丧胆的 `NullPointerException`（NPE）。

## 1. 今天学什么

Java 里 `null` 表示"这个变量没有指向任何对象"。引用类型（对象、数组、字符串、包装类）都可以被赋值为 null，而一旦你对 null 调用方法或访问属性，程序立刻抛出 `NullPointerException` 并中断当前逻辑——它不是编译错误，而是运行时才暴露的事故。

NPE 之所以在 Java 后端如此出名，是因为 Java 的类型系统对 null 完全不设防：方法签名写着返回 `User`，实际却可能返回 null，编译器不会提醒调用方去判空。一个服务里几十个接口、成百上千次方法调用，只要有一处漏判，线上日志里就多一摞红色堆栈。

今天的目标是建立一套肌肉记忆级别的防 NPE 姿势：知道 null 会从哪些地方冒出来（数据库聚合函数、查无记录的查询、没填的字段、方法返回），以及每种情况的标准防御写法。

## 2. 前端工程师视角理解

你对这类错误其实再熟悉不过了。JS 里 `const name = user.name`，如果 `user` 是 null，控制台立刻报错 `Cannot read properties of null (reading 'name')`——Java 的 NPE 和它是同一类错误，只是换了个名字。区别在于 JS 给了你两件防身武器：可选链 `user?.name` 和空值合并 `user?.name ?? '匿名'`，一行代码安全落地。

Java 没有 `?.` 运算符，至今没有。所以 Java 的防御只能靠显式判空：`if (user != null)`、工具方法 `Objects.equals(a, b)`、以及下一篇要讲的 `Optional`。初看会觉得啰嗦，但好处是所有判空逻辑都明晃晃写在代码里，评审时一眼能看到作者考虑过哪些分支。

另一个视角差异：JS 是动态类型，null 什么时候出现全靠运行时才知道，所以大家习惯了处处 `?.` 保底；Java 是静态类型，理想情况是"类型即契约"，但 null 恰恰是类型系统的一个漏洞——`String` 类型的字段照样可以是 null，编译器不管。Java 社区后来的补救手段（`@Nullable` / `@NonNull` 注解、Optional）都是在给这个漏洞打补丁，明天会详细讲。

## 3. 和 JavaScript / TypeScript 的对比

**概念数量不同。** JS 有两个"空"：`undefined`（声明了没赋值、对象上没这个属性）和 `null`（主动表示"没有"）。Java 只有一个 `null`，语义上更接近"引用没有指向对象"。从 JS 切过来不需要纠结两者的区别，但也少了 `??` 这种只针对 null/undefined 的精准兜底运算符。

**访问空值的行为几乎一样。** JS 访问 null 的属性抛 `TypeError`，Java 对 null 调用方法抛 `NullPointerException`，都是运行时崩溃。差异在防御工具：JS 用 `?.` 和 `??` 一个表达式解决；Java 只能 `if` 判空或用 `Objects` 工具类，没有语法糖。

**类型系统对 null 的态度不同。** TS 开启 `strictNullChecks` 后，`User | null` 和 `User` 是两个类型，不判空直接编译报错——null 被纳入了类型系统。Java 做不到这一点，方法返回 `User` 时你无法从签名判断它会不会是 null，只能靠文档、注解或读实现。这是前端工程师转 Java 最需要适应的一点：**在 TS 里编译器替你盯 null，在 Java 里得自己盯。**

**包装类型拆箱是 Java 特有的坑。** JS 的 number 没有"null 的 number"这种状态；Java 的 `Integer` 可以是 null，但把它赋给基本类型 `int` 时会自动拆箱（相当于隐式调用 `intValue()`），null 一拆就炸。这类 NPE 在 JS 世界完全没有对应物，要单独警惕。

## 4. 真实业务场景

**场景：门店月度经营报表，统计本月 GMV 并展示最近一笔订单的备注。**

业务背景：运营后台的门店详情页要展示"本月 GMV"和"最近订单备注"。后端一个接口里做两次查询：`SUM(total_amount)` 聚合本月 GMV，`selectOne` 取该门店最新一条订单。

两个查询都藏着 null。第一，本月一家新门店还没开过单，`SUM` 在没有匹配行时返回的不是 0 而是 SQL 的 NULL，映射到 Java 就是 null 的 BigDecimal——如果直接 `gmv.compareTo(target)` 判断是否达标，当场 NPE，整个报表接口 500，运营页面白屏。第二，`selectOne` 查无记录时返回 null，直接 `latestOrder.getRemark()` 同样 NPE；就算订单存在，备注字段用户没填也是 null，还要再防一层。

如果写错，症状不是"数据不准"而是"接口直接挂掉"，而且只在特定门店（新店、无单店）上复现，测试环境拿老店数据永远测不出来——这正是 NPE 类事故阴险的地方。

## 5. Java 示例代码

```java
// Service：月度报表，两处查询结果都可能为 null
public StoreMonthReportVO monthReport(Long storeId, LocalDate month) {
    // 沿用第 29 篇的左闭右开区间算法
    LocalDateTime begin = month.atStartOfDay();
    LocalDateTime end = month.plusMonths(1).atStartOfDay();

    // 坑点 1：没有匹配行时 SQL 的 SUM 返回 NULL，Java 侧拿到 null
    BigDecimal gmv = orderMapper.sumAmountByStore(storeId, begin, end);
    if (gmv == null) {
        gmv = BigDecimal.ZERO; // 空月 GMV 是 0 而不是 null，语义要给前端交代清楚
    }

    // 坑点 2：查无记录时 selectOne 返回 null
    Order latestOrder = orderMapper.selectLatestByStore(storeId);
    String lastRemark = "暂无订单";
    if (latestOrder != null && latestOrder.getRemark() != null) { // 订单和备注两层判空
        lastRemark = latestOrder.getRemark();
    }

    StoreMonthReportVO vo = new StoreMonthReportVO();
    vo.setStoreId(storeId);
    vo.setGmv(gmv);
    vo.setLastRemark(lastRemark);
    return vo;
}
```

## 6. 常见坑

**坑 1：Mapper 查询结果直接用，不判空。** 错误写法：`orderMapper.selectById(id).getStatus()`。问题：查无记录时返回 null，链式调用立刻 NPE，而且堆栈里只看到调用行，排查时还得回头确认到底是哪个环节为 null。正确做法：先接收结果再判空；查详情类接口查不到记录时应返回明确的业务错误码（呼应第 21 篇状态码设计），而不是让 NPE 冒到全局异常处理器。

**坑 2：包装类型 null 拆箱成基本类型。** 错误写法：`Integer count = configMap.get(key); int c = count;`。问题：`count` 为 null 时，赋值给 `int` 触发自动拆箱，等价于 `count.intValue()`，直接 NPE。这类问题在循环、缓存取值场景高频出现。正确做法：拆箱前先判空，或给默认值 `int c = count == null ? 0 : count;`。

**坑 3：聚合函数结果当非 null 用。** 错误写法：拿到 `SUM` / `MAX` 的结果直接 `.add()` 或 `.compareTo()`。问题：SQL 聚合函数在无匹配行时返回 NULL（`COUNT` 除外，它返回 0），Java 侧就是 null。正确做法：聚合结果一律先判空补默认值（第 5 节的写法），或在 SQL 里 `SELECT IFNULL(SUM(total_amount), 0)` 收口。

**坑 4：长链式调用一路点到底。** 错误写法：`order.getUser().getAddress().getCity()`。问题：链条上任何一环为 null 都会 NPE，且你根本不知道断在哪一环。正确做法：拆开逐层判空，或重新审视数据模型——如果城市是必填展示项，也许该在下单时就校验并冗余存到订单表（呼应第 14 篇参数校验的思路）。

**坑 5：返回 null 的集合。** 错误写法：查询无结果时 `return null;`。问题：每个调用方都得先判空，总有人会忘，忘了就是 NPE。正确做法：返回空集合 `Collections.emptyList()`，调用方可以放心直接 for 循环和 stream，这也是"接口契约不给调用方挖坑"的体现。

## 8. 面试 / 工作中常见问题

### 问题 1：NullPointerException 一般怎么防？你们项目里有什么实践？

参考答案：核心是"null 出现的地方都显式处理"。查询结果先判空再使用；聚合函数结果补默认值；比较用 `Objects.equals` 或常量在前；方法入参用 `Objects.requireNonNull` 快速失败；集合类返回值用空集合代替 null。项目层面还可以上 `@Nullable` / `@NonNull` 注解配合静态检查，以及用 Optional 表达"可能为空"的返回值（下一篇的主题）。

### 问题 2：为什么 `Integer a = null; int b = a;` 会抛空指针？

参考答案：`Integer` 是包装类型，可以持有 null；赋值给基本类型 `int` 时编译器自动插入拆箱调用 `a.intValue()`，而 a 是 null，对 null 调用方法自然抛 NPE。本质是"自动装箱拆箱"语法糖掩盖了 null 检查。规避方式：涉及包装类型的算术和赋值前先判空，或明确使用基本类型贯穿整条链路。

### 问题 3：方法查不到数据时，返回 null 还是空集合还是抛异常？

参考答案：分情况。返回集合的方法一律返回空集合（`Collections.emptyList()`），不返回 null，让调用方零成本遍历；返回单个对象的方法，若"查不到"是正常业务分支（如查最近订单但还没有订单），返回 null 或 Optional.empty 并要求调用方处理；若"查不到"代表数据异常（如按订单号查已支付的订单却不存在），应抛出带明确错误码的业务异常，而不是返回 null 让调用方猜。

## 9. 今日小结

- Java 只有一个 null，对 null 调用方法即抛 NPE；它是运行时事故，编译器不提醒。
- 和 JS 的 TypeError 同源，但 Java 没有 `?.` 和 `??`，只能显式判空——TS 里编译器帮你盯 null，Java 里自己盯。
- null 的高发地：selectOne 查无记录、SUM 等聚合函数无匹配行、用户未填字段、包装类型拆箱。
- 防御肌肉记忆：查询结果先判空、聚合结果补默认值、比较用 Objects.equals、必传参数用 requireNonNull、返回空集合不返回 null。
- NPE 阴险在"特定数据才复现"：新店、空月、未填字段，测试环境的老数据永远测不出来。

原因：今天学的防御全靠手写 `if (x != null)`，写多了代码又啰嗦又容易漏。Java 8 给出的答案是 `Optional`——把"这里可能没有值"写进类型，让编译器提醒你处理空值，思路上很像 TS 的 `User | null`。但它并非万能钥匙，滥用 Optional（当字段、当参数、`get()` 不判断）反而制造新问题。明天讲 Optional 的正确用法、适用边界，以及为什么阿里规范劝你别把它到处乱用。
