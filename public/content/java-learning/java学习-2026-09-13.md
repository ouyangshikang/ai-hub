# Java 学习：单元测试

> 系列第 53 篇 · 第六阶段：工程化
> 衔接上一篇「慢 SQL 排查」：昨天的结论是"防劣化要在合并前"，但 SQL 门禁只守住数据层，代码层的同类问题得靠测试。同时要说清一件事——**单测测不出慢 SQL**，昨天的隐式转换问题，mock 掉 Mapper 之后照样全绿。
> **边界**：今天只讲单元测试（不启容器、不连数据库）。集成测试（`@SpringBootTest`、Testcontainers、真 SQL）是明天第 7 项。

## 1. 今天学什么

单元测试是**给一个类的分支和边界留下可执行的证据**，让任何人改动这段逻辑时，机器能在 30 秒内告诉他有没有改坏。它解决的不是"有没有测试"，而是**重构安全网**和**需求可执行化**两件事。

今天讲四块：① 后端测试的分层边界（单元 / 集成 / E2E 各测什么，为什么 mock 掉 Mapper 就测不到 SQL）；② JUnit 5 + Mockito + AssertJ 的组合怎么写，和第 4 篇的 `mvn test` 怎么接上；③ Service 层到底该断言什么（分支、边界、异常路径），什么不该测；④ 让测试可重复的关键——时间、随机数、静态状态必须可控。

它的工程价值在多人协作和大项目里才显现：一个改动影响 40 处调用点，只有测试能让你敢改。

## 2. 前端工程师视角理解

好消息是：**心智模型几乎不用换。** Jest / Vitest 那一套在后端有一一对应的东西——`describe/it/expect` 对应 `@Nested/@Test/assertThat`，`vi.fn()` 对应 `@Mock`，`mockReturnValue` 对应 `when().thenReturn()`，`expect(spy).toHaveBeenCalled()` 对应 `verify(...)`。第 4 篇也已经提过 `mvn test` 就是 `vitest run`。

真正需要重建的是**替换依赖的方式**。前端 mock 靠模块系统（`vi.mock('./api')` 把整个模块换掉，本质是运行时改引用）；Java 里你不能随手替换别人的属性，靠的是**构造注入**——被测类只认接口，测试从构造函数把假实现塞进去。这就是第 8 篇反复强调"Controller 别直接调 Mapper"的隐藏收益：分层不只是为了整洁，**它决定了这个类能不能被单测**。一个 `new OrderMapper()` 写死在方法里的类，测试无从下手。

第二个新直觉是**断言要够狠**：前端常见病是"渲染不报错即通过"，后端同样。判断一个测试有没有价值只有一条标准——**这段逻辑被改错时，它会不会红？** 不会红，它就只是覆盖率数字。

## 3. 和 JavaScript / TypeScript 的对比

| Jest / Vitest | JUnit 5 + Mockito + AssertJ | 差异点 |
|---|---|---|
| `it('...', () => {})` | `@Test void ...()` | 测试方法必须无参、public，靠注解而非函数 |
| `expect(x).toBe(3)` | `assertThat(x).isEqualTo(3)` | Java 断言失败抛异常，不中断其它测试 |
| `vi.fn()` / `mockReturnValue` | `@Mock` / `when().thenReturn()` | 必须匹配真实方法签名，编译期就报错 |
| `expect(spy).toHaveBeenCalledWith` | `verify(mock).markUsed(id)` + `ArgumentCaptor` | 后端更推荐断言**返回值**，`verify` 只留给副作用 |
| `vi.useFakeTimers()` | 注入 `Clock.fixed(...)` | Java 没有全局时间钩子，只能改代码把时间注入进来 |

**三条真实差异值得单独记。** 第一，**类型是双刃剑**：mock 必须按接口签名造，改签名时测试同步报错（前端 `vi.fn()` 可以随便假），但代价是测试代码更长。第二，**静态方法和 `new` 出来的对象很难 mock**：JS 里随手能替换，Java 要靠 `mockStatic`（Mockito 3.4+）这种重工具——正确反应不是学它，而是**别写静态依赖**，把时钟、随机数、当前用户都做成注入的 Bean。第三，**默认更严格**：`MockitoExtension` 用的是 strict stubs，你多打了一个 `when()` 没用上就抛 `UnnecessaryStubbingException`。这是好事——它逼你保持测试诚实，前端很多 mock 早就和被测代码脱节却没人发现。

## 4. 真实业务场景

**场景：一次"把满减 5 元改成 6 元"，让外卖渠道订单少算钱。**

业务背景：门店订单的应付金额 = 商品总价 → 扣会员折扣 → 判断满减门槛 → 叠加优惠券。规则有 6 条分支，其中一条是"**企业员工账户 + 到店自取**时，满减不打折但券仍可用"，只有约 0.4% 的订单会走到。

改动只有一行：运营要求满减从 5 元变 6 元。开发顺手把那段计算抽了个方法调整了运算顺序——**满减和券的叠加先后变了**，而这条分支的例外逻辑被挪到了新的顺序里。本地手工试了三种常见组合，金额都对，上线。三天后财务对账发现外卖渠道的企业订单每天少收几十元，一单差 1 元，没人有权限改回去，只能出退款流程。

如果当时有参数化测试把「会员等级 × 配送方式 × 券类型」的组合钉住（18 个 case，含那条 0.4% 分支），这行改动在 CI 上就会红，成本是 5 分钟。

**但要清楚单测的边界**：这类测试把 Mapper 全 mock 掉了，所以第 52 篇那种"参数类型不对导致索引失效""影响行数为 0"的问题它一概测不到——**单测保证逻辑分支正确，SQL 与装配正确性归集成测试**。两边都补，才是完整防线。

## 5. Java 示例代码

```java
/** 被测类：时间和依赖都从构造注入，测试才能替换（第 8 篇的分层在这里兑现） */
@Service
@RequiredArgsConstructor
public class OrderAmountService {

    private final PromoMapper promoMapper;
    private final Clock clock;                         // 不在代码里写 now()（第 29 篇）

    /** 应付金额：会员折扣 → 满减 → 优惠券 */
    public BigDecimal calcPayable(List<OrderItem> items, PayContext ctx) { /* ... */ }

    /** 用券：查券 → 校验可用 → 标记已使用 */
    public BigDecimal applyCoupon(String orderNo, String couponCode) { /* ... */ }
}
```

```java
@ExtendWith(MockitoExtension.class)                    // JUnit 5 + Mockito，默认 strict stubs
class OrderAmountServiceTest {

    @Mock private PromoMapper promoMapper;             // 只假装有 DB

    /** 时间钉死在 2026-09-13：涉及"活动是否生效"的逻辑不再随今天是哪天变化 */
    private final Clock clock = Clock.fixed(
            Instant.parse("2026-09-13T02:00:00Z"), ZoneOffset.UTC);

    private final List<OrderItem> items = List.of(new OrderItem(new BigDecimal("30.00")));
    private OrderAmountService service;

    /** 手动装配而不用 @InjectMocks：@InjectMocks 只注入 @Mock 字段，自己 new 的 Clock 它不管 */
    @BeforeEach
    void setUp() {
        service = new OrderAmountService(promoMapper, clock);
    }

    @ParameterizedTest(name = "{0} + {1} + 券 {2} → 应付 {3}")
    @CsvSource({
            "NORMAL, DELIVERY, NONE, 30.00",
            "STAFF,  PICK_UP,  C5,   24.00",       // ★ 出事的那条 0.4% 分支，必须钉住
            "MEMBER, DELIVERY, C5,   22.00",
    })
    @DisplayName("满减与优惠券的叠加结果符合规则")
    void calcPayable_rules(MemberLevel level, DeliveryType type, String coupon, String expected) {
        when(promoMapper.selectFullReduction(type)).thenReturn(new PromoRule("30", "6"));

        BigDecimal payable = service.calcPayable(items, new PayContext(level, type, coupon));

        // 比较值而不是比 scale：isEqualTo 会因 24.0 vs 24.00 失败（第 28 篇那个坑）
        assertThat(payable).isEqualByComparingTo(expected);
    }

    @Test
    @DisplayName("券查不到时抛业务异常，且绝不能把它标记为已使用")
    void applyCoupon_couponNotFound() {
        when(promoMapper.selectCoupon("C404")).thenReturn(null);        // 第 15 篇：未命中即 null

        assertThrows(BizException.class, () -> service.applyCoupon("O20260913001", "C404"));

        verify(promoMapper, never()).markCouponUsed(anyString());       // 失败路径不许留下副作用
    }
}
```

跑法就是第 4 篇那条命令：`mvn test`（surefire 插件负责执行，测试失败会让构建失败，CI 门禁由此成立）；覆盖率用 JaCoCo：`mvn test jacoco:report`。

## 6. 常见坑

**坑 1：测的是 mock，不是逻辑。** 错误写法：`when(mapper.select()).thenReturn(x)` 之后断言"返回值等于 x"，或者只写 `verify(mapper).select()`。问题：这验证了 Mockito 自己没坏，被测类的任何改动都不会让测试红。正确做法：**stub 只用于隔离外部世界，断言必须落在被测方法的输出与副作用上**；一个测试里如果断言全在 mock 上，删掉它。

**坑 2：只测快乐路径。** 错误做法：一条 case 走通就提交，异常和边界全靠手工试。问题：线上事故集中在边界（null、金额为 0、数量上限、并发重复提交，正是第 35 篇列的那批）。正确做法：每个分支都要有 case，边界值成对写（门槛 29.99 / 30.00 / 30.01），异常路径用 `assertThrows` 断言**具体异常类型和错误码**，而不是"抛了个异常"。

**坑 3：测试不可重复。** 错误写法：代码里 `LocalDateTime.now()`、`new Random()`、读环境变量或依赖上一个测试留下的静态状态。问题：今天绿、明天红；单独跑通过、批量跑失败，团队很快学会"忽略那一条红"，测试就废了。正确做法：时间注入 `Clock`、随机注入种子、静态可变状态改成 Bean；测试之间不共享实例字段，需要前置数据就在 `@BeforeEach` 里建。

**坑 4：为了覆盖率写废测试。** 错误做法：给 getter/setter、VO 转换、`toString` 写测试，把覆盖率刷到 80% 好过门禁。问题：这类测试既不能发现 bug，又让每次重构都要改一片。正确做法：**把覆盖率当体检指标而非 KPI**，门禁设在核心业务包（`service/`、`domain/`）的分支覆盖率上；转换器交给明天的集成测试用真实数据验证，不为它们写单测。

- **第 29 篇「日期时间处理」**：`LocalDateTime.now()` 散落各处会让测试无法固定时间，今天用注入 `Clock` 收口；这也是"可测性驱动设计"最常见的一个具体形态。
- **第 52 篇「慢 SQL 排查」**：单测把 DB mock 掉了，所以隐式转换、影响行数为 0 这类问题它天然测不到，必须靠 SQL 门禁 + 集成测试补上——这决定了单测在防线里的位置。

## 8. 面试 / 工作中常见问题

### 问题 1：这个 Service 依赖 Mapper、Redis、第三方 HTTP，你怎么单测？

参考答案：都按接口注入，测试里全部换成 mock，只测这个 Service 自己的判断：分支怎么走、金额怎么算、异常怎么抛、要不要调下游。要点是**别 mock 被改造的那个类本身**，也别把断言写成"下游被调用了几次"——主断言落在被测方法的返回值上，`verify` 只用在一处：某个副作用必须发生或绝不能发生（比如失败时不许退款）。DB 语句本身对不对不在单测范围内，交给集成测试。

### 问题 2：私有方法有复杂逻辑，怎么测？

参考答案：先问它为什么复杂——大概率说明它该是一个自己的类，抽出去公开测。真不想抽，就通过公有方法的输入输出把它各分支覆盖掉，不必直接调它；**用反射测私有方法是坏味道**，它把实现细节钉死，重构必红。极端情况（比如工具类里一段纯算法）可以把方法改成包级私有并加 `@VisibleForTesting` 注释，让同包测试能调。

### 问题 3：项目没测试，现在要补，从哪开始？

参考答案：不要按覆盖率倒着补。顺序是：① 先给**最近 3 个月出过线上问题的地方**补（那就是真实风险清单）；② 再给纯计算、纯规则的类补（无外部依赖，成本最低收益最高，比如金额、库存、优惠）；③ 有外部依赖的类挑分支密集的补；④ 最后用 JaCoCo 设门禁**只保证不再下降**，并把"新代码必须带测试"进评审清单。给一堆 `@Data` 写测试是浪费所有人时间。

## 9. 今日小结

- 单测的产出是**重构安全网**：判据只有一条——逻辑被改错时测试会不会红。
- Jest 的概念能整套搬过来，真正要适应的是：**用构造注入替换 mock，而不是运行时改引用**，所以分层决定可测性。
- 断言要狠：覆盖每个分支和成对边界值，异常路径断言具体类型与错误码，别只断言"调用了"。
- 不可重复的测试等于没有：时间注入 `Clock`、随机给种子、静态状态改成 Bean。
- 单测测不到 SQL、序列化和 Bean 装配——这不是它的失职，是明天集成测试的存在理由。
