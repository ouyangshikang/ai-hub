# Java 学习：状态码设计

> 系列第 23 篇 · 第三阶段：接口与规范  
> 上一篇我们定义了 `Result<T>` 统一返回结构，所有接口都返回 `{ code, message, data }`。但目前 `code` 只用了 200、400、404 三个值，真实业务里错误场景远不止这些。今天讲怎么设计一套结构化的业务状态码体系，让前端根据 code 做差异化处理，而不是所有错误都弹一个"操作失败"。

## 1. 今天学什么

统一返回结构解决了"格式一致"的问题，但没解决"语义精确"的问题。如果所有失败都返回 `code=500`，前端只能弹一个通用错误提示，用户看到"系统异常"完全不知道该怎么办。实际上，"未登录"应该跳登录页、"无权限"应该提示联系管理员、"库存不足"应该引导换商品、"重复提交"应该告诉用户已经成功了——每种错误需要不同的前端处理逻辑。

状态码设计就是给每种业务错误分配一个唯一的、有规律的编号。前端拿到 code 后，能精确判断该跳转、该提示、该重试还是该静默。这不是可选项，而是系统规模变大后前后端协作的刚需。

## 2. 前端工程师视角理解

你在前端一定写过类似的错误处理逻辑：

```typescript
// axios 拦截器里的错误分支
axios.interceptors.response.use((response) => {
  const { code, message, data } = response.data;
  if (code === 200) return data;

  // 如果没有细分状态码，你只能这样：
  ElMessage.error(message);
  return Promise.reject(new Error(message));

  // 但真实需求是这样的：
  // if (code === 40101) { router.push('/login'); }
  // if (code === 40301) { ElMessage.error('无权限，请联系管理员'); }
  // if (code === 42901) { ElMessage.warning('操作太频繁，请稍后重试'); }
  // if (code === 40901) { ElMessage.info('订单已提交，请勿重复操作'); }
});
```

没有细分状态码，前端只能"一刀切"弹提示。有了状态码体系，前端可以写一个 code-to-action 的映射表，每种错误走不同处理路径。这和你用 HTTP 状态码做路由守卫是一个思路——401 跳登录、403 跳无权限页——只不过业务状态码比 HTTP 状态码粒度更细。

后端要做的就是：把错误码定义清楚、文档化、前后端共享一份码表。前端不需要知道后端为什么报错，只需要知道"这个码意味着我该做什么"。

## 3. 和 JavaScript / TypeScript 的对比

### 错误码管理：枚举 vs 常量对象

```typescript
// TypeScript：用 enum 或常量对象管理错误码
enum BizCode {
  SUCCESS = 200,
  PARAM_ERROR = 40000,
  STORE_NOT_FOUND = 40401,
  UNAUTHORIZED = 40100,
  FORBIDDEN = 40300,
  DUPLICATE_SUBMIT = 40901,
  RATE_LIMITED = 42900,
}

// 前端根据码做映射
const codeActionMap: Record<number, () => void> = {
  [BizCode.UNAUTHORIZED]: () => router.push('/login'),
  [BizCode.FORBIDDEN]: () => ElMessage.error('无权限'),
  [BizCode.RATE_LIMITED]: () => ElMessage.warning('请稍后重试'),
};
```

```java
// Java：用枚举类管理错误码（最常见的工程写法）
@Getter
@AllArgsConstructor
public enum ErrorCode {

    SUCCESS(200, "操作成功"),
    PARAM_ERROR(40000, "参数校验失败"),
    STORE_NOT_FOUND(40401, "门店不存在"),
    UNAUTHORIZED(40100, "未登录或登录已过期"),
    FORBIDDEN(40300, "无操作权限"),
    DUPLICATE_SUBMIT(40901, "请勿重复提交"),
    RATE_LIMITED(42900, "操作过于频繁，请稍后重试");

    private final int code;
    private final String message;
}
```

两者的核心差异在于：TypeScript 的 enum 是"可选的约定"，不用也能跑；Java 的枚举是"强约束"，`Result.fail()` 方法签名要求传入 `ErrorCode` 类型，你传一个裸数字编译都过不了。Java 通过类型系统强制所有错误码必须从枚举里取，杜绝了"随手写个 999"的情况。

### 为什么 Java 偏爱枚举而不是常量

```typescript
// TS 里你可能这样写（也能工作）
const ERR_STORE_NOT_FOUND = 40401;
const ERR_UNAUTHORIZED = 40100;
```

Java 里当然也能用 `public static final int`，但枚举多了三个关键能力：每个码自带 message（不用另维护一份映射表）、可以加方法（比如 `ErrorCode.isClientError()` 判断是否是客户端错误）、switch 语句编译器会检查你是否遗漏了某个分支。对错误码这种"只增不删、全局引用"的东西，枚举是最合适的载体。

## 4. 真实业务场景

**场景：门店运营后台的"创建优惠券"接口。**

业务背景：运营人员在后台创建一张优惠券，涉及登录态校验、权限校验、参数校验、业务规则校验多个环节。

如果所有失败都返回 `code=500, message="创建失败"`：
- 运营看到"创建失败"，不知道是自己没权限还是参数填错了
- 前端无法判断该弹表单校验提示还是该跳登录页
- 客服接到投诉只能让运营"再试一次"

有了结构化状态码后：

| 场景 | code | message | 前端处理 |
|------|------|---------|----------|
| 登录过期 | 40100 | 登录已过期 | 跳登录页 |
| 无优惠券管理权限 | 40302 | 无优惠券管理权限 | 提示联系管理员 |
| 优惠券名称为空 | 40001 | 优惠券名称不能为空 | 表单字段标红 |
| 折扣超出范围 | 40002 | 折扣须在0.1-9.9之间 | 表单字段标红 |
| 同名优惠券已存在 | 40902 | 已存在同名优惠券 | 弹确认框"是否覆盖" |
| 当日创建数量达上限 | 42901 | 今日创建已达上限(50张) | 提示明天再试 |

前端拿到 code 后精确路由：401xx 跳登录、403xx 提示权限、400xx 标红表单、409xx 弹确认、429xx 提示频率。每种错误的用户体验完全不同，但后端只需要在抛异常时选对枚举值。

## 5. Java 示例代码

```java
// ========== 错误码枚举（按模块分段） ==========
@Getter
@AllArgsConstructor
public enum ErrorCode {

    // 通用：200, 40000-40099
    SUCCESS(200, "操作成功"),
    PARAM_ERROR(40000, "参数校验失败"),

    // 认证与权限：40100-40399
    UNAUTHORIZED(40100, "未登录或登录已过期"),
    TOKEN_EXPIRED(40101, "登录已过期，请重新登录"),
    FORBIDDEN(40300, "无操作权限"),
    FORBIDDEN_COUPON(40302, "无优惠券管理权限"),

    // 业务冲突：40900-40999
    DUPLICATE_SUBMIT(40901, "请勿重复提交"),
    COUPON_NAME_EXISTS(40902, "已存在同名优惠券"),

    // 频率限制：42900-42999
    RATE_LIMITED(42900, "操作过于频繁"),
    COUPON_DAILY_LIMIT(42901, "今日创建已达上限"),

    // 门店模块：50100-50199
    STORE_NOT_FOUND(50100, "门店不存在"),
    STORE_CLOSED(50101, "门店已停业");

    private final int code;
    private final String message;
}
```

```java
// ========== Result 类配合 ErrorCode 使用 ==========
public class Result<T> {
    private int code;
    private String message;
    private T data;

    public static <T> Result<T> success(T data) {
        Result<T> r = new Result<>();
        r.code = ErrorCode.SUCCESS.getCode();
        r.message = ErrorCode.SUCCESS.getMessage();
        r.data = data;
        return r;
    }

    // 失败时只接受 ErrorCode，不接受裸数字（编译期约束）
    public static <T> Result<T> fail(ErrorCode errorCode) {
        Result<T> r = new Result<>();
        r.code = errorCode.getCode();
        r.message = errorCode.getMessage();
        r.data = null;
        return r;
    }
}
```

```java
// ========== Service 层抛出带状态码的业务异常 ==========
@Service
public class CouponService {

    public Long createCoupon(CouponCreateDTO dto, Long operatorId) {
        // 权限校验
        if (!permissionService.hasPermission(operatorId, "coupon:manage")) {
            throw new BizException(ErrorCode.FORBIDDEN_COUPON);
        }
        // 业务规则：同名检查
        if (couponMapper.existsByName(dto.getName())) {
            throw new BizException(ErrorCode.COUPON_NAME_EXISTS);
        }
        // 业务规则：每日上限
        int todayCount = couponMapper.countTodayCreated(operatorId);
        if (todayCount >= 50) {
            throw new BizException(ErrorCode.COUPON_DAILY_LIMIT);
        }
        // 正常创建...
        return couponId;
    }
}
```

```java
// ========== 全局异常处理器统一转 Result ==========
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public Result<?> handleBizException(BizException e) {
        // 业务异常：返回具体错误码，HTTP 状态码仍为 200
        return Result.fail(e.getErrorCode());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<?> handleValidation(MethodArgumentNotValidException e) {
        // 参数校验失败：统一返回 PARAM_ERROR
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(FieldError::getDefaultMessage)
            .collect(Collectors.joining("; "));
        return Result.fail(ErrorCode.PARAM_ERROR, msg);
    }
}
```

## 6. 常见坑

**坑 1：错误码没有分段，全挤在一起。**

错误写法：`ERROR_1(1001)`, `ERROR_2(1002)`……一路编到 1999，看不出哪个是权限、哪个是业务。正确做法：按 HTTP 状态码语义分段（401xx 认证、403xx 权限、404xx 资源不存在、409xx 冲突、429xx 频率），模块内再细分。前端可以根据百位/千位做批量路由，不需要逐个码判断。

**坑 2：把 HTTP 状态码和业务状态码混为一谈。**

错误理解：业务失败时返回 HTTP 500 + `code=500`。问题：axios 的 catch 会捕获所有非 2xx 响应，前端需要在 catch 里再解析 body 拿业务码，逻辑割裂。正确做法：HTTP 状态码统一 200（表示"请求被正常处理了"），业务成功/失败全靠 body 里的 `code` 区分。HTTP 层只在真正的通信故障（网关超时、服务不可用）时才出现非 200。

**坑 3：错误码由每个人随手定义，没有统一管理。**

错误做法：张三定义了 10001，李四定义了 50001，王五定义了 9999，没有文档、没有规律。正确做法：错误码枚举类只有一个（或按模块拆几个），新增码必须 Code Review，配合一份在线文档（码值 + 含义 + 前端处理建议），前后端共同维护。

**坑 4：message 里暴露系统内部信息。**

错误写法：`message = "NullPointerException at CouponService.java:87"`。问题：用户看不懂，且暴露了代码结构。正确做法：message 永远是"用户能理解的人话"，技术细节写进日志（用 traceId 关联），不返回给前端。

**坑 5：前端对未知 code 没有兜底。**

后端新增了一个码但前端还没适配，如果前端 switch 没有 default 分支，用户看到的是白屏或无反应。正确做法：前端 code 映射表必须有 default——未知码统一弹 `message` 内容，保证任何新码上线后用户至少能看到提示。

## 7. 和之前知识的连接

- **第 22 篇「统一返回结构」**：今天是在 `Result<T>` 的 `code` 字段里"填什么值"的规范。上一篇解决了信封格式，今天解决了信封里错误码的编排规则。
- **第 21 篇「请求参数校验」**：校验失败时返回的 `code=40000` 就是今天状态码体系里"参数错误段"的一员。之前校验只管"拦不拦"，今天管"拦了之后返回什么码"。
- **第 20 篇「RESTful 接口设计」**：RESTful 里 HTTP 状态码（404、409、429）表达的是协议层语义，今天的业务状态码是应用层语义。两者不冲突——HTTP 200 + 业务码 40901 表达"请求通信正常，但业务上重复了"。
- **第 8 篇「Controller / Service / Mapper 分层」**：状态码在 Service 层通过 `BizException` 抛出，在 Controller 层被全局异常处理器捕获并转为 `Result`——分层架构让错误码的产生和消费各归其位。

## 8. 面试 / 工作中常见问题

### 问题 1：你们项目的错误码是怎么设计的？前端怎么用？

参考答案：按 HTTP 语义分段 + 模块细分。通用段 200/40000，认证段 40100-40199，权限段 40300-40399，冲突段 40900-40999，频率段 42900-42999，各业务模块 5xxxx。用 Java 枚举统一管理，每个码自带 message。前端在 axios 拦截器里维护一个 code-to-action 映射表：401xx 跳登录、403xx 弹权限提示、400xx 标红表单、其余 default 弹 message。新增码必须前后端同步更新文档。

### 问题 2：为什么不直接用 HTTP 状态码表达所有错误？

参考答案：HTTP 状态码只有几十种，粒度太粗——"门店不存在"和"优惠券不存在"都是 404，前端无法区分该提示什么。而且 HTTP 4xx/5xx 会被 axios 拦截进 catch，前端需要同时维护 then 和 catch 两套错误处理逻辑。统一 HTTP 200 + 业务码后，前端所有业务错误都在同一条路径处理，代码更简洁。HTTP 状态码只表达"通信层面"的状态，业务语义交给应用层。

### 问题 3：新加了一个错误码，前端没适配，线上会怎样？怎么预防？

参考答案：如果前端 switch/映射没有 default 分支，用户可能看到无反应或白屏。预防措施有三：一是前端 code 处理必须有 default（弹 message 兜底）；二是错误码枚举变更走 Code Review，前后端同步评审；三是联调环境先上后端、前端确认适配后再上生产，避免"后端悄悄加了个码前端不知道"。

## 9. 今日小结

- 状态码是前后端的"错误语义协议"：前端根据 code 做差异化处理（跳转/提示/重试），而不是所有错误一刀切弹 toast。
- 分段设计：按 HTTP 语义分百位（401 认证、403 权限、409 冲突、429 频率），模块内再细分，前端可以按段批量路由。
- Java 枚举是错误码的最佳载体：自带 message、类型安全、编译期约束不允许传裸数字。
- HTTP 状态码统一 200，业务成败全靠 body 里的 code——前端 catch 只管网络异常，then 里判 code 管业务。
- 前端 code 映射必须有 default 兜底，后端新增码必须同步文档和前端。
