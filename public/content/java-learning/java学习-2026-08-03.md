# Java 学习：接口兼容性

> 系列第 26 篇 · 第三阶段：接口与规范  
> 上一篇我们用幂等 key + Redis SETNX + 唯一索引防住了重复请求，接口在并发和重试下行为正确了。但接口上线后还有一个更隐蔽、更长期的风险：前端不止一个版本在线。App 用户不一定升级、H5 有浏览器缓存、小程序要过审核周期——后端改了字段名、删了参数、调了返回结构，老版本前端会不会直接崩？今天讲接口兼容性：如何在不搞崩老版本的前提下迭代接口。

## 1. 今天学什么

接口兼容性解决的是一个时间差问题：后端可以随时发布，但前端的多个版本会同时存活很长一段时间。你在公司内网刷新页面就能拿到最新代码，但用户手机里三个月前下载的 App 还是旧逻辑。如果后端把 `storeName` 改成 `name`、把某个字段删掉、把返回结构从对象改成数组，旧版本前端轻则显示 `undefined`，重则整页白屏。

所以接口兼容性的核心原则只有一句话：**对已经发布的接口做"破坏性变更"（Breaking Change）之前，必须保证老调用方还能正常工作**。什么叫破坏性变更？删字段、改字段名、改字段类型、把可选参数变成必填——这些都是。加字段一般是安全的，因为老前端会忽略它不认识的字段。

这不是理论问题。"后端一上线，老用户全白屏"是真实发生过的事故级别场景，而且往往在发版当晚才暴露，排查和回滚成本极高。

## 2. 前端工程师视角理解

你一定经历过这种时刻：联调时后端说"我把那个字段名改了一下"，然后你的页面某个地方突然变成 `undefined`，或者 `xxx.map is not a function`。在联调环境这只是十分钟的事，但同样的变更如果发生在已上线的 App 上，就是几万个用户同时遇到。

前端自己对"版本共存"其实很熟悉——你写的 npm 包就面临同样的问题。所以社区有语义化版本（semver）：`major.minor.patch`，只有 breaking change 才允许升 major，使用方通过 `^1.2.3` 声明"我可以接受 minor 和 patch，但别给我 major"。HTTP 接口没有版本号的强制约束，但道理完全一样：**改接口就是改一份对外契约，契约一旦发布，修改就要考虑所有已存在的消费方**。

前端能为兼容性做的配合是防御式编码：

```typescript
// 不要假设字段一定存在、一定是某种类型
const list = Array.isArray(res.data?.records) ? res.data.records : []
const name = res.data?.storeName ?? res.data?.name ?? '-'
```

但防御式编码只是降低伤害，真正的兼容性责任在后端——因为前端版本你控制不了，后端版本你一个发布就能全量切换。**后端是唯一能主动保证兼容的一方**。

## 3. 和 JavaScript / TypeScript 的对比

### TS 有编译器，接口没有

这是最关键的差异。在 TypeScript 项目里，你把 `interface Store { storeName: string }` 改成 `{ name: string }`，所有引用 `storeName` 的地方立刻编译报错——编译器帮你找到了全部调用方。但 Java 后端接口和前端调用方之间没有任何编译期检查，接口就是一段 JSON 文本，改完发布，问题只会在运行时、在用户的设备上暴露。

所以 Java 后端需要人工手段弥补这个缺口：接口文档（哪些字段已废弃）、灰度发布（先放一小部分流量）、监控告警（老版本错误率突增）。TS 的 `@deprecated` JSDoc 标注在 Java 里有直接对应物——`@Deprecated` 注解：

```typescript
// TypeScript：标记废弃，IDE 划删除线，但代码还能跑
/** @deprecated 请改用 name 字段，下个版本移除 */
storeName: string
```

```java
// Java：标记废弃，编译警告，运行时不受影响
@Deprecated
private String storeName;
```

两边语义一致：不是立刻删除，而是先告知、给调用方迁移时间、过段时间再真正删。

### npm semver vs 接口版本

npm 用版本号隔离 breaking change，接口通常用两种方式：一是 URL 版本，`/api/v1/stores` 和 `/api/v2/stores` 并存，老版本继续走 v1，新功能走 v2；二是约定"只加不删"，同一个 URL 永久向后兼容，字段只增不减、不改名不改类型。多数内部系统选第二种（维护成本低），面向大量不可控客户端的开放平台选第一种（v1 可以冻结）。

### 为什么 Java 后端对"加字段"很随意

Java 对象序列化到 JSON 时，前端拿到不认识的字段会自动忽略（JS 对象访问不存在的属性只是 `undefined`，不会报错）。所以后端给 VO 加一个新字段，老前端完全无感。反过来也一样要注意：前端给请求体多传了字段，后端 Jackson 反序列化默认也会忽略未知字段。两个方向上，"多给"是安全的，"少给、改名、换类型"才是危险的。

## 4. 真实业务场景

**场景：门店管理系统的"门店详情"接口，要支持新的"营业时间"功能。**

业务背景：门店表原本只有名称、地址、电话。产品要求新增营业时间（周一到周日分段配置），同时运营反馈旧字段 `storeName` 命名不规范，希望统一改成 `name`，和创建接口的 DTO 保持一致。

如果不懂兼容性，后端可能这样"顺手"改掉：

```java
// 危险操作：改名 + 新增，一次发布全改完
public class StoreVO {
    private String name;          // storeName 改名而来
    private String address;
    private List<OpenTime> openTimes;  // 新增
}
```

上线后果：App 老版本读 `res.data.storeName` 拿到 `undefined`，门店列表全部显示空白标题；H5 老版本如果写了 `storeName.trim()`，直接抛 `Cannot read property 'trim' of undefined` 白屏。而这两个版本的用户加起来可能占 70%——他们只是没升级而已。

正确思路是：新增字段随便加；改名必须"新老字段同时返回"过渡。老前端继续用 `storeName`，新前端用 `name`，等埋点显示还在读 `storeName` 的老版本流量趋近于零，再考虑下线旧字段。

## 5. Java 示例代码

```java
/**
 * 门店详情 VO：兼容式演进
 * 原则：新增随意、改名双写、删除走废弃流程
 */
public class StoreVO {

    // 新字段：直接加，老前端自动忽略，零风险
    private Long id;
    private String address;
    private List<OpenTimeVO> openTimes;

    // 改名字段：新老双写，过渡期两个都返回
    private String name;

    @Deprecated // 标记废弃：提醒后端同事不要再依赖它，但运行时照常返回
    private String storeName;

    // Service 组装时两个字段赋同一个值
    // vo.setName(store.getName());
    // vo.setStoreName(store.getName());
}
```

```java
/**
 * 反序列化方向：前端还在传老字段名时，后端也能接住
 * @JsonAlias 让一个 Java 字段接受多个 JSON 字段名
 */
public class StoreUpdateDTO {

    @JsonAlias({"storeName", "shopName"}) // 兼容历史调用方的老字段名

    private String address;

// 前端传 {"name": "xx"} 或 {"storeName": "xx"} 都能正确映射到 name
```

```java
 */
@JsonInclude(JsonInclude.Include.NON_NULL)

```

```java
/**
 * 真正的大改版：URL 版本并存
 * v1 冻结不再加新功能，v2 承载新结构，老 App 永远有 v1 可用

@RestController
@RequestMapping("/api/v1/stores")

    @GetMapping("/{id}")

}

@RestController
@RequestMapping("/api/v2/stores")
public class StoreV2Controller {
    @GetMapping("/{id}")
    public Result<StoreV2VO> detail(@PathVariable Long id) { /* 新结构 */ }
}
```

```typescript
// 前端配合：新字段用可选链，老逻辑不受影响
const openTimes = res.data?.openTimes ?? []  // 后端没返回时用空数组兜底
```

## 6. 常见坑

**坑 1：把"加字段"和"改字段"混在一次发布里顺手全改。**

错误写法：新增 `openTimes` 的同时把 `storeName` 改名成 `name`，觉得"反正前端这次要一起发"。问题：你的前端发了，App 老版本没发。加字段本身无害，但改名会立刻搞崩老版本，两个变更混在一起还让回滚定位变难。正确做法：拆开评估——加字段可以直接上，改名走双写过渡，永远不要假设"所有前端都会和后端同步更新"。

**坑 2：用"改字段类型"来扩展功能。**

错误写法：`openTime` 原来是字符串 `"09:00-21:00"`，要支持分段营业，直接把类型改成数组 `["09:00-12:00", "14:00-21:00"]`。问题：老前端做 `openTime.split('-')` 直接报错，这是比删字段更隐蔽的破坏——字段还在，类型变了。正确做法：保留老字段不动，新开一个字段承载新结构（如 `openTimeSegments`），老字段标记 `@Deprecated` 后择机下线。

**坑 3：把可选参数改成必填参数。**

错误写法：`@RequestParam(required = true)` 加到原来可选的 `regionId` 上，因为新逻辑"必须"按区域过滤。问题：老版本前端从不传这个参数，一夜之间全部收到 400。正确做法：新参数保持可选并给默认值（如不传则查全部区域），在业务层处理缺省语义；确需强制时，只能开新版本接口。

**坑 4：@Deprecated 标了，但没告诉任何人。**

错误写法：字段上加个 `@Deprecated` 就完事，前端团队完全不知道要迁移。问题：注解只在后端代码里可见，前端看不到；半年后有人"清理废弃代码"把字段删了，老版本崩了才想起来没人迁移过。正确做法：废弃必须同步到接口文档（标注废弃版本 + 计划下线时间 + 替代字段），和前端约定迁移窗口，下线前通过埋点/网关日志确认旧字段流量已清零。

**坑 5：删除"看起来没人用"的字段。**

错误理解：代码全局搜索没找到引用，或者测试环境没人传这个字段，就觉得可以删。问题：你搜到的只是当前仓库，App 老版本、其他团队的调用方、开放出去的第三方接入都在你视野之外。正确做法：接口字段的"没人用"只能靠线上流量数据证明（网关日志统计字段出现频率），而且要观察足够长的周期覆盖低频场景，确认后才能删。

## 7. 和之前知识的连接

- **第 25 篇「接口幂等性」**：幂等和兼容性同属"接口稳定性"范畴，上一篇防的是同一时刻的重复调用，今天防的是不同时间点的版本差异。两者共同构成接口对外承诺的完整性——调用方不必担心"多发一次"或"晚升级几个月"会出事。

- **第 22 篇「统一返回结构」**：今天所有兼容动作都发生在 `Result<T>` 的 `data` 内部，信封结构 `{ code, message, data }` 本身永远不变——这正是统一返回结构的长期价值：外层契约冻结，内层数据才有演进空间。

- **第 24 篇「Controller 参数接收」**：今天讲的"可选参数不能变必填"，对应的就是上一篇 `@RequestParam(required = ...)` 和 `@RequestBody` 的接收方式。改 required 属性、把 `@RequestParam` 换成 `@RequestBody`，对老调用方都是破坏性变更。

- **第 20 篇「RESTful 接口设计」**：URL 版本方案（`/api/v1`、`/api/v2`）是在 RESTful 资源路径上叠加版本维度。当时说过资源路径要稳定，今天补上例外情况——结构大改版时，宁可新开路径也不要破坏老路径。

## 8. 面试 / 工作中常见问题

### 问题 1：接口字段要改名，你怎么保证不出线上问题？

参考答案：四步走。第一步双写：新老字段同时返回同一个值，老前端继续用老字段。第二步通知：接口文档标注废弃版本、替代字段、计划下线时间，和所有调用方对齐迁移窗口。第三步观察：通过网关日志或前端埋点监控老字段的读取流量，等流量趋近于零。第四步下线：确认无流量后删除老字段，保留一个回滚窗口。全程老版本前端不需要任何改动。

### 问题 2：加字段一定是安全的吗？有没有例外？

参考答案：返回方向基本安全，老前端会忽略未知字段；但也有例外——如果老前端对返回结构做了严格校验（比如按 key 数量做断言），或者新字段序列化开销很大导致响应变慢，都可能出问题。请求方向则要反过来注意：后端如果开了 Jackson 的 `FAIL_ON_UNKNOWN_PROPERTIES`，前端多传字段会直接 400，所以后端一般保持默认的忽略未知字段。结论是"加字段安全"成立的前提是双方都宽容解析。

### 问题 3：什么时候该用 /api/v1、/api/v2 这种 URL 版本？

参考答案：当变更是大面积结构性改版（整体换 DTO、合并拆分接口），双写过渡成本过高时。v1 冻结只修 bug，v2 承载新结构，两端并行维护，等 v1 流量清零再下线。内部系统一般不用 URL 版本——调用方就一两个前端团队，双写 + 文档约定成本更低，多一套版本反而长期背维护包袱。面向不可控客户端的开放 API（小程序 SDK、第三方接入）则推荐 URL 版本，因为契约必须能冻结。

## 9. 今日小结

- 接口是对外契约，发布后修改必须考虑所有存量调用方——App 老版本、H5 缓存、小程序审核期让多版本共存成为常态。
- 变更安全性排序：加字段（安全）< 改字段名/类型（破坏，需双写过渡）< 删字段/可选变必填（破坏，需版本隔离或等流量清零）。
- 改名标准流程：双写 → 文档标废弃 → 监控旧字段流量 → 清零后下线；`@Deprecated` 只是起点，不是终点。
- TS 有编译器兜底，接口没有——Java 后端要用文档、灰度、监控弥补这个缺口，后端是唯一能主动保证兼容的一方。
- 结构大改版用 `/api/v1`、`/api/v2` 并存；日常迭代坚持"只加不删"，维护成本最低。

明天建议学习：`前后端字段命名约定`

原因：今天讲改名时必须"新老双写过渡"，代价很高——那为什么 `storeName` 和 `name` 这种命名分歧一开始就会出现？根源是前后端对字段命名的约定不统一：Java 习惯驼峰、数据库习惯下划线、前端有时又想要别的名字。下一篇收口第三阶段：搞清楚 Entity（下划线转驼峰）、DTO、VO 到前端 JSON 的完整命名链路，以及 `@JsonProperty`、Jackson 命名策略怎么从机制上避免"同一份数据三个名字"的混乱，让接口从第一天就不需要兼容性补救。
