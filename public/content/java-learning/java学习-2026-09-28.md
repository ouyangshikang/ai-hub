## 1. 今天学什么

连接池是最便宜的容量——它不增加服务器，只是把从"用完就丢"变成了"复用"。但池是共享资源，一个人占久了，全组人都排。

四块内容：① **池大小怎么算**——不是"多多益善"，是"刚好扛住稳态并发 + 留出余量给慢查询和瞬发毛刺"，用 Little's Law 算起点再压测验证；② **泄漏发现与定位**——active 连接只涨不降、pending 排队持续存在时，谁是占用者；③ **有效性检测与闪断**——`isValid` 比 `validationQuery` 更快，但检测频率要在可用性与性能之间平衡；④ **多数据源的池规划**——主库、从库、归档库各需多大的池，以及连接耗尽时"现场证据"的固定法。

一句心法：**池大小设定的上限不是"连接够不够"，而是"数据库能扛多少"。** 把池开到 200 不过是一行配置，但 MySQL 的连接数上限、事务锁的冲突概率都与连接数正相关。

## 2. 前端工程师视角理解

你太熟悉这个体验了：打开一个页面，某张配图的接口卡了 6 秒，别的接口都在排队——因为浏览器对同域名的**6 个并发连接**全被这张图占住了（第 58 / 62 篇提过）。这个阶段和后端连接池耗尽完全是同一回事：**一个慢调用占住一个连接，后续请求在"等待"上消耗时间，直到超时。**

前端解决这个问题的办法是 `AbortSignal.timeout()` + 在 `finally` 里释放请求（取消订阅 / 关 AbortController）——后端的对应物就是 **`connectionTimeout` + `leakDetectionThreshold`**。你还会用一个习惯来避免占住连接：在 `useEffect` 的清理函数里 `abort()` 未完成的请求——后端的"事务要短、finally 要回连接"就是同一个纪律。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端连接池 |
|---|---|---|
| 并发上限 | 同域 6 连接 | HikariCP 配置的池大小（默认 10） |
| 等待排队 | 浏览器排队（第 58 篇提过） | `connectionTimeout` 内排队，超时才抛 |
| 慢调用影响 | 一个慢接口占一个连接 | 一个慢事务占用一个连接，池被迫等着 |
| 泄漏清理 | `abort()`、`cleanup` | `leakDetectionThreshold`（警告 + 堆栈） |
| 有效性检查 | `fetch` 超时后自动重试 | `isValid` 心跳 + `maxLifetime` 轮换 |
| 扩容方向 | 多域名 / 连接复用 | 调池大小、改连接超时、读从库分担 |

**前端的 6 连接和后端的 10（默认值）不是巧合——都很小，是因为多的代价常被忽略。** 浏览器 6 连接是因为每个域名一张 TCP 连接表，太多会占用系统资源；后端的连接数是数据库进程的"会话数"，每个都要内存、锁结构、事务日志资源。所以两者遵循同一个贪婪原则：**不是能开多少开多少，而是够用就行，留余量给毛刺。**

## 4. 真实业务场景

**场景：一份导出报表，让下单接口"卡死"了 20 分钟。**

业务背景：门店订单服务，HikariCP 池大小 30，日常稳态并发约 12 个连接，从来没触过天花板。某天下午运营导出一份"全店订单明细"（按第 16 篇的提醒，这种导出没加 LIMIT 很危险），但这次更糟：导出 Service 在事务内做了两步——拉全量数据（300 万行，耗时 2 分钟）→ 逐行调用 Excel 生成逻辑（又 2 分钟）。**单个连接被占住 4 分钟**，四个运营同时导出后 16 个连接被永久扣住。下单接口的 `connectionTimeout` 配了 3 秒（第 51 篇改过的），但在 30 个池里只有 14 个空闲 → 全部在 3 秒内被新请求填满 → 此后所有请求排队 → 很快所有线程都在等连接，接口大面积超时。

事故后的发现惊出冷汗：**HikariCP 的监控显示 active 一直是 30（全满），pending 在 30 以上——但没有人告警，因为 CPU 没高、内存没涨，唯一能证明"连接是瓶颈"的证据是那个时间段的线程 dump 里大量 `WAITING (parking)` 堆栈指向 HikariCP 的连接获取点。**

修复三件事：**长查询分离**（导出不走下单池，另配一个 pool（max 5，超时宽容）——舱壁思想，第 62 篇的 pool isolation 用于连接池是首次提出但在本系列合理）→ 拉数据用流式 cursor 避免全量进内存（第 15/18 篇的 MyBatis Cursor）→ 事务内不做耗时的纯计算。另外加上 `leakDetectionThreshold=30000`（超过 30 秒没归还就 warn），并把 active/pending 打点进 Grafana（第 64 篇）。

**用错的代价**：连接池弹尽粮绝时，**功能全好的代码、数据库也正常、CPU 才 20%**，但接口就是超时——这种故障最容易被误诊为"下游慢"或"网络问题"，因为没有错误日志告诉你"连接池满了"。

## 5. Java 示例代码

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 30        # Little's Law 起点：目标 100 TPS × RT 200ms ≈ 20，开 30 留余量
      minimum-idle: 10             # 空闲保留（云环境省资源，但注意频繁创建也有代价）
      connection-timeout: 3000     # 拿不到连接等多久，不是 SQL 执行超时（第 51 篇）
      idle-timeout: 600000         # 10 分钟空闲才释放
      max-lifetime: 1800000        # 30 分钟强制轮换，防止被网络设备掐断
      leak-detection-threshold: 30000   # 超过 30 秒不归还 → 日志 warn + 堆栈（发现泄漏者）
# 多数据源各自独立配池：导出库另走 @Bean 与 @ConfigurationProperties(prefix="app.datasource.export")，不嵌套在此；导出池通常小（5～10）且超时宽容。
```

```java
/** 泄漏定位：不在 HikariCP 配置上就停了——泄漏可能是代码的**每个**连接获取点没在 finally 里 release */
@Component
@RequiredArgsConstructor
@Slf4j
public class ConnectionHealthProbe {

    private final HikariDataSource dataSource;          // Spring Boot 自动配好的 HikariCP

    @Scheduled(fixedDelay = 30_000)
    void logPoolStats() {
        HikariPoolMXBean pool = dataSource.getHikariPoolMXBean();
        if (pool == null) return;
        int active = pool.getActiveConnections();
        int idle = pool.getIdleConnections();
        int pending = pool.getThreadsAwaitingConnection();   // ★ 这是"线程在等连接"的真实数字
        log.info("连接池 active={} idle={} pending={}", active, idle, pending);
        if (pending > 0 && active > pool.getTotalConnections() * 0.8) {
            log.error("连接池接近满水位 active={} pending={}，请在 60 秒内取线程 dump", active, pending);
            // 第 57 篇"先取证再止血"——线程 dump 要在 pending 消退前抓，否则看不见谁在等
        }
    }
}
```

## 6. 常见坑

**坑 1：按最大并发估算池大小，忘了事务持有时间。** 错误做法：`100 TPS × 50ms = 5` 就开 10，但事务里调了第三方接口（RT 1s），那么**一个事务内连接被占住的时间是 1050ms**，实际吞吐上限是 10 ÷ 1.05 ≈ 9.5 TPS。问题：连接池的核心参数不是"每秒新建多少次"，而是"**一个请求平均持有连接多少毫秒**"（第 39 篇说过的"连接被事务占住"）。正确做法：Little's Law 反推的是**持有时间**，包括事务内的一切（SQL + RPC + 计算）；把长事务拆短，或者用中间的 `DataSourceUtils.releaseConnection` 提前释放——但 Spring 管理的 `@Transactional` 中做不到，所以是非注解的事务模板（第 39 篇的 `TransactionTemplate`）。

**坑 2：多数据源只用同一份连接池配置。** 错误做法：主库、从库、导出库都用默认 10，或者全用 30。问题：第 65 篇从库的读密集型流量可能需要更大的池，但第 4 节导出库只需要 5——用一样的配置要么主库连接不足、要么对慢查询太宽容。正确做法：**每个数据源根据其负载特征独立配池**（主库=写较多连接、从库=读大量慢查询短连接、归档/导出=少并发容忍长连接），并在监控上分开跟踪。连接数还受数据库侧限制影响——所有实例的总和不能超过 DB 的 `max_connections`，这是硬天花板。

## 7. 和之前知识的连接

- **第 51 篇「接口压测」**：拐点就是连接池被填满的那一瞬间；池大小的依据来自压测（下游 P99 + 事务持有时长），而不是拍脑袋。今天补上 Little's Law 的反推公式。
- **第 58 篇「线程池与并发」**：线程池与连接池的"等待"是乘法关系（一根线程拿一个连接等），第 4 节的 "WAITING (parking)" 堆栈正是两个池同时阻塞的交叉点。
- **第 39 篇「Spring 事务注解」**：事务持连接的时间决定了"一个请求需要多少个连接"，今天第 1 节的"持有时间"公式就是那篇的量化延伸。

## 8. 面试 / 工作中常见问题

### 问题 1：连接池大小怎么设定？

参考答案：Little's Law 算起点：**连接数 ≈ 目标 TPS × 每个请求持有连接的平均时间（含事务内的所有 SQL 与 RPC）**。例如目标 100 TPS、事务持有 300ms，需要约 30 个连接。然后压测验证：人为把下游拖慢到 P99，看池是否被占满。还要留出"慢查询"和"瞬发流量"的余量，以及数据库侧的 `max_connections` 上限——所有实例的池总和必须低于它。公式只是起点，压测才是判决依据（第 51 篇）。

### 问题 2：连接池里 active 一直是 full，pending 很高，但代码看起来没问题——你怀疑泄漏吗？

参考答案：先确认"泄漏"的定义：连接**归还了但被另一个人占住**是正常业务高峰，不算泄漏；**借了没还**才算泄漏。区分方法有两个：① 看 `leakDetectionThreshold` 日志（如果配了）——它会打出"超过配时未归还"的具体堆栈；② 抓线程 dump，搜索 `HikariCP connection is not available` / `WAITING (parking)` 找到等在哪，同时搜 `HikariCP connection not returned`。如果两者都搜不到，大部分排在等连接，而 active 全在正常运行 SQL——那就是"池不够大"，不是泄漏。

### 问题 3：数据库连接池与线程池配大了哪个更危险？

参考答案：配大了**连接池**的优先危害更大——因为线程池变大有上下文切换与内存代价，但**连接池变大会把数据库拉垮**：MySQL 每个连接都占内存、锁结构、可能的事务日志（长事务导致 undo 膨胀），而且连接数过高时数据库进程的上下文切换和锁争用会把延迟推高。经验教训：单实例连接数通常不要超过 100~200（以 DB 侧为准），连接池的值乘上服务实例数就是 DB 侧的总连接数——**配池时必须把"所有实例加总"算进去**，而不是孤立地看一个实例。

## 9. 今日小结

- 池大小的公式是 **Little's Law：连接数 ≈ TPS × 持有时长**，但压测才是判决依据。
- 连接泄漏靠 `leakDetectionThreshold` 定位（上线就配，日志留精确堆栈）；耗尽时的现场证据是 active/pending 指标 + 线程 dump 中指向 HikariCP 连接获取点的 `WAITING (parking)` 堆栈。
- 多数据源要独立配池（主/从/导出各按负载），且所有实例总和不能超过 DB 的 `max_connections`。
- 把长查询从主服务线程与连接池中隔离出去——舱壁思想同样适用于连接池（第 62 篇）。
