## 1. 本周摘要

本周前端生态的绝对主题是"安全"。Next.js 一次性披露 9 个 App Router 相关 CVE（4 个高危），其中 Server Action DoS 和 Turbopack 中间件绕过都可能直接影响生产服务；Node.js 紧随其后预告下周一（7 月 27 日）发布 HIGH 级安全更新，三条主线版本全部受影响；认证生态（Auth.js/next-auth、Hono）也在同一时间窗口集中修复。前端基础设施层正在经历一轮集体安全加固，团队未来两周需要为补丁预留明确的时间窗口。功能侧同样有重量级进展：Vue 3.6 进入 RC 阶段（Vapor Mode + Alien Signals），Chrome 151 从 Beta 推进到 Early Stable，pnpm 一口气发布 11.11-11.14 并带来内置 workspace 发布工作流。AI 工具链的主题则从上期的"可编程 Agent"切换为"安全加固 + 后台化"。整体趋势判断：前端生态正进入一个"安全基线升级"窗口期，补丁响应速度将直接影响团队的技术风险敞口。

## 2. 本周值得关注的 8 个变化

### 变化 1：Next.js 七月安全发布 —— v16.2.11 / v15.5.21 集中修复 9 个 CVE

* 分类：框架生态 / 安全
* 雷达评级：**采用**（立即打补丁）
* 来源：[Next.js July 2026 Security Release](https://nextjs.org/blog/july-2026-security-release) | [Next.js, Keycloak & Hono Patch Critical CVEs This Week](https://oday-bakkour.com/blog/nextjs-keycloak-hono-critical-cve-patches-july-2026)
* 发生了什么：Next.js 于 7 月 20 日发布安全公告、7 月 21 日推出补丁版本 v16.2.11（Active LTS）和 v15.5.21（Maintenance LTS），一次性修复 4 个高危 + 5 个中危漏洞。高危项包括：（1）**CVE-2026-64641**——针对使用 Server Actions 的 App Router 应用构造请求可导致 CPU 耗尽，阻塞同进程后续请求（DoS）；（2）**CVE-2026-64642**——使用 Turbopack 构建且 `config.i18n.locales` 只有单个条目的应用存在中间件/代理绕过，认证和安全检查可被跳过；（3）**CVE-2026-64645**——`rewrites()`/`redirects()` 的目标主机名若由请求输入拼接，可被指向任意主机，构成 SSRF 或开放重定向；（4）**CVE-2026-64649**——自定义服务器场景下 Server Action 转发请求时可被诱导发起 SSRF。中危项包括：SVG 图片优化 API 的 CPU 耗尽（64644）、Edge 运行时 Server Action 无界载荷导致内存消耗（64646）、Server Function 内部端点 ID 未授权泄露（64643）、以及两个服务端 `fetch` 请求体缓存混淆问题（64648/64647，特定调用形态或包含非法 UTF-8 字节时，可能返回同 URL 不同 body 请求的缓存响应）。值得注意的背景是：这是 Next.js 上周宣布"预公告安全发布模式"（[security release program](https://nextjs.org/blog/next-security-release-program)）后的第一次执行——先公告、后发补丁，给团队预留规划时间。
* 为什么值得关注：9 个 CVE 集中在 App Router + Server Actions 这条 Next.js 最主流的技术路径上，且多个高危项的利用门槛不高（构造请求即可）。DoS 和中间件绕过对生产服务是现实威胁，不是理论风险。同时，"预公告 + 定时补丁"的新机制意味着未来 Next.js 安全更新会变成可预期的例行事项，团队流程需要适配。
* 对前端工程师的影响：使用 Next.js App Router 的项目需要本周内完成升级。即使项目没有显式使用 Server Actions，只要依赖链中存在（包括框架内部生成的），也可能落在受影响面上。
* 对现有项目的影响：所有低于 16.2.11 / 15.5.21 的 Next.js App Router 项目存在安全风险。使用 Turbopack + 单 locale 配置的项目尤其需要确认中间件绕过项。
* 建议动作：**本周内升级到 v16.2.11 或 v15.5.21**。升级后对照 CVE 列表做一次暴露面自查：是否使用 Server Actions、是否有 Turbopack + 单 locale 配置、`rewrites()`/`redirects()` 目标是否包含请求可控输入。16.3 canary 用户升级到 `16.3.0-canary.92`+。

### 变化 2：Node.js 预告 7 月 27 日 HIGH 级安全发布 —— 26.x / 24.x / 22.x 全部受影响

* 分类：工程化 / 安全
* 雷达评级：**采用**（提前准备补丁）
* 来源：[Node.js July 2026 Security Releases 公告](https://nodejs.org/zh-cn/blog/vulnerability/july-2026-security-releases) | [Node.js Security Release: HIGH Severity - TechTimes](https://www.techtimes.com/articles/321432/20260723/nodejs-security-release-high-severity-vulnerabilities-hit-all-three-lines.htm)
* 发生了什么：Node.js 项目于 7 月 21 日发布预告：将于 **2026 年 7 月 27 日（下周一）或之后不久** 发布 26.x、24.x、22.x 三条发布线的安全更新，本次修复的最高严重级别为 **HIGH**，且三条线均为 HIGH。按惯例，漏洞细节在补丁发布前不予披露。公告同时提醒：已 EOL 的版本虽然同样受影响，但通常不会收到修复。
* 为什么值得关注：HIGH 级漏洞 + 三条主线全部受影响 + 细节保密到发布那一刻——这意味着周一补丁落地后，团队需要快速响应而不是慢慢排期。结合上期雷达提到的 Node.js 年度发布节奏调整（每个版本都有 LTS），Node 运行时的安全维护正在变得更加常规化和高频化。
* 对前端工程师的影响：所有以 Node.js 为运行时的项目（前端构建、SSR 服务、BFF、CI 环境）都在受影响范围内。需要确认本地、CI、生产环境各自使用的 Node 版本落在哪条发布线上。
* 对现有项目的影响：潜在影响面广，但具体风险要等周一补丁披露 CVE 细节后才能精确评估。
* 建议动作：**本周内盘点项目/CI/生产环境的 Node 版本分布**（22.x / 24.x / 26.x 各有多少），为周一的升级预留时间窗口和负责人。如果使用版本管理工具（nvm / fnm / volta），提前确认升级命令可行。

### 变化 3：Vue 3.6 进入 RC 阶段 —— Vapor Mode 与 Alien Signals 临近落地

* 分类：框架生态
* 雷达评级：**观察**（实验性项目可试点）
* 来源：[vuejs/core Releases](https://github.com/vuejs/core/releases) | [Vue 3.6 and Vapor Mode - José Gutierrez](https://jose-gutierrez.com/en/articles/vue-36-and-vapor-mode-this-is-another-level)
* 发生了什么：Vue 3.6 本周完成 RC 化——v3.6.0-rc.1 于 7 月 18 日发布，v3.6.0-rc.2 于 7 月 22 日发布（均在本期扫描窗口附近，rc.2 在窗口内）。3.6 是 Vue 3.0 以来最大的一次架构演进，两个核心新东西：（1）**Vapor Mode**——一种新的编译策略，将模板编译为细粒度的直接 DOM 操作，绕过虚拟 DOM，大幅降低渲染和内存开销；（2）**Alien Signals**——重写的响应式引擎，社区测试显示内存占用较 3.5 有明显下降、computed 副作用处理更快（具体幅度以官方最终发布说明为准）。此外 3.6 还瘦身了基础运行时，并改善了与 Oxc、Rolldown 等 Rust 工具链的集成。
* 为什么值得关注：RC 意味着 API 基本冻结、进入稳定性验证期，按 Vue 的惯例稳定版通常在数周内发布。Vapor Mode 不是"又一个性能优化"，而是 Vue 第一次提供"无虚拟 DOM"的渲染路径——它决定了 Vue 未来几年在极致性能场景（大列表、高频更新、嵌入式组件）下的竞争力。对以 Vue 为主力的团队，这是必须提前理解的架构变化。
* 对前端工程师的影响：稳定版发布后，Vue 项目将多出一个"是否启用 Vapor"的决策点。Vapor Mode 保持现有 API 兼容，理论上可渐进采用，但生态（组件库、工具链）的跟进需要时间。
* 对现有项目的影响：短期内无影响——RC 不建议进生产。但 3.6 稳定版发布后，升级评估需要提上日程。
* 建议动作：**不急着进生产**。可以在实验项目或独立页面上安装 rc.2 体验 Vapor Mode，重点观察与现有组件库的兼容情况。同时关注 vue-tsc / Volar 对 3.6 的适配进度（与上期跟踪的 TS 7.0 编程式 API 问题相关联）。

### 变化 4：Chrome 151 推进到 Early Stable —— textStream()、软导航指标等能力进入生产可用

* 分类：浏览器 / Web 平台
* 雷达评级：**试点**
* 来源：[Chrome Releases: July 2026](https://chromereleases.googleblog.com/2026/07/) | [Microsoft Edge 151 web platform release notes](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/release-notes/151)
* 发生了什么：上期雷达覆盖的 Chrome 151 Beta 本周正式推进到稳定通道——7 月 22 日桌面端与 Android 发布 151.0.7922.47/.48（Early Stable，先覆盖小部分用户），7 月 23 日 Chrome 150 稳定版推送安全补丁（150.0.7871.186/.187），同日 Chrome Dev 通道出现 152.0.7965.2。Edge 151（计划 7 月 30 日发布）的 release notes 本周公开，确认了 151 的完整特性清单。除上期已介绍的 `textStream()`、软导航/交互内容绘制指标、跨 Shadow Root ARIA（reference targets）、`<usermedia>`、Rust XML 解析器外，本期补充几个对日常开发有直接影响的点：（1）**CSS `alpha()` 函数**——对已有颜色应用指定透明度（`alpha(from red / 0.5)`）；（2）**`position-anchor` 初始值从 `none` 改为 `normal`**——这是一个行为变化，使用 CSS 锚点定位的项目需要验证；（3）**`animation-trigger` 的 `play` 系列值不再自动回带动画**；（4）**Speculation Rules 新增 `form_submission` 字段**——搜索结果页等可预测 URL 的表单提交现在可以激活预渲染；（5）**`WheelEvent.momentum`**——区分惯性滚动事件和真实触控板事件；（6）**LanguageDetector 可区分简繁中文**（返回 `zh-Hans`/`zh-Hant`）。
* 为什么值得关注：上期这些能力还只是 Beta，本周已进入稳定通道，意味着可以从"了解"转入"使用"。其中 `position-anchor` 初始值变化是本期唯一需要警惕的兼容性行为变化——锚点定位是近两年的热门 CSS 能力，已有项目在使用的话要确认表现是否符合预期。`form_submission` 预渲染则给搜索类站点提供了一个低成本的首屏提速手段。
* 对前端工程师的影响：`textStream()` 现在可以在生产代码中使用（配合降级）；SPA 项目可以开始用原生 `soft-navigation` 指标替代自定义路由计时；使用锚点定位的组件需要回归测试。
* 对现有项目的影响：低，整体是渐进增强。唯一的行为变化点是 `position-anchor` 初始值（影响使用 CSS anchor positioning 的项目）。
* 建议动作：在 API 调用层启用 `textStream()`（上期已给出代码示例，本周可正式落地）；使用锚点定位的项目做一次定位行为回归；搜索类站点评估 `form_submission` 预渲染的收益。

### 变化 5：pnpm 11.11-11.14 连发 —— 内置 workspace 发布工作流 + 安全加固继续

* 分类：工程化与团队实践 / 安全
* 雷达评级：**采用**（安全修复）/ **试点**（发布工作流）
* 来源：[pnpm 11.11-11.14 Release Notes](https://pnpm.io/blog/releases/11.11-11.14)
* 发生了什么：pnpm 于 7 月 18 日（上期截稿后、本期窗口前，上期未覆盖）一次性发布了 11.11 至 11.14 四个版本。安全方面延续了前几期的加固节奏：（1）修复一个新的**路径穿越缺陷**——恶意 manifest 名称可在 `pnpm install` 期间（即使带 `--ignore-scripts`）把文件写到 `node_modules` 之外；（2）隔离链接器、PnP 解析映射和全局虚拟存储路径检查会拒绝可重构穿越序列的恶意 lockfile 路径键；（3）更新 adm-zip 规避恶意压缩包导致的内存爆炸；（4）self-update 支持 `trustPolicy=no-downgrade` 并在切换前验证新二进制。功能方面最大的变化是 **pnpm 内置了 workspace 发布工作流**：`pnpm change` 以 changeset 风格记录版本计划，`pnpm version -r` 应用版本、推进 `workspace:` 范围、生成 changelog；支持 release lanes（`pnpm lane` 生成预发布版本）和 `versioning.epics`（成员包跟随主包大版本带）。此外新增 `pnpm doctor`（环境健康检查：版本、安装方式、PATH、缓存/存储可写性、registry 可达性、离线安装测试）、`pnpm access` / `pnpm team`（registry 包可见性与团队管理），冷缓存解析的峰值内存下降约 30%。
* 为什么值得关注：两条线都值得注意。安全线上，这是连续第五期跟踪 pnpm 安全修复——路径穿越问题在 11.7 修过一轮，本周又修一轮，说明依赖安装环节的攻击面比想象的更持久。功能线上，pnpm 正式进入 monorepo 发布管理领域，直接对标 changesets——如果这套工作流成熟，monorepo 团队可以少维护一个工具链环节。
* 对前端工程师的影响：所有 pnpm 用户应升级获得安全修复。monorepo 团队多了一个发布工具选项，但新工作流刚发布，生态验证不足。
* 对现有项目的影响：安全修复为增量更新，破坏性风险低。发布工作流是 opt-in，不影响现有项目。
* 建议动作：**升级到 11.14**（`pnpm self-update` 或 `corepack prepare pnpm@latest --activate`），升级后顺手跑一次 `pnpm doctor` 做环境体检。monorepo 团队可以阅读发布工作流文档做评估，但不建议本周就替换 changesets。

### 变化 6：AI 编程工具本周主题：安全加固 + 后台化

* 分类：前端 AI 工具链
* 雷达评级：**观察**（持续趋势）
* 来源：[Claude Code Changelog](https://code.claude.com/docs/en/changelog) | [Cursor Changelog](https://cursor.com/changelog) | [Node.js Flags Major Patch, Auth Stack Hardens This Week](https://oday-bakkour.com/blog/nodejs-security-auth-hardening-july-23-2026)
* 发生了什么：本周 AI 编程工具的更新呈现出高度一致的主题。（1）**Claude Code** 在 7 月 18-22 日连发 2.1.214 至 2.1.218 五个版本：2.1.218 把 `/code-review` 改造为**后台审查 Agent**（异步执行、不阻塞主对话）；2.1.217 限制并发子 Agent 数量并修复内存泄漏；2.1.216 新增 `sandbox.filesystem.disabled` 配置、修复 worktree/子 Agent 逃逸和符号链接相关的安全问题；2.1.215 停止自动执行 `/verify` 和 `/code-review`（改为用户显式触发）；2.1.214 修复多个命令审批绕过漏洞。（2）**Cursor** 于 7 月 22 日推出 **Cursor Router**——Auto 模式引入模型路由，按任务特征自动分发到不同模型，用户无需手动选择。（3）**Prisma 7.9.0** 新增 "AI safety checkpoint"——当 AI Agent 试图执行破坏性 CLI 操作时，未经确认会被拦截。
* 为什么值得关注：上期雷达观察到 Cursor Cloud Agent Hooks 开启"可编程 Agent"阶段，本周这个趋势进一步分化为两个清晰方向：一是**安全加固**——命令审批绕过修复、沙箱配置、子 Agent 逃逸防护、破坏性操作拦截，AI 工具正在补齐企业级安全底线；二是**后台化**——代码审查从同步阻塞变为异步后台 Agent，模型选择从人工决策变为自动路由。这两个方向合起来意味着 AI 工具正在从"需要人盯着的助手"变成"可以托管的基础设施"。
* 对前端工程师的影响：Claude Code 用户可以体验后台代码审查——提交前让 Agent 在后台跑一轮 review，不打断开发节奏。Cursor 用户的 Auto 模式会自动做模型路由，使用成本不变但行为会变化。
* 对现有项目的影响：低。工具链层面的变化，不影响项目代码。但团队的 AI 工具安全配置（沙箱、审批、破坏性操作拦截）值得纳入使用规范。
* 建议动作：Claude Code 用户升级到最新版并试用后台 `/code-review`；在团队 AI 工具使用建议（上期小动作的产出）中补充安全配置项——沙箱策略、命令审批、破坏性操作确认。

### 变化 7：Nuxt 3 EOL 进入最后一周（7 月 31 日）—— v3.21.9 可能是最后一次补丁

* 分类：框架生态
* 雷达评级：**采用**（完成迁移或敲定应急方案）
* 来源：[Nuxt Releases（v4.5.0 / v3.21.9）](https://github.com/nuxt/nuxt/releases) | [Nuxt 3 EOL 讨论 - GitHub](https://github.com/nuxt/nuxt/discussions/33918) | [Nuxt 4 升级指南](https://nuxt.com/docs/4.x/getting-started/upgrade)
* 发生了什么：Nuxt 于 7 月 18 日发布 v4.5.0 和 v3.21.9。v3.21.9 很可能是 Nuxt 3 在 7 月 31 日 EOL 之前的最后一次补丁。这是连续第六期技术雷达跟踪的最高优先级事项——倒计时从第 25 周的"半年"一路收紧到本周的"最后一周"。Nuxt 4 侧则保持活跃迭代（4.5.0 为迁移目标版本）。
* 为什么值得关注：已经没有缓冲期了。7 月 31 日之后 Nuxt 3 不再收到任何安全补丁，8 月 1 日起暴露的每一个零日漏洞都需要团队自行修补。v3.21.9 的发布本身就是一个信号——官方在做 EOL 前的最后收尾。
* 对前端工程师的影响：仍在 Nuxt 3 上的团队本周必须做出最终决定：要么冲刺迁移，要么正式敲定 EOL 后的自行维护方案（包括安全监控、补丁 fork、明确的最终迁移截止日期）。
* 对现有项目的影响：使用 Nuxt 3 的生产项目将在一周后失去官方安全支持。
* 建议动作：**本周是最后一个完整工作周**。能迁移的立即执行 `compatibilityVersion: 4` 渐进迁移 + `npx nuxt upgrade --dedupe`；确实无法在本周完成的，必须产出书面的应急预案，而不是继续观望。

### 变化 8：认证生态集中安全修复 —— Auth.js/next-auth 与 Hono

* 分类：工程化与安全
* 雷达评级：**采用**（相关用户升级）
* 来源：[Next.js, Keycloak & Hono Patch Critical CVEs This Week](https://oday-bakkour.com/blog/nextjs-keycloak-hono-critical-cve-patches-july-2026) | [Node.js Flags Major Patch, Auth Stack Hardens This Week](https://oday-bakkour.com/blog/nodejs-security-auth-hardening-july-23-2026)
* 发生了什么：本周认证与 Web 框架生态有两组值得注意的安全修复。（1）**Auth.js / next-auth** 于 7 月 20 日发布 4.24.15 和 5.0.0-beta.32：将 OAuth state / PKCE cookie 绑定到具体 provider（防止跨 provider 的 CSRF 混淆），并修复一个同形字符（homoglyph）邮箱绕过问题——攻击者可用视觉上相同的"假 @ 符号"邮箱绕过校验。（2）**Hono** 于 7 月 21 日披露三个中危 CVE（均已在 6 月 23 日的 v4.12.27 修复，当前最新 v4.12.31）：CVE-2026-59896（并发 SSR 请求之间组件上下文数据泄漏）、CVE-2026-59895（样式类字符串未转义导致服务端渲染 XSS）、CVE-2026-59897（API Gateway v1 适配器对重复 header 匹配过松）。
* 为什么值得关注：这两组修复和 Next.js 的 9 个 CVE 出现在同一周不是巧合——安全研究者正在系统性地审计前端基础设施的每一层（框架、认证、Web 运行时）。Auth.js 的同形字符邮箱绕过尤其值得注意：这类"看起来像合法邮箱"的攻击很难被常规校验发现。Hono 的 SSR 上下文泄漏则提醒使用边缘渲染框架的团队：并发隔离是 SSR 安全的隐藏雷区。
* 对前端工程师的影响：使用 NextAuth/Auth.js 的项目应升级到 4.24.15（v5 用户升级到 beta.32+）；使用 Hono 的项目确认版本不低于 4.12.27。
* 对现有项目的影响：仅影响使用这两个库的项目。修复均为补丁版本，升级风险低。
* 建议动作：检查依赖树中是否有 `next-auth` / `@auth/core` / `hono`，有则本周升级。如果项目涉及邮箱校验逻辑，可以顺手自查是否存在同形字符处理盲区。

## 4. 可以引入团队的实践

### 实践 1：建立"安全预公告 → 补丁"响应小流程

* 适合场景：所有前端团队——本周 Next.js 和 Node.js 都采用了"先公告、后发补丁"的模式，这种模式正在成为主流
* 引入成本：低
* 预期收益：把安全补丁从"看到新闻才反应"变成"有节奏地响应"，缩短风险敞口时间
* 建议试点方式：在团队维护一份极简的"运行时/框架版本清单"（Next.js、Node.js、pnpm、认证库各用什么版本、谁负责），并订阅两个官方安全通道：Next.js 安全公告（[nextjs.org/blog](https://nextjs.org/blog)）和 nodejs-sec 邮件列表。收到预公告后，在清单上标注受影响项、预留补丁时间窗口。本周就是现成的演练机会：Node.js 周一补丁 + Next.js 本周补丁。

### 实践 2：把上期试点的 Chrome 151 新能力从 Beta 升级到生产可用

* 适合场景：有流式请求（AI 对话、SSE）或 SPA 路由的项目
* 引入成本：低
* 预期收益：`textStream()` 简化流式文本处理代码；`soft-navigation` 指标让 SPA 性能度量不再依赖自定义 hack
* 建议试点方式：上期雷达给出了 `textStream()` 的替换示例（`response.body.pipeThrough(new TextDecoderStream())` → `response.textStream()`），本周 Chrome 151 已进入 Early Stable，可以在主项目中正式落地（保留旧写法降级）。SPA 项目可以开始用 Performance Timeline 监听 `soft-navigation` 条目，采集页面切换耗时基线数据，为后续性能优化提供依据。

### 实践 3：用 `pnpm doctor` 做一次依赖环境体检

* 适合场景：所有使用 pnpm 的项目，尤其是 CI 环境
* 引入成本：低
* 预期收益：一次性检查版本、安装方式、PATH、缓存/存储可写性、registry 可达性、离线安装能力，提前发现环境隐患
* 建议试点方式：升级到 11.14 后，在本地和 CI 各跑一次 `pnpm doctor`（支持 `--json` 输出和 `--offline` 离线模式）。把检查项纳入新环境搭建的标准步骤，避免"在我机器上能装"类问题。

## 5. 只是噱头，暂时不用管

### 内容 1：急着把 Vue 3.6 Vapor Mode 上生产

* 为什么不用急：Vapor Mode 进入 RC 是重要的架构信号，但 RC 不等于稳定版——API 仍可能微调，生态（组件库、vue-tsc、SSR 工具链）对 Vapor 的适配也还没跟上。Vapor 的价值在极致性能场景（大列表、高频更新），绝大多数业务页面用标准虚拟 DOM 模式完全够用，现在迁移没有实际收益，反而要承担预发布版本的风险。
* 后续观察点：关注 3.6 稳定版的发布时间、主流组件库（Element Plus、Naive UI、Vuetify 等）的 Vapor 兼容声明，以及 vue-tsc 的适配进度。

### 内容 2：WebMCP / 浏览器内 Agent（Edge 本期加入 Origin Trial）

* 为什么不用急：Edge 151 的 Origin Trial 列表中出现了 WebMCP（让网站向浏览器内 Agent 注册工具），加上之前 Chrome 的 WebMCP Origin Trial 和 Lighthouse Agentic Browsing 评估，"网站对 AI Agent 可编程"的叙事确实在升温。但这仍处在实验阶段——没有稳定规范、没有跨浏览器共识、没有真实用户规模。现在投入开发 WebMCP 集成，大概率要面对规范变动带来的返工。
* 后续观察点：关注 W3C 是否启动相关标准化讨论，以及 Chrome / Safari / Firefox 是否从 Origin Trial 走向默认启用。

### 内容 3：立即用 pnpm 内置发布工作流替换 changesets

* 为什么不用急：`pnpm change` / release lanes / epics 的设计思路很好（版本计划、changelog、workspace 范围推进一站式完成），但它刚发布不到一周，没有任何生态验证和踩坑积累，文档和社区实践都还是空白。发布流程是 monorepo 里最脆弱的环节之一，用零验证的新工具替换正在工作的 changesets，风险收益比不划算。
* 后续观察点：关注 pnpm 发布工作流的文档完善度、社区迁移案例，以及它是否能处理 monorepo 之外的发布场景。等出现 2-3 个可参考的团队实践后再评估。

### 小动作：完成 Next.js 补丁 + 备好周一 Node.js 安全升级

     # CI：检查 .github/workflows 或 CI 配置中的 node-version
