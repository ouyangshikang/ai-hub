# Java 学习：统一返回结构

> 系列第 22 篇 · 第三阶段：接口与规范  
> 上一篇参数校验失败时返回了 `{ "code": 400, "message": "门店名称不能为空" }`，成功时返回了 `{ "code": 200, "data": 10086 }`。这个 `code + message + data` 的结构就是今天的主角。目前每个接口各自包装返回值，格式不统一、字段名不一致，前端每次对接都要猜"这个接口的成功标识是 code=200 还是 success=true"。今天讲怎么设计一套全局统一的响应结构，让所有接口的返回格式一致，前端只需要一套通用的响应拦截逻辑。

## 1. 今天学什么

一个后端系统可能有上百个接口。如果没有统一的返回结构，每个开发者按自己的习惯包装返回值——有人返回 `{ "status": "ok", "result": ... }`，有人返回 `{ "errCode": 0, "body": ... }`，有人直接返回裸数据。前端对接时，每个接口都要单独处理响应格式，axios 拦截器写不出通用逻辑，错误处理散落各处。

统一返回结构的核心思想是：所有接口，无论成功还是失败，都返回同一个"信封"格式。信封里有固定的字段（业务状态码、提示信息、数据体），前端只需要一套拦截器就能处理所有接口的成功和失败。这不是什么高深技术，但它是前后端协作效率的基础设施——没有它，每次联调都在对齐"你这个接口成功时返回什么、失败时返回什么"。

## 2. 前端工程师视角理解

你在前端一定写过 axios 拦截器：

```typescript
// axios 响应拦截器
axios.interceptors.response.use(
  (response) => {
    const { code, message, data } = response.data;
    if (code === 200) {
      return data; // 成功：直接返回业务数据
    }
    // 失败：统一弹提示
    ElMessage.error(message || '请求失败');
    return Promise.reject(new Error(message));
  },
  (error) => {
    // HTTP 层面的错误（网络断开、502 等）
    ElMessage.error('网络异常，请稍后重试');
    return Promise.reject(error);
  }
);
```

这段代码能工作的前提是：后端所有接口都返回 `{ code, message, data }` 这个结构。如果某个接口返回的是 `{ success: true, result: ... }`，你的拦截器就判断不了，得单独处理。

后端的"统一返回结构"就是给这个拦截器提供稳定契约。你在前端定义一个 TypeScript 接口：

```typescript
interface ApiResponse<T> {
  code: number;
  message: string;
  data: T | null;
}
```

后端要做的就是：每个接口都返回符合这个结构的 JSON，成功时 `code=200`、`data` 有值；失败时 `code` 是具体错误码、`message` 是人话、`data` 为 null。前后端围绕这个结构达成契约，联调效率直接翻倍。

## 3. 和 JavaScript / TypeScript 的对比

### 返回值包装：Node.js vs Spring Boot

```typescript
// Node.js + Express：手动包装返回值
app.get('/api/stores/:id', async (req, res) => {
  try {
    const store = await storeService.getById(req.params.id);
    res.json({ code: 200, message: 'success', data: store });
  } catch (e) {
    res.json({ code: 500, message: e.message, data: null });
  }
});
```

```java
// Spring Boot：用统一的 Result 类包装
@GetMapping("/{id}")
public Result<StoreVO> detail(@PathVariable Long id) {
    StoreVO store = storeService.getById(id);
    return Result.success(store);
}
```

Node.js 里你通常手动 `res.json({ code, message, data })`，每个路由都写一遍。Spring Boot 的做法是定义一个泛型类 `Result<T>`，提供静态工厂方法 `Result.success(data)` 和 `Result.fail(code, message)`，Controller 方法直接返回 `Result<T>`，Spring MVC 自动序列化成 JSON。

### 泛型约束：TypeScript interface vs Java 泛型类

```typescript
// TypeScript：用泛型接口约束返回结构
interface ApiResponse<T> {
  code: number;
  message: string;
  data: T | null;
}

// 使用时类型安全
const res: ApiResponse<StoreVO> = await fetch('/api/stores/1');
res.data.name; // ✅ 类型推导正确
```

```java
// Java：用泛型类约束返回结构
public class Result<T> {
    private int code;
    private String message;
    private T data;

    public static <T> Result<T> success(T data) {
        return new Result<>(200, "success", data);
    }

    public static <T> Result<T> fail(int code, String message) {
        return new Result<>(code, message, null);
    }
}

// 使用时类型安全
public Result<StoreVO> detail(@PathVariable Long id) { ... }
// 前端拿到的 JSON：{ "code": 200, "message": "success", "data": { "name": "..." } }
```

两者的设计思路完全一致：用泛型让"信封"和"内容物"分离。`Result<StoreVO>` 表示信封里装的是门店数据，`Result<PageResult<OrderVO>>` 表示信封里装的是分页订单列表。Java 的泛型在运行时会被擦除（不像 TypeScript 有类型守卫），但在编译期同样能帮你检查"这个接口该返回什么类型的数据"。

### 为什么 Java 后端更强调统一结构

前端项目里，API 层通常一个人封装，风格不一致时自己改就行。后端是多人协作——张三写门店接口、李四写订单接口，如果没有统一的 `Result` 类，张三返回 `{ code, msg, data }`，李四返回 `{ errCode, errMsg, result }`，前端要写两套解析逻辑。Java 后端通过一个公共的 `Result` 类 + 团队规范，从代码层面杜绝格式不一致。

## 4. 真实业务场景

门店管理系统里，前端需要对接的接口包括：门店列表、门店详情、新增门店、修改门店状态、删除门店、订单列表、订单导出。

如果没有统一返回结构会怎样？

一是前端拦截器写不出通用逻辑。门店列表接口返回 `{ "code": 200, "data": [...] }`，订单导出接口返回 `{ "success": true, "url": "..." }`，新增门店接口返回 `{ "id": 10086 }`。前端每个接口都要单独判断"怎么算成功、数据在哪个字段"，axios 拦截器形同虚设。

二是错误处理不一致。有的接口失败时返回 HTTP 200 + `{ "code": 500, "message": "..." }`，有的直接返回 HTTP 500 + 一段 HTML 错误页。前端 `catch` 里拿到的东西格式不统一，有的能解析出 message 展示给用户，有的只能显示"服务器错误"。

三是联调成本翻倍。每对接一个新接口，前端都要问后端"你这个接口成功返回什么格式、失败返回什么格式"。有了统一结构后，前端只需要知道 `data` 里的业务字段是什么，外层信封永远不变。

## 5. Java 示例代码

```java
/**
 * 统一响应结构 —— 所有接口的"信封"
 * 泛型 T 表示 data 字段的类型
 */
public class Result<T> {

    private int code;       // 业务状态码：200 成功，其他为具体错误码
    private String message; // 提示信息：成功时为 "success"，失败时为人话错误描述
    private T data;         // 业务数据：成功时有值，失败时为 null

    // 私有构造，强制通过静态方法创建
    private Result(int code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    // 成功：带数据
    public static <T> Result<T> success(T data) {
        return new Result<>(200, "success", data);
    }

    // 成功：无数据（比如删除操作）
    public static <T> Result<T> success() {
        return new Result<>(200, "success", null);
    }

    // 失败：指定错误码和消息
    public static <T> Result<T> fail(int code, String message) {
        return new Result<>(code, message, null);
    }

    // getter / setter 省略（或用 Lombok @Data）
}
```

```java
/**
 * 分页结果的通用包装
 * 嵌套在 Result 里使用：Result<PageResult<StoreVO>>
 */
public class PageResult<T> {

    private List<T> list;  // 当前页数据
    private long total;    // 总记录数
    private int pageNum;   // 当前页码
    private int pageSize;  // 每页条数

    public static <T> PageResult<T> of(List<T> list, long total, int pageNum, int pageSize) {
        PageResult<T> result = new PageResult<>();
        result.setList(list);
        result.setTotal(total);
        result.setPageNum(pageNum);
        result.setPageSize(pageSize);
        return result;
    }

    // getter / setter 省略
}
```

```java
/**
 * Controller 中的实际使用
 * 所有方法返回 Result<T>，格式统一
 */
@RestController
@RequestMapping("/api/stores")
public class StoreController {

    @Autowired
    private StoreService storeService;

    // 列表查询：Result 里装分页数据
    @GetMapping
    public Result<PageResult<StoreVO>> list(StoreQueryParam param) {
        PageResult<StoreVO> page = storeService.queryStores(param);
        return Result.success(page);
    }

    // 详情查询：Result 里装单个对象
    @GetMapping("/{id}")
    public Result<StoreVO> detail(@PathVariable Long id) {
        StoreVO store = storeService.getById(id);
        if (store == null) {
            return Result.fail(404, "门店不存在");
        }
        return Result.success(store);
    }

    // 新增：Result 里装新记录的 id
    @PostMapping
    public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) {
        Long storeId = storeService.createStore(dto);
        return Result.success(storeId);
    }

    // 删除：成功但无数据
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) {
        storeService.deleteStore(id);
        return Result.success();
    }
}
```

前端收到的 JSON 永远是这个形状：

```json
// 成功
{ "code": 200, "message": "success", "data": { "list": [...], "total": 128, "pageNum": 1, "pageSize": 20 } }

// 失败
{ "code": 404, "message": "门店不存在", "data": null }
```

前端拦截器只需要判断 `code === 200`，然后取 `data` 就行——不管对接哪个接口，逻辑完全一样。

## 6. 常见坑

### 坑 1：HTTP 状态码和业务状态码混为一谈

```java
// ❌ 业务失败时直接返回 HTTP 500
@GetMapping("/{id}")
public ResponseEntity<StoreVO> detail(@PathVariable Long id) {
    StoreVO store = storeService.getById(id);
    if (store == null) {
        return ResponseEntity.status(500).body(null); // HTTP 500
    }
    return ResponseEntity.ok(store);
}
```

"门店不存在"是业务层面的"没找到"，不是服务器出了故障。返回 HTTP 500 会让前端的 axios 走进 `catch` 分支（因为 HTTP 状态码非 2xx），和真正的服务器错误混在一起。正确做法：HTTP 状态码永远返回 200（表示"请求本身是成功的"），业务层面的成功/失败用 `Result` 里的 `code` 字段区分。这样前端只需要在 `then` 里判断 `code`，不需要同时处理 `then` 和 `catch` 两种路径。

### 坑 2：Result 类没有用泛型，data 写成 Object

```java
// ❌ data 是 Object，前端拿到的 JSON 没有类型约束
public class Result {
    private int code;
    private String message;
    private Object data; // 什么都能塞，编译期无法检查
}
```

用 `Object` 虽然能跑，但 Controller 方法的返回值无法体现"这个接口的 data 是什么类型"。新人接手时看不出接口契约，IDE 也无法做类型提示。正确做法：`Result<T>` 泛型，方法签名 `Result<StoreVO>` 一眼就知道 data 里是门店数据。

### 坑 3：部分接口忘了包装，直接返回裸数据

```java
// ❌ 这个接口直接返回 List，没有 Result 包装
@GetMapping("/api/stores/all")
public List<StoreVO> allStores() {
    return storeService.findAll();
}
```

前端拦截器期望所有响应都是 `{ code, message, data }` 结构，突然收到一个裸数组 `[{...}, {...}]`，`response.data.code` 是 `undefined`，拦截器判断失败。正确做法：所有接口无例外地返回 `Result<T>`，哪怕数据是一个简单列表。

### 坑 4：错误码定义随意，没有统一管理

```java
// ❌ 每个人自己编错误码
return Result.fail(1001, "门店不存在");  // 张三用 1001
return Result.fail(40001, "门店不存在"); // 李四用 40001
return Result.fail(-1, "门店不存在");    // 王五用 -1
```

错误码没有统一规范，前端无法根据 code 做差异化处理（比如 401 跳登录、403 提示无权限、404 显示空状态）。正确做法：定义一个错误码枚举类或常量类，按模块分段（比如 1xxxx 门店模块、2xxxx 订单模块），团队统一引用，不允许自己编。

### 坑 5：成功时也塞了 message 提示，前端误弹 toast

```java
// ❌ 成功时 message 写了业务提示
return Result.success(data, "保存成功！");
// 前端拦截器：if (code === 200) { ElMessage.success(res.message) }
// 结果每个接口都弹一次"success"或"保存成功"，用户体验很差
```

成功时 `message` 固定为 `"success"` 即可，具体的操作反馈（"保存成功"、"删除成功"）由前端根据用户操作自行提示，不由后端决定。后端管数据，前端管交互反馈。

## 7. 和之前知识的连接

- **第 21 篇「请求参数校验」** 是今天的直接前置。上一篇校验失败时我们写了 `Result.fail(400, "门店名称不能为空")`，成功时写了 `Result.success(storeId)`——那时候 `Result` 类已经出场了，今天正式把它作为全局规范来设计。参数校验管"入口数据合不合规"，统一返回结构管"出口格式一不一致"，一入一出，接口层就稳了。

- **第 20 篇「RESTful 接口设计」**：RESTful 规范了 URL 和 HTTP 方法，统一返回结构规范了响应体。两者配合，接口从"路径 → 方法 → 参数 → 响应"全链路都有统一约定。前端对接时：看 URL 知道操作什么资源，看 HTTP 方法知道做什么操作，看 `Result<T>` 的泛型知道 data 里是什么类型。

- **第 10 篇「DTO / VO / Entity 的区别」**：`Result<StoreVO>` 里的 `StoreVO` 就是那篇讲的"给前端展示的数据结构"。统一返回结构不改变 DTO / VO 的设计，它只是在 VO 外面再套一层"信封"。VO 管"数据长什么样"，Result 管"数据怎么送达"。

## 8. 面试 / 工作中常见问题

### 问题 1：你们项目的统一返回结构是怎么设计的？包含哪些字段？

参考答案：三个核心字段：`code`（业务状态码，200 表示成功，其他为具体错误码）、`message`（提示信息，成功时为 "success"，失败时为用户可读的错误描述）、`data`（泛型，承载业务数据，失败时为 null）。HTTP 状态码统一返回 200，业务成功/失败通过 `code` 区分。分页接口 data 里嵌套 `PageResult`（list + total + pageNum + pageSize）。前端 axios 拦截器只判断 `code === 200`，统一处理所有接口。

### 问题 2：为什么 HTTP 状态码统一返回 200，而不是用 4xx / 5xx 表达业务错误？

参考答案：两个原因。一是简化前端处理：如果业务失败返回 HTTP 4xx/5xx，axios 会走进 catch 分支，前端需要同时处理 then（业务成功）和 catch（业务失败 + 网络错误）两条路径，逻辑分散。统一 200 后，所有业务逻辑都在 then 里通过 code 判断，catch 只处理真正的网络异常。二是语义清晰：HTTP 状态码表达的是"HTTP 通信层面"的状态（请求到达了、服务器处理了），业务层面的"门店不存在"、"余额不足"不是 HTTP 协议该管的事。

### 问题 3：如果团队里有人不按统一格式返回怎么办？

参考答案：三层保障。一是代码层面：`Result` 类只提供静态工厂方法，构造器私有，强制通过 `Result.success()` / `Result.fail()` 创建，减少随意包装的可能。二是 Code Review：接口返回值不是 `Result<T>` 类型的不允许合入。三是全局兜底：通过 `ResponseBodyAdvice` 拦截所有 Controller 返回值，如果不是 `Result` 类型就自动包装——即使有人忘了手动包装，框架也会兜底。

## 9. 今日小结

- 统一返回结构是前后端协作的"通信协议"：所有接口返回同一个 `{ code, message, data }` 信封，前端一套拦截器处理所有接口。
- `Result<T>` 泛型类 + 静态工厂方法（`success` / `fail`），让 Controller 返回值既有统一格式又有类型约束。
- HTTP 状态码统一 200，业务成功/失败用 `code` 字段区分——前端 catch 只管网络异常，then 里判断 code 管业务逻辑。
- 错误码必须统一管理、按模块分段，不允许每个人自己编。
- 所有接口无例外地返回 `Result<T>`，不允许裸数据、不允许部分接口特殊格式。

## 10. 明日预告

明天建议学习：`状态码设计`

原因：今天定义了 `Result` 里的 `code` 字段，但目前只用了 200（成功）和 400（参数错误）、404（不存在）这几个。真实系统里错误场景远不止这些——未登录、无权限、库存不足、重复提交、频率限制……每种场景都需要一个明确的错误码，前端根据码做差异化处理（401 跳登录、403 提示无权限、429 提示稍后重试）。明天讲怎么设计一套结构化的业务状态码体系：怎么分段、怎么命名、怎么和 HTTP 状态码配合、怎么让前端根据码做路由级处理。
