# Java 学习：参数边界

> 系列第 35 篇 · 第四阶段：精度、安全与稳定性
> 昨天复盘那次事故：根因是"回调字段名和约定不一致，解析出 null"，脏数据一路穿过 Service 到达数据库，全程无人拦截。日志是事后定位，更好的做法是事前拦截。今天讲参数边界：进入接口的每个值该有什么合法边界、在哪一层拦住它，让脏数据死在门口。

## 1. 今天学什么

第 21 篇我们学过 `@NotNull`、`@NotBlank` 这类基础校验注解，解决的是"有没有传"的问题。但线上事故的大头不是传了空，而是"有值、但出界"：5000 字的备注落进 varchar(200) 的字段、价格传了 -1、批量接口一次塞进 5 万条。这些值都"有值"，都能通过非空校验，却个个要命。

参数边界回答三个问题：每个参数的边界是什么（长度、范围、枚举、格式、集合大小）；在哪一层拦截（Controller 注解、Service 业务校验、数据库兜底）；越界了怎么办（明确拒绝并说清哪个参数越了哪条界，而不是含糊地 500）。今天把校验从"判空"升级成完整的边界防御体系。

## 2. 前端工程师视角理解

你一定写过表单校验：zod 的 `.max(50)`、`.min(1)`、`.regex(...)`。这些就是参数边界——只不过在前端这一侧。但有个事实前端工程师必须先接受：**前端根本守不住边界**。请求可以绕过页面用 Postman、curl、脚本直接发；前端校验代码自己可能有 bug；第三方系统直接对接，压根没有你的表单校验。所以后端必须独立做一套完整的边界检查；前端校验只管体验（尽早报错、少等一次往返），从来不是安全边界。

换个说法：TypeScript 的 interface 是"编译期契约"，JSON 一过网络就是没有类型的运行时数据——Java 无从得知声明为 `Integer` 的字段实际传来的是 999999999 还是 "abc"。每个边界注解，都是给这份"没人看门"的数据补一次运行时检查。

## 3. 和 JavaScript / TypeScript 的对比

**TS 的联合类型在运行时不存在。** `type Status = 'ON_SHELF' | 'OFF_SHELF'` 能让编译器拒绝其他取值，但只在编译期——数据从接口 axios 回来，TS 就管不着了。后端同理：Java 字段声明成 String 或枚举，都挡不住有人在 JSON 里传 `"随便什么"`。所以枚举参数必须显式做运行时校验（Set.contains 或自定义注解）——这是 TS 没给你的"运行时契约"，Java 得自己补上。

**数字边界的手感完全不同。** JS 的 number 是双精度浮点，没有 int/long 之分，整数超过 2^53 - 1 就悄悄丢精度——大数 ID 差一位的坑你一定踩过。Java 相反：数值类型有明确范围，解析阶段超范围直接抛异常，绝不悄悄变成另一个数。所以 Java 靠类型系统挡住"类型级"越界，再用 `@Max`、`@DecimalMax` 框住"业务级"边界。大数 ID 常以字符串返回前端，防的就是 JS 丢精度。

**zod 的 `.refine()` 对应 Java 的 Service 层校验。** 单字段边界两边都能声明式表达：zod 的 `.max(50)` 对应 `@Size(max = 50)`，`.regex()` 对应 `@Pattern`。但跨字段规则（开始时间必须早于结束时间）zod 只能写 `.refine()`；Java 的注解同样不便表达跨字段关系，惯例是放到 Service 层写成显式 if。思路一致：静态边界声明式，动态关系手写代码。

**数组：JS 天然不限长，Java 必须限。** JS 数组没有长度上限，前端也没有"限制列表参数"的习惯。但后端拿到一个 list，第一反应必须是"它最长能有多长"——列表长度直接对应 SQL 的 IN 子句长度、事务持锁时长和内存占用。这是前端转后端最容易漏掉的边界。

## 4. 真实业务场景

**场景：门店运营后台的"批量改商品价格"接口。**

业务背景：连锁门店系统的大促调价——运营勾选一批商品、填入新价格、一键提交。接口接收列表，每项含 skuId、新价格、备注和状态。

这个接口集齐了所有类型的参数边界：

一是集合大小。列表不限长，有人拿脚本塞 5 万条进来：内存吃满、事务巨大、数据库长时间持锁，其他下单请求全在等锁超时。

二是数值范围。价格传 -1，结算时订单变成"倒贴用户钱"，实打实的资损；传 99999999，展示和对账报表全部错乱。

三是长度。备注字段是 varchar(200)，前端传 500 字，数据库直接报 `Data truncation`，接口 500，运营盯着"系统繁忙"不知道是自己备注写长了。

四是枚举。状态字段什么字符串都收，库里混进 `"已上架"`、`"on_shelf"`、`"ON_SHELF"` 三种写法，之后按枚举过滤一种都匹配不上，变成永久脏数据。

正确做法：列表上限 500 条；价格限定 0.01 ~ 99999.99 且最多两位小数；备注 `@Size(max = 200)` 与数据库列长对齐；状态只接受 `ON_SHELF` / `OFF_SHELF`。任何一条越界都在入口拒绝，报错精确到"第几项、哪个字段、越了哪条界"，运营看到就能改。

## 5. Java 示例代码

```java
// 请求 DTO：静态边界全部声明在类上
public class PriceBatchUpdateDTO {

    // 边界 1：集合大小 —— 批量接口必须给列表封顶
    @NotEmpty(message = "价格列表不能为空")
    @Size(max = 500, message = "单次最多修改 500 条")
    @Valid  // 关键：没有它，嵌套元素上的校验注解不会生效
    private List<PriceItem> items;
}

public class PriceItem {

    @NotNull(message = "skuId 不能为空")
    private Long skuId;

    // 边界 2：金额范围 —— 配合第 28 篇的 BigDecimal 规范使用
    @NotNull(message = "价格不能为空")
    @DecimalMin(value = "0.01", message = "价格不能低于 0.01")
    @DecimalMax(value = "99999.99", message = "价格不能超过 99999.99")
    @Digits(integer = 5, fraction = 2, message = "价格最多两位小数")
    private BigDecimal price;

    // 边界 3：长度 —— 必须和数据库列长（varchar(200)）对齐
    @Size(max = 200, message = "备注最多 200 字")
    private String remark;

    // 边界 4：枚举 —— 注解不便表达，放到 Service 层校验
    private String status;
}
```

```java
// Controller：@Valid 触发注解校验，越界抛 MethodArgumentNotValidException
// 由第 33 篇的 2 号处理器接住，前端拿到"价格不能低于 0.01"这类精确提示
@PostMapping("/prices/batch")
public Result<Void> batchUpdate(@RequestBody @Valid PriceBatchUpdateDTO dto) {
    priceService.batchUpdate(dto);
    return Result.success(null);
}
```

```java
// Service：注解管不了的边界 —— 枚举、跨字段、依赖数据库状态的规则
@Slf4j
@Service
public class PriceService {

    // 枚举边界：只接受这两个值。枚举少时 Set 判断最直接
    //（校验场景多了可以封装自定义 @EnumValue 注解，原理一样）
    private static final Set<String> VALID_STATUS = Set.of("ON_SHELF", "OFF_SHELF");

    public void batchUpdate(PriceBatchUpdateDTO dto) {
        for (PriceItem item : dto.getItems()) {
            if (item.getStatus() != null && !VALID_STATUS.contains(item.getStatus())) {
                // 报错带定位：精确到哪一项错了，运营看到就能改
                throw new BizException(ErrorCode.PARAM_ERROR,
                        "非法状态: " + item.getStatus() + ", skuId=" + item.getSkuId());
            }
            // 业务边界：新价不能低于成本 —— 依赖库里的数据，注解不可能知道
            BigDecimal cost = skuMapper.selectCost(item.getSkuId());
            if (item.getPrice().compareTo(cost) < 0) {
                throw new BizException(ErrorCode.PARAM_ERROR,
                        "价格不能低于成本, skuId=" + item.getSkuId());
            }
        }
        // 全部校验通过，才执行批量更新……
    }
}
```

// 查询接口的分页边界：pageSize 也是参数，也要设卡
public PageResult<OrderVO> list(OrderQueryParam param) {
    if (param.getPageSize() == null || param.getPageSize() > 100) {
        throw new BizException(ErrorCode.PARAM_ERROR, "每页最多 100 条");

三层防线各管一段：Controller 注解管静态边界，Service 管业务边界，数据库约束只是兜底——别指望它，它报错的样子是 `Data too long for column 'remark'`，既不友好也不精确，传到前端只剩"系统繁忙"。

还有个细节：参数"类型"传错（Integer 字段传 `"abc"`、数字超出 Long 范围）时，抛的是 `HttpMessageNotReadableException`——JSON 在反序列化阶段就失败了，全局处理器不单独接住会掉进兜底，前端只看到"系统繁忙"。

## 6. 常见坑

**坑 1：只判空、不设边界。** 错误理解："我加了 `@NotNull` 就是校验过了。"问题：脏数据大头是"有值但出界"，非空校验全放行——price = -1 有值，备注 5000 字也有值。正确做法：每个字段问三个问题——最长多少？范围多大？能取哪些值？对应补上 `@Size`、`@Min/@Max`、`@DecimalMin/@DecimalMax`、`@Pattern`。

**坑 2：注解边界和数据库列长不一致。** 错误写法：字段是 varchar(200)，DTO 上写 `@Size(max = 500)`。问题：虚假安全感，200~500 字的输入校验通过、落库时炸，前端只收到含糊的 500。正确做法：对着表结构写边界，改字段长度时两边同步改。

**坑 3：集合参数不设上限。** 错误写法：`List<Long> ids` 直接进 SQL 的 IN 子句，批量接口的 list 无 `@Size`。问题：一次传 5 万个 id，IN 子句撑爆、事务长时间持锁，一个请求拖垮整库。正确做法：一切 List 入参必须有上限（批量接口通常 200~1000），超出的要求分批提交。

**坑 4：以为 Controller 校验过就万事大吉。** 错误理解：`@Valid` 是全局防线。问题：Service 还会被定时任务、MQ 消费者、内部 RPC 调用，这些入口不走 `@Valid`（第 33 篇坑 1 同理）。正确做法：Service 对关键业务边界自己再守一道，或把校验抽成公共方法供所有入口调用。

**坑 5：静默截断代替拒绝。** 错误写法：`pageSize = Math.min(pageSize, 100)`，看似防住了。问题：前端传 10000 得到"成功"，实际只返回 100 条，数据对不上时排查极其隐蔽。正确做法：默认显式拒绝并明确告知；只有产品语义允许时才截断（如"简介最多展示 20 字"）。

## 8. 面试 / 工作中常见问题

### 问题 1：参数校验应该放在哪一层？只在 Controller 校验够吗？

参考答案：分层防御。Controller 的 `@Valid` 管格式和静态边界，Service 管业务边界（跨字段关系、依赖数据库数据的规则），数据库约束只做兜底。只在 Controller 校验不够：业务规则注解表达不了，而且 Service 不只被 Controller 调用，定时任务和 MQ 消费不走 `@Valid`。

### 问题 2：前端已经做了表单校验，后端为什么还要再校验一遍？

参考答案：前端校验可以被绕过：Postman 直接调、脚本批量调、第三方对接、前端代码自己有 bug。前端校验是体验层（让用户少犯错），后端校验是安全层（保证无论谁调用，脏数据都进不了库）。一句话：凡是能被绕过的，都不能算边界。

### 问题 3：设计一个批量操作接口（批量修改、批量导入），要限制哪些边界？

参考答案：至少三件事。一是列表长度：`@Size(max = N)` 封顶（常见 200~1000），防止一次塞 5 万条打爆内存和事务；二是每个元素的边界：`@Valid` 嵌套校验逐项检查，报错要能定位到"第几项、哪个字段"；三是越界时明确拒绝、要求分批提交，而不是后端硬扛。此外还有下一篇的权限问题——这个人有没有资格改这批数据。

## 9. 今日小结

- 线上事故的大头不是"传了空"，而是"有值但出界"：边界校验比判空更重要。
- 三层防御：Controller 注解管静态边界，Service 管业务边界，数据库约束只做兜底、不可依赖。
- 集合参数必须设上限，分页 pageSize 必须封顶——任何"不限长的列表"都是潜在事故。
- 注解边界必须和数据库列长对齐，`@Size(max=500)` 配 varchar(200) 就是虚假安全感。
- 越界要显式拒绝并精确告知"哪个参数越了哪条界"，静默截断是最隐蔽的坑。
