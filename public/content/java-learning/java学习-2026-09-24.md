> 衔接上一篇「微服务边界与拆分」：十几服务、几条异步链路的系统刚画完边界，最后要回答一个问题——**你现在是好的还是坏的？**

## 1. 今天学什么

可观测性解决的不是"数据够不够"，而是"**出事时你手上有多少能回答问题的数据**"。三根支柱各有明确的职责边界：

- **指标（metrics）**：聚合数字，回答"**现在是否正常、趋势如何**"——成本低、可长期保留、天然适合告警，但不知道"是哪个请求出的问题"；
- **日志（logs）**：离散事件，回答"**这一次发生了什么**"——细节最全，但量大、贵、保留期短；
- **链路（traces）**：请求级因果与耗时分解，回答"**这次慢在哪一段、跨了几个服务**"——是跨服务排障的唯一完整视图。

今天讲四块：① 三者怎么分工、怎么用 traceId 与 exemplar 缝合；② 指标该埋什么（技术四信号 + 本系列学过的业务指标）；③ 告警怎么设计才不被静音（症状导向 + SLO 燃烧率 + 分级）；④ 落地顺序与成本控制（基数爆炸、采样率）。

## 2. 前端工程师视角理解

你其实每天都在用这三件套，只是前端把它们放在同一个面板里了：**Lighthouse 分数是指标**（聚合数字、能追踪趋势）、**console 与埋点事件是日志**（这一次发生了什么）、**Performance 面板的 waterfall 是链路**（时间花在哪一段、谁等谁）。后端把它们拆成三套系统，是因为规模：几百万请求无法像单个页面那样全量录 waterfall。

第二个直觉来自 **Sentry**：它有 `sampleRate`（错误采样）和 `tracesSampleRate`（链路采样）两个配置，还支持 issue 忽略规则——这三样对应后端的三件套成本控制：**日志按级别与采样留、链路按比例采样、告警按分级抑制**。你在 Sentry 里见过的"一个报错刷了 8000 次事件"，就是后端"高基数标签把指标系统打爆"的同构问题。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 指标 | Lighthouse 分数、RUM 面板 | Prometheus + Grafana（Micrometer 采集） |
| 日志 | console + 埋点事件 | ELK / Loki（第 50 篇那套） |
| 链路 | Performance waterfall、Sentry trace | 分布式追踪（OpenTelemetry / SkyWalking） |
| 缝合方式 | 同一次会话一个 sessionId | traceId + **exemplar**（指标样本链到具体 trace） |
| 成本控制 | 采样率、忽略规则 | 基数控制 + 采样 + 保留期分级 |
| 告警 | 前端罕见（用户先发现） | 必须主动：症状告警 + 值班 |

**最需要建立的新直觉：三者不是"三套日志系统"，而是三个不同粒度的问题。** 你可以用一句话记住分工：**指标回答"要不要叫人"，链路回答"叫谁来看"，日志回答"到底怎么了"。** 三者靠 traceId 缝合：每个请求的日志带 traceId（第 50 篇已建），链路用它串起跨服务调用，而指标通过 exemplar 把"某分钟的 P99 毛刺"直接指向一个具体 trace——排障从"拼三条线索"变成"点进去看"。

## 4. 真实业务场景

**场景：会员日大促，接口成功率从 99.9% 掉到 97%，但没有人知道为什么。**

值班同学手上有三份数据，但都停在半路：① Grafana 上指标显示"下单接口 5xx 比例上升"，**但不知道是哪些门店、哪些下游**；② 日志里有错误，但采集是按 10% 采样入的（成本考虑），按时间窗捞出来的几百条彼此没有 traceId 关联（只有部分服务接入了 traceId 传递）；③ 链路系统上线了，但采样率 1%，恰好漏掉了这 3% 的失败请求——**三根支柱各自都在，却拼不出一次完整的事故**。

最后靠"止血四板斧 + 业务指标"定位：把对账差异率（第 61 篇）拉出来看，发现差异集中在"支付成功后未入账"，再结合第 62 篇的熔断状态指标，确认是支付方半开探测期间放进去的一批请求失败。修复不是加监控，而是补齐三个缝合点：**把 traceId 补全到所有服务与 MQ 消费端**（第 50 篇那套）、**给关键指标挂 exemplar**、**错误日志不采样全量入库**（正常日志才采样）。第二次同类事故时，值班同学直接在 Grafana 的毛刺点上点进 trace，看到"支付 → 入账"这一段耗时 8 秒，五分钟定位。

**用错的代价**：不是"监控不够多"，而是**数据很多但没有一条能回答"哪次请求坏了"**——每一次事故都靠人肉拼线索，MTTR 的下限就被锁死在"运气"上。

## 5. Java 示例代码

**指标要埋得"低基数"：标签是枚举，不是业务主键。**

```java
@Component
@RequiredArgsConstructor
public class OrderMetrics {

    private final MeterRegistry registry;

    /** 业务指标：成功/失败数——标签只放枚举维度，绝不放 orderNo / userId（基数爆炸） */
    public void recordSubmit(String channel, boolean success) {
        Counter.builder("order.submit")
                .tag("channel", channel)                 // pay / risk，取值有限
                .tag("result", success ? "success" : "fail")
                .register(registry)
                .increment();
    }

    /** 与第 61 / 62 篇打通：对账差异率、熔断状态都应是可告警的指标，而不是藏在日志里 */
    private final Map<String, Long> latestDiff = new ConcurrentHashMap<>();   // ★ 强引用容器

    public void recordReconcileDiff(String bizType, long diffCount) {
        latestDiff.put(bizType, diffCount);
        // Micrometer 的 gauge 对数值对象是弱引用：必须一直持有它，否则被 GC 后指标变成 NaN
        registry.gauge("reconcile.diff.count", Tags.of("bizType", bizType),
                latestDiff, m -> m.getOrDefault(bizType, 0L));
    }
}
```

## 6. 常见坑

**坑 1：把业务主键塞进指标标签。** 错误做法：`Counter...tag("orderNo", orderNo)` 或按 userId 打点。问题：**基数爆炸**——每个唯一值都是一条时间序列，几万个订单号能让 TSDB 内存和查询成本失控，最终监控系统自己先挂。正确做法：标签只放**取值有限的枚举**（渠道、结果、错误类型）；要查"哪个订单"，那是日志和链路的事（它们本来就是按记录存的）。

**坑 2：三件套各建各的，互不缝合。** 错误做法：指标只到接口维度、日志没有 traceId、链路采样过低保不住错误请求。问题：出事故时数据都在，但没有一条能"从指标跳到具体请求"——第 57 篇里那句"两条线索拼起来"就是这种痛的写照。正确做法：**三个缝合点**——全链路 traceId 贯通（第 50 篇）、指标挂 exemplar、错误请求的日志与 trace **不采样或全量保留**。

**坑 3：用"原因"告警而不是"症状"告警。** 错误做法：CPU > 70%、队列长度 > 100、磁盘 > 80% 全部直接叫醒人。问题：原因类指标波动频繁、和用户受损无必然关系，结果就是值班麻木、真告警被淹没（第 34 / 57 篇都提过这个后果）。正确做法：**告警只挂在用户能感知的症状上**（错误率、延迟、成功率、滞后、对账差异率），原因类指标作为看板供定位；用 SLO 燃烧率做分级与抑制，定期清理长期未触发的告警。

## 8. 面试 / 工作中常见问题

### 问题 1：指标、日志、链路各自解决什么问题，怎么配合？

参考答案：按**粒度**分工。指标是聚合数字（服务/接口维度），负责发现与告警，回答"要不要叫人"；链路是请求级耗时分解（traceId 串起的跨服务调用），回答"叫谁来看、慢在哪一段"；日志是最细的事件记录，回答"到底怎么了"。配合靠缝合：traceId 贯通全链路（含 MQ）、指标挂 exemplar 从毛刺跳到 trace、错误请求的日志全量保留。三者缺一，排障就会退化成"人肉拼线索"。

### 问题 2：怎么设计告警才不会被团队静音？

参考答案：四条原则：**① 只告症状**（错误率、延迟、成功率、滞后、对账差异率），原因类指标只做看板；**② 用 SLO 燃烧率分级**（快烧 P1 叫人、慢烧 P2 工单），让"告警强度"与"用户受损程度"对齐；**③ 每个告警都必须可行动**——收到后第一件事做什么要能写出来，写不出来的删掉；**④ 定期清理**：统计哪些告警长期未触发或长期被忽略，前者降级、后者改阈值或补 Runbook（第 57 篇）。

### 问题 3：链路采样率怎么定？

参考答案：先分类型：**错误与慢请求要全量保留**（头部采样会恰好漏掉它们，所以成熟的追踪系统用**尾部采样**——请求结束后按"是否有错/是否超时"决定留不留）；正常请求按比例采样，常见 1%~10%，用尾巴补足；高频低价接口可以低采样，核心交易链路调高。另外把采样率写进文档，别让"为什么这次请求查不到 trace"变成每次事故都要重新讨论的问题。

## 9. 今日小结

- 三根支柱按粒度分工：**指标回答"要不要叫人"，链路回答"叫谁来看"，日志回答"到底怎么了"**。
- 缝合靠 traceId 与 exemplar：从 Grafana 的一个毛刺点直接跳到具体 trace，是排障效率的分水岭。
- 指标标签只放**有限枚举**，业务主键属于日志与链路——基数爆炸会让监控系统自己先挂。
- 告警只挂**症状**（错误率 / 延迟 / 成功率 / 滞后 / 对账差异率）并用 SLO 燃烧率分级；采样上**错误与慢请求全留**（尾部采样），正常请求按比例——策略要写进文档。
