# Java 学习：消息可靠性与最终一致性

> 系列第 61 篇 · 第七阶段：分布式一致性与容错（第 2 篇）
> 衔接上一篇「分布式锁与幂等」：那篇的三层（CAS、幂等表、fencing）都假设"DB 这一步不会丢"，今天补上不受本地事务保护的那一段——**DB 提交了、消息没发出去（或发重、乱序）怎么办**。
> **与第 47 篇的分工**：第 47 篇讲"别丢别重"的基础（ack 时机、消费幂等、重试退避 + 死信、顺序为什么贵），并给了本地消息表（Outbox）的骨架。今天讲骨架之外的**并发正确性与收尾工程**：多实例同时扫 Outbox 会怎样、乱序靠什么收敛、不一致怎么**发现和修复**。

## 1. 今天学什么

"消息可靠性"常被简化成"生产端别丢、消费端别重"，但两条都做到之后系统仍会不一致——因为 **至少一次投递 + 幂等消费 = 有效一次** 这个等式里，每一环都有并发与崩溃窗口。

四块内容：① **投递器的并发正确性**：谁能扫到待投递记录（`SKIP LOCKED` 认领）、投递成功但置位失败怎么办（允许重投 + 下游幂等）、退避与上限；② **乱序的工程收敛**：不追求全局有序，用"事件版本 + 状态机"丢弃旧事件；③ **对账与可重放补偿**：差异清单 + 幂等补偿器；④ **一致性的度量**：端到端滞后与差异率要能告警。

一句话心法：**不追求"不发生不一致"，而是让不一致可发现、可修复、可度量。**

## 2. 前端工程师视角理解

你做过两个高度相关的模式。第一个是**乐观更新**：先改 UI，等接口回来再确认，失败回滚。最终一致性是它的放大版——先写本地库并记下"待通知"意图，异步推给下游，**再配一个对账把"看着成功、实际没同步"的差异捞回来**；没有回滚/重试的乐观更新就是假状态，没有对账的最终一致也一样。

第二个是 **Service Worker 的离线队列（Background Sync）**：用户在地铁下单，请求先落 IndexedDB，联网后补发，补发必须自带幂等键（第 25 篇）。Outbox 就是**服务端的离线队列**：意图与业务写在同一个本地事务里，由独立进程投递。前端经验里最值钱的一条直觉是——"队列投递天然至少一次，所以接收端必须幂等"，你在离线队列踩过的重复提交，就是今天要防的重复加分。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端 |
|---|---|---|
| 待发送落盘 | IndexedDB 队列 | Outbox 表（与业务同一个本地事务） |
| 投递者 | 页面重连后补发 | 定时扫描器，**多副本并发** |
| 重复投递 | 重连重发致重复提交 | 至少一次的必然产物，靠下游幂等收敛 |
| 乱序 | 单线程天然串行 | 跨分区无序，靠版本号丢弃旧事件 |
| 一致性验收 | 用户看到的对不对 | 对账：差异清单 + 补偿 + 差异率 |

**最需要重建的直觉：投递者也是分布式的一部分。** 前端离线队列只有一个发送者（这个用户的页面），后端扫描器**每个实例都在跑**——第 44 篇的多副本问题在这里第三次出现（定时任务、库存扣减、现在是 Outbox）：三个人扫同一张待办表，不加约束就是每人投一遍。

## 4. 真实业务场景

**场景：积分服务上线 Outbox 后，"有人加两次分，有人一分没加"。**

按第 47 篇的骨架，`OrderService.pay()` 在同一本地事务里写订单状态 + 插一条 `outbox(status='TODO')`，扫描器每 2 秒取 200 条投递。一周后两类投诉同时出现：① **重复加分**——扫描 SQL 没有并发保护，三个实例每轮取到同一批，同一条消息投了三遍，积分服务只做了"防 HTTP 重试"没做"防重复事件"；② **有人漏加**——某条记录投递时 MQ 抖动，重试次数被加到上限后停在 TODO，而告警只统计"投递失败次数"，没人看，积分就永远少加了。

修补四步：**认领用 `SKIP LOCKED`**（实例间自动错开）+ **置位用 CAS**（重复投递最多一次，交给下游幂等兜住，第 60 篇同一套思想）；**退避 + 上限 + 正确的告警指标**——把"TODO 停留超过 5 分钟"当告警，而不是"失败次数"；**每日对账**比对 `orders` 已支付订单与 `points_log` 入账流水，差异进清单，交给**幂等可重放**的补偿任务；**乱序**单独处理：同一订单的"支付"与"退款"被并行消费，退款先到把余额算成负数——修法不是强行排序，而是事件带 `event_version`，消费端只应用比当前版本更新的事件（第 47 篇"用版本号自己判断"的落地）。

**用错的代价**：漏加分不会报警，它安静积累，最后以"10% 会员发现积分不对"爆发——补数据只能靠对账清单一遍遍回放。

## 5. Java 示例代码

**认领与投递分两步：事务只包"取任务"，绝不能包网络调用。**

```java
@Mapper
public interface OutboxMapper {

    /** ★ 认领一批：SKIP LOCKED 让多实例各取不相交的一批，避免同批被投三遍 */
    @Select("SELECT * FROM outbox WHERE status='TODO' AND next_retry_at <= NOW() " +
            "ORDER BY id LIMIT #{n} FOR UPDATE SKIP LOCKED")
    List<OutboxMsg> lockBatch(@Param("n") int n);

    /** 置为 SENDING：与上面的 SELECT 同处一个短事务，事务里不做任何 IO */
    @Update("UPDATE outbox SET status='SENDING', claimed_at=NOW() WHERE id=#{id} AND status='TODO'")
    int markSending(@Param("id") long id);

    /** CAS 置位：并发下只有一个人能把 SENDING 改成 SENT（第 60 篇的思想） */
    @Update("UPDATE outbox SET status='SENT', sent_at=NOW() WHERE id=#{id} AND status='SENDING'")
    int markSent(@Param("id") long id);

    /** 失败退避；到 10 次转 DEAD 交人工，绝不无限重试（第 47 篇坑 4 的状态机版本） */
    @Update("UPDATE outbox SET retry_count=retry_count+1, " +
            "next_retry_at=DATE_ADD(NOW(), INTERVAL #{delaySeconds} SECOND), " +
            "status=IF(retry_count+1 >= 10, 'DEAD', 'TODO') WHERE id=#{id}")
    int markRetry(@Param("id") long id, @Param("delaySeconds") long delaySeconds);
}

// 另需一个"捡漏"任务：进程在 SENDING 状态崩溃会把记录卡住，用超时把它捞回 TODO
// UPDATE outbox SET status='TODO' WHERE status='SENDING' AND claimed_at < NOW() - INTERVAL 5 MINUTE;
```

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class OutboxDispatcher {

    private final OutboxMapper outboxMapper;
    private final RabbitTemplate rabbitTemplate;

    /** 第一步：短事务认领（第 47 篇坑 3 的反面教材：事务里同步发 MQ 会长时间持锁） */
    @Transactional
    public List<OutboxMsg> claim() {
        List<OutboxMsg> batch = outboxMapper.lockBatch(200);
        batch.forEach(m -> outboxMapper.markSending(m.id()));
        return batch;
    }

    /** 第二步：事务外投递；成功 CAS 置位，失败退回 TODO 并指数退避（2s→300s 封顶） */
    public void dispatch() {
        for (OutboxMsg msg : claim()) {
            try {
                rabbitTemplate.convertAndSend(msg.exchange(), msg.routingKey(), msg.payload());
                outboxMapper.markSent(msg.id());     // 置位失败 → 下轮重投 → 依赖下游事件级幂等
            } catch (Exception e) {
                long backoff = Math.min(300, (long) Math.pow(2, msg.retryCount()));
                outboxMapper.markRetry(msg.id(), backoff);
                log.warn("outbox 投递失败 id={} bizKey={} retry={}", msg.id(), msg.bizKey(), msg.retryCount(), e);
            }
        }
    }
}
```

## 6. 常见坑

**坑 1：以为"扫描器只有一个实例"。** 错误做法：把投递当单进程逻辑写，取一批投一批。问题：3 副本就有 3 个扫描器（第 44 篇的老朋友），同批记录被投三遍；下游只做请求级幂等，就直接重复入账。正确做法：**认领（`SKIP LOCKED` 或分片）+ CAS 置位 + 下游按业务键的事件级幂等**，三处一起才成立；还要有 SENDING 超时捡漏，防进程崩溃卡死。

**坑 2：用"强制全局有序"解决乱序。** 错误做法：所有消息进一个队列、单消费者串行。问题：吞吐被单线程封死，热点无法扩容，消费者重启的 rebalance 期间照样乱序——为不需要的保证付了整个系统的代价。正确做法：顺序只在**同一业务键内**需要（用业务键做路由键）；更稳的是不依赖顺序本身：事件带版本号/时间戳，消费端只应用更新的事件，旧事件丢弃并计数。

**坑 3：把对账当"以后再说"。** 错误做法：只做"尽力投递 + 幂等消费"。问题：这个组合保证"不重不错"，**不保证不漏**——扫描器停机、消息进 DEAD、payload 字段缺失被 DLQ 吞掉，全都静默；等业务发现时原始流水可能已过期。正确做法：核心链路必须有 T+1 对账 + 差异清单 + 幂等补偿器 + 差异率指标（>0.01% 告警），并把"最长允许不一致时长"写进 SLO。

## 8. 面试 / 工作中常见问题

### 问题 1：本地消息表怎么保证"消息一定发出去"？

参考答案：它保证的不是"一定发出"，而是**"库里有记录就一定会被反复尝试，直到发出或进人工队列"**。机制三步：业务与消息同一事务落库（这步原子）、独立投递器扫表、成功 CAS 置位。任何环节崩溃的结果都是"至少一次投递"，所以下游必须幂等。另外必须补上限 + 退避 + DEAD 状态和对账兜底——漏发只能靠对账发现。

### 问题 2：消息重复、乱序、丢失，先解决哪个？

参考答案：先幂等（重试必然发生），再防丢（丢是静默的），最后是乱序（多数只影响短窗口的状态展示）。具体：重复靠下游幂等消化；丢失分两端——生产端用本地消息表，消费端"业务成功才 ack"；乱序不该在 MQ 层硬解，让事件带版本、消费端按状态机拒绝旧事件即可。

### 问题 3：怎么证明系统最终会一致，而不是永远不一致？

参考答案：三个可验证的东西：① 对账任务按业务键比对两侧流水、差异落清单（发现）；② 补偿器按业务键幂等重放、可重复执行无副作用（修复）；③ 端到端滞后与差异率进监控并写进 SLO（度量）。三样齐了才叫最终一致——只做前两样等于有药没体检。

## 9. 今日小结

- 至少一次投递 + 幂等消费 = **有效一次**；投递端与消费端各自都要成立，缺一头就出重复或漏。
- Outbox 投递器是多副本定时任务：**短事务认领（`SKIP LOCKED`）+ 事务外投递 + CAS 置位 + 退避上限 + SENDING 捡漏**。
- 乱序不靠排队解决，靠**事件版本 + 状态机**：旧事件丢弃并计数，吞吐与正确性都不牺牲。
- 对账不是可选工程：差异清单 + 幂等补偿器 + 差异率告警，是"不漏"的唯一发现手段。
