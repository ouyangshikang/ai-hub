# Java 学习：异常处理

> 系列第 32 篇 · 第四阶段：精度、安全与稳定性
> 昨天 `orElseThrow` 抛出了一个 `BizException`，故事讲到一半就停了：这个异常抛出后会发生什么？Checked 和 Unchecked 有什么区别、throw 和 throws 各管什么？今天把 Java 的异常体系完整过一遍，为明天的全局异常处理铺路。

## 1. 今天学什么

Java 把程序运行中的一切意外都建模成一棵异常树：顶层是 `Throwable`，往下分两支——`Error` 是 JVM 自己扛不住的事故（OOM、栈溢出），业务代码救不了也不该救；`Exception` 是程序能预见、能处理的意外。Exception 里又分两类：`RuntimeException` 及其子类叫非受检异常（Unchecked），编译器不管你；其余的叫受检异常（Checked），编译器强制你要么 try-catch、要么在签名上声明，否则编译不通过。

这套机制解决的核心问题是：**失败该由谁负责**。异常沿调用栈一路向上抛，每一层都有机会接住处理；没人接住，当前线程就终止。对后端来说，异常最终会在 Web 框架的边界被接住，转成响应——但"怎么转"是明天的主题，今天先把"抛出、声明、捕获、传播"这四件事搞明白。

## 2. 前端工程师视角理解

写 JS 时你对异常的认知是：`throw new Error('xxx')`，想接就 try/catch，不接就冒泡到顶层，Node 里进程崩溃、浏览器里报错红屏。所有异常一视同仁，没有任何机制逼你处理。

Java 把异常分成了两档，区分标准是"这个失败是否可以被合理预见和恢复"：

- **受检异常（Checked）**：外部世界的不确定性。读文件可能没文件（`IOException`）、连数据库可能连不上（`SQLException`）。这些失败不是你代码写错了，而是环境不可靠，编译器逼你提前想好"失败了怎么办"。
- **非受检异常（Unchecked）**：程序逻辑错误或业务规则不满足。NPE 是你没判空，`IllegalArgumentException` 是参数传错，昨天的 `BizException` 是"库存不足"这类业务上不成立。编译器不强制处理——因为正确处理方式是别让它发生。

最像受检异常的前端经验其实是 Node.js 的 err-first 回调：`fs.readFile(path, (err, data) => ...)`，err 参数摆在脸上，你不处理它就没法拿 data。Java 的 Checked 异常就是编译器帮你强制执行的"err 必须处理"。

## 3. 和 JavaScript / TypeScript 的对比

**JS 全是"非受检"。** JS 没有 Checked 异常的概念，try/catch 完全可选。好处是写起来自由，坏处是失败路径全靠自觉——async 函数里忘了 catch，就是一个 unhandled rejection。Java 的 Checked 异常把失败路径写进编译期，代价是代码里多出 try-catch 或 throws 声明。

**Java 有 `throws` 声明，TS 没有。** Java 方法签名可以写 `throws IOException`，调用方看到签名就知道这里可能失败，这是接口契约的一部分。TS 的类型系统表达不了"这个函数会抛什么"，JSDoc 的 `@throws` 只是注释，编译器不认。这也是 Java 敢把受检异常设计成强制的原因——有 throws 声明机制兜底，失败信息不会丢。

**传播规则一致，终点不同。** 两边都是异常沿调用栈向上冒泡、遇到 catch 就停。区别在终点：JS 没人接住就崩进程/弹红屏；Java 在 Web 场景下最终会被 Tomcat/Spring 框架接住，返回一个 500 页面——但那个默认页面里往往带着堆栈信息，对安全不利，所以明天要讲全局异常处理来接管这个终点。

**finally 两边都有。** 释放资源用 finally 在两边是同一个习惯。Java 额外提供了 try-with-resources 语法（下一节有例子），自动关闭实现 `AutoCloseable` 的资源，比手写 finally 更不容易漏。

## 4. 真实业务场景

**场景：门店下单接口，扣库存失败抛业务异常，调第三方支付遇到受检异常。**

业务背景：门店系统里，用户在小程序下单，后端下单接口要做三件事：校验并扣减库存、调用第三方支付渠道创建预支付单、落库生成订单。

库存不足时应该抛 `BizException(STOCK_NOT_ENOUGH)`——这是业务规则不满足，属于非受检异常，调用方不需要也不该靠 catch 它来走流程，它一路抛到框架边界，转成"库存不足"的错误提示返回前端。

而调用第三方支付 SDK 时，HTTP 通信会声明 `throws IOException`——这是受检异常，编译器盯着你：要么 try-catch，要么继续往上 throws。正确姿势是 catch 住它，记日志，然后包一层业务异常抛出："支付渠道暂不可用，请稍后重试"。

如果用错会怎样？最常见的错误是把 `IOException` 吞掉——catch 块里什么都不写，然后代码继续往下走，订单落库成功但支付单没创建。用户付不了钱，订单却挂在库里，对账时才发现资损。**受检异常存在的意义，就是逼你在编译期对这种外部失败做决定，而不是让它悄悄溜过去。**

## 5. Java 示例代码

```java
// 自定义业务异常：继承 RuntimeException（非受检），携带错误码
// 错误码体系来自第 23 篇「状态码设计」，这里复用 ErrorCode 枚举
public class BizException extends RuntimeException {
    private final ErrorCode errorCode;

    public BizException(ErrorCode errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }

    public ErrorCode getErrorCode() {
        return errorCode;
    }
}
```

```java
// Service：throw 负责"真的抛"，throws 负责"签名上声明"
public Order createOrder(Long storeId, Long skuId, int quantity) {
    // 1) 业务规则不满足：直接 throw 非受检异常，不需要 throws 声明
    int stock = stockMapper.getStock(storeId, skuId);
    if (stock < quantity) {
        throw new BizException(ErrorCode.STOCK_NOT_ENOUGH, "库存不足，剩余 " + stock);
    }

    // 2) 调外部支付：SDK 声明了 throws IOException（受检），必须显式处理
    try {
        payGateway.createPrepayOrder(storeId, skuId, quantity);
    } catch (IOException e) {
        // 保留原始异常作为 cause，日志里才能看到真实堆栈
        log.error("调用支付渠道失败, storeId={}, skuId={}", storeId, skuId, e);
        throw new BizException(ErrorCode.PAY_CHANNEL_ERROR, "支付渠道暂不可用，请稍后重试");
    }

    return orderMapper.insert(...);
}
```

```java
// try-with-resources：资源自动关闭，不用手写 finally
// 导出门店月报时读模板文件（InputStream 实现了 AutoCloseable）
try (InputStream in = new FileInputStream(templatePath)) {
    // 无论正常结束还是抛异常，in 都会被自动 close
```

## 6. 常见坑

**坑 1：吞异常。** 错误写法：catch 块空着，或者只写一行 `e.printStackTrace()`。问题：异常被静默吃掉，上层以为调用成功，故障排查时连日志都没有。printStackTrace 打到标准输出，生产日志系统根本收集不到。正确做法：catch 了就必须做决定——记 log 并包装成业务异常重抛，或者明确写注释说明为什么可以忽略。

**坑 2：catch 大而全的 `Exception`。** 错误写法：`catch (Exception e)` 一把梭。问题：把本不该接的异常也接住了（比如参数校验失败的 IllegalArgumentException），掩盖真正的 bug，还容易在 catch 里写一堆 instanceof 判断。正确做法：只 catch 你真正知道怎么处理的那类异常，其余让它继续向上抛。

**坑 3：包装异常时丢掉原始异常链。** 错误写法：`throw new BizException("支付失败")`，把 `e` 弄丢了。问题：线上只看到一句"支付失败"，原始堆栈、根因全部消失，排查无从下手。正确做法：`new XxxException(msg, e)` 把原始异常作为 cause 传入，或至少在 log.error 时把 e 作为最后一个参数带上。

**坑 4：finally 里 return。** 错误写法：在 finally 块里写 return。问题：finally 的 return 会覆盖 try/catch 里的 return，甚至把抛出的异常直接吞掉——方法看起来正常返回了，异常凭空消失。正确做法：finally 只负责清理资源，永远不要在里面 return 或抛新异常。

**坑 5：用异常做流程控制。** 错误写法：用 try-catch 捕获"查无记录"这类正常业务状态，把异常当 if 用。问题：异常的创建和抛出有昂贵的堆栈填充开销，且把"正常分支"和"错误分支"混在一起，可读性差。正确做法：查无记录返回 `Optional.empty()`（昨天学的），业务规则判断用 if，异常只用于"真正意外"的情况。

## 8. 面试 / 工作中常见问题

### 问题 1：Checked 和 Unchecked 异常的区别？Java 为什么要这么设计？

参考答案：Checked 异常编译器强制处理（try-catch 或 throws 声明），代表可预见的外部失败，如 IOException、SQLException；Unchecked 异常（RuntimeException 及其子类）编译器不管，代表程序逻辑错误或业务规则不满足，如 NPE、IllegalArgumentException。设计意图是把"环境不可靠导致的失败"和"代码写得不对"区分开：前者逼你提前规划恢复路径，后者靠写好代码避免而不是靠 catch 兜底。

### 问题 2：Error 和 Exception 的区别？OOM 能 catch 吗？

参考答案：Error 是 JVM 层面的严重故障（OutOfMemoryError、StackOverflowError），程序通常无力恢复；Exception 是程序可以预见并处理的。语法上 Error 也继承 Throwable 所以"能"catch，但不该 catch——发生 OOM 时 JVM 状态已不可靠，catch 后继续跑只会掩盖问题、扩大故障。正确做法是让线程终止，靠监控告警发现，从内存治理层面解决。

### 问题 3：为什么自定义业务异常通常继承 RuntimeException，而不是做成 Checked？

参考答案：三个原因。一是业务规则不满足（库存不足、余额不够）属于"不该发生"的场景，正确姿势是在上游校验拦截，而不是逼每个调用方写 try-catch；二是业务异常要一路抛到框架边界由全局异常处理器统一转换，中间层并不处理它，Checked 的强制声明反而变成层层 throws 的样板代码；三是 RuntimeException 不污染方法签名，Service 接口保持干净。这也呼应了"异常只用于真正意外"的原则。

## 9. 今日小结

- 异常树：Throwable → Error（别管）/ Exception；Exception 里 RuntimeException 是非受检，其余是受检。
- Checked 逼你对"外部失败"做编译期决策；Unchecked 代表逻辑或业务错误，靠写好代码避免。
- throw 是真的抛，throws 是签名上声明；异常沿调用栈向上传播，直到被 catch 或到达框架边界。
- 吞异常、catch 太宽、丢 cause、finally 里 return，是排查事故时最常见的四宗罪。
- 业务异常继承 RuntimeException 并携带错误码，为明天的全局异常处理做准备。
