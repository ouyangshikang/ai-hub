# Java 学习：事务传播机制

> 系列第 41 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「事务失效场景」：上篇修正方案"把事务方法抽到独立 Service"带来一个新问题——两个各自带 @Transactional 的方法互相调用时，它们算一个事务还是两个？内层失败，外层的要不要跟着回滚？想让内层独立提交、外层回滚互不影响，该怎么配？这就是 propagation（传播机制）要回答的事。

## 1. 今天学什么

上一篇把事务抽到独立 Bean 后，你的 Service 之间开始出现"事务方法调用事务方法"的情况：下单方法有事务，里面调了扣库存方法也有事务——它们共享同一个事务，还是各开各的？内层扣库存失败抛异常，外层下单跟着回滚吗？反过来，外层后续步骤失败了，已经成功的内层能"独善其身"吗？Spring 用 `@Transactional(propagation = ...)` 这个参数来精确控制这件事。今天重点讲实际项目里会用到的三种：REQUIRED（默认，共享事务）、REQUIRES_NEW（挂起外层、另起新事务）、NESTED（嵌套事务，子事务可独立回滚但不提交）。搞清这三者的区别和适用场景，你就不会再被"外层回滚了为什么里面还有数据"这类问题困扰。

## 2. 前端工程师视角理解

把事务想象成一个"操作上下文"。前端最接近的类比是 `async/await` 的作用域链：内部函数抛异常，如果不 catch，就沿着调用链一路冒到最外层——所有中间步骤都没法"单独提交"。REQUIRED 就是这个默认行为：内层和外层是同一个上下文，一个炸全炸。

那"内层不管外面死活"怎么类比？前端里你发埋点日志时用 `navigator.sendBeacon()` 或者 `fetch(...).catch(() => {})`，意思就是"埋点是独立的，失败了也不影响主流程"。REQUIRES_NEW 就是给内层方法开了一个完全独立的"事务通道"——外面回滚了，里面该提交的已经提交。

NESTED 像一个中间态：你在编辑器里 Ctrl+Z 可以回退到上一个保存点。子事务回滚只回到子事务开始时的状态，外层事务的其他修改还在——不丢。但外层回滚时，子事务（哪怕已经"成功"）也会一起消失，因为它从没真正独立提交过。

## 3. 和 JavaScript / TypeScript 的对比

**JS/TS 里没有"事务传播"这个概念。** Node.js 操作数据库（Prisma、TypeORM）时，如果你想让几个操作共享一个事务，必须手动把 `tx` 对象一层层往下传。`prisma.$transaction(async (tx) => { await step1(tx); await step2(tx); })`——step1 和 step2 共享 tx 就是 REQUIRED 的等价；如果你想 step1 用另一个独立事务，你得自己再开一个 `$transaction`，框架不会自动帮你"挂起"当前的。Spring 的 propagation 本质上把这个"手动决定共享还是独立"的过程变成了声明式配置：在方法上写个枚举值，框架自动帮你做"加入 / 挂起 / 新建 / 嵌套"。

**为什么 Java 要这么设计？** 因为真实 Java 后端项目动辄几十个 Service、上百个方法互相调用。如果每个调用关系都要手动传递事务上下文，代码会一团糟。声明式传播让调用双方"各自声明自己对事务的需求"，由 Spring 的 AOP 代理在运行时自动协调，调用者不需要知道被调用者内部有没有事务。

**enum 类型 vs 字符串字面量。** Spring 的 propagation 用 Java enum（`Propagation.REQUIRED`、`Propagation.REQUIRES_NEW`），写错编译就报错。TS 里你可能写 `as const` 的对象联合类型来模拟，但没有编译器强制——漏写、拼错、运行时才暴露。Java 的 enum 天然规避了"把 'REQUIRES_NEW' 写成 'REQUIRE_NEW'"这种低级错误。

## 4. 真实业务场景

**场景：门店订单系统——下单成功后写积分，积分写失败不能影响订单。**

业务背景：顾客下单成功后，后端 OrderService.createOrder 有事务，做三步：① 扣库存 ② 写订单 ③ 调 PointService.addPoints 写积分。一开始 PointService 没有特殊配置，和 createOrder 共享同一个事务（REQUIRED）。

事故：某天积分服务内部逻辑抛了异常。因为同一个事务，createOrder 整体回滚——顾客钱付了、订单没了、库存也没扣。客服炸锅。

分析后业务结论：积分是"锦上添花"，不应该影响订单主流程。于是把 PointService.addPoints 改成 `propagation = REQUIRES_NEW`，让它开独立事务——积分写失败只回滚积分，订单照常提交。

但改完又发现新问题：积分写成功了，订单后续步骤（发优惠券）失败导致主事务回滚——此时积分已经独立提交了，回不去了，顾客白拿积分。这时 NESTED 就能派上用场：子事务回滚不影响外层，但外层回滚时子事务跟着消失。

结论：REQUIRED / REQUIRES_NEW / NESTED 对应三种业务语义——"同生共死"、"各管各的"、"我可以先走但你要回滚我就跟着消失"。

## 5. Java 示例代码

```java
@Service
public class OrderService {

    @Resource
    private PointService pointService;
    @Resource
    private CouponService couponService;
    @Resource
    private OrderMapper orderMapper;
    @Resource
    private StockMapper stockMapper;

    @Transactional(rollbackFor = Exception.class)
    public Long createOrder(CreateOrderDTO dto) {
        // ① 扣库存（REQUIRED，与 createOrder 同事务，同生共死）
        stockMapper.deduct(dto.getStoreId(), dto.getSkuId(), dto.getQuantity());

        // ② 写订单主记录
        orderMapper.insert(order);

        // ③ 加积分（REQUIRES_NEW：独立事务，积分失败不回滚订单）
        pointService.addPoints(order.getUserId(), order.getAmount());

        // ④ 发优惠券（NESTED：子事务可以独立回滚，
        //     但如果 createOrder 后续失败回滚，优惠券也跟着消失）
        couponService.issueCoupon(order.getId());

        return order.getId();
    }
}

@Service
public class PointService {

    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void addPoints(Long userId, BigDecimal amount) {
        // 挂起 createOrder 的事务，开一个全新事务执行积分写入
        // 本方法返回时独立提交——外层回滚也撤不回已提交的积分
        pointMapper.increase(userId, amount.multiply(POINT_RATE));
    }
}

@Service
public class CouponService {

    @Transactional(propagation = Propagation.NESTED, rollbackFor = Exception.class)
    public void issueCoupon(Long orderId) {
        // 使用 savepoint 实现：在外层事务内部设一个"回滚锚点"
        // 如果本方法抛异常，只回滚到 savepoint，外层事务的其他修改不受影响
        // 但如果外层回滚，本方法的写入也一起消失（因为从没独立提交过）
        couponMapper.insert(buildCoupon(orderId));
    }
}
```

传播行为速查（实际项目高频的三种）：

| 传播类型 | 外层有事务时 | 外层无事务时 | 典型场景 |
|---|---|---|---|
| REQUIRED（默认） | 加入外层事务 | 新建事务 | 业务主流程各步骤 |
| REQUIRES_NEW | 挂起外层，开新事务 | 新建事务 | 审计日志、积分等辅助写入 |
| NESTED | 在外层事务内建 savepoint | 新建事务 | 批量导入里单条失败不影响整批 |

其余 4 种（SUPPORTS / NOT_SUPPORTED / MANDATORY / NEVER）在 99% 的业务代码里不会用到，面试被问时一句话带过即可，不必花时间背。

## 6. 常见坑

**坑 1：以为 REQUIRES_NEW 就是"异步"。** 错误理解："内层独立事务，那它失败不失败跟外层无关。"问题：REQUIRES_NEW 是同步执行——外层事务被挂起（pause），等内层完成才恢复。如果内层执行慢（比如锁等待），外层的事务连接也被占住不放。不是"各跑各的"，是"排队跑、各管各的结果"。正确做法：不要在 REQUIRES_NEW 里做耗时操作，否则连接池很快耗尽。

**坑 2：NESTED 和 REQUIRES_NEW 搞混。** 错误理解：两者都能让子方法失败时外层不回滚，随便用一个。问题：关键区别在"外层回滚时子事务保不保得住"。REQUIRES_NEW 子事务已经独立提交了，外层回滚它撤不回来——积分白给了。NESTED 用 savepoint，从没独立提交，外层回滚子事务也消失。正确做法：问自己"外层回滚时内层该不该跟着消失"——该就 NESTED，不该就 REQUIRES_NEW。

**坑 3：传播配置了但不生效——还是代理问题。** 错误形态：在同一个类里 this.method() 调另一个带 propagation 的方法。问题：和上一篇讲的完全一样，不走代理就没有事务拦截器介入，propagation 配什么都没用。正确做法：同「事务失效场景」——拆 Bean 或自注入。

**坑 4：REQUIRED 嵌套时以为"内层 catch 了异常外层不受影响"。** 错误形态：内层用 REQUIRED，抛了异常你外层 catch 住继续走。问题：同一个事务里一旦标记了 rollback-only，外层即使 catch 继续执行，最终提交时会报 `UnexpectedRollbackException`——事务已经被标记为"只能回滚"。正确做法：内层如果可能失败且外层要继续走，用 REQUIRES_NEW 或 NESTED，不要用 REQUIRED 再 catch。

**坑 5：批量导入场景不加 NESTED，一条失败全部重来。** 错误形态：1000 条导入全放一个 REQUIRED 事务，第 999 条数据格式错误抛异常，前 998 条白写了。正确做法：每条导入逻辑放在 NESTED 子事务里——单条失败只回滚该条，外层记录"第 999 条失败"后继续提交前 998 条。

- **第 38 篇「事务是什么」**：当时说"事务从方法开始持续到方法结束"，今天多问一步：两个方法嵌套时，"结束"的定义变了——REQUIRED 是外层结束才结束，REQUIRES_NEW 是内层自己就结束。

## 8. 面试 / 工作中常见问题

### 问题 1：REQUIRED 和 REQUIRES_NEW 的核心区别是什么？

参考答案：REQUIRED 加入当前事务，所有写操作在同一个事务里，一荣俱荣一损俱损。REQUIRES_NEW 挂起当前事务、开一个全新事务，内层方法返回时就独立提交——外层后续回滚也撤不回它。一句话区分：REQUIRED 共享回滚边界，REQUIRES_NEW 独立回滚边界。

### 问题 2：NESTED 能替代 REQUIRES_NEW 吗？

参考答案：不能。关键区别在外层回滚时：REQUIRES_NEW 内层已独立提交，不受外层回滚影响（积分给了就收不回）；NESTED 从未独立提交，外层回滚它跟着消失。选择标准就一句话：外层回滚时子事务"该不该跟着消失"——该就 NESTED，不该就 REQUIRES_NEW。另外 NESTED 依赖 JDBC Savepoint，MyBatis 默认支持，但某些 ORM 或分库分表中间件可能不兼容。

### 问题 3：批量导入 1000 条，要求"单条失败不影响其他"，事务怎么配？

参考答案：外层方法开一个 REQUIRED 事务负责"整批"语义（写批次号、最终状态等），每条导入逻辑抽到独立 Bean 的方法上配 NESTED。单条失败只回滚到 savepoint，该条记为失败；外层继续处理后续条目。最后整批提交时，成功的条目全部生效，失败的条目已回滚，互不干扰。不要用 REQUIRES_NEW，因为每条都独立提交意味着 1000 次 commit，性能远差于 savepoint。

## 9. 今日小结

- propagation 解决的是"事务方法互相调用时，事务怎么组合"——共享（REQUIRED）、独立（REQUIRES_NEW）、嵌套（NESTED）。
- REQUIRED 是默认值，同生共死；REQUIRES_NEW 独立提交，外层回滚也撤不回；NESTED 用 savepoint，外层回滚则子事务跟着消失。
- 实际项目 99% 的场景只用这三种，其余四种了解即可不必硬背。
- REQUIRES_NEW 是同步挂起不是异步——内层慢会把外层的连接也占住。
- 传播机制依赖 AOP 代理生效，同类自调用照样绕过——和上一篇是同一个底层原因。
