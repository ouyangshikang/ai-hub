# Java 学习：集成测试

> 衔接上一篇「单元测试」：昨天反复撞到同一堵墙——Mapper 被 mock 掉之后，第 52 篇那类 SQL 问题、字段映射（第 14 篇）、事务到底有没有生效（第 39 篇）全都测不到。今天补这半张网。
> **与第 4 篇的分工**：第 4 篇讲 `mvn verify` 里 surefire 与 failsafe 的**阶段顺序**；今天讲**测试本身怎么写、怎么分层、怎么在 CI 里跑得起来**。

## 1. 今天学什么

集成测试检验的是**装配之后的真实行为**：SQL 能不能跑、字段映射对不对、参数绑定会不会报错、Bean 能不能注起来、返回的 JSON 长什么样。单测把这些全 mock 掉了，所以它绿着上线、线上炸掉，是同一件事的两面。

今天讲四件事：① 粒度怎么选——`@MybatisTest`/`@WebMvcTest` 这类**切片测试**和 `@SpringBootTest` 全量启动各自的代价与用途；② 用 **Testcontainers** 起一个真的 MySQL 让 SQL 被真正执行，而不是换成 H2；③ 测试类的**数据隔离与回滚**机制，以及 `@Transactional` 自动回滚在哪几种情况下不生效；④ 两级 CI 门禁——快的挡 PR，慢的挡合并，否则团队会开始"手动跳过测试"。

它排在单元测试之后很自然：**mock 换来的速度，是用"看不见真实世界"换的**，集成测试就是把真实世界请回来。

## 2. 前端工程师视角理解

最强的锚点是 **MSW（Mock Service Worker）的经典事故**。你写过 `server.use(http.post('/api/coupon', () => ({ code: 0 })))`，前端测试全绿，线上却炸——因为 mock 的返回结构和真实后端不一致：真实接口把 `data` 里的字段做了驼峰转换、`null` 会省略、错误时 HTTP 200 但 `code != 0`。**mock 越不像真的，测试越像假的。** Java 里 mock Mapper 就是同一件事：MyBatis 的 XML 根本没参与，字段名拼错、`#{}` 参数写错、`resultMap` 少配一列，单测一个都发现不了。

第二个锚点是 **Playwright / Cypress**。你明知道它们比 vitest 慢十倍，还是要留几个 E2E，因为它们起真浏览器、走真网络。Testcontainers 在后端就是这个角色——**起真数据库**（一个 `mysql:8.0` 容器），代价是慢，收益是"这段 SQL 在 MySQL 上真的能跑"这件事被验证了。前端同学对 Docker 起库并不陌生，只是这里换成了测试自动拉起、跑完销毁。

第三个差异是**分层习惯**：前端一般只有"组件测试 + E2E"两层，后端因为进程边界多（DB、Redis、MQ、第三方）必须再分出**切片**这一层（只启相关那一层），目的只有一个——**反馈速度**：仓库有 300 个集成测试时，粒度选错就是 CI 从 3 分钟变 40 分钟。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | 后端集成测试 |
|---|---|---|
| 替身策略 | MSW 拦网络、mock 返回体 | mock（单测） vs 真容器（集成） |
| 只测一层 | 组件测试不碰网络 | `@WebMvcTest` / `@MybatisTest` 切片 |
| 全链路 | Playwright 起浏览器 | `@SpringBootTest` + `RANDOM_PORT` |
| 数据准备 | seed 脚本 / fixture SQL | `@Sql` 脚本 / Testcontainers 初始化 |
| 清理 | 每轮重建库或事务回滚 | 测试类 `@Transactional` 回滚、容器复用 |
| CI 分层 | lint+单测挡 PR，E2E nightly | 单测+切片挡 PR，全量与集成挡合并 |

**回滚这件事两边直觉不同。** 前端 E2E 通常靠"跑完清库"；Spring 的切片测试默认带 `@Transactional`，测试方法结束就回滚，所以你写完数据不用担心污染下一个用例。但它有三个真实的失效场景，正好是第 40 篇「事务失效场景」在测试里的复现：① 被测代码用了 `REQUIRES_NEW` 或自己 `commit`，那部分**不会跟着回滚**；② 用 `TestRestTemplate` 打真实 HTTP，业务在**另一个线程的事务**里跑，测试线程的回滚管不到它；③ 自增主键、序列、以及容器里的 binlog 不受回滚影响——所以下一个用例不要假设 id 还是 1。

## 4. 真实业务场景

**场景：券核销成功但订单金额没变，单测 300 多个全绿。**

业务背景：门店优惠券核销流程是 `Controller → CouponService → (更新券状态 + 更新订单应付金额)`。第 53 篇那种单测把 Mapper 全 mock 了，断言的都是 Service 的分支逻辑——它们当然全过。

线上现象是核销接口返回成功，但订单金额没变。查下去发现三处都是"只有真跑才暴露"的问题：① Mapper XML 里写的是 `#{couponCode}`，而接口方法参数叫 `coupon_code`，MyBatis 在**执行时**才抛 `BindingException: Parameter 'couponCode' not found`——编译期和启动期都不报错；② `resultMap` 少配了 `pay_amount` 一列，查询回来的对象这个字段永远是 null（第 14 篇的映射坑）；③ 核销失败走全局异常处理时（第 33 篇），返回体 `data` 是 `null` 而前端按约定直接取 `data.status`，页面白屏——这条只有把整个 HTTP 层跑起来才测得到。

补的三个集成测试：一个 `@MybatisTest` + Testcontainers 跑真实更新语句（抓到 ①②），一个 `@WebMvcTest` 断言异常时的返回结构含 `code`（抓到 ③），一个 `@SpringBootTest` 打通核销主链路。**总耗时从 0.4 秒涨到 26 秒，换来的是这三个 bug 在 PR 阶段就红。**

**用错的代价**：不是"漏测几个用例"，而是团队形成"单测通过 = 可以上线"的错误共识——mock 测试给的安全感，恰好覆盖了它测不到的那一整层。

## 5. Java 示例代码

**依赖（test scope，别漏进生产包）：**

```xml
<dependency>
    <groupId>org.mybatis.spring.boot</groupId>
    <artifactId>mybatis-spring-boot-starter-test</artifactId>   <!-- 提供 @MybatisTest -->
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>mysql</artifactId>
    <scope>test</scope>
</dependency>
```

**切片测试：只启 MyBatis 这一层，但连真的 MySQL。**

```java
@MybatisTest                                                // 只加载 Mapper / SqlSession，秒级启动
@Testcontainers(disabledWithoutDocker = true)               // 本地没 Docker 时跳过而不是全红
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)  // ★ 关键：别换成 H2
class CouponMapperIT {

    @Container
    static final MySQLContainer<?> MYSQL = new MySQLContainer<>("mysql:8.0")
            .withDatabaseName("store_test");                // static：多个测试类共用一个容器

    @DynamicPropertySource                                   // 容器随机端口回填到 Spring 配置
    static void datasource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", MYSQL::getJdbcUrl);
        registry.add("spring.datasource.username", MYSQL::getUsername);
        registry.add("spring.datasource.password", MYSQL::getPassword);
    }

    @Autowired private CouponMapper couponMapper;

    /** 建表和种子数据：集成测试的数据准备要显式，别依赖库里"刚好有" */
    @Sql(scripts = "/sql/coupon-schema.sql", executionPhase = Sql.ExecutionPhase.BEFORE_TEST_CLASS)
    @Test
    @DisplayName("核销应同时更新券状态并返回真实影响行数")
    void markUsed_updatesRow() {
        int rows = couponMapper.markUsed("C20260914001", "O20260914001");

        // 这里断言的是"真实 SQL 的影响行数"，正是第 52 篇 warn 日志的证据来源
        assertThat(rows).isEqualTo(1);
        assertThat(couponMapper.selectById("C20260914001").getStatus()).isEqualTo(CouponStatus.USED);
    }
}
```

**接口级：整个应用真起来、真发一个 HTTP 请求。**

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class CouponRedeemIT {

    @Autowired private TestRestTemplate rest;      // RANDOM_PORT 下自动带服务地址，无需拼端口

    @Test
    @DisplayName("券不存在时返回业务码而不是 500，且 data 不为 null")
    void redeem_couponNotFound() {
        var body = rest.postForEntity(
                "/api/coupons/redeem?orderNo=O1&couponCode=C404", null, ApiResult.class).getBody();

        // 第 22 篇的统一返回结构契约：失败也要有 code，data 不能是前端会崩的 null
        assertThat(body.getCode()).isEqualTo(ErrorCode.COUPON_NOT_FOUND.getCode());
        assertThat(body.getData()).isNotNull();
    }
}
```

注意这个测试**不能靠 `@Transactional` 回滚**——请求在 Tomcat 的线程里执行，与测试线程不同事务（第 3 节失效场景②），所以要靠独立数据或 `@Sql` 的 `AFTER_TEST_METHOD` 清理。

## 6. 常见坑

**坑 1：集成测试里还留着 mock。** 错误做法：`@SpringBootTest` 里给被测 Service 注入 `@MockBean` 的 Mapper，只为了"跑通流程"。问题：真实 SQL、映射、事务全被绕开，测试退化成一个昂贵的单测。正确做法：集成测试**就是要让真东西参与**；需要隔离的是外部第三方（支付、短信），那才用 `@MockBean`，且要写注释说明为什么可以 mock 它。

**坑 2：以为加了 `@Transactional` 就一定回滚。** 错误理解："测试类上标一下，脏数据自然没了。" 问题：`REQUIRES_NEW` 的内层事务、真实 HTTP 触发的另一线程事务、以及自增序列都不受回滚影响，于是留下脏数据坑后面的用例。正确做法：切片测试（无真实 HTTP）可以用默认回滚；走真实端点的测试改用**独立数据 + 显式清理**（`@Sql` 的 `AFTER_TEST_METHOD`）或每个类一个新 schema。

**坑 3：CI 不分层，把所有测试塞进一个阶段。** 现象：PR 门禁跑 40 分钟，开发开始申请"先合并后补测试"，或直接本地 `skipTests`。原因：全量启动的集成测试和毫秒级单测混在一起跑。正确做法：按命名分层——`*Test` 归 surefire（PR 必跑，控制在 1 分钟内），`*IT` 归 failsafe（`mvn verify` 时才跑，即第 4 篇那条 CI 命令）；再给全量启动的测试做**去重**，同类断言降级到切片层。

## 7. 和之前知识的连接

- **第 53 篇「单元测试」**：那篇的边界声明就是今天的起点——mock 只用于隔离外部世界，SQL、映射、装配、序列化必须真跑，两级测试合起来才是完整防线。
- **第 14 篇「MyBatis 查询结果映射」**：`resultMap` 少一列、列名映射不上，这类问题编译器和启动器都不报错，只有真连一次 MySQL 才现形——集成测试最主要的捕获对象就是它。
- **第 40 篇「事务失效场景」**：`REQUIRES_NEW`、跨线程、自增序列不受测试回滚影响，是那篇"代理与事务边界"知识在测试环境里的复现，也是坑 2 的成因。

## 8. 面试 / 工作中常见问题

### 问题 1：`@SpringBootTest`、`@WebMvcTest`、`@MybatisTest` 什么时候用哪个？

参考答案：先问"我要验证的是哪一层"。只验 SQL 与映射用 `@MybatisTest`；只验参数绑定、校验、返回结构（不起 DB）用 `@WebMvcTest`；跨层协作、事务传播、缓存与 MQ 装配一起生效的才用 `@SpringBootTest`。默认从最便宜的切片开始，**只有当"装配本身"就是被测对象时才付全量启动的成本**。

### 问题 2：集成测试要不要连公司共享的测试库？

参考答案：不建议。共享库的问题在于数据被别人改、表结构漂移、权限与保留期不可控，结果就是 flaky 且没人能复现。用 Testcontainers 每次拉起一次性数据库，schema 由仓库里的建表脚本管理——**环境即代码**，别人 clone 下来就能跑出同样结果。确实需要连公司测试库的（比如验证一个真实视图或存储过程），把这类测试单独归类、少而精，并允许 `disabledWithoutDocker` 之类的开关。

### 问题 3：一个 flaky 的集成测试怎么处理？

参考答案：先分类再动手。① 数据依赖型（顺序、共享行、自增 id）→ 用例自带唯一主键 + 显式清理；② 时序型（异步任务、缓存过期、消息未消费完）→ 用**条件轮询**（`Awaitility` 风格"最多等 5 秒直到 X 成立"）替代固定 sleep，这是最常见的修复；③ 资源型（容器端口冲突、连接池耗尽）→ 检查容器是否 static 共享、连接是否关闭。定不了位的临时降级是隔离出主门禁并挂 issue，而不是原地重跑。

## 9. 今日小结

- 单测证明"逻辑分支对"，集成测试证明"装配与真实 SQL 对"——**mock 掉被测主角的测试没有价值**。
- 粒度从便宜到贵：`@MybatisTest` / `@WebMvcTest` 切片 → `@SpringBootTest` 全量；真跑 SQL 靠 Testcontainers，两把钥匙是 `@AutoConfigureTestDatabase(replace = NONE)` 和 `@DynamicPropertySource`。
- 回滚不是万能的：`REQUIRES_NEW`、真实 HTTP 跨线程、自增序列都会漏；脏数据要么靠回滚，要么每个用例自带唯一主键 + 显式清理。
- CI 分两层：`*Test` 归 surefire 挡 PR（秒级），`*IT` 归 failsafe 走 `mvn verify` 挡合并——慢门禁一旦挡人，就会被绕过。
