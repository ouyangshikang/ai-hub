# Java 学习：读写分离与主从延迟

> 系列第 65 篇 · 第八阶段：数据架构进阶（开篇）
> 衔接上一篇「可观测性三件套」：那篇讲"怎么知道系统好坏"，其中"滞后"这个指标在数据库层有一个最经典的特例——**主从复制延迟**。
> **与第 16~18 篇的分工**：那三篇是**单库视角**（慢 SQL、索引、深分页）；今天开始看**库与库之间**：读写怎么路由、延迟从哪来、以及"写后立刻读"这个业务级陷阱。

## 1. 今天学什么

读写分离解决的是最朴素的容量问题：**读的请求远多于写**（典型业务 9:1 到 100:1），而单机数据库的读能力有上限。于是把读分摊到多个副本（从库），主库只负责写。

但它换来的是一整套新问题：① **路由**：哪些 SQL 走从库、哪些必须走主库，谁来判定；② **延迟**：从库落后主库多久，`Seconds_Behind_Master` 这个数字为什么经常骗人；③ **头号陷阱——写后立刻读**：用户刚提交就看到旧数据，报"我的修改丢了"；④ **时机**：什么时候读写分离不够用，必须上分库分表，以及那笔账有多贵。

一句话定位：读写分离不是"配个中间件就完事"，**它是一个用一致性换吞吐的交易**，而交易条款藏在延迟数字里。

## 2. 前端工程师视角理解

你其实最熟悉这个现象的**前端版本**：改完数据刷新页面还是旧的——因为你读到了 **CDN 或浏览器缓存**，而源站早就更新了。用户当时的体感就是"我的修改没保存"，你会教他"硬刷新一下"；后端读写分离之后，同样的体感会出现在**所有人**身上，而且没有"硬刷新"这种解法。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端读写分离 |
|---|---|---|
| 读的来源 | CDN / 浏览器缓存 / 本地状态 | 从库（replica） |
| 写后立刻读 | 从本地状态读，天然强一致 | 从库可能落后，读到旧数据 |
| 一致性窗口 | 缓存 TTL | 复制延迟（毫秒到分钟，看负载） |
| 兜底 | 硬刷新、加版本号查询参数 | 强制走主库、GTID 等待、半同步复制 |
| 观测 | CDN 缓存命中率 | 复制延迟、从库滞后、回放线程 |
| 扩容方向 | 多级缓存、边缘节点 | 加副本 → 分库分表 |

**最需要建立的直觉：一致性窗口可以被"缩小"，但很少有人能把它"消除"。** 加从库必然引入延迟；半同步复制能把窗口压到毫秒级，代价是主库写延迟变高；想让"写后立刻读"百分百正确，唯一可靠的办法是**让这一次读走主库**——就像你在前端写完不等接口回来、直接用本地状态渲染一样，是"绕过缓存"而不是"让缓存更快"。

## 4. 真实业务场景

**场景：门店改完商品价格，前台还是旧价；运营连续提交三次，产生了三条调价记录。**

业务背景：商品服务上线读写分离——查询走两个从库，写入走主库，主从延迟平时 20ms。运营在后台改价后立刻刷新商品列表（走从库），看到旧价，以为没保存又提交两次；更糟的是门店小程序在调价后 30 秒内下单，读到的还是旧价，按错价成交了几十单。

三个原因叠加：**① 写后立刻读走了从库**——后台"保存后刷新"这个最自然的操作恰好命中不一致窗口；**② 延迟不是常数**——当晚主库在跑一次批量调价（大事务），复制延迟飙到 40 秒，远超平时的 20ms，而从库监控只在"延迟 > 10 秒"时才告警，肉眼没发现；**③ 业务上的"价格"是强一致诉求**，它本不该允许读旧值。

修复三件事：**写后短窗口强制读主库**（后台写操作后给该会话打 1 秒"读主标记"，代价可忽略）；**钱与库存类读永远走主库**（价格、余额、库存不做"最终一致妥协"）；**把延迟监控换成真实心跳**（pt-heartbeat 风格），并把批量 DDL 与大事务安排到低峰——第 52 篇那条规则在这里又多了一个理由。

**用错的代价**：不是"偶尔读旧值"，而是**用户会对系统的正确性失去信任**——运营不敢信后台、门店不敢信价格，最后所有人都去问客服。

## 5. Java 示例代码

**路由用 `AbstractRoutingDataSource` + 写标记：写后一段时间内该会话强制读主。**

```java
/** 路由键：只决定"这一次查走谁"；写标记由业务在写操作后打上（AOP 或显式调用） */
public class ReplicaAwareRoutingDataSource extends AbstractRoutingDataSource {

    /** 读主窗口的过期时间戳；分布式会话下换成 Redis 的 SET 带 TTL，效果一致 */
    private static final ThreadLocal<Long> FORCE_PRIMARY_UNTIL = new ThreadLocal<>();

    /** 写操作后调用：接下来的一小段时间内本线程的所有读都强制走主库 */
    public static void forcePrimaryForAWhile(long millis) {
        FORCE_PRIMARY_UNTIL.set(System.currentTimeMillis() + millis);
    }

    @Override
    protected Object determineCurrentLookupKey() {
        Long until = FORCE_PRIMARY_UNTIL.get();
        boolean forcePrimary = until != null && System.currentTimeMillis() < until;
        return forcePrimary ? "primary" : "replica";      // 两个 key 与 targetDataSources 对应
    }
}
```

```java
/** 关键读：用 GTID 等待把"猜延迟"换成"确定回放"（MySQL 8.0.22+ 术语为 REPLICA） */
public void readAfterWrite(String requiredGtidSet) {
    // 在从库会话上等待回放到指定 GTID 集合：返回 0 表示已追上，1 表示超时
    Integer result = jdbcTemplate.queryForObject(
            "SELECT WAIT_FOR_EXECUTED_GTID_SET(?, ?)", Integer.class, requiredGtidSet, 1);
    if (result == null || result != 0) {
        throw new BizException(ErrorCode.REPLICA_LAG_TOO_LONG, "从库延迟过大");   // 让上层改走主库
    }
}
```

## 6. 常见坑

**坑 1：以为"读走从库"是透明的，不区分字段的一致性要求。** 错误做法：配好中间件后所有 `SELECT` 都走从库。问题：价格、余额、库存、订单状态这些字段的旧值会直接变成业务事故（按错价成交、看到已取消的订单还在），而这类读恰恰是最不能妥协的。正确做法：**按字段/接口划分一致性等级**——钱与状态类读强制主库；列表、报表、非关键详情走从库；把这个规则写进团队规范，而不是留给每个开发临时判断。

**坑 2：用 `Seconds_Behind_Master` 当延迟告警的唯一依据。** 错误做法：看到它为 0 就认为从库已同步。问题：这个值的含义是"SQL 线程落后 IO 线程多少秒"，当 IO 线程卡住、或从库根本没在复制（复制中断）时，它可能显示 0 或 NULL；大事务回放期间它也会剧烈跳变。正确做法：用**真实心跳**（主库写入时间戳、从库读出来算差）或 GTID 位点差来度量；同时监控 IO/SQL 线程状态与复制中断事件。

**坑 3：把读写分离当成分库分表的替代品，或者反过来过早分片。** 错误做法：容量一紧张就直接上分片；或者读再慢也只会加从库。问题：读写分离解决**读多**，解决不了**写瓶颈与单表过大**；而分片的代价是跨库事务、跨库分页、扩容搬迁，上了很难回头。正确做法：**顺序是 SQL 与索引治理 → 缓存 → 读写分离 → 最后才是分片**（第 16~18、45 篇），分片前先确认写入量与单表规模真的到了阈值。

## 8. 面试 / 工作中常见问题

### 问题 1：读写分离后，写完立刻读不到新数据，怎么解决？

参考答案：按代价从低到高：① **写后短窗口强制读主**（AOP 打标记，1 秒左右足够覆盖大部分场景，用 Redis TTL 支持多实例）；② **关键读永远走主**（钱、库存、订单状态）；③ **GTID 等待**——拿着上次写的事务位点去从库等回放，超时就转主库，把猜延迟变成确定回放；④ 半同步复制把窗口压到毫秒级，代价是主库写变慢。原则是"用绕过缓存解决，而不是指望缓存更快"。

### 问题 2：`Seconds_Behind_Master` 为 0 就代表数据一致吗？

参考答案：不代表。它是"从库 SQL 线程落后 IO 线程的秒数"，在复制中断、IO 线程卡死、或从库根本没有流量时都可能显示 0 或 NULL；大事务回放期它还会剧烈跳变。工程上更可信的是**真实心跳延迟**（主库定时写时间戳，从库读出后与当前时间做差）或 GTID 位点差，同时把复制线程状态、错误日志一并纳入监控。

### 问题 3：什么时候该从读写分离走到分库分表？

参考答案：看信号而不是看心情。读写分离解决读压力；当出现**单表增长到千万级以上、写入成为瓶颈、单库连接数或磁盘接近上限、DDL 时间无法接受**这些信号时，才考虑分片。而且顺序不能跳：先把索引与慢 SQL 治理干净（第 16~18 篇）、把能缓存的读缓存掉（第 45 篇），再评估分片。分片的代价是跨库事务、跨库分页、扩容搬迁与运维复杂度——**上一次容易，回头很难**。

## 9. 今日小结

- 读写分离是**用一致性换吞吐**的交易：读分摊到从库，代价是写后读的一致性窗口。
- 头号陷阱是"写后立刻读"：解法是**强制读主 / GTID 等待 / 半同步**，而不是等从库追上来。
- 按字段划分一致性等级：钱、库存、状态类读永远走主库，报表与列表可以读从库。
- 延迟要看**真实心跳**而不是 `Seconds_Behind_Master`（大事务与 DDL 是延迟的头号制造者）；扩展路径的顺序是 SQL 治理 → 缓存 → 读写分离 → 分片，每一步都要有容量依据。
