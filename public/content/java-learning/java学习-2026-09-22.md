# Java 学习：超时、重试与熔断

> 系列第 62 篇 · 第七阶段：分布式一致性与容错（第 3 篇）
> 衔接上一篇「消息可靠性与最终一致性」：那篇讲异步链路的"至少一次 + 幂等 + 对账"；今天讲**同步链路**里同样决定生死的三件事。
> **与第 61 / 51 篇的分工**：第 61 篇的退避与上限是给**消息投递**用的（异步、可无限重试）；第 51 篇给出"超时会拖住连接池"的现象。今天讲**同步调用的容错设计**：超时预算怎么分配、重试为什么常常放大故障、熔断与舱壁怎么把故障关在局部。

## 1. 今天学什么

同步调用和异步消息最大的区别是：**调用方一直在等**，而等待要占线程、占连接（第 58、51 篇）。所以超时、重试、熔断不是三个独立配置项，而是**一组互相牵制的预算**。

四块内容：① **超时预算**：从入口 SLA 反推每一跳的额度，逐跳递减、每跳必设，包括最容易被忘的 DB 与锁等待；② **重试的边界**：只重试幂等且可重试的失败，退避带抖动，且**同一条链路只允许重试一层**；③ **熔断**：用三态把"下游已经挂了"从"每次请求都等一个超时"变成"立刻失败"；④ **舱壁隔离**：每个下游独立池，一个慢下游拖不垮全部。

## 2. 前端工程师视角理解

你手里的 `fetch` 默认**永不超时**——请求会一直挂着，直到浏览器自己放弃。前端为此付出的代价你见过：同域只有 6 个并发连接（第 58 篇提过），一个卡死的请求就永久占掉一个名额，页面越用越慢。后端一模一样，只是"连接名额"换成了线程与数据库连接：**没设超时的下游调用，会把线程池一个接一个占死**（第 51 篇那次拐点就是这么来的）。所以你熟悉的 `AbortSignal.timeout(3000)` 不是前端小技巧，它和后端的 `readTimeout` 是同一个东西。

第二个直觉来自 **React Query**：查询默认会重试 3 次，而**变更（mutation）默认不重试**——因为 POST 不是幂等的，重试可能造成重复下单。后端的重试规则完全一致：GET/查询可重试，扣款、下单这类写操作要么不重试，要么先有幂等键（第 25、60 篇）。而"熔断"你在前端也用过雏形：接口连续失败时先展示缓存或降级 UI，别再无限打后端——这就是断路器从 closed 翻到 open 的手工版。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端 |
|---|---|---|
| 默认超时 | `fetch` 无超时，需 `AbortSignal.timeout()` | 各客户端默认值不一（有的 30s，有的无限），**必须显式设** |
| 占用的资源 | 同域 6 个连接名额 | 线程、连接池、被下游占用的并发 |
| 重试默认 | React Query：query 重试、mutation 不重试 | 无默认重试；一旦自己加，就要管幂等与放大 |
| 退避 | axios-retry 的指数退避 | 指数退避 + **抖动**，且总预算要算进 SLA |
| 熔断 | 手工写"失败几次就切降级 UI" | 断路器标准三态（closed / open / half-open） |
| 隔离 | 分域、分请求池 | 舱壁：每个下游独立线程池与连接池 |

**为什么 Java 更痛？** 因为它的"等待"是**实打实占用资源**：一个 30 秒超时的下游调用会占住一根线程 + 一个连接 30 秒。前端等 30 秒只是页面卡一下，后端等 30 秒，200 根线程里的 200 个都可能在各等各的。**超时值决定的不是"用户等多久"，而是"资源被占用多久"**——这就是超时预算必须比 SLA 更严的原因。

## 4. 真实业务场景

**场景：支付方抖动 20 分钟，下单接口全站不可用 4 小时。**

业务背景：下单要同步调支付网关（受理）、风控、库存三个下游，入口 SLA 是 P99 < 800ms。某天支付方网络抖动，20 分钟内它的 P99 从 200ms 涨到 5 秒。

四件事同时发生，把 20 分钟的抖动变成了 4 小时故障：① **同一条链路上重试了三层**（网关 2 次 × 服务内部 3 次 × 客户端 1 次 = 最坏 6 倍流量）打向已经变慢的支付方；② **重试没有抖动**，所有实例在同一秒齐步重试形成冲击波；③ **支付与风控、库存共用同一个线程池**，支付变慢把池占满，连"不涉及支付"的订单历史查询一起拖死；④ **没有熔断**，每次请求都老实等 5 秒，用户超时、重试制造更多请求，直到支付方限流彻底拒绝。

修复按三件套落地：**超时预算重排**——入口 800ms 拆成 风控 150 + 库存 200 + 支付 300，再加 150ms 余量，三层各自收紧（DB `connectionTimeout` 从默认 30s 改 2s，池等待超时算进预算）；**重试收敛**——只在网关层重一次，带 100~300ms 随机抖动，下单服务内部不再重试；**熔断 + 舱壁**——支付调用独立线程池（上限 20），错误率 50%（10 次窗口）就打开 30 秒，半开只放 3 个探测请求，熔断期间走"先受理、稍后补单"的降级路径（第 48 篇的开关）。

**用错的代价**：重试和超时配错，会把一次"20 分钟的下游抖动"放大成"全站 4 小时不可用"——**故障不是被下游传染的，是被自己的容错策略放大的。**

## 5. Java 示例代码

```yaml
# 超时预算：每一跳都要显式，且逐层递减（外层 > 内层之和 + 余量）
store:
  timeout:
    ingress-ms: 800        # 入口 SLA，先定这个
    risk-ms: 150
    stock-ms: 200
    pay-ms: 300            # 150+200+300=650，留 150 余量给序列化/GC
spring:
  datasource:
    hikari:
      connection-timeout: 2000   # 默认 30000！拿不到连接等 30 秒，直接吃掉整个预算（第 51 篇）
```

```java
/**
 * 熔断 + 舱壁 + 带抖动的单次重试：手写一版理解三态，生产上可直接换成 Resilience4j / Sentinel。
 * 关键点：失败要"快"，恢复要"试探"，隔离要"按下游分池"。
 */
@Component
@Slf4j
public class PayClient {

    private enum State { CLOSED, OPEN, HALF_OPEN }

    private volatile State state = State.CLOSED;
    private final AtomicInteger windowCalls = new AtomicInteger();
    private final AtomicInteger windowFails = new AtomicInteger();
    private volatile long openUntil = 0L;

    /** 舱壁：支付专用线程池与连接池，慢下游不能占满全站资源（第 58 篇的池隔离） */
    @Resource(name = "payExecutor")
    private ThreadPoolTaskExecutor payExecutor;

    public PayResult apply(PayRequest req) {
        if (state == State.OPEN) {
            if (System.currentTimeMillis() < openUntil) {
                throw new BizException(ErrorCode.PAY_DEGRADED, "支付通道繁忙");   // 快速失败，不等超时
            }
            state = State.HALF_OPEN;                       // 窗口到期：放少量请求探测
        }

        Future<PayResult> future = payExecutor.submit(() -> doApply(req));
        try {
            PayResult r = future.get(300, TimeUnit.MILLISECONDS);   // 超时兜底：超过预算立刻放弃
            onSuccess();
            return r;
        } catch (Exception e) {
            future.cancel(true);                            // ★ 超时后必须取消，否则任务还在池里占着资源
            onFailure();
            // 重试只做一次，且只在"可重试失败"上做（连接失败/超时）；熔断打开后不再重试
            if (state == State.CLOSED && isRetryable(e)) {
                LockSupport.parkNanos((100 + ThreadLocalRandom.current().nextLong(200)) * 1_000_000L);
                return retryOnce(req);                      // 抖动：避免全实例齐步重试
            }
            throw new BizException(ErrorCode.PAY_UNAVAILABLE, "支付暂不可用");
        }
    }

    private PayResult doApply(PayRequest req) { /* 真实 HTTP 调用，超时取 store.timeout.pay-ms */ return null; }

    private boolean isRetryable(Exception e) {
        return e instanceof TimeoutException || e instanceof ConnectException;   // 5xx 同理，业务错误不重试
    }

    private PayResult retryOnce(PayRequest req) { return doApply(req); }

    /** 成功要区分状态：半开探测成功说明下游已恢复，必须回 CLOSED 并清空窗口 */
    private void onSuccess() {
        windowCalls.set(0);
        windowFails.set(0);
        if (state == State.HALF_OPEN) {
            state = State.CLOSED;
            log.warn("支付熔断关闭，恢复正常调用");
        }
    }

    /** 滑动窗口统计：10 次里失败过半就打开 30 秒（生产上用带时间窗的成熟实现） */
    private void onFailure() {
        if (windowCalls.incrementAndGet() >= 10 && windowFails.incrementAndGet() * 2 >= windowCalls.get()) {
            state = State.OPEN;
            openUntil = System.currentTimeMillis() + 30_000;
            log.error("支付熔断打开，30 秒内快速失败");
        }
    }
}
```

## 6. 常见坑

**坑 1：只在最外层设超时。** 错误做法：网关配了 800ms，服务内部的 HTTP 客户端、DB 连接池、Redis 客户端都用默认值。问题：外层超时只是让**用户**少等，**资源仍在被占用**——连接池默认 30s 的等待会一直排到超时为止，线程照样被占满（第 51 篇的拐点）。正确做法：**逐跳设置且递减**（内层之和 < 外层），把池等待时间、MQ 消费超时、分布式锁等待都算进预算表；预算表要写进文档，压测时按它验证（第 51 篇）。

**坑 2：多层重试叠加 + 无抖动。** 错误做法：网关、服务、客户端各配几次重试。问题：重试次数是**乘法关系**（2×3×1 = 6 倍流量），叠加无抖动（所有实例同秒重试）就是人为制造的雪崩；而且对非幂等的写操作重试，直接变重复下单。正确做法：**整条链路只在一层重试**（通常是离失败最近、最了解幂等性的一层），只重试幂等 + 可重试的错误（连接失败、超时、502/503），退避带随机抖动，并把重试的**总时间**算进超时预算。

**坑 3：把熔断当"自动恢复开关"，忽略了降级与半开的代价。** 错误做法：配了熔断却没有降级路径，熔断打开后接口直接报错。问题：熔断只是"快速失败"，用户看到的失败率并没有变好；半开期若放全量流量进去，会把刚缓过来的下游再次打挂。正确做法：熔断必须配**降级动作**（返回兜底值、走备用通道、受理后补偿——第 48 篇的开关与第 61 篇的补偿），半开只放少量探测（如 3 个请求），通过后再按比例恢复。

- **第 51 篇「接口压测」**：超时值的依据来自压测（下游 P99 + 余量），而不是拍脑袋；今天补上"预算分配"这一层。
- **第 61 篇「消息可靠性与最终一致性」**：异步链路的退避/上限/对账与今天同步链路的重试/熔断互为镜像——一个"可以慢慢重试"，一个"必须快速失败"。
- **第 57 篇「线上问题排查流程」**：今天的三件套正是那篇"止血四板斧"里降级与限流的**技术底座**；熔断打开的那一刻，就是系统在替你执行止血。

## 8. 面试 / 工作中常见问题

### 问题 1：超时时间怎么定？

参考答案：从入口 SLA 倒推：先定用户能接受的总时长（如 P99 800ms），扣掉序列化、GC 与框架开销，把剩余额度按呼叫顺序分给各下游，保证**内层之和 + 余量 < 外层**。每个值要有压测依据（下游 P99 之上留 20~50%），并且逐跳设置——HTTP 客户端、DB 连接池、Redis、锁等待一个都不能漏。

### 问题 2：什么情况下能重试，重试几次？

参考答案：三个条件同时满足才能重试：**幂等**（或先有幂等键）、**错误可重试**（连接失败、超时、502/503，不是 400/401/业务失败）、**总预算够**（退避时间算得进 SLA）。次数通常 1~3 次 + 指数退避 + 抖动；更重要的是位置——整条链路只让最了解幂等性的一层重试，避免多层乘法放大。写操作如果没有幂等键，宁可不重试，让上层用对账补偿（第 61 篇）。

### 问题 3：熔断和限流、降级是什么关系？

参考答案：三个不同维度。**限流**是入口限速，保护自己不被打死，针对"进来的量"；**熔断**是出口保护，当下游持续失败时快速失败，针对"出去的调用"，避免资源被无效等待吃掉；**降级**是熔断/限流触发后的业务动作——返回兜底数据、走备用通道或受理后补偿。三者串起来才完整：限流挡住超量、熔断切断坏依赖、降级兜住用户体验。

## 9. 今日小结

- 超时不是"设一个数"，是**逐跳预算**：从入口 SLA 倒推、内层之和小于外层，DB 池等待与锁等待都要计入——它决定的是**资源被占用多久**，不是用户等多久。
- 重试次数是乘法关系：**整链路只重一层**、只重幂等且可重试的失败、必带抖动；否则是在替故障放大流量。
- 熔断把"每次请求都等一个超时"变成"立刻失败"，但它必须配降级动作与少量半开探测才完整。
- 舱壁隔离按下游分池：一个慢下游只能打满自己的池，不能吃掉全站资源。
