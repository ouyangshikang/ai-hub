> 系列第 52 篇 · 第六阶段：工程化

## 1. 今天学什么

慢 SQL 排查解决的不是"看懂一条 SQL"，而是**在几百张表、几万条语句里，用数据找出真正吃掉容量的那几条，并把修复闭环走完**。它有三个环节：① 发现——慢查询日志 + 语句聚合视图，按**总耗时占比**而不是单条最慢来排序；② 归因——同一句话为什么上周快这周慢（统计信息、数据分布、排序溢写），以及慢的到底是 SQL 还是锁与连接；③ 治理——在线加索引怎么不锁表、改完怎么验收、怎么防止同类 SQL 再写回来。

它排在压测之后很自然：**连接持有时间 = SQL 时间 + 事务里其他事情的时间**，而昨天那条拐点就是被这个总和顶出来的。

## 2. 前端工程师视角理解

最贴合的类比是 **bundle 分析器**（rollup-plugin-visualizer）。你排查打包体积时不会盯着"哪个文件最大"，而是看**按 gzip 后总占比排序**的前几名——一个 20KB 的库被 300 个模块各引一次，比一个 300KB 的单文件更值得先动。慢 SQL 完全同理：一条稳定 200ms 的查询，被 1500 TPS 放大后比凌晨那条跑 8 秒的报表更致命，因为它**每天占用几千小时的连接**。所以治理清单的第一列应该是"总耗时占比"，不是"最慢耗时"。

第二个类比是 **Performance 面板的长任务**。前端一个长任务会把主线程占死，其它交互全排队；数据库的对应物是**锁**——一条没走索引的 `UPDATE` 可能锁住极大范围，此时慢下来的是**所有别的 SQL**，而它们本身都没写错。这类问题光看单条 SQL 永远看不懂，必须去看谁在等谁。还有一个前端人会心一笑的点：防劣化靠的是 **ESLint + CI 体积门禁**，合并前挡住而不是上线后查——SQL 治理的终点同样是这道门禁（见第 8 节）。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | MySQL 慢 SQL |
|---|---|---|
| 找元凶 | bundle 分析器按占比排序 | 语句聚合按**总耗时**排序 |
| 单条诊断 | Performance 火焰图 | `EXPLAIN ANALYZE`（8.0.18+，真的执行一遍） |
| 环境差异 | 开发机快、低端机慢 | 统计信息与数据量不同，计划会**突变** |
| 防劣化 | ESLint / size limit 门禁 | SQL 审核平台 / CI 执行计划检查 |
| 变更风险 | 发版回滚即可 | DDL 加索引可能锁表、拖慢主从 |

**最需要注意的是"同一个字符串不是同一条 SQL"。** JS 里 `arr.filter(...)` 每次跑的都是同一段代码，性能差异来自数据规模；MySQL 的优化器是**按统计信息估成本再选索引**，同一句话在数据分布变化后可能换一条执行路径——昨天还 5ms，今天 500ms，代码一个字没改。这也是为什么 `EXPLAIN` 必须在**接近生产数据量**的库上看：它对空表永远"计划完美"。而 `EXPLAIN ANALYZE` 会真的执行并给出每步实际行数与耗时，两者差别相当于"读代码"和"跑一遍看火焰图"。

## 4. 真实业务场景

**场景：门店库存同步接口 P99 从 60ms 涨到 1.4s，元凶是一条从没被关注过的 UPDATE。**

业务背景：门店库存在 `store_stock`（约 4000 万行）里，库存同步任务收到 MQ 消息后按 `store_code + sku_code` 更新数量。接口在昨天压测的拐点上出现连接池 pending，值班同学一开始怀疑"SQL 慢"，但把这条 `UPDATE` 拿到测试库单跑只要 3ms。

真正的链路是这样查出来的：先在聚合视图里按总耗时排序，命中一条 `UPDATE store_stock SET quantity=? WHERE store_code=? AND sku_code=?`——单条 12ms，但每分钟执行两万次，**占了总耗时的 38%**。再看它为什么慢：`store_code` 是 `varchar(32)`，而 Mapper 里传的是**未加引号的数字**，MySQL 只能把列值逐个转成数字再比较，索引**根本用不上**。表只有 800 万时全表扫描也就几十毫秒，没人察觉；涨到 4000 万后同一条语句变成 500ms——**不是计划突变，而是代价一直存在、只是被小表藏住了**。真正叫"计划突变"的是另一种：走索引的语句因统计信息漂移被优化器换成了别的索引，这种要靠 `EXPLAIN ANALYZE` 的实际行数才能看出来。接着发现它还会连累别人：这条语句扫表时持有的行锁范围极大，同表的两条查询被堵住，`sys.innodb_lock_waits` 里能看到它们全在等它。

修复分三步走：SQL 参数类型对齐、给 `(store_code, sku_code)` 建联合索引（第 17 篇的规则）、在线 DDL 低峰执行。**验收不看单条耗时，看接口 P99 和连接池 pending 是否归零**（第 51 篇的指标口径）。

**用错的代价**：这类问题的表象是"某个接口突然慢"，实际是**全服务的连接池被拖穿**——只优化被投诉的那条 SQL，明天会换一个接口继续被投诉。

## 5. Java 示例代码

**工程侧自动发现：把慢 SQL 打到日志里，而不是等人去查库。**

```yaml
spring:
  datasource:
    druid:
      filter:
        stat:
          enabled: true
          log-slow-sql: true       # 开启慢 SQL 记录（Druid 直接在日志里给语句+耗时）
          slow-sql-millis: 500     # 阈值别照默认：生产常见瓶颈在 200~800ms 这一段
          merge-sql: true          # 参数归一化，同类 SQL 聚成一条，否则日志被刷屏
```

**数据库侧：按"总耗时占比"排 TOP，而不是找最慢的那条。**

```sql
SET GLOBAL slow_query_log = 1;
SET GLOBAL long_query_time = 0.5;          -- 默认 10 秒，等于只看灾难级慢查询

-- 最近哪些语句最贵（DIGEST 聚合，单位是皮秒，除以 1e12 换成秒）
SELECT DIGEST_TEXT,
       COUNT_STAR                          AS exec_count,
       ROUND(AVG_TIMER_WAIT / 1e12, 3)     AS avg_sec,
       ROUND(SUM_TIMER_WAIT / 1e12, 1)     AS total_sec   -- ★ 按这一列排序
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 5;

-- 看真实执行代价：ANALYZE 会真的跑一遍，所以只在副本上、并用等价的 SELECT 复刻条件，
-- 别对 UPDATE/DELETE 直接 EXPLAIN ANALYZE（那会真实改数据）
EXPLAIN ANALYZE SELECT id, quantity FROM store_stock
  WHERE store_code = 1024 AND sku_code = 88;   -- 场景里那条 UPDATE 的 where，数字未加引号
```

**治理回写：让"事务持连接"的时间只包含 DB 操作。**

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class StockSyncService {

    private final TransactionTemplate txTemplate;   // 编程式事务：边界自己控制
    private final StockMapper stockMapper;

    /**
     * 慢 SQL 常和"事务太长"绑在一起：连接被事务占住，SQL 再快也会把池压满。
     * 做法是把 RPC / 消息发送挪到事务外，事务里只留 DB 写。
     */
    public void sync(StockMsg msg) {
        int affected = stockMapper.updateByStoreAndSku(msg.storeCode(), msg.skuCode(), msg.quantity());

        if (affected == 0) {
            // 隐式转换或数据不存在都会让影响数为 0，这里必须留证据（第 34 篇）
            log.warn("库存更新未命中 storeCode={} skuCode={}", msg.storeCode(), msg.skuCode());
            return;
        }
        txTemplate.executeWithoutResult(status -> stockMapper.writeSyncLog(msg));  // 只包这一句
    }
}
```

## 6. 常见坑

**坑 1：用 `EXPLAIN` 的计划当结论。** 错误做法：在只有几百行数据的测试库看 `key` 不是 NULL，就判定"走了索引，安全"。问题：`EXPLAIN` 不执行，选择依据是统计信息估算，数据量与分布一变就可能换索引。正确做法：在接近生产数据量的副本上用 `EXPLAIN ANALYZE` 看实际行数与真实耗时；怀疑统计信息过期时 `ANALYZE TABLE` 重算后再对比。

**坑 2：大表直接 `ALTER TABLE ADD INDEX`。** 错误理解："加个索引而已。" 问题：DDL 期间的临时空间膨胀、主从延迟、以及不可用窗口都可能把线上打死，而"回滚"意味着再跑一次 DDL。正确做法：优先用 online DDL 并显式声明意图（`ALGORITHM=INPLACE, LOCK=NONE`），超大表走 gh-ost / pt-osc；低峰执行、先确认磁盘余量与主从延迟，并预留应急手段——新索引若让优化器选错计划，可用 `IGNORE INDEX` 或优化器 hint 临时固定，必要时 `DROP INDEX` 回退。

**坑 3：只优化 SQL 本身，不看谁在等锁。** 错误做法：接口 P99 高，就去改那条被查出来的 SQL。问题：慢的可能是**被别人的锁挡住**，或事务里夹了 RPC 导致连接被长期占用（第 39 篇）——改语句毫无效果。正确做法：先看等待关系（`sys.innodb_lock_waits`、`SHOW ENGINE INNODB STATUS` 的死锁段），再看事务边界与持有时长，最后才优化语句本身。

## 8. 面试 / 工作中常见问题

### 问题 1：一条 SQL 昨天 5ms、今天 500ms，代码没改，你怎么查？

参考答案：按"变的是什么"排：① 数据量与分布（是否新增热点、表是否膨胀），用 `EXPLAIN ANALYZE` 对比实际行数与预估行数；② 统计信息过期，`ANALYZE TABLE` 后看计划是否回到原来那条；③ 参数与传值类型（隐式转换、字符集不一致）；④ 环境侧：锁等待、连接池 pending、主从延迟、当天是否有 DDL 或在跑的大任务。多数"莫名其妙变慢"最后落在 ①②④。

### 问题 2：生产表 5000 万行，怎么加索引才安全？

参考答案：先确认这条索引真的要加（用聚合视图和执行计划拿证据，而不是"看起来该加"）。执行上走 online DDL：`ALTER TABLE ... ADD INDEX ..., ALGORITHM=INPLACE, LOCK=NONE`，超大表或版本不满足时用 gh-ost / pt-osc 影子表切换；低峰期做，盯磁盘临时空间、主从延迟和复制中断，并预设应急路径：索引建好后若优化器乱选可用 hint 固定，索引本身可以 `DROP INDEX` 快速回退。

### 问题 3：怎么防止慢 SQL 反复被写回来？

参考答案：把治理从"事后"挪到"事前"。① 评审门禁：新 SQL 必须附执行计划与预估扫描行数，核心表加索引由 DBA 或审核平台把关；② CI 检查：对变更的 Mapper XML 在影子库跑 `EXPLAIN`，出现 `type=ALL` 或预估行数超阈值就失败（等价于前端的 size limit 门禁）；③ 运行时兜底：Druid 慢 SQL 日志 + 聚合报表按周看 TOP，配告警；④ 兜底手段：给关键查询设超时（`statement` 超时 / 连接池获取超时），宁可失败也别把池拖穿。

## 9. 今日小结

- 排序依据换成**总耗时占比**：高频的 200ms 比低频的 8s 更值得先修，这决定了治理清单对不对。
- `EXPLAIN` 是读代码，`EXPLAIN ANALYZE` 是跑火焰图；统计信息一变计划就可能突变，测试库的结论不可信。
- 看到慢先分清三种：**SQL 自身慢、被锁挡、事务把连接占太久**——只有第一种该改语句。
- DDL 也是发布：要灰度、要监控主从延迟、要有回退手段（索引可 DROP，计划可用 hint 固定）。
