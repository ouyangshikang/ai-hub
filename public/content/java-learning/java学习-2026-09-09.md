# Java 学习：配置管理

> 系列第 49 篇 · 第六阶段：工程化
> 衔接上一篇「环境区分」：profile 把环境切开了，但配置项本身还是散的——十几份 yml 各改各的、调一个超时值要走一次发版、开关没人知道谁在用。
> **与第 7 篇的分工**：那篇讲**单个项目怎么读配置**（YAML 语法、`@Value`、`@ConfigurationProperties`）；今天讲**配置作为资产怎么管**——归属分类、集中下发、动态刷新的失效边界、以及怎么评审和回滚。

## 1. 今天学什么

配置管理的目标是：**该改的能立刻改、不该改的改不到、改错了能一秒回滚。** 昨天解决的是"这份配置属于哪个环境"，今天解决三个问题：① 一个配置项该放 yml 还是配置中心；② 改完怎么在不重启的情况下让**所有实例**一致生效，以及它在哪几种写法下会静默失效；③ 怎么审计、灰度、回滚，怎么避免半年后没人敢删的僵尸开关。

它属于工程化而不是语法环节：配置错误的爆炸半径是**全量实例**，比只影响单条请求的代码 bug 大得多。

## 2. 前端工程师视角理解

第一件熟悉的系统是 **`.env`**。它的值在构建时被内联进 JS 产物，"改配置"必然等于"重新构建 + 重新发布"。后端接了配置中心之后，恰恰是另一种模式：实例启动时拉配置，之后变更由配置中心推下来，进程内替换掉生效值，**不发版**。所以判断一个值该不该进配置中心，标准只有一条：**你希望它改完之后不用发版就生效吗？**

第二件是 **feature flag**。如果你有 GrowthBook / LaunchDarkly 的经验，"集中管理、按用户灰度、随时关掉"这套心智模型可以直接搬过来——后端的业务开关（限流阈值、活动规则、灰度比例、降级开关）就是同一个东西。差别在于**爆炸半径**：前端 flag 关掉，最坏是部分用户看到旧版页面；后端开关推错，是全部实例在同一秒行为异常，而且它们会被同时拉起重启。

最难迁移的直觉是**"配置和代码不同步发布"**。前端产物自包含，一个 bundle 里的配置和代码必然配套；后端配置存在远端，新代码可能读到旧配置（发布中），旧代码也会读到新配置（回滚后）。这是昨天"一个产物跑多环境"的自然延伸——**配置要能同时兼容前后两个代码版本**。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端（Vite / Remote Config） | Spring Boot + 配置中心 |
|---|---|---|
| 注入时机 | `import.meta.env` 构建时内联，改一次发一次版 | 启动拉取 + 长轮询推送，运行中可变 |
| 类型 | 全是字符串，自己 `parseInt` | 绑定到 `int` / `Duration` / `List`，可 `@Validated` 校验 |
| 生效范围 | 用户下次加载页面才拿到新值 | 一次推送，全部实例同时生效（也可能只生效一半） |
| 失败模式 | 页面白屏、功能缺失 | 实例重启失败 → 全量不可用（雪崩） |
| 开关治理 | flag 腐烂，删不掉也敢不删 | 同样问题，且有集中控制台可查引用与审计 |
| 变更回滚 | 重新发布上一版产物 | 控制台一键回到上一个配置版本（秒级） |

一个 TS 同学会特别注意到的差异：**类型安全救不了你**。Java 能把 `"30s"` 绑成 `Duration`、把 `"1000"` 绑成 `long`，但这种检查只发生在**启动绑定的那一刻**——第 7 篇 `012345` 掉前导零那类坑，在这里升级为：改错的配置能顺利发布，等下一个实例重启时才炸。所以动态刷新和重启发布是两类风险：**不重启就生效的配置，等于跳过了所有验证。**

## 4. 真实业务场景

**场景：门店中台的"半夜改超时"连环事故。**

业务背景：门店优惠券服务上挂着运营频繁调整的参数——满减门槛、每人每日领券上限、风控接口超时、活动总开关，原来全在 `application-prod.yml` 里。事故链分三段：

第一段是**流程**。运营把风控超时从 800ms 调到 200ms，开发改 yml、提 MR、等测试、走发版，前后两小时；当天活动开始，风控 P99 是 750ms，新超时还没上线。这类问题不致命，但让研发沦为"配置修改器"。

第二段是**刷新静默失效**。接了配置中心后，开发给 `RiskClient` 加上 `@RefreshScope` 就上线了。但超时值是在**构造器里传给 HttpClient 的**，而 `RiskClient` 被一个单例连接池持有——池不重建，超时值就永远是旧的。控制台显示 200ms，线上实跑 800ms，**没有任何报错**。

第三段是**炸在全量重启**。有人把超时写成 `risk.timeout: 200`（单位是秒），格式与值都合法，但类型不匹配导致启动绑定失败；配置中心按"变更即重启"推给全部 60 个实例，**一台都起不来**。服务从"超时偏慢"变成全量不可用，回滚花了十几分钟。

**用错的代价**：配置同时成了**故障源**和**排查障碍**——控制台的值和实际跑的值不一致，比一个明确的报错更耗时间。

## 5. Java 示例代码

**第一步：先分类，再决定放哪。** 四类归属：**① 环境与基础设施**（DB / Redis / MQ 地址）、**② 运行参数**（超时、阈值、限流速率）、**③ 业务规则与开关**（门槛、上限、灰度开关）、**④ 密钥**。混在一起是绝大多数问题的源头。

```yaml
# application.yml —— 只留跨环境共用 + 安全默认值，其余全部外置
store:
  promo:
    rate-limit-qps: 200          # ② 运行参数：可调，需要热更 → 配置中心
    daily-claim-limit: 3         # ③ 业务规则：运营会改 → 配置中心
  feature:
    new-coupon-rule: false       # ③ 开关：必须带 owner 和到期日注释
# ① 环境/基础设施（DB、Redis、MQ 地址）→ 由 profile + 外部注入（第 48 篇）
# ④ 密钥（DB_PASSWORD、AK/SK）→ 只走 K8s Secret / 密文配置，永不进 Git
```

**接入配置中心，并且用 `optional:` 保住启动。**

```yaml
spring:
  config:
    # optional: 配置中心不可用时用本地快照启动，别让依赖变成生死开关
    import: optional:nacos:${spring.application.name}.yaml
  cloud:
    nacos:
      server-addr: ${NACOS_ADDR:nacos.middleware.internal:8848}
      config:
        namespace: ${APP_ENV:local}     # 用昨天的 profile 值做命名空间隔离
        group: STORE_CENTER
        refresh-enabled: true           # 动态刷新总开关
```

**优先用 `@ConfigurationProperties` 而不是 `@Value` 接收热更。**

```java
/**
 * 配置项的"唯一真相"：带类型、带校验、集中声明。
 * @ConfigurationProperties Bean 在配置刷新时会被重新绑定，无需 @RefreshScope。
 */
@Component
@ConfigurationProperties(prefix = "store.risk")
@Validated                                    // 复用第 21 篇的校验能力来校验配置
@Data
public class RiskProperties {

    /** 绑定 Duration：写 200ms / 2s 都可以，杜绝"200 到底是毫秒还是秒" */
    @NotNull private Duration timeout = Duration.ofMillis(800);
    @NotNull @Positive private Integer maxConnections = 200;
    /** 缺省即关闭：新增配置项默认必须保持旧行为 */
    private boolean fastFailEnabled = false;
}
```

**热更的正确姿势：原地改可变状态，而不是重建持有连接的 Bean。**

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class RiskLimiter {

    private final Environment env;            // 真相来源：Environment 一定已是新值
    private final RateLimiter limiter;        // Guava/自研，支持 setRate 原地调整

    /**
     * 只处理"能安全热更"的配置：阈值、开关、限流速率。
     * 线程池 / 连接池 / DataSource 这类不热更，改了走受控重启。
     */
    @EventListener
    public void onChange(EnvironmentChangeEvent event) {
        String key = "store.promo.rate-limit-qps";
        if (!event.getKeys().contains(key)) return;   // 别被别人的刷新事件带跑

        // 注意：此刻 @ConfigurationProperties Bean 可能还没重绑定，直接从 Environment 读
        Integer qps = env.getProperty(key, Integer.class, 200);
        if (qps <= 0 || qps > 5000) {   // 边界守住，防手滑（第 35 篇）
            log.error("拒绝生效的限流配置 qps={}，保持原值", qps);
            return;
        }
        limiter.setRate(qps);
        log.warn("限流阈值热更新生效 keys={} qps={}", event.getKeys(), qps);  // 生效要留痕
    }
}
```

## 6. 常见坑

**坑 1：以为加了 `@RefreshScope` 就万事大吉。** 问题在于它的机制是下次访问时**重建这个 Bean**：① 值若已传给长生命周期对象（线程池、HttpClient、`static` 字段、`@PostConstruct` 算好的派生值），重建也拿不回来；② 与 `@Scheduled` 同时使用可能重复注册任务（第 44 篇）。正确做法：**热更的值只放在"每次调用都现读"的地方**；连接池类参数明确标记"需重启生效"，别伪装成动态配置。

**坑 2：缺类型和校验，错误值在重启时才炸。** 像 `risk.timeout: 200` 单位不明、`@Value("${a.b}")` 无默认值、值没有范围检查，改的时候不报错，实例下次重启全起不来。正确做法：用 `Duration` / `DataSize` 这类带单位的类型，`@ConfigurationProperties` + `@Validated` 加约束，代码里给**安全默认值**，写入前再做一次业务范围校验。

**坑 3：把配置中心当成"更方便的 yml"，什么都往里塞。** 现象：一个 namespace 下 600 个 key，一半没人知道是什么。问题：配置的隐性成本不是改，而是**读它的人要判断它还有没有用**。正确做法：每个开关登记 owner 和到期日，过期就删；命名带业务前缀，禁止 `config1` / `temp_flag`；长期规则挪进数据库表或规则引擎，配置中心只留**技术参数和开关**。

**坑 4：一次推送打全量，没有灰度与回滚预案。** 错误做法：60 个实例直接在控制台点"发布"。问题：配置错误的生效速度比人反应快，全量推等于放弃观察窗口；而且"改回去"未必等于回滚——已消费的消息、已写脏的数据不会倒退。正确做法：**先推 1 个实例观察再全量**；确认控制台保留版本历史且能一键回滚；影响数据写入的开关要配套降级路径（第 46 篇缓存、第 47 篇 MQ 的兜底）。

## 8. 面试 / 工作中常见问题

### 问题 1：哪些配置可以热更新，哪些必须重启？

参考答案：按"值有没有被复制出去"判断。每次调用都现读的值可以热更：限流阈值、开关、白名单、传给单次调用的超时。已经被构造成对象或连接的值必须重启：线程池与连接池大小、DataSource、MQ topic 与消费组、以及任何在 `@PostConstruct` 里算出的派生值。稳妥做法是给配置清单加一列"生效方式"，别让运维以为改了就是生效了。

### 问题 2：改了一个配置，线上怎么确认真的生效了？

参考答案：看三层证据。① 配置中心侧的下发记录与实例 ACK；② 应用侧刷新监听里打的日志（`keys=... newQps=...`），没有这行就是没生效；③ 一个带鉴权的 actuator 端点（`/env`、`/configprops`）看每个 key 的**当前值和来源**，这是唯一不会说谎的。最常见的失效原因是值被 `@Value` 注进了普通单例 Bean，或已被复制进 `static` 字段和池对象。

### 问题 3：配置中心挂了会怎样？你怎么设计这个依赖？

参考答案：先区分"读不到新配置"和"起不来"两种后果。① 客户端本地有快照缓存，配合 `optional:` / 关闭 fail-fast，挂掉时能用最后一次成功值启动；② 关键参数在代码里必须有默认值，不能读不到就 NPE；③ 配置中心的凭据与网络路径不要和生产业务共用同一个故障域，否则它一挂你的服务全挂。一句话：**配置中心是增强，不是启动前置条件**。

## 9. 今日小结

- 先分类再存放：**环境/密钥 → profile + 外部注入；运行参数与业务开关 → 配置中心；长期规则 → 数据库或规则引擎**。是否值得动态化只看一条：**改完希不希望不发版就生效**。
- `@RefreshScope` 不是魔法，它只是"下次访问重建 Bean"——值一旦传进池对象或 `static`，刷新就静默失效；连接池类参数老实标记为需重启。
- 配置要走和代码一样的发布流程：带单位的类型 + 校验、安全默认值、先灰度一个实例、保留版本可一键回滚。
- 每个开关都要有 owner 和到期日；僵尸配置的代价不是存储，是**下一次排障时没人敢动它**。
