# Java 学习：拦截器与过滤器

> 系列第 43 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「AOP 是什么」：昨天我们把横切逻辑做到了"方法层"——切面能拦 Bean 的 public 方法。但一个 HTTP 请求从进来到返回，在抵达 Service 方法之前还要路过两道关卡：Servlet 容器的 **Filter（过滤器）** 和 Spring MVC 的 **Interceptor（拦截器）**。今天把这三层放到一条时间线上：谁先执行、各自能拿到什么、登录鉴权 / 跨域 / traceId 分别该放哪一层。学完这篇，你在前端写的 axios 拦截器、在 Node 写的 Express 中间件，终于能在 Java 后端找到完整对应物。

## 1. 今天学什么

Filter 和 Interceptor 都是"在真正处理请求前后插一段逻辑"的机制，作用位置不同：**Filter 在 Servlet 容器层**（Tomcat 里，比 Spring 还早），**Interceptor 在 Spring MVC 层**（已知的 Controller、能拿到 HandlerMethod），**AOP 在方法层**（任意 Spring Bean 的 public 方法）。今天讲三件事：① 三者各自的定位、能拿到什么上下文、生命周期钩子；② 一条完整的请求路径时间线（Filter → preHandle → Controller → AOP → 返回 → postHandle → afterCompletion → Filter 出栈）；③ 用两个真实工程写法演示——Filter 打全局 traceId、Interceptor 做登录鉴权，并回答"鉴权到底放 Filter 还是 Interceptor"这个高频争议。

## 2. 前端工程师视角理解

**Filter ≈ Express 的 `app.use(...)` 中间件。** Node 里你写 `app.use(logger)`、`app.use(cors())`，它们在最外层、路由匹配之前就跑，能看到原始 req/res，也能直接短路返回。Java 的 Filter 就是同一个位置：只要请求进了 Tomcat，无论最终有没有匹配到 Controller，Filter 都会执行；CORS、字符编码、Gzip、traceId 这类"跟具体接口无关"的活儿都在这里做。

**Interceptor ≈ NestJS 的 Guard + Interceptor 合体。** NestJS 里 `@UseGuards(AuthGuard)` 拦在 handler 之前，能拿到 `ExecutionContext`（含当前路由、装饰的元数据），鉴权特别顺手；`Interceptor` 还能像 RxJS 的 pipe 一样包住返回值。Spring 的 HandlerInterceptor 就干这两件事：`preHandle` 相当于 Guard（返回 false 直接短路），`postHandle` / `afterCompletion` 相当于 Interceptor 的"响应前后钩子"，而且它能直接拿到"当前请求映射到哪个 Controller 的哪个方法、方法上打了什么注解"——Filter 拿不到这个信息。

**关键差异**在于**能否感知路由**。前端中间件默认在路由之前，鉴权要么硬解 URL、要么把守卫塞进每个 handler。Spring 的 Interceptor 天然是"路由后"的，可以按 `@RequireLogin` 之类的注解决定要不要拦——这跟 NestJS 用 `Reflect.getMetadata` 读装饰器是同一个思路。

## 3. 和 JavaScript / TypeScript 的对比

**签名对比一眼看懂：**

```java
// Java Filter（Servlet 规范）
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
    // before
    chain.doFilter(req, res);   // ← 类似 Express 的 next()
    // after
}
```

```js
// Express 中间件
function logger(req, res, next) {
  // before
  next();                        // ← 完全对应 chain.doFilter
  // after
}
```

结构一模一样——都是"中间函数拿到 next / chain，决定要不要往下传"。区别只有两点：① Java 是**面向对象**（实现接口 or 继承 `OncePerRequestFilter`），JS 是函数即中间件；② Java 的 `doFilter` 一个方法里 before/after 靠 `chain.doFilter` 前后代码分开写，Spring Interceptor 直接给你三个方法（preHandle / postHandle / afterCompletion），职责更明确。

**类型系统的差异**：Filter 拿到的是 `ServletRequest`，你几乎一定要 `cast` 成 `HttpServletRequest` 才能读 header、method；Spring 给了 `HttpServletRequest` 泛化的 `HandlerInterceptor`，签名直接就是 HTTP。这就是强类型语言的代价——规范层和实现层要各自留接口。

**"下一次请求会不会重新执行"的错觉**：Node 中间件对每个请求都重跑一次闭包，Java 也是——Filter / Interceptor 都是**每请求一次**。区别是 Spring 里 Filter / Interceptor 实例本身是**单例 Bean**，被所有线程共享，所以字段不能存请求级状态（写进 `ThreadLocal` 或用方法参数），这个坑和第 42 篇 AOP 切面"字段不能存状态"完全一致。

## 4. 真实业务场景

**场景：门店后台管理系统——一个请求进来，串起 traceId 与登录鉴权。**

业务背景：后台管理系统要给区域经理看门店销售报表、给运营改商品价格。出问题时（页面卡、数据不对、报错），运维必须能凭一个"追踪 ID"在网关、应用、SQL 日志里查到同一条链路；同时接口必须校验登录态、区分角色（谁能改价、谁能看数据）。

分层落位：

- **Filter 层**做 traceId：请求一进来就生成一个 UUID 放进 MDC（日志上下文），响应头里回给前端。为什么放 Filter？——**它最早执行、且对静态资源、404 也会执行**，即使请求没进 Spring 也能被追踪。
- **Interceptor 层**做登录鉴权：Token 校验、角色判断、按注解放行（比如登录接口本身要跳过）。为什么放 Interceptor 不放 Filter？——需要知道"这个 URL 对应的是 `AuthController#login` 还是 `PriceController#updatePrice`"，从而读方法上的 `@RequireRole("ADMIN")`；Filter 只看见 URL，做基于注解的鉴权非常别扭。
- **AOP 层**做操作审计（第 42 篇）：只有真正进入业务方法、需要落"谁改了什么"的才用切面。

用错的代价：把鉴权写进 Filter，遇到 `@RequireRole` 你得手写一份 URL 到角色的映射表，改一次接口要同步两处；把 traceId 写在 Interceptor，404 和静态资源的日志就丢了 traceId，排查线上图片加载 404 时一头雾水。

## 5. Java 示例代码

**Filter：给每个请求打 traceId，写进 MDC 让全链路日志都能带上。**

```java
@Component                                 // 交给 Spring，会被 Tomcat 自动注册
@Order(1)                                  // 顺序：越小越早，参考第 42 篇 @Order
public class TraceIdFilter extends OncePerRequestFilter {
    public static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = UUID.randomUUID().toString().replace("-", "");
        req.setAttribute(TRACE_ID, traceId);           // 后续 Interceptor/Controller 可复用
        res.setHeader("X-Trace-Id", traceId);          // 回给前端，用户截图带 ID 就能反查
        MDC.put(TRACE_ID, traceId);                    // ★ 写入日志上下文，此后 log 自动带
        try {
            chain.doFilter(req, res);                  // 传递给下一个 Filter/Servlet
        } finally {
            MDC.remove(TRACE_ID);                      // 必须清理——线程池复用，否则串号
        }
    }
}
```

**Interceptor：按注解做登录鉴权，未登录直接返回 401。**

```java
@Component
public class AuthInterceptor implements HandlerInterceptor {

    @Resource private LoginService loginService;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res,
                             Object handler) throws Exception {
        // 1. 只拦 Controller 方法；静态资源 handler 不是 HandlerMethod，直接放行
        if (!(handler instanceof HandlerMethod hm)) return true;

        // 2. 方法或类上有 @PublicApi → 无需登录（如 /auth/login、/captcha）
        if (hm.hasMethodAnnotation(PublicApi.class)
                || hm.getBeanType().isAnnotationPresent(PublicApi.class)) {
            return true;
        }

        // 3. 校验 token → 拿到当前登录人放进 ThreadLocal，供 Service/AOP 读取
        String token = req.getHeader("Authorization");
        LoginUser user = loginService.verify(token);
        if (user == null) {
            res.setStatus(401);
            res.setContentType("application/json;charset=UTF-8");
            res.getWriter().write("{\"code\":401,\"msg\":\"未登录\"}");
            return false;                              // ★ 短路：Controller 不再执行
        }
        UserContext.set(user);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        UserContext.clear();                           // 无论成功失败都清理，避免线程污染
    }
}
```

注册拦截器（还要配置放行 / 拦截路径）：

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {
    @Resource private AuthInterceptor authInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(authInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/auth/**", "/api/captcha");
    }
}
```

**执行顺序一览（一个请求的一生）：**

```
请求进入 Tomcat
  → Filter#1 (TraceId) 前  → Filter#2 (Cors) 前  → DispatcherServlet
      → Interceptor#1.preHandle  →  Interceptor#2.preHandle
          → Controller#method  → [AOP 环绕 → Service 方法 → @Transactional 边界]
          ← Controller 返回
      ← Interceptor#2.postHandle  ← Interceptor#1.postHandle
  → DispatcherServlet 写响应
  ← Filter#2 后  ← Filter#1 后（MDC 清理）
响应返回前端
```

## 6. 常见坑

**坑 1：在 Filter 里读 `@RequestBody`，Controller 里就再也读不到。** 错误写法：Filter 里 `req.getInputStream()` 打印请求体做参数校验。问题：Servlet 输入流**只能读一次**，读完 Controller 拿到的就是空。正确做法：包一层 `ContentCachingRequestWrapper` 或者用 `Filter` + 自定义可重复读 Request，把 body 缓存下来；一般业务不需要在 Filter 读 body，把参数校验放到 Interceptor 之后的 `@Valid` 或 AOP 里更合适。

**坑 2：`preHandle` 返回 false 忘了写响应体。** 现象：前端拿到 200 空 body，或浏览器显示白屏。问题：`return false` 只是"停止后续处理"，Servlet 不会自动帮你写 401/403 响应。正确做法：在 return false 之前显式 `res.setStatus(401); res.getWriter().write(...)`；或者抛自定义异常交给第 15 篇的全局异常处理器统一渲染。

**坑 3：把 ThreadLocal / UserContext 存了忘清理。** 现象：偶尔 A 用户看到 B 用户的数据。问题：Tomcat 用线程池复用线程，`afterCompletion` 没跑或抛异常提前结束，ThreadLocal 就残留。正确做法：**清理一定写在 `afterCompletion` 或 Filter 的 `finally` 块**里，且用 `remove()` 而不是 `set(null)`（后者仍留 key，内存会缓慢泄漏）。

**坑 4：混淆 Filter 和 Interceptor 的能力，硬在 Filter 里做鉴权。** 现象：Filter 里靠 URL 前缀判断"是不是登录接口"，遇到接口重命名/新增就漏。问题：Filter 不知道 handler、读不到方法注解。正确做法：**基于注解的鉴权放 Interceptor**，Filter 只做与业务无关的容器级横切（CORS、编码、traceId）。

**坑 5：拦截器没注册或路径 pattern 不匹配，静默失效。** 现象：本地跑没问题，线上发现鉴权没生效。问题：Interceptor 必须在 `WebMvcConfigurer#addInterceptors` 里注册（或用 `@Configuration` 手写 `MappedInterceptor`），光有 `@Component` 不会自动挂上。正确做法：启动时看日志或 debug `InterceptorRegistry`；本地用 Postman 打一次受保护接口，验证是否真的走了 `preHandle`。

## 7. 和之前知识的连接

- **第 42 篇「AOP 是什么」**：那篇讲切面只在"方法层"生效，本篇补上"HTTP 请求层"的两个兄弟——三层串起来就是 Java 后端完整的横切视图；`@Order` 控制 Filter 顺序也是那篇讲过的机制。
- **第 40 篇「事务失效场景」**：事务靠代理生效、切面靠代理织入——今天 Interceptor 的 `handler instanceof HandlerMethod` 判断，正是"请求经过 DispatcherServlet 才能拿到方法级信息"的体现，这就是为什么鉴权注解放 Interceptor 而不是 Filter 才可行。
- **第 15 篇「全局异常处理」**：Interceptor `preHandle` 里 `return false` 之前手动写 401 是临时手段，更规范的做法是抛业务异常交给 `@RestControllerAdvice` 统一渲染，避免每个拦截器重复写 JSON 输出。
- **第 8 篇「Controller / Service / Mapper 分层」**：Filter 和 Interceptor 是"进入分层之前"的关卡，AOP 是"分层内部方法级"的增强——把这三段一起看，就理解了 Spring Boot 一个请求的完整生命周期。

## 8. 面试 / 工作中常见问题

### 问题 1：Filter 和 Interceptor 有什么区别，分别在什么时候用？

参考答案：Filter 属于 Servlet 规范、由容器（Tomcat）管理，在所有请求（含静态资源、404）上执行，能拿到 `ServletRequest`，不知道 handler；Interceptor 属于 Spring MVC、由 `DispatcherServlet` 调度，只对进入 Spring MVC 的请求生效，能拿到 `HandlerMethod`（当前 Controller 方法 + 注解）。用武之地：CORS、字符编码、traceId、Gzip 用 Filter；登录鉴权、按注解放行、接口限流、日志埋点用 Interceptor。

### 问题 2：一个请求的执行顺序是怎样的？

参考答案：Filter 前 → DispatcherServlet → Interceptor#1.preHandle → Interceptor#2.preHandle → Controller → [AOP 环绕 → 事务开启 → Service 方法 → 事务提交/回滚 → AOP 后置] → 返回 → Interceptor.postHandle（逆序）→ Interceptor.afterCompletion（逆序）→ Filter 后（逆序）。任何一层的 `preHandle return false` 或 Filter 不调 `chain.doFilter` 都会短路后续，但 `afterCompletion` / Filter 的 finally 仍会执行，清理逻辑写在这里。

### 问题 3：登录鉴权到底放 Filter 还是 Interceptor，还是都能做？

参考答案：都能做，但工程上**优先 Interceptor**。理由：① 现代鉴权都是基于注解（`@PublicApi`、`@RequireRole`），Interceptor 天然能读 HandlerMethod 上的注解；② Interceptor 已经确定"这个 URL 一定映射到某个 Controller 方法"，不会误伤静态资源、actuator、健康检查；③ Filter 更早执行，适合做无差别容器级横切（CORS / traceId）。如果做网关级、跨服务的鉴权（如 Spring Cloud Gateway），或者需要拦所有资源类型（包括静态文件），才把鉴权放到 Filter 层。

## 9. 今日小结

- 后端横切三层：**Filter 管容器级、Interceptor 管 HTTP 路由级、AOP 管方法级**，位置和拿到的上下文完全不同。
- 顺序记忆点：**Filter 前 → Interceptor preHandle → Controller → AOP/事务 → 回程逆序**；`preHandle` 返回 false 会短路，但 `afterCompletion` 仍跑。
- 工程分配：traceId / CORS / 编码 → Filter；登录鉴权 / 按注解放行 → Interceptor；方法审计 / 参数日志 → AOP；事务 → @Transactional 代理。
- 前端类比锚点：Filter = Express `app.use` + `next()`；Interceptor = NestJS Guard（能读装饰器）；AOP = 方法级 Interceptor / 高阶函数包装。
- 三个必踩的坑：Filter 读 body 让 Controller 空、preHandle 拒请求忘写响应、ThreadLocal 忘在 `afterCompletion` 清理。

## 10. 明日预告

明天建议学习：`定时任务`

原因：今天我们把"被动接收 HTTP 请求 → 走完 Filter / Interceptor / AOP 一整条链"讲透了，但真实后端还有一半工作是**主动发起**——每天凌晨跑对账、每分钟同步门店库存、每 5 秒拉一次汇率。这些和"是否有用户点按钮"完全无关，靠的是**定时任务**。明天从 Spring 的 `@Scheduled` 讲起，说清 cron 表达式怎么写、单机 `@Scheduled` 为什么不能直接上生产、分布式下的重复执行问题（多实例同一分钟跑了两遍发工资），以及和今天 Interceptor 的 `preHandle` 一样——定时任务里也要自己处理 traceId、异常兜底、幂等锁。
