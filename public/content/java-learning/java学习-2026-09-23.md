# Java 学习：微服务边界与拆分

> 系列第 63 篇 · 第七阶段：分布式一致性与容错（收尾篇）
> 衔接上一篇「超时、重试与熔断」：这一阶段后半段处理的锁、消息、对账、超时、熔断，**全都是"服务被拆开之后"才存在的成本**。今天回到源头：当初为什么要拆、拆错了长什么样、以及怎么给已经拆开的系统兜底。
> **与第 55 / 26 篇的分工**：第 55 篇讲**进程内**的包与依赖方向（ArchUnit 那套）；第 26 篇讲接口的版本兼容。今天讲**进程之间**：拆分的判据、数据归属、分布式单体的识别，以及"契约"如何成为服务边界的一部分。

## 1. 今天学什么

微服务不是架构目标，而是**组织与规模的解法**。它买来的东西很明确——独立部署、独立扩缩容、故障隔离、团队自治；代价也很明确——网络不可靠、事务变最终一致、调试要跨进程、版本要跨服务兼容、运维复杂度翻倍。

今天讲四块：① **拆的判据**：什么时候才值得付上面那笔账（独立部署/扩缩容/团队/数据归属至少一条真实成立）；② **怎么切**：按业务能力与数据归属切，而不是按技术层次切；③ **分布式单体的识别**：拆了一堆服务却每次发版都一起发、共享一张库表——这是最常见的失败形态；④ **边界的兜底**：契约与防腐层、跨服务一致性策略阶梯、以及用第 61 篇的对账给边界上保险。

> 结论先行：**能用一个服务解决的问题，不要用两个。** 六个阶段以来我们学的所有分布式技巧，都是"拆"的账单。

## 2. 前端工程师视角理解

你经历过同一道选择题：**monorepo 还是多仓库？** 多仓库的收益是独立发布、各团队自治、依赖边界天然清晰；代价是跨包改动要发多个版本、依赖升级要挨个 PR、本地联调要 link 一堆包。后端拆服务是完全一样的权衡——只不过后端把"跨包引用"换成了"网络调用"，把"版本不兼容"换成了"老服务还在跑旧接口"。所以你会发现一个很熟的现象：**拆了 5 个 repo 但每次上线要同时发，那和 monorepo 相比只剩麻烦**——这就是分布式单体在前端的对应物。

第二个类比更有意思：微前端（Module Federation 那套）。社区吵了很多年的结论是——**微前端解决的主要不是技术问题，而是组织问题**（多团队要不要共享发布节奏）；技术上的复杂度（运行时隔离、依赖版本、通信）反而是代价。微服务同理：它最硬的前提是**有多个能独立负责的团队**，否则你只是把模块拆分变成了运维负担。这条判断标准能帮你在评审会上直接问一句："拆开之后，谁独立负责它？"

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 拆分的收益 | 独立发布、依赖隔离 | 独立部署与扩缩容、故障隔离、团队自治 |
| 拆分的代价 | 跨包改动、link 联调、版本漂移 | 网络不可靠、最终一致、跨进程调试、版本兼容 |
| 组织映射 | 微前端 ≈ 多团队共享发布节奏 | 康威定律：系统的结构会映射组织的沟通结构 |
| 拆错的形态 | 拆了 repo 但要一起发 | 分布式单体：一起发版、共享库表 |
| 边界表达 | package exports / 版本号 | API 契约、事件、独占数据库 |
| 兜底手段 | 单测 + e2e + 版本共存 | 契约测试 + 对账 + 灰度（第 61 篇那套） |

**最需要建立的新观念：边界的第一载体是数据库，不是代码。** 前端拆包时，边界体现在 `exports` 和依赖声明上；后端拆服务时，**只要两个服务还在读写同一张表，它们在业务上就是一个服务**——代码分开了，"边界"是假的。所以数据归属（谁写谁读、谁能改）是拆分时唯一不能含糊的东西，比接口怎么设计重要得多。

## 4. 真实业务场景

**场景：拆了 6 个服务的"门店中台"，一次改价要发 4 次版。**

业务背景：两年前团队按"技术层次"拆服务——用户服务、商品服务、库存服务、订单服务、支付服务、报表服务。听上去很合理，但业务演进暴露了问题：

- **一次"会员价"需求**要同时改用户（等级）、商品（价格）、订单（计价）、支付（实收）四个服务，且必须**同一晚上按顺序发布**：先发商品（新价格字段），再发订单（读新字段），最后发支付；漏一个就出金额错误。这直接违反了"独立部署"这个拆服务的第一收益。
- **共享库表**：库存和订单都直连 `store_stock` 表（为了"避免跨服务调用"），一个加索引的 DDL 要协调两个团队；而 `store_stock` 加了个订单侧才懂的字段，商品服务导出报表时又不敢动它。
- **同步调用成环**：订单 → 库存 → 商品 → 订单（查折扣）——一个三节点的环，任何一处抖动全站都慢（第 62 篇那种放大在这里更容易发生）。
- **联调要起 6 个服务**，新人第一周全花在环境上。

这不是微服务失败，而是**边界切错了**：按技术层次切，把同一个业务能力（定价）的数据和逻辑拆到了四个服务里，于是"变更"必然跨服务。修复方案不是拆得更细，而是**按业务能力重新画边界**：定价（价格、等级、优惠）合成一个"计价"服务、独占价格类数据；订单只持有订单数据，通过事件订阅价格变更（第 61 篇的 Outbox）；库存独占 `store_stock`，订单不再直连；把那个环拆成"订单 →（事件）→ 计价 →（事件）→ 订单"的异步闭环。

**用错的代价**：拆错的微服务不会以"服务挂了"的形式报警，它只是让**每一次业务变更都变慢、变贵、变得更危险**——团队会用加班和流程来消化它，直到某次发布顺序错了，才发现账单。

## 5. Java 示例代码

**边界的第一道防线：防腐层（ACL）——只依赖对方的 api 包，并把对方模型翻译成本地模型。**

```java
/**
 * 防腐层：库存服务的对外模型（StockApiDTO）只允许在 api 包出现（第 55 篇的 ArchUnit 规则可强制）。
 * 作用：对方改字段/换语义时，只需要改这一层转换，不会污染本地领域模型。
 */
@Component
@RequiredArgsConstructor
public class StockAcl {

    private final StockApiClient stockApiClient;   // 只认对方 api 包的契约

    /** 把对方的 DTO 翻译成本地领域对象：跨服务不共享模型，是边界最重要的一条纪律 */
    public LocalStock toLocal(StockApiDTO dto) {
        if (dto == null || dto.getAvailable() == null) {
            return LocalStock.unknown(dto == null ? null : dto.getSkuId());   // 语义不明确时显式建模
        }
        return new LocalStock(dto.getSkuId(), dto.getAvailable(), dto.getVersion());
    }
}
```

**边界的第二道防线：跨服务一致性按"代价阶梯"选，而不是默认上分布式事务。**

```java
@Service
@RequiredArgsConstructor
public class PriceChangeService {

    private final PriceMapper priceMapper;         // 价格数据只属于本服务（独占库）
    private final OutboxMapper outboxMapper;       // 第 61 篇的本地消息表

    /**
     * 阶梯第一档：单库单事务（能用就用）。
     * 第二档：同库多表事务（也在一个服务内）。
     * 第三档：跨服务最终一致——本地事务提交 + Outbox 发事件，下游按事件更新自己的读模型。
     * 第四档：分布式事务（2PC/Saga）——协调者单点、锁持有时间长，只在钱款强一致等场景慎用。
     */
    @Transactional
    public void changePrice(PriceCmd cmd) {
        priceMapper.update(cmd);                                     // 本地事务：价格变更落库
        outboxMapper.insert(OutboxMsg.of("price-changed", cmd.skuId(), cmd));   // 同事务写事件
        // 订单/支付不再同步调用本服务拿价格，而是订阅 price-changed 事件，各自维护读模型
    }
}
```

## 6. 常见坑

**坑 1：按技术层次拆服务。** 错误做法：拆成用户服务、商品服务、订单服务、报表服务——每个都对应"一类数据"，而不是"一个业务能力"。问题：任何一个业务需求都会横跨 3~5 个服务（改价要动四处），变更成本随服务数上升，独立性收益归零。正确做法：**按业务能力与数据归属切**（定价、下单、履约、结算），一个能力一个主人，数据只有它的主人能写；实在分不开的，先留在同一个服务里，用第 55 篇的包结构在进程内约束边界。

**坑 2：共享数据库，却自称微服务。** 错误做法：几个服务连同一个库、甚至同一张表，理由是"避免跨服务调用"。问题：表结构变成一个隐式契约（改列 = 全量破坏性变更，第 26 篇的问题在库层重演），DDL 需要跨团队协调，服务间通过数据事实上咬死——**这是分布式单体最典型的特征**。正确做法：**每个服务独占自己的库/表**，跨服务只能走 API 或事件；共用数据用事件同步副本（接受最终一致 + 对账），而不是两边都连同一张表。

**坑 3：因为"拆错了"就继续拆更细。** 错误做法：发现问题后引入更多服务、更细的边界，以为粒度能救回独立性。问题：服务数增长会**线性放大**前面所有代价（网络、一致性、版本、联调），而"变更跨服务"的根因通常是**边界切错**，不是粒度不够。正确做法：先做**合并**——把共享数据的服务合回去（monolith first 的思路），把契约重新画在业务能力上；只有当"独立部署/扩缩容/团队/数据归属"至少一条真实成立，才重新拆出来。

## 8. 面试 / 工作中常见问题

### 问题 1：什么时候该拆服务？

参考答案：先问四个问题，至少有一个明确为"是"才拆：**是否需要独立扩缩容**（比如报表服务吃内存，不该拖累下单）、**是否有独立团队负责**（康威定律，没人独立负责就别拆）、**是否要求独立部署节奏**（一方一天十次、一方一周一次）、**数据归属是否清晰**（这个能力的数据能不能独占）。四个都答不上来，说明现在拆只是把复杂度提前付掉；用包结构 + ArchUnit 在进程内保持整洁，等条件成立再拆。

### 问题 2：跨服务的强一致场景怎么做？

参考答案：按代价阶梯逐档试：优先把数据放到同一个服务里用单库事务解决；确实跨服务时用"本地事务 + Outbox 事件 + 下游幂等消费 + 对账"（第 61 篇）——牺牲实时一致换可靠与简单；需要业务级回滚的用 Saga（编排或协同），每一步都要有幂等与补偿动作；**2PC 之类的分布式事务尽量不用**（协调者单点、锁持有时间长，还有不可用风险）。判据是：不一致窗口能不能被业务接受，以及差异能不能被对账发现和修复。

### 问题 3：怎么判断我们拆出的是微服务还是分布式单体？

参考答案：看四个信号：① 每次发版是否需要多个服务同时上线（独立性是假的）；② 是否有服务间共享库表或直连对方数据库（数据边界不存在）；③ 服务间是否有同步调用成环（故障会整体放大）；④ 联调是否必须起全量服务（围绕"系统"而非"服务"在开发）。命中两条以上基本就是分布式单体，处理方式是按业务能力与数据归属重新画边界，必要时先合并回单体再重拆。

## 9. 今日小结

- 微服务是**组织与规模的解法**，不是架构目标：收益是独立的部署/扩缩容/团队/故障域，代价是网络、一致性、调试与版本的全套账单。
- 判据先问四个"是否独立"（扩缩容、团队、部署节奏、数据归属），一个都不成立就先别拆。
- **边界的第一载体是数据库**：共享库表的服务在业务上就是同一个服务。
- 切法按**业务能力与数据归属**，不按技术层次；切错了先合并重画边界，而不是继续拆细。
- 兜底三件套：api 包 + 防腐层（模型不跨境）、Outbox + 事件 + 对账（一致性按阶梯选）、契约与灰度（版本共存）。
