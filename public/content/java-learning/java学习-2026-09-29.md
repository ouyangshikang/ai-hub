# Java 学习：Nginx 与反向代理

> 系列第 69 篇 · 第九阶段：网关与接入层（开篇）
> 衔接上一篇「数据库连接池与连接治理」：数据架构线告一段落；从今天起看**请求进门的第一道关卡**——网关层。
> **与第 43 / 62 篇的分工**：第 43 篇讲**进程内**的过滤器与拦截器；第 62 篇讲**应用内**的超时/重试/熔断。今天讲**应用之前**那一层：TLS、静态资源、负载均衡、限流黑名单——很多事在这里做，比在每个服务里各写一遍省得多。

## 1. 今天学什么

反向代理是"**请求到达你的 Java 服务之前，先经过的那一跳**"。它解决四件事：**证书与 TLS 终止**（后端不用管 https）、**静态资源托管**（前端 build 产物直接由它发）、**负载均衡**（把请求分给多个实例）、**入口治理**（限流、黑白名单、请求大小与超时）。

为什么后端工程师必须懂它：① 大量"后端明明没问题但接口 504/413"的事故，根因在这一层；② 第 57 篇"止血四板斧"里的限流与切流，放在这一层最快；③ 前端同学最熟悉的 SPA 部署与缓存策略，也在这里配置。

一句话定位：**Nginx 不是"运维的东西"，它是后端接口的入口契约**——头部怎么传、超时多大、包体限制多少，都会变成业务行为。

## 2. 前端工程师视角理解

你**已经用过反向代理**，就是 Vite 的 `server.proxy`：

```js
// vite.config.js —— 开发时的反向代理：浏览器以为在请求同源，实际被转发到了后端
server: { proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } } }
```

Nginx 在生产环境做的正是这件事，区别只有三点：它跑在服务器上、多了 TLS 与负载均衡、**配置错了没人给你热更新提示**（所以第 5 节的头部与超时设置才那么关键）。理解了"浏览器看到的域名 ≠ 真正处理请求的服务"，Nginx 的定位就通了。

第二个熟悉的东西是 **SPA 的 history 路由**：`/order/123` 刷新就 404，因为服务器上并没有这个文件——这个问题的解法（`try_files`）也在 Nginx 里，你多半在部署文档里抄过。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Nginx（反向代理层） |
|---|---|---|
| 同类角色 | Vite dev proxy、CDN 边缘 | 生产入口：TLS + 转发 + 负载均衡 |
| 转发头部 | 浏览器自动带 `Origin`、`Referer` | 必须手动配 `X-Forwarded-For` / `Host` / `Proto` |
| 缓存策略 | HTTP 缓存头、Service Worker | `Cache-Control` 由 Nginx 按文件类型下发 |
| 入口限制 | 无（浏览器不管） | `limit_req`、`client_max_body_size`、连接数限制 |
| 路由重写 | 前端 router | `location` 前缀匹配 + `rewrite` |
| 调试方式 | DevTools Network 看请求 | `nginx -t` 验配置、access/error log 排障 |

**最需要建立的直觉：Nginx 看到的和你的服务看到的可能不是同一个请求。** 你配了 `proxy_pass`，但没配 `proxy_set_header Host $host`，后端拿到的 Host 就是 `127.0.0.1:8080`；没配 `X-Forwarded-For`，后端日志里所有客户端 IP 都是 Nginx 的地址；没配 `X-Forwarded-Proto`，后端不知道用户走的是 https，重定向就会跳回 http（第 3 篇那个"环境错配"的翻版）。**头部转发是入口层的第一条契约。**

## 4. 真实业务场景

**场景：大促当天，上传图片全部失败，订单导出偶发超时。**

业务背景：门店后台的前端资源与 API 都挂在 Nginx 后面：静态资源直接由 Nginx 发，`/api` 转发到订单服务（三个实例）与风控服务。大促当天出两个问题：

- **上传商品图片返回 413**：`client_max_body_size` 用的是默认值 **1MB**，而运营上传的高清图普遍 3~5MB。413 是 Nginx 直接返回的，**请求根本没到 Java 服务**——所以后端日志里一条记录都没有，排查时一度以为是前端问题（第 57 篇"没有日志的故障"的入口版本）；
- **导出接口偶发 504**：`proxy_read_timeout` 配的是默认 **60 秒**，而导出大数据量时要 90 秒。Nginx 到 60 秒就断开并记一条 504，同时**把连接上的后端处理也置为无效**——更糟的是运营看到失败就重试，每次重试又占住一个后端连接（第 68 篇的连接池压力）。
- 还有一个小事变成了大事故：`X-Forwarded-For` 没配，后端把"上传失败"的告警通知里的客户端 IP 全记成了 Nginx 内网地址，运营反馈"定位不到是谁"，问题排查多了半小时。

修复：`client_max_body_size` 按业务上限设置（如 10M）并**与前端上传组件的限制对齐**（否则前端以为能传、后端 413）；超时按**分层预算**设置——Nginx 的超时必须**大于**后端服务自己的总预算（第 62 篇：入口 800ms 的链路，Nginx 设 5s 留出余量），而不是反过来让 Nginx 抢先后端；再把 `X-Real-IP` / `X-Forwarded-For` / `X-Forwarded-Proto` 补齐，后端有了真实 IP 才能做风控与日志。

**用错的代价**：入口层的每个默认值（1MB、60s、无头部转发）都是**静默的**——它们不出现在你的代码里、不出现在应用日志里，只出现在 Nginx 的错误日志和用户的报错截图中。

## 5. Java 示例代码

**Nginx 侧：最小可用的生产配置（头部、超时、限流、SPA）。**

```nginx
# http 块里先定义限流区（10MB 共享内存，按客户端 IP 限速 100 请求/秒）
limit_req_zone $binary_remote_addr zone=api:10m rate=100r/s;

upstream order_service {
    least_conn;                          # 导出这类长请求多的场景，比默认轮询更均衡
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;   # 被动健康检查
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
}

server {
    listen 443 ssl;
    client_max_body_size 10m;            # ★ 默认 1m，上传功能必调，否则 413（请求进不了后端）

    location /api/ {
        proxy_pass http://order_service;
        # ★ 三条头部转发：不配的话，后端看到的 Host、客户端 IP、协议全是错的
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # ★ 超时要大于后端自己的预算（第 62 篇），否则 Nginx 会先于业务超时返回 504
        proxy_connect_timeout 3s;
        proxy_read_timeout    10s;

        limit_req zone=api burst=50 nodelay;   # 限流放这里：省掉每个服务各写一套（第 57 篇）
    }

    # SPA：hash 资源长缓存，index.html 绝不缓存
    location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; }
    location / { try_files $uri /index.html; add_header Cache-Control "no-cache"; }
}
```

**Java 侧：信任代理头，并正确取出真实客户端 IP。**

```yaml
server:
  forward-headers-strategy: framework   # Boot 会据此校正 scheme / remoteAddr（不配则 scheme 恒为 http）
```

```java
/**
 * 取真实客户端 IP：只信任可信代理链（自己的 Nginx），否则 XFF 可被伪造。
 * 第 36 篇权限校验、第 34 篇日志规范都依赖这个值。
 */
public String clientIp(HttpServletRequest request) {
    String xff = request.getHeader("X-Forwarded-For");
    if (xff == null || xff.isBlank()) {
        return request.getRemoteAddr();
    }
    // XFF 是逐跳追加的列表：第一个是原始客户端（前提是入口可信）；内部调用时最后一个是最近的代理
    String first = xff.split(",")[0].trim();
    return first.isEmpty() ? request.getRemoteAddr() : first;
}
```

## 6. 常见坑

**坑 1：转发头部不配齐。** 错误做法：只写 `proxy_pass` 就上线。问题：后端拿到的都是 Nginx 的地址与 http 协议——日志里所有客户端 IP 相同（无法风控、无法审计）、https 站点重定向跳回 http、`Referer`/`Host` 相关的业务判断全错。正确做法：**Host / X-Real-IP / X-Forwarded-For / X-Forwarded-Proto 四条一起配**，后端开 `server.forward-headers-strategy`；并记住 XFF 只在"入口可信"时才可采信，直接暴露的服务不能信它（第 36 篇的越权风险）。

**坑 2：超时与包体限制和业务脱节。** 错误做法：全用默认值（`client_max_body_size 1m`、`proxy_read_timeout 60s`）。问题：413 与 504 都**不经过 Java 代码**，应用日志里没有痕迹，排查很容易跑偏；而且 Nginx 超时小于后端预算时，会打断还在正常执行的请求，制造"后端没报错但接口失败"的诡异现象（第 62 篇的预算纪律在入口层同样适用）。正确做法：**包体限制与前端上传组件按同一数值对齐；超时按"入口预算 > 后端总预算"设置**；关键接口的长任务（导出）单独放宽 location 级别配置。

**坑 3：在 Nginx 和网关/应用层重复做同一件事。** 错误做法：Nginx 配一份限流、Gateway 再配一份、应用里还有一套重试；或者只在应用层做灰度，Nginx 又加了 ip_hash 导致流量分布失控。问题：规则叠加后互相抵消或相乘（第 62 篇"重试放大"的翻版），出问题时不知道该看哪一层。正确做法：**每类能力只在一层做主实现**——TLS、静态、包体限制、基础限流放 Nginx；鉴权、灰度、业务级限流放网关或应用（第 63 篇的边界原则）；其他层只做兜底且有注释说明。

## 7. 和之前知识的连接

- **第 62 篇「超时、重试与熔断」**：入口层是超时预算的"最外层"，Nginx 的 timeout 必须大于后端总预算，否则 504 会先于业务的优雅失败发生。
- **第 57 篇「线上问题排查流程」**：止血四板斧里的"限流"与"切流"放在 Nginx 最快；同时也解释了为什么有些故障"应用日志里什么都没有"——请求被入口层拦掉了。
- **第 26 篇「接口兼容性」**：同一 API 让多版本前端共存时，Nginx 可以按版本路由（`/v1`、`/v2` 或按 Header 灰度），是那篇"版本共存"最省事的落地层。

## 8. 面试 / 工作中常见问题

### 问题 1：Nginx 的 `proxy_read_timeout` 应该设多少？

参考答案：它必须**大于后端自己那条链路的超时预算**（第 62 篇：内层之和 + 余量），目的是让**后端优雅地返回业务错误**，而不是让 Nginx 半路掐断连接——掐断会产生"后端还在跑、用户在等失败"的浪费。例如后端入口预算 800ms，Nginx 设 5s 就够；导出这类长接口单独放在一个 location 里设 120s，不要为它把全局超时放宽。

### 问题 2：用户上传大文件报 413，你怎么排查？

参考答案：先看是谁返回的 413——如果是 `nginx/版本号` 的响应头，说明**请求根本没到 Java 服务**（应用日志搜不到是正常的，别在应用侧白找），问题在 `client_max_body_size`（默认 1m）。修的时候三处要一致：Nginx 的包体限制、Spring 的 `spring.servlet.multipart.max-file-size`（第 7 篇的 yml 配置）、以及前端上传组件的校验；只改一处会出现"前端放过、后端拒绝"或反之的割裂。

### 问题 3：后端怎么拿到用户的真实 IP？

参考答案：入口代理要配 `X-Forwarded-For`（追加式列表）与 `X-Real-IP`，Spring Boot 侧开 `server.forward-headers-strategy=framework` 让它校正 `scheme` 与远端地址；取 IP 时**按信任链解析**——只有入口是可信的（你自己的 Nginx），才能取 XFF 的**第一个** IP，否则这个头可以被客户端随便伪造，用它做风控或限流等于白送。服务直连时一律用 `getRemoteAddr()`。

## 9. 今日小结

- 反向代理是请求进门的第一跳：**TLS、静态资源、负载均衡、入口治理**都在这一层，前端最熟的 Vite `server.proxy` 就是它的开发版。
- **头部转发是入口契约**：Host / X-Real-IP / X-Forwarded-For / X-Forwarded-Proto 缺一个，后端的日志与安全判断就会错一处。
- 入口层的默认值是静默事故源：`client_max_body_size 1m`、`proxy_read_timeout 60s` 造成的 413/504 都不经过 Java 代码。
- 超时纪律是**入口 > 后端总预算**，让后端优雅失败；长任务单独放宽 location，别动全局。
- 每类能力只在一层做主实现：Nginx 管入口，网关/应用管业务，重复建设会让规则互相放大（第 62 篇）。
