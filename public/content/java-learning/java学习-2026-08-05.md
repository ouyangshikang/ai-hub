# Java 学习：BigDecimal 金额计算

> 系列第 28 篇 · 第四阶段：精度、安全与稳定性（开篇）  
> 昨天用命名约定给第三阶段收了口，示例里的金额字段 `monthGmv` 当时的类型就是 `BigDecimal`——为什么金额不直接写成 `double`？因为 Java 的 `double` 算钱会丢精度，这正是你在 JavaScript 里踩过的 `0.1 + 0.2 !== 0.3` 那个坑。今天开始进入第四阶段，第一站就看 Java 后端怎么用 BigDecimal 从根上解决金额精度问题。

## 1. 今天学什么

Java 的 `double` 和 JS 的 `number` 一样，是 IEEE 754 双精度浮点数，用二进制表示十进制小数时天然有误差：`0.1` 在二进制里是无限循环小数，存进去就已经是近似值了。用这种类型做金额计算，误差会随着加减乘除不断累积，最后出现"订单总额和明细加起来差一分钱"这种财务对不平的事故。

`BigDecimal` 是 Java 标准库提供的任意精度十进制数类型。它内部不存浮点近似值，而是把一个数拆成"整数数值 × 10 的负 scale 次方"：`123.45` 存成整数 `12345` 加上 scale=2。这样 `0.1` 就是精确的 `1 × 10⁻¹`，加减乘除全程十进制运算，不存在二进制转换误差。

凡是和钱有关的字段——价格、金额、折扣、成本、报表汇总——在 Java 后端几乎是无条件的规矩：**类型必须是 BigDecimal**。这不是最佳实践级别的建议，而是事故换来的底线。

## 2. 前端工程师视角理解

这个坑你在前端太熟悉了。打开浏览器控制台敲 `0.1 + 0.2`，得到 `0.30000000000000004`；`0.3 - 0.1` 得到 `0.19999999999999998`。前端社区的应对方案你大概率也用过：要么把金额全部转成"分"用整数算，展示时再除以 100；要么引入 `big.js`、`decimal.js`、`currency.js` 这类库。

Java 的处境和你完全一样，区别是：JS 的 `number` 是语言里唯一的数字类型，没有内置替代品，只能靠约定（转分）或第三方库；而 Java 把"精确十进制数"做成了标准库的一等公民 `BigDecimal`，金额场景直接用官方方案，不需要任何第三方依赖。可以把它理解为：**BigDecimal 就是 JDK 自带的 decimal.js，而且是银行、支付、财务系统的行业标配**。

还有一个思维差异要适应：JS 里数字是原始类型，直接 `a + b`；BigDecimal 是对象，不能写 `+`，要调方法 `a.add(b)`。第一次看会觉得啰嗦，但它带来一个前端熟悉的特性——不可变性。BigDecimal 和 JS 的字符串一样，每次运算都返回新对象、原对象不变，这对并发安全很重要（第四阶段后面会讲到线程问题）。

## 3. 和 JavaScript / TypeScript 的对比

**类型地位不同。** JS/TS 里 `number` 一把梭，TypeScript 的类型系统也分不出"金额"和"普通数字"，只能靠命名约定（`priceInCents`）提醒同事。Java 里金额字段写 `BigDecimal` 本身就是一种类型表达——看到字段是 BigDecimal，就知道这是钱，不能随便转 double。TS 里最接近的做法是 branded type（`type Money = number & { __brand: 'Money' }`），但那只是编译期幻觉，运行时还是浮点数；BigDecimal 是运行时真的精确。

**API 风格不同。** JS 是运算符风格 `price * quantity`，BigDecimal 是方法风格 `price.multiply(BigDecimal.valueOf(quantity))`。另外注意 JS 的 `toFixed(2)` 返回字符串、且四舍五入行为在不同引擎有细微差异；BigDecimal 的 `setScale(2, RoundingMode.HALF_UP)` 返回精确的数，舍入模式要显式声明（HALF_UP 是四舍五入，HALF_EVEN 是银行家舍入，DOWN 是截断），不存在"默认帮你猜"。

**JS 独有的大数坑，Java 这样对应。** JS 的 `Number.MAX_SAFE_INTEGER`（2⁵³-1）导致大订单号、雪花 ID 传给前端会丢精度，常见解法是后端序列化成字符串。金额虽然一般超不过这个范围，但习惯上很多团队也把 BigDecimal 序列化成字符串输出——既防精度问题，也避免前端拿到 number 后再做浮点运算把误差引回前端。这个点在第 5 节代码里会看到。

## 4. 真实业务场景

**场景：门店订单系统，财务月底对账发现总额对不上。**

业务背景：一笔订单包含多个商品，订单总额 = Σ(单价 × 数量)，再扣减优惠券。数据库里价格字段是 `DECIMAL(10,2)`，接口返回给前端展示。

问题代码长这样：

```java
// 有同事图省事，中间计算用了 double
double unitPrice = 19.9;
double lineAmount = unitPrice * 3;   // 59.699999999999996
double total = lineAmount - 10.0;    // 误差继续传播
```

单笔订单的误差小到看不出来，但门店一天几千单，财务做月度汇总时把每笔订单金额加起来，和订单明细逐行加起来的结果出现了偏差——有时多几分、有时少几分。对账系统直接报警，排查了一天最后定位到一个 `double` 中间变量。更恶劣的场景是优惠券分摊：一张 10 元券分摊到 3 件商品，`10 / 3 = 3.333...` 除不尽，用 double 处理会各有各的舍入，三件商品分摊额加起来可能等于 9.99 或 10.01，又是对不平。

用错类型的代价不是"页面显示难看"，而是**财务数据不可信**，这类问题往往是月底才爆发，回溯修复成本极高。

## 5. Java 示例代码

```java
// 订单金额计算服务：全程 BigDecimal，不出现任何 double
@Service
public class OrderAmountService {

    public BigDecimal calcPayable(List<OrderItem> items, BigDecimal coupon) {
        BigDecimal subtotal = BigDecimal.ZERO; // 常量起步，别用 new BigDecimal(0)
        for (OrderItem item : items) {
            // 单价 × 数量：保留 2 位小数，HALF_UP = 四舍五入
            BigDecimal line = item.getPrice()
                    .multiply(BigDecimal.valueOf(item.getQuantity()))
                    .setScale(2, RoundingMode.HALF_UP);
            subtotal = subtotal.add(line); // 不可变对象：必须接收返回值
        }
        BigDecimal payable = subtotal.subtract(coupon);
        // 金额兜底：优惠券超额时不能出现负数
        return payable.compareTo(BigDecimal.ZERO) < 0 ? BigDecimal.ZERO : payable;
    }

    // 优惠券分摊：10 元券分给 3 件商品 → 3.33 + 3.33 + 3.34，最后一件兜底余数
    public List<BigDecimal> splitCoupon(BigDecimal coupon, int itemCount) {
        BigDecimal share = coupon.divide(BigDecimal.valueOf(itemCount), 2, RoundingMode.DOWN);
        List<BigDecimal> result = new ArrayList<>();
        BigDecimal allocated = BigDecimal.ZERO;
        for (int i = 0; i < itemCount - 1; i++) {
            result.add(share);
            allocated = allocated.add(share);
        }
        result.add(coupon.subtract(allocated)); // 余数全给最后一件，保证总和精确等于券额
        return result;
    }
}
```

```java

```

## 6. 常见坑

**坑 1：用 `new BigDecimal(double)` 创建。** 错误写法：`new BigDecimal(0.1)`。问题：构造的瞬间就把 double 的二进制误差带进来了，后面再精确也没用。正确做法：字符串构造 `new BigDecimal("0.1")` 或 `BigDecimal.valueOf(0.1)`；数据库读出来的字段本身就是 BigDecimal，不需要手工转。

**坑 2：`divide` 不指定精度和舍入模式。** 错误写法：`a.divide(b)`。问题：遇到除不尽（如 10 ÷ 3）直接抛 `ArithmeticException`，线上报错。正确做法：永远写全三个参数 `a.divide(b, 2, RoundingMode.HALF_UP)`。

**坑 3：用 `equals` 比较金额。** 错误写法：`a.equals(b)` 判断两笔金额是否相等。问题：equals 会比较 scale，`1.0` 和 `1.00` 数值相等但判为不等。正确做法：数值比较一律用 `a.compareTo(b) == 0`。

**坑 4：链式运算不接收返回值。** 错误写法：单独一行 `total.add(fee);` 然后以为 total 变了。问题：BigDecimal 不可变，add 返回新对象，原对象纹丝不动。正确做法：`total = total.add(fee);`——和 JS 里 `str.replace()` 不改变原字符串是一个道理。

**坑 5：BigDecimal 转成字符串用了 `toString`。** 问题：toString 可能输出科学计数法（如 `1E+2`），拼 SQL、写文件、给老系统对接时全乱套。正确做法：展示和传输用 `toPlainString()`。

## 7. 和之前知识的连接

- **第 27 篇「前后端字段命名约定」**：昨天示例里的 `monthGmv` 字段类型就是 BigDecimal。今天补上了原因：报表金额要参与求和与比较，用 double 会累计误差；而昨天讲的 JSON 出口序列化，正好和今天的 `@JsonFormat` 字符串输出衔接——命名统一 + 类型安全，接口契约才完整。
- **第 10 篇「DTO / VO / Entity 的区别」**：金额字段在三层之间流转时类型要保持一致——Entity（对应数据库 DECIMAL 列）、DTO（接收前端传入的价格）、VO（输出给前端展示）全部用 BigDecimal，任何一层偷偷换成 double，精度链就断了。
- **第 22 篇「统一返回结构」**：金额字段是装在 `Result<T>` 的 data 里返回的，外层信封冻结、内层字段用 BigDecimal + 字符串序列化，前端解析时不会因为 `Result` 结构变化而踩数字精度的坑。

## 8. 面试 / 工作中常见问题

### 问题 1：为什么金额不能用 double？BigDecimal 内部是怎么存的？

参考答案：double 是二进制浮点数，0.1 这类十进制小数在二进制里是无限循环小数，存储时就已失真，多次运算误差累积，导致财务对账不平。BigDecimal 内部用两部分表示一个数：unscaledValue（一个任意精度的 BigInteger 整数）和 scale（小数点位数），即 `unscaledValue × 10^(-scale)`，所以 `123.45` 就是 `12345 × 10⁻²`，全程十进制精确表示。

### 问题 2：BigDecimal 的 equals 和 compareTo 有什么区别？业务里怎么比大小？

参考答案：equals 同时比较数值和精度（scale），`new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 返回 false；compareTo 只比较数值大小，返回 -1/0/1，上面两个值比较结果为相等。业务里判断金额相等、比较大小、判断是否为负，一律用 compareTo；equals 只在放入 HashMap/HashSet 这类需要精确键匹配的场景才需要留意。

### 问题 3：优惠券分摊除不尽怎么办？怎么保证分摊后总和等于券额？

参考答案：分摊不能简单地每份都四舍五入，否则各份加起来可能多一分或少一分。标准做法是"末位兜底"：前 n-1 份用 `divide(n, 2, RoundingMode.DOWN)` 向下取整，最后一份用"总额减去已分摊之和"得出，数学上保证所有份额相加精确等于原金额。同理，任何"一笔钱拆多份"的场景（分账、退款拆分）都要有兜底项，不能依赖舍入凑整。

## 9. 今日小结

- Java 的 double 和 JS 的 number 一样是二进制浮点数，算钱必有误差；金额字段一律用 BigDecimal，这是事故换来的底线。
- BigDecimal 内部是"整数 × 10 的负幂"，十进制精确表示；创建只用字符串构造或 valueOf，禁止 `new BigDecimal(double)`。
- 运算四件套：`add / subtract / multiply / divide`；divide 必须带精度和 RoundingMode；对象不可变，必须接收返回值。
- 比较金额用 compareTo，不用 equals；转字符串用 toPlainString，不用 toString。
- 给前端的金额字段建议 `@JsonFormat` 序列化成字符串，把精度问题挡在后端，别引到 JS 的 number 里。
