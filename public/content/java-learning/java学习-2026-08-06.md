# Java 学习：日期时间处理

> 系列第 29 篇 · 第四阶段：精度、安全与稳定性
> 昨天解决了"钱算不准"，今天解决"时间算不对"。金额和日期是订单、报表系统里出场率最高的两种数据类型，也是后端最容易出线上事故的两类字段。Java 的老 `Date` / `Calendar` API 坑比 `double` 还多，好在 Java 8 的 `java.time` 做了一次彻底重设计，思路和昨天的 BigDecimal 一脉相承：不可变、显式、用类型表达语义。

## 1. 今天学什么

Java 早期的 `Date` 和 `Calendar` 是上世纪 90 年代的设计：对象可变（随便一个 `setMonth` 就改掉原对象）、线程不安全、月份从 0 开始、`SimpleDateFormat` 多线程共用会解析出离谱的日期。这些问题在并发服务器上不是理论风险，是真实事故来源。

Java 8 引入了 `java.time` 包（出自 Joda-Time 作者之手）：`LocalDate` 表示纯日期、`LocalDateTime` 表示日期加时间、`Instant` 表示 UTC 时间线上的一个瞬间、`ZonedDateTime` 表示带时区的时间。它们全部不可变、线程安全，且类型本身就携带语义——看到方法参数是 `LocalDate`，就知道这里只关心"哪一天"，不关心几点几分。

业务里日期无处不在：订单创建时间、报表统计区间、会员到期日、优惠券有效期。日期算错，轻则报表数据偏移一天，重则结算周期错乱。

## 2. 前端工程师视角理解

JS 的 `new Date()` 你肯定踩过坑：月份从 0 开始（`new Date(2026, 7, 6)` 是 8 月 6 日）、对象可变（`setMonth` 直接改原对象）、字符串解析行为各浏览器不一致。所以前端世界才有 moment.js，后来又换成更轻的 day.js。

Java 的处境几乎一样——`Date` / `Calendar` 就是同一时代的产物，月份同样从 0 开始，还额外附赠线程安全问题。Java 的解法不是引第三方库，而是 Java 8 把 `java.time` 做进标准库。可以这样对应：`java.time` ≈ day.js 开了 immutable 插件 + timezone 插件，但是官方标配、零依赖。

还有个思维差异：JS 里 `Date` 一个类型打天下，"日期""时间""时刻"全混在一起；Java 把它们拆成多个类型，让编译器帮你把关——接口只统计"天"就传 `LocalDate`，谁也别想偷偷塞个时间进来。这和昨天 BigDecimal 用类型表达"这是钱"是同一个设计哲学。

## 3. 和 JavaScript / TypeScript 的对比

**月份起点不同，跨端要警惕。** JS 的 `getMonth()` 返回 0-11；Java 的 `LocalDate.getMonthValue()` 返回 1-12。前端同事手写 `month + 1` 拼日期的习惯，切到 Java 后容易反向多减一次，评审代码时重点盯这类转换。

**类型粒度不同。** JS 只有一个 `Date`，想表达"纯日期"只能靠约定；Java 用类型区分：`LocalDate`（哪一天）、`LocalDateTime`(哪天几点，不带时区)、`Instant`（UTC 时刻）、`ZonedDateTime`（带时区的时刻）。TS 的类型系统也分不出来，通常只能靠命名（`xxxUtcMs`、`xxxLocalDate`）提醒，Java 是编译期强约束。

**格式化有同名不同义的坑。** JS 用 `day().format('YYYY-MM-DD')`，Java 用 `DateTimeFormatter.ofPattern("yyyy-MM-dd")`。注意 Java 里 `MM` 是月、`mm` 是分钟；更隐蔽的是大写 `YYYY` 在 Java 里表示"基于周的年份"，元旦前后几天会格式化出错误的年份——day.js 里 `YYYY` 没有这个问题，这是前端转 Java 的高频翻车点，业务代码一律小写 `yyyy`。

**可变性相反。** JS 的 `Date` 可变（`d.setDate(d.getDate() + 1)` 改原对象）；`java.time` 全部不可变，`localDate.plusDays(1)` 返回新对象、原对象不动，必须接收返回值——和昨天 BigDecimal 的 `add` 一个道理，目的都是并发安全。

## 4. 真实业务场景

**场景：门店运营报表，查询"近 7 天每日 GMV 趋势"。**

业务背景：运营后台要画一张折线图，接口接收前端传来的起止日期（`yyyy-MM-dd`），后端换算成时间范围去查订单表，按天聚合 GMV。

最容易写错的地方是"某一天的范围"怎么表示。错误写法是拼字符串 `startDate + " 00:00:00"` 和 `endDate + " 23:59:59"`，再用 `<=` 查询。问题有两个：第一，数据库时间字段如果带毫秒（`DATETIME(3)`），23:59:59.001 到 23:59:59.999 之间的订单会被漏掉，报表 GMV 莫名比实际少一截，运营对不上数；第二，字符串拼时间绕开了类型系统，格式写错编译期毫无提示。

正确思路是左闭右开区间：`>= 当天 00:00:00` 且 `< 次日 00:00:00`，数学上无缝衔接，不漏数据也不重复。

## 5. Java 示例代码

```java
// Controller：Spring 把 "2026-08-01" 自动转成 LocalDate，类型即契约
@GetMapping("/report/gmv-trend")
public Result<List<DailyGmvVO>> gmvTrend(
        @RequestParam @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate startDate,
        @RequestParam @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate endDate) {
    return Result.ok(reportService.gmvTrend(startDate, endDate));
}
```

```java
// Service：把"天"换算成左闭右开的时间区间
public List<DailyGmvVO> gmvTrend(LocalDate startDate, LocalDate endDate) {
    LocalDateTime begin = startDate.atStartOfDay();               // 2026-08-01T00:00:00
    LocalDateTime exclusiveEnd = endDate.plusDays(1).atStartOfDay(); // 结束日 +1 天的 0 点
    return orderMapper.sumGmvGroupByDay(begin, exclusiveEnd);
}
```

```xml
<!-- Mapper XML：created_time 是 DATETIME 类型，直接和 LocalDateTime 比较 -->
<select id="sumGmvGroupByDay" resultType="DailyGmvVO">
    SELECT DATE(created_time) AS statDate,
           SUM(total_amount)  AS gmv
    FROM orders
    WHERE created_time &gt;= #{begin}
      AND created_time &lt; #{exclusiveEnd}
    GROUP BY DATE(created_time)
    ORDER BY statDate
</select>
```

```java
// VO：日期和金额的出口格式都要显式约定
public class DailyGmvVO {
    @JsonFormat(pattern = "yyyy-MM-dd") // 明确告诉前端格式，别让它猜
    private LocalDate statDate;

    private BigDecimal gmv; // 金额沿用昨天学的 BigDecimal
}
```

## 6. 常见坑

**坑 1：老代码里继续用 `new Date()` + `SimpleDateFormat`。** 错误理解：以为"能跑就行"。问题：`SimpleDateFormat` 内部用共享的 `Calendar` 做解析，多线程共用同一个实例会抛异常或者解析出错日期，且极难复现。正确做法：一律用 `java.time` + `DateTimeFormatter`（线程安全、不可变）；接手老代码时把这类静态 `SimpleDateFormat` 列为优先整改项。

**坑 2：用 `23:59:59` 表示一天的结束。** 错误写法：`created_time <= '2026-08-06 23:59:59'`。问题：带毫秒的数据会被漏掉，且不同库对秒以下精度的处理不一致。正确做法：左闭右开，`< 次日 00:00:00`，这也是第 4 节报表场景的标准解法。

**坑 3：格式化 pattern 用错大小写。** 错误写法：`YYYY-MM-dd` 或 `yyyy-MM-dd HH:MM`。问题：`YYYY` 是"基于周的年"，跨年那一周会输出错误年份；`MM` 写在时间位会把月份当分钟。正确做法：日期用 `yyyy-MM-dd`，时间用 `HH:mm:ss`，形成肌肉记忆。

**坑 4：LocalDateTime 和 Instant 混用导致时区偏移。** 错误理解：以为 `LocalDateTime` 是"当前时间"。问题：它不带时区信息，如果服务器系统时区是 UTC 而业务按北京时间算，所有"今天"都会偏 8 小时，凌晨后下单的数据归错日期。正确做法：部署时统一服务器与数据库时区（如 Asia/Shanghai）；表示"时刻"用 `Instant`，表示"业务上的某一天"用 `LocalDate`，跨系统传输用带时区的 ISO 格式。

**坑 5：前后端日期传输没约定格式。** 错误写法：前端随手 `date.toString()` 或后端随便 parse。问题：`new Date().toString()` 的输出格式又长又依赖浏览器本地化，后端解析极易失败。正确做法：接口契约固定为 `yyyy-MM-dd`（日期）或 ISO 8601 / 毫秒时间戳（时刻），两端各用一个统一的工具函数收口。

## 8. 面试 / 工作中常见问题

### 问题 1：SimpleDateFormat 为什么线程不安全？线上项目应该用什么替代？

参考答案：`SimpleDateFormat` 解析日期时依赖内部共享的 `Calendar` 实例做中间计算，多线程并发调用 parse/format 会互相覆盖中间状态，导致抛 NumberFormatException 或得到错误日期。线上应使用 Java 8 的 `DateTimeFormatter`，它不可变、线程安全，可作为 static 常量共享；日期类型相应换成 `LocalDate` / `LocalDateTime`。

### 问题 2：LocalDateTime 和 Instant 有什么区别？数据库时间字段怎么选？

参考答案：`LocalDateTime` 是"墙上的日历时间"，不带时区，`2026-08-06T10:00` 在全球任何地方读出来都是这个字面值；`Instant` 是 UTC 时间线上的一个绝对时刻，与时区无关。业务时间（订单创建时间、报表统计）如果公司只在一个时区运营，数据库存 `DATETIME` + 应用层用 `LocalDateTime`、统一服务器时区即可；涉及跨时区（海外业务、多地域部署）则应存 UTC（`TIMESTAMP` / `Instant`），展示时再转目标时区。

### 问题 3：查询"某一天的数据"，为什么推荐左闭右开区间？

参考答案：用 `>= 当天 00:00` 且 `< 次日 00:00` 有三个方面的好处：一是不漏数据，`<= 23:59:59` 会丢掉秒以下的精度（毫秒、微秒）；二是区间无缝拼接，连续多天统计时相邻区间不重叠不空缺；三是与数据库索引友好，范围查询可以直接走 created_time 上的索引，配合第 18 篇讲的索引知识效率更高。

## 9. 今日小结

- Java 老 Date/Calendar 可变、线程不安全、月份从 0 开始；Java 8 的 java.time 全面替代：LocalDate（日期）、LocalDateTime（日期时间）、Instant（UTC 时刻）。
- java.time 与 BigDecimal 同宗：不可变对象，`plusDays(1)` 必须接收返回值。
- 查"某一天的数据"一律左闭右开：`>= 当天 0 点 AND < 次日 0 点`，不用 `23:59:59`。
- 格式化记住：`yyyy-MM-dd HH:mm:ss`，大写 YYYY 和大写 MM 是高频翻车点。
- 给前端的日期字段要用 `@JsonFormat` 显式约定格式，接口契约里日期和金额一样不能含糊。
