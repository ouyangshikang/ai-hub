# Java 学习：环境区分

> 系列第 48 篇 · 第六阶段：工程化
> 衔接上一篇「消息队列基础」：第五阶段收官后进入工程化，主题从"功能怎么写对"转向"项目怎么稳定上线"。而 MQ 的 name-server、Redis 地址、消费组开关恰好最先撞上环境问题。
> **与第 7 篇的分工**：第 7 篇讲的是 profile **语法**（`application-dev.yml` 怎么建、`${DB_PASSWORD}` 怎么写）；今天讲**工程实践**——环境该隔离什么、一个 jar 如何跑遍所有环境、profile 的叠加优先级、以及怎么从机制上防止"测试环境连了生产库"。

## 1. 今天学什么

环境区分解决一件事：**同一份代码，在不同地方跑出不同行为，且绝不越界。** 它的重要性不在开发期，而在事故期——绝大多数"删了生产数据""给真实用户发了券"的故障，根因都是环境串了。今天讲四点：① 一个成熟项目需要哪几套环境、各自隔离什么；② profile 的**激活与叠加优先级**；③ 为什么必须"一次构建，到处运行"，而不是为 prod 单独打包；④ 怎么用代码把环境错配变成**启动失败**而不是线上事故。

## 2. 前端工程师视角理解

**你被这个坑埋过，只是换了个名字。** Vite 里 `import.meta.env.VITE_API_BASE` 是**构建时**替换的——值被烧进 JS 产物里。于是 CI 上 build 出一份 dist，想部署到预发就得改环境变量重新 build，一份二进制对应一个环境。后端也犯过同样的错，而后端的解法更彻底：**构建产物完全不含环境信息，环境在启动时才注入**。同一个 `app.jar` 可以在本地、测试、生产跑，区别只是启动时给了哪个 profile。

这就是 12-Factor 里的"构建一次、部署多次"，价值很实际：**你没法验证一个"生产专用的包"在生产之外会怎么表现**，而回滚时你需要的恰恰是"那个我验证过的包"。

第二个前端锚点是 **`.env`**。你知道 `.env.local` 不能提交、`.env.production` 里的密钥会随产物发给所有用户——后端风险更高一档：jar 里的配置是**全服共享**的，生产库密码泄漏等于直接可连。所以环境区分的核心不是"少写几个 if"，而是**权限与数据的边界**。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端（Vite / Next.js） | Spring Boot |
|---|---|---|
| 注入时机 | `import.meta.env` **构建时**内联 | `${...}` / 环境变量 **启动时**解析 |
| 产物与环境 | 每个环境一份构建产物（易失控） | 一个 jar 跑所有环境（推荐） |
| 环境标识 | `NODE_ENV` 单一维度 | `spring.profiles.active`，可**多值叠加** |
| 条件代码 | `if (import.meta.env.DEV)` | `@Profile("prod")` 决定 Bean 是否被创建 |
| 配置优先级 | 只有文件级覆盖 | 命令行 > 外置配置 > profile 文件 > 主文件 |

**最需要注意的是"叠加"。** 前端环境变量基本是"读哪个文件"的二选一；Spring 的 profile 可以**同时激活多个并按声明顺序覆盖**，后声明的覆盖先声明的。再配合 `spring.profiles.group`（一个 profile 展开成一组），你就能表达"prod = 云上基础设施 + 生产密钥 + 关闭 mock"这种组合，而不是塞进一个巨型文件。

覆盖链也是排查现场问题的第一手线索：配置来源包括 jar 内 `application.yml`、jar 同级 `config/`、环境变量、启动参数、profile 文件，谁最终生效别靠猜——**看启动日志的 `The following profiles are active`，或直接查 actuator 的 `/actuator/configprops`**（该端点必须鉴权，否则等于公开生产配置）。

还有一个观念差异：前端 `if (import.meta.env.DEV)` 是常态，后端把环境判断写进业务分支是**坏味道**。因为环境差异通常是"某组件在本地不该启动"，而不是"这段逻辑在本地要换算法"——前者该用 `@Profile` 让 Bean 压根不存在，后者往往说明你把配置值写成了代码常量。

## 4. 真实业务场景

**场景：门店中台一次"环境串线"事故复盘。**

业务背景：门店系统有 dev（开发自测）、test（测试团队）、staging（预发，连生产同款中间件、只读生产数据副本）、prod 四套环境，后端服务 12 个。某次排查问题，开发在本地 IDE 直接把 profile 从 `dev` 改成 `prod` 起来调试——因为"prod 配置最全"。

后果连锁：本地进程注册进了生产 MQ 消费组，抢走了生产订单消息却在本地事务里失败；本地起的定时任务（第 44 篇）在生产库上跑了一遍对账；`localhost:8080` 还被网关注册进了生产服务列表。三个问题同时发生，排查花了四小时。

这里暴露的不是"某人手滑"，而是**缺少机制约束**：环境标识靠手改文件、没有启动自检、本地能连生产网络、定时任务和消费者不区分环境。**用错的代价**从"数据不对"升级成"生产链路被本地进程污染"，这正是环境区分要消灭的那一类事故。

## 5. Java 示例代码

**主配置：默认本地，环境由部署注入，永不手改文件。**

```yaml
# application.yml —— 只放跨环境共用配置 + 一个安全的默认值
spring:
  application:
    name: store-center
  profiles:
    active: ${APP_ENV:local}        # 部署平台注入 APP_ENV；本地不注入就是 local，安全
    group:
      prod: cloud,prod-secret       # prod 展开为 prod + cloud + prod-secret，按序叠加
      staging: cloud,staging-mock   # 预发复用云上配置，再叠加 mock 层
  datasource:
    url: ${DB_URL}                  # 地址与凭据一律外部注入，不写进文件
    password: ${DB_PASSWORD}
```

**让"本地不该跑的东西"压根不被创建，而不是在代码里 if。**

```java
/**
 * 只在 prod / staging 注册消费者。
 * 本地和测试环境这个 Bean 不存在 → 不可能抢走生产消息（第 47 篇的手动 ack 才有意义）。
 */
@Component
@Profile({"prod", "staging"})
public class OrderPaidConsumer { /* ... */ }

/** 定时任务同理：开发机不该跑对账（第 44 篇讲过它天然全局生效） */
@Component
@Profile("!local")
public class StoreDailyJob { /* ... */ }
```

**把环境错配变成启动失败，而不是线上事故。**

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class ProfileGuard implements ApplicationRunner {

    private final Environment env;

    /** 启动自检：非 prod profile 却连着生产库，直接拒绝启动 */
    @Override
    public void run(ApplicationArguments args) {
        Set<String> profiles = Set.of(env.getActiveProfiles());
        String jdbcUrl = env.getProperty("spring.datasource.url", "");
        boolean hitsProdDb = jdbcUrl.contains("prod-db.internal");   // 生产库主机白名单

        if (hitsProdDb && !profiles.contains("prod")) {
            throw new IllegalStateException("环境错配：非 prod profile 连接了生产库，profiles=" + profiles);
        }
        log.info("启动环境 profiles={} jdbcUrl={}", profiles, jdbcUrl);  // 排障先看这一行
    }
}
```

## 6. 常见坑

**坑 1：把 profile 名当业务分支条件写进代码。** 错误写法：`if (isProd()) { 走真实短信 } else { 只打日志 }`。问题：环境判断散进业务方法后，新环境（比如灰度）一加就要改代码，而且这类分支永远没人给它写测试。正确做法：**面向能力编程**——定义 `SmsSender` 接口，`@Profile` 或 `@ConditionalOnProperty` 决定注入哪个实现，业务代码只看接口。

**坑 2：为不同环境打不同的包。** 错误做法：CI 里 `npm build --mode=prod` 式的"生产专用 jar"。问题：生产包只在生产跑过，你无法在预发验证它；回滚时拿不到"当初那个被验证过的产物"。正确做法：**一个产物 + 启动参数区分环境**。真要区分，只区分到"打包时不含任何环境值"这一层。

**坑 3：只有配置区分了环境，中间件没区分。** 现象：测试环境的定时任务往生产 MQ 发消息、往生产库里写测试门店。问题：只换 DB 地址，Redis / MQ topic / 第三方网关还是共享的。正确做法：**同一环境的所有依赖整体切换**——MQ 用 topic 前缀或独立 vhost，Redis 用独立实例（别只换 db 编号），支付网关必须走沙箱；网络层再加一道访问控制，让本地根本连不上生产。

**坑 4：敏感信息进 Git 或进镜像。** 错误做法：`Dockerfile` 里 `ENV DB_PASSWORD=xxx`，或想着"我删掉就好了"。问题：镜像 layer 和 Git 历史都留着，任何能拉镜像/读仓库的人都能拿到。正确做法：密钥只走部署平台注入（K8s Secret / 配置中心），仓库里只放**变量名**；一旦泄漏，无论有没有删干净，都必须立即**轮换**密钥。

## 7. 和之前知识的连接

- **第 7 篇「application.yml 配置」**：那篇的语法是今天的地基；那篇的坑 4（生产密码写进配置文件）今天扩展成了"泄漏面与轮换"，坑 3（profile 不生效）今天升级为"多 profile 叠加优先级"。
- **第 44 篇「定时任务」**：`@Scheduled` 一旦注册就在**每个实例**上生效，所以本地、测试、生产都会跑——定时任务必须按环境关掉，这是那篇"多副本"问题在环境维度的复现。
- **第 47 篇「消息队列基础」**：消费组是跨进程共享的，环境混用等于把本地调试进程接进生产消费组，直接抢走真实消息。

## 8. 面试 / 工作中常见问题

### 问题 1：一个请求进来，你怎么确认它跑在哪个环境、配置生效的是哪一份？

参考答案：三层。① 看启动日志的 `The following profiles are active`，它决定加载哪些 profile 文件；② 查 actuator 的 `/actuator/env` 或 `/configprops`（生产必须鉴权并限制来源，否则等于公开配置），能看到每个属性的**最终值和来源**，这是覆盖链最直接的证据；③ 关键 Bean 初始化时把它读到的配置值打进日志——真实排障里最常用的恰恰是这条最朴素的办法。

### 问题 2：`@Profile` 和 `@ConditionalOnProperty` 该用哪个？

参考答案：语义不同。`@Profile` 表达"这个组件只属于某些环境"，粗粒度、和部署环境绑死；`@ConditionalOnProperty` 表达"某个能力开关打开才注册"，细粒度、可与环境解耦。工程上更推荐后者做能力开关：配置名描述**行为**（`feature.sms.enabled`）而非描述**环境**，这样新增环境不用碰代码。两者常配合：properties 给默认值，profile 文件按环境覆盖。

### 问题 3：本地想调试生产问题，怎么做才安全？

参考答案：原则是**让本地永远够不到生产**。① 用与生产同构的 staging（同款中间件 + 脱敏数据副本），而不是手改 profile 连生产；② 生产只读从库供查询，账号无写权限；③ 需要生产配置就读配置中心，不落本地文件；④ 网络层加白名单，本地连不上生产 VPC；⑤ 依赖日志与链路系统做只读排查（第 34 篇）。手改 profile 起服务连生产，是清单里唯一要明令禁止的动作。

## 9. 今日小结

- 环境区分的第一价值不是"配置整洁"，是**边界**：防止测试进程污染生产链路，这类事故远比功能 bug 贵。
- 铁律一：**一个产物跑所有环境**，环境在启动时注入（`APP_ENV` / 配置中心），不靠手改文件。
- 铁律二：**同一环境的所有依赖整体切换**——DB、Redis、MQ topic、第三方沙箱必须一起换，只换数据库等于没换。
- 环境差异用 `@Profile` / 配置开关表达，业务代码里出现 `if (isProd())` 就是坏味道。
- 兜底机制：**启动自检 + 断言**，把环境错配变成"起不来"，而不是变成凌晨的告警电话。

原因：今天解决的是"怎么把环境切开、切安全"，但配置项本身还是会失控——十几个环境各自一份 yml、改一个超时值要走一次发版、开关散落无人知道谁在用。第六阶段第 2 项「配置管理」讲的正是这一层：配置中心（Nacos / Apollo）的定位与选型、动态刷新与 `@RefreshScope` 的失效边界、配置的分层归属（哪些属于环境、哪些属于业务开关、哪些属于密钥），以及"配置即代码"怎么评审。今天的 profile 体系是它的静态底座。
