# Java 学习：权限校验

> 系列第 36 篇 · 第四阶段：精度、安全与稳定性
> 衔接上一篇「参数边界」：参数边界解决了"传进来的值合不合法"，上一篇结尾留了个尾巴——提交参数的人有没有资格做这个操作？店长拿着完全合法的参数调价，也只该改得了自己门店的商品。今天讲权限校验：让每个请求先回答"你是谁、你能干什么、这条数据是不是你的"。

## 1. 今天学什么

上一篇我们给参数设了边界，但有个前提一直没点破：这些参数是"谁"提交的？一个完全合法的请求（参数全部合规），依然可能是越权操作——普通店员调用了总部才有的调价接口，或者 A 店长把 B 店长的商品价格改了。参数校验挡不住这类问题，因为它只看值，不看人。

权限校验要回答三层问题：**认证（Authentication）**——你是谁，靠登录换 token 解决；**功能权限（Authorization）**——你能不能调这个接口，靠角色/权限点解决；**数据权限**——你能操作的数据范围是什么，靠业务层的数据归属校验解决。三层缺一不可，其中数据权限是最容易被忽略、也最容易出资损的一层。

## 2. 前端工程师视角理解

你一定写过前端的"权限控制"：登录成功后把 token 存进 localStorage，axios 拦截器统一加到请求头；根据用户角色动态渲染菜单，普通员工看不到"价格管理"入口，路由守卫拦住直接输 URL 的访问。

现在要接受一个关键事实：**前端做的一切权限控制，都只是"展示层的礼貌"，不是安全边界。** 菜单隐藏了，接口地址还在代码里；路由守卫拦得住页面，拦不住直接发到服务器的 HTTP 请求。拿 curl 或 Postman 构造一个带合法 token 的请求，前端所有权限逻辑瞬间蒸发。所以后端必须独立完整地重做一遍：token 是否有效（认证）、该用户的角色能否访问这个接口（功能权限）、操作的数据是否属于该用户（数据权限）。前端权限管体验——让用户少看到无权的东西；后端权限管安全——无论谁来调，都拦得住。

## 3. 和 JavaScript / TypeScript 的对比

**前端的 route guard 对应后端的拦截器，但防线位置不同。** Vue Router 的 `beforeEach`、Next.js 的 middleware，本质上都是"请求到达处理逻辑前先检查一次"。Spring 的 HandlerInterceptor 是同一角色：在 Controller 执行前校验 token，无效就拦下。区别在于：前端守卫拦的是页面跳转，用户还能绕过；后端拦截器拦的是 HTTP 请求本身，绕不过去——这是唯一的真正关卡。

**JWT 两边都见过，用法相反。** 前端是"带 token 的人"：登录拿到后存起来，每个请求塞进 Authorization 头。后端是"验 token 的人"：收到后验签名（防伪造）、验过期时间、再从载荷里取出 userId 和角色。一个细节要扭转：前端常把 JWT 载荷当可信数据直接展示，后端绝不能这么干——**载荷里放了什么不等于真的**，签名只能证明"没被改过"，不能证明"发的时候就是对的"，关键权限信息要么查库核实，要么签发时严格把关。

**TS 类型管不住权限。** `type User = { role: 'admin' | 'staff' }` 只是编译期声明，运行时从接口返回什么就是什么，前端判断 `if (user.role === 'admin')` 的代码随时可能被绕过或改错。所以权限判断的权威永远在后端：角色从 token 解出、从数据库核实，而不是信任前端传来的任何字段。

## 4. 真实业务场景

**场景：连锁门店系统的"批量改价"接口，被 A 店长改了 B 门店的商品。**

业务背景：总部给各门店店长开放调价能力，规则是店长只能改自己门店的商品。接口接收 skuId 列表和新价格——这正是上一篇参数边界的批量改价接口，现在加一个角色：操作人。

事故是这样发生的：接口有登录校验（token 有效），也有参数校验（价格范围合法），但 Service 里拿着前端传来的 skuId 直接更新，没检查这些 sku 属于哪个门店。A 店长抓包拿到 B 门店的 skuId，构造请求一发，B 门店商品价格全被改掉——第二天 B 门店按错误的价格卖了一上午，实打实的资损。这就是**横向越权**：角色相同、数据跨界。更危险的还有**纵向越权**：普通店员拿到了总部运营的接口地址，直接调用"全量调价"。

正确做法分三层：拦截器验 token（挡掉未登录）；接口级权限判断角色（店员调总部接口直接 403）；Service 里把"该 sku 是否属于当前用户门店"作为业务规则强制校验。三层都过了才执行更新。

## 5. Java 示例代码

```java
// 第一步：认证 —— 拦截器解析 token，把用户身份放进当前线程的上下文
public class AuthInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response, Object handler) {
        String token = request.getHeader("Authorization");
        // 验签名 + 验过期，任何一步失败都返回 null
        LoginUser user = tokenService.parse(token);
        if (user == null) {
            // 认证失败：抛 BizException，由第 33 篇的全局异常处理器
            // 转成统一返回体（未登录/登录过期，前端据此跳登录页）
            throw new BizException(ErrorCode.UNAUTHORIZED, "登录已过期，请重新登录");
        }
        // 放进 ThreadLocal：本次请求的后续代码随时能取到"当前用户是谁"
        UserContext.set(user);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request,
                                HttpServletResponse response,
                                Object handler, Exception ex) {
        // 关键：请求结束必须清理，否则线程池复用线程时会串用户
        UserContext.clear();
    }
}
```

```java
// 第二步：功能权限 —— 自定义注解 + AOP 声明式校验
// 写法类似前端给路由加 meta.requiresRole，但校验发生在服务端
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequirePermission {
    String value();  // 需要的权限点，如 "price:update"
}

@Aspect
@Component
public class PermissionAspect {
    @Around("@annotation(requirePermission)")
    public Object check(ProceedingJoinPoint pjp,
                        RequirePermission requirePermission) throws Throwable {
        LoginUser user = UserContext.get();
        // 角色对应的权限点在登录时已查库放进 token/缓存
        if (!user.getPermissions().contains(requirePermission.value())) {
            // 纵向越权拦截：身份合法，但没资格调这个接口
            throw new BizException(ErrorCode.FORBIDDEN, "没有操作权限");
        }
        return pjp.proceed();
    }
}

// Controller 上的用法：一行注解声明"这个接口需要调价权限"
@PostMapping("/prices/batch")
@RequirePermission("price:update")
public Result<Void> batchUpdate(@RequestBody @Valid PriceBatchUpdateDTO dto) {
    priceService.batchUpdate(dto);
    return Result.success(null);
}
```

```java
// 第三步：数据权限 —— Service 里校验"这条数据是不是你的"
// 这是防横向越权的唯一防线，注解和拦截器都帮不上忙
public void batchUpdate(PriceBatchUpdateDTO dto) {
    LoginUser current = UserContext.get();

    List<Long> skuIds = dto.getItems().stream()
            .map(PriceItem::getSkuId).toList();
    // 用当前用户的 storeId 过滤：查出这批 sku 里属于本店的有几个
    int ownedCount = skuMapper.countOwnedByStore(skuIds, current.getStoreId());
    if (ownedCount != skuIds.size()) {
        // 有 sku 不属于本店 —— A 店长在动 B 门店的数据
        log.warn("越权改价拦截, userId={}, storeId={}, skuIds={}",
                current.getUserId(), current.getStoreId(), skuIds);
        throw new BizException(ErrorCode.FORBIDDEN, "包含非本门店商品，无权修改");
    }
    // 归属校验通过，继续上一篇的边界校验和更新逻辑……
}
```

三层防线各管一段：拦截器管"是不是登录用户"，AOP 注解管"有没有资格调这个接口"，Service 管"动的数据是不是自己的"。上一篇的结论在这里升级：合法参数 + 合法身份 + 越权数据 = 资损，三关必须都过。

## 6. 常见坑

**坑 1：前端隐藏了按钮，后端就不校验了。** 错误理解："这个入口普通员工看不到，接口不用管。"问题：接口地址在前端代码里是明牌，抓包一次全知道，curl 直接调用毫无障碍。正确做法：每个接口的权限以后端校验为唯一依据，前端隐藏只是体验优化。

**坑 2：只验角色、不验数据归属。** 错误理解："校验了店长角色就够了。"问题：店长是合法角色，但 A 店长调 B 门店的数据照样畅通无阻——横向越权就是这么来的。正确做法：凡是"操作某条/某批数据"的接口，Service 里必须有一次数据归属校验（storeId、userId 是否匹配当前用户）。

**坑 3：把前端传的 userId 当"当前用户"。** 错误写法：接口接收 `userId` 参数，拿它去查数据、改数据。问题：攻击者把参数换成别人的 userId，以他的身份操作他的数据，后端全程无感知。正确做法：当前用户只从 token 解析结果取（UserContext），接口参数里出现的"我是谁"一律拒绝信任。

**坑 4：ThreadLocal 用完不清理。** 错误写法：拦截器里 `UserContext.set(user)` 之后没有 afterCompletion 清理。问题：Tomcat 用线程池复用线程，上一个请求的用户信息残留在线程上，下一个请求如果没有覆盖（比如某个免登录接口），就会"以别人的身份"执行——串号事故，且极难复现。正确做法：afterCompletion 里必须 clear。

**坑 5：校验只覆盖主入口。** 错误理解：Controller 加了注解就安全了。问题：同一个 Service 方法还会被定时任务、MQ 消费者、内部 RPC 调用，这些入口不经过拦截器和 AOP——和上一篇"校验不能只放 Controller"是同一个道理。正确做法：数据归属这类关键校验写进 Service，所有入口天然共享。

## 7. 和之前知识的连接

- **第 35 篇「参数边界」（上一篇）**：今天补上了它留下的尾巴——参数合法不代表操作合法。上一篇坑 4 说"Service 不只被 Controller 调用"，今天的坑 5 是同一原则在权限上的翻版。
- **第 33 篇「全局异常处理」**：认证失败抛的 `BizException(UNAUTHORIZED)`、越权抛的 `FORBIDDEN`，都由它转成统一返回体，前端拦截器据此区分"跳登录页"还是"弹无权提示"。
- **第 23 篇「状态码设计」**：UNAUTHORIZED / FORBIDDEN 就是在那篇错误码体系里追加的两个码，前端依赖它们做不同的跳转逻辑。
- **第 34 篇「日志规范」**：越权拦截那条 `log.warn` 带了 userId、storeId、skuIds——这类"未遂的越权"正是安全排查时最需要检索到的日志。

## 8. 面试 / 工作中常见问题

### 问题 1：401 和 403 有什么区别？前端应该怎么处理？

参考答案：401（UNAUTHORIZED）是"不知道你是谁"——token 缺失、无效或过期，处理方式一般是引导重新登录；403（FORBIDDEN）是"知道你是谁，但你没资格"——登录有效但角色/数据权限不足，一般提示无权操作，不用跳登录页。分清楚这两个码，前端的错误拦截器才能做出正确的分支，而不是所有失败都弹同一句"系统错误"。

### 问题 2：怎么防止横向越权？说说你的落地方案。

参考答案：横向越权的本质是"同级用户跨界访问他人数据"，功能权限（角色）完全拦不住它，必须靠数据权限。落地：所有涉及具体数据的接口，在 Service 层强制校验数据归属——操作前用当前用户的 storeId/userId（从 token 取，不是前端传的）过滤或核对目标数据，不匹配直接拒绝并记日志。更进一步可以让 DAO 层的查询统一自动拼接归属条件，让"查不到别人的数据"变成默认行为而不是每个接口自觉。

### 问题 3：JWT 存用户信息有什么风险？能直接信任载荷里的内容吗？

参考答案：不能。JWT 的签名只保证载荷"签发后没被篡改"，不保证"签发时内容真实"，也不阻止有人盗用一个合法 token。所以：敏感权限不要只塞进 token，关键操作回查数据库核实；token 要设较短的有效期并支持失效（黑名单或刷新机制）；token 在日志、URL 参数里绝不出现，避免泄露后被直接冒用。

## 9. 今日小结

- 权限三层：认证（你是谁）→ 功能权限（能调什么接口）→ 数据权限（能动什么数据），缺任何一层都有漏洞。
- 前端的菜单隐藏、路由守卫只是体验，后端拦截器 + Service 校验才是唯一的安全边界。
- 横向越权靠数据归属校验拦截：A 店长改 B 门店商品，角色校验完全无感。
- 当前用户永远从 token 上下文（UserContext）取，前端传上来的"我是谁"一个字都不能信。
- ThreadLocal 用完必须清理，否则线程池复用会造成"串用户"事故。

明天建议学习：`数据脱敏`

原因：今天解决了"谁能看"，紧接着的问题是"看到多少"——有权限的客服确实能打开用户详情页，但手机号、身份证号不该完整展示；日志和导出文件里的敏感字段同样要处理。权限控制管住入口，脱敏管住出口，两者合起来才是完整的数据安全。明天讲 Java 里怎么优雅地做脱敏，而不需要在每个接口里手写 `substring`。
