# Java 学习：Controller 参数接收

> 系列第 24 篇 · 第三阶段：接口与规范  
> 上一篇我们设计了结构化的业务状态码，前端根据 code 做差异化处理。但那是"响应侧"的事。今天回到"请求侧"——前端用 axios 发出的数据，后端 Controller 到底怎么接？`@RequestParam`、`@PathVariable`、`@RequestBody`、`@RequestHeader` 分别对应前端什么样的请求写法？搞清楚这个，你就能完整理解一个 HTTP 请求从前端发出到后端接收的全链路。

## 1. 今天学什么

前端发请求时，数据可以放在 URL 路径里（`/stores/10086`）、查询参数里（`?pageNum=1&size=20`）、请求体里（JSON body）、请求头里（`Authorization: Bearer xxx`）。后端 Controller 必须用对应的注解去"接"对应位置的数据，接错了位置就拿不到值。

这不是什么高深原理，但它是前后端联调时最高频的"对不上"问题：前端把参数放在了 query 里，后端用 `@RequestBody` 去接，结果拿到 null；前端把 id 放在了 body 里，后端用 `@PathVariable` 去接，直接 404。今天把每种参数接收方式和它对应的前端请求写法一一对齐，以后联调不再猜。

## 2. 前端工程师视角理解

你在前端发请求时，参数放置的位置其实就这几种：

```typescript
// 1. 路径参数：id 嵌在 URL 里
axios.get(`/api/stores/${storeId}`)

// 2. 查询参数：跟在 ? 后面
axios.get('/api/stores', { params: { pageNum: 1, pageSize: 20, keyword: '咖啡' } })

// 3. 请求体：JSON 放在 body 里
axios.post('/api/stores', { name: '望京店', phone: '13800138000' })

// 4. 请求头：放在 headers 里
axios.get('/api/stores', { headers: { Authorization: `Bearer ${token}` } })
```

后端 Controller 接收参数时，必须用"对的位置"去接：

```java
// 1. 路径参数 → @PathVariable
@GetMapping("/{id}")
public Result<StoreVO> detail(@PathVariable Long id) { ... }

// 2. 查询参数 → @RequestParam（或直接用对象接收）
@GetMapping
public Result<PageResult<StoreVO>> list(@RequestParam int pageNum, @RequestParam int pageSize) { ... }

// 3. 请求体 → @RequestBody
@PostMapping
public Result<Long> create(@RequestBody StoreCreateDTO dto) { ... }

// 4. 请求头 → @RequestHeader
@GetMapping("/me")
public Result<UserVO> me(@RequestHeader("Authorization") String auth) { ... }
```

核心规则就一句话：**前端把数据放在哪，后端就用对应的注解去哪接。** 放错位置，后端拿到的就是 null 或直接 400。

## 3. 和 JavaScript / TypeScript 的对比

### 路径参数：Express req.params vs Spring @PathVariable

```typescript
// Node.js + Express
app.get('/api/stores/:id', (req, res) => {
  const id = req.params.id; // 字符串 "10086"，需要手动转数字
  const storeId = Number(id);
});
```

```java
// Spring Boot
@GetMapping("/{id}")
public Result<StoreVO> detail(@PathVariable Long id) {
  // id 已经是 Long 类型，Spring 自动转换
  // 如果前端传了 /stores/abc，Spring 直接返回 400（类型转换失败）
}
```

Express 里 `req.params.id` 永远是字符串，你得自己 `Number()` 转换、自己判断 NaN。Spring 的 `@PathVariable Long id` 声明了类型，框架自动转换，传了非数字直接 400 拒绝——类型安全从"运行时手动判断"变成了"框架自动保障"。

### 查询参数：Express req.query vs Spring @RequestParam

```typescript
// Express：req.query 是一个对象，所有值都是 string | string[]
const { pageNum, pageSize, keyword } = req.query;
// pageNum 是 "1" 不是 1，需要手动 parseInt
// keyword 可能是 undefined，需要自己判空
```

```java
// Spring Boot：逐个声明，带类型、带默认值
@GetMapping
public Result<PageResult<StoreVO>> list(
    @RequestParam(defaultValue = "1") int pageNum,
    @RequestParam(defaultValue = "20") int pageSize,
    @RequestParam(required = false) String keyword
) { ... }
```

Express 的 `req.query` 是一个松散的对象，所有值都是字符串，类型转换和空值判断全靠手动。Spring 的 `@RequestParam` 逐个声明参数，可以指定类型（自动转换）、默认值（`defaultValue`）、是否必填（`required`）。少传了必填参数，框架直接 400，不需要你写 `if (!pageNum)` 的防御代码。

### 请求体：Express req.body vs Spring @RequestBody

```typescript
// Express + body-parser 中间件
app.use(express.json()); // 先注册中间件解析 JSON
app.post('/api/stores', (req, res) => {
  const { name, phone } = req.body; // 直接解构，没有类型约束
});
```

```java
// Spring Boot：@RequestBody 自动反序列化 JSON 为 Java 对象
@PostMapping
public Result<Long> create(@RequestBody StoreCreateDTO dto) {
    dto.getName();  // 有类型、有 IDE 提示、编译期检查
    dto.getPhone();
}
```

Express 里 `req.body` 是 `any`，你解构出来的字段没有类型约束，拼错了字段名运行时才发现。Spring 的 `@RequestBody StoreCreateDTO dto` 把 JSON 反序列化为强类型对象，字段名拼错编译就报错，配合 `@Valid` 还能自动校验（第 21 篇学过的）。

### 为什么 Java 要拆成这么多注解

前端觉得"参数不就是从请求里取吗，为什么搞这么多注解？"因为 HTTP 请求的参数位置是协议层面的约定——路径参数表达"操作哪个资源"，查询参数表达"筛选/分页条件"，请求体表达"提交的数据"，请求头表达"元信息"。Java 用不同注解强制你区分这些语义，而不是像 Express 那样所有东西都从 `req` 上随手取。结果是：看 Controller 方法签名就知道前端该怎么传参，不需要翻文档。

## 4. 真实业务场景

**场景：门店管理后台的"门店列表 + 筛选 + 排序"接口。**

业务背景：运营人员在后台查看门店列表，支持按名称搜索、按区域筛选、按创建时间排序、分页浏览。

前端请求：

```typescript
axios.get('/api/stores', {
  params: {
    pageNum: 1,
    pageSize: 20,
    keyword: '望京',
    regionId: 110105,
    sortBy: 'createTime',
    order: 'desc'
  }
})
```

如果后端参数接收方式搞错会怎样？

一是用 `@RequestBody` 接 GET 请求的查询参数。GET 请求没有 body，`@RequestBody` 拿到的是 null，接口直接报错或返回空数据。运营看到"暂无门店"，以为是数据问题，实际上是后端接参方式错了。

二是 `@RequestParam` 的 `required` 默认为 true。前端筛选条件 `keyword` 是可选的，用户不搜索时不传这个参数。如果后端 `@RequestParam String keyword` 没加 `required = false`，不传 keyword 时 Spring 直接返回 400——用户第一次打开列表页就报错。

三是类型不匹配。前端传 `regionId=110105`（字符串），后端声明 `@RequestParam Long regionId`，Spring 自动转换没问题。但如果前端不小心传了 `regionId=all`，Spring 转换失败返回 400，前端如果没有兜底处理，用户看到白屏。

## 5. Java 示例代码

```java
/**
 * 门店查询参数对象
 * 用于接收 GET 请求的多个查询参数（比逐个 @RequestParam 更整洁）
 */
@Data
public class StoreQueryParam {
    private int pageNum = 1;          // 默认第 1 页
    private int pageSize = 20;        // 默认每页 20 条
    private String keyword;           // 搜索关键词（可选）
    private Long regionId;            // 区域 ID（可选）
    private String sortBy = "createTime"; // 排序字段
    private String order = "desc";    // 排序方向
}
```

```java
@RestController
@RequestMapping("/api/stores")
public class StoreController {

    @Autowired
    private StoreService storeService;

    /**
     * 列表查询：查询参数用对象接收
     * 前端 axios.get('/api/stores', { params: {...} })
     * Spring 自动把 query string 的字段映射到对象属性
     * 注意：这里不加 @RequestParam，Spring 按字段名自动绑定
     */
    @GetMapping
    public Result<PageResult<StoreVO>> list(StoreQueryParam param) {
        PageResult<StoreVO> page = storeService.queryStores(param);
        return Result.success(page);
    }

    /**
     * 详情查询：路径参数用 @PathVariable
     * 前端 axios.get(`/api/stores/${id}`)
     */
    @GetMapping("/{id}")
    public Result<StoreVO> detail(@PathVariable Long id) {
        StoreVO store = storeService.getById(id);
        if (store == null) {
            return Result.fail(ErrorCode.STORE_NOT_FOUND);
        }
        return Result.success(store);
    }

    /**
     * 新增门店：请求体用 @RequestBody
     * 前端 axios.post('/api/stores', { name, phone, address })
     * JSON body 自动反序列化为 StoreCreateDTO 对象
     */
    @PostMapping
    public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) {
        Long storeId = storeService.createStore(dto);
        return Result.success(storeId);
    }

    /**
     * 修改门店状态：路径参数 + 请求体混合使用
     * 前端 axios.put(`/api/stores/${id}/status`, { status: 'closed' })
     */
    @PutMapping("/{id}/status")
    public Result<Void> updateStatus(
            @PathVariable Long id,
            @RequestBody @Valid StatusUpdateDTO dto) {
        storeService.updateStatus(id, dto.getStatus());
        return Result.success();
    }

    /**
     * 删除门店：路径参数
     * 前端 axios.delete(`/api/stores/${id}`)
     */
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) {
        storeService.deleteStore(id);
        return Result.success();
    }

    /**
     * 获取当前登录用户信息：从请求头取 token
     * 前端 axios.get('/api/stores/current-user', { headers: { Authorization: 'Bearer xxx' } })
     */
    @GetMapping("/current-user")
    public Result<UserVO> currentUser(@RequestHeader("Authorization") String authorization) {
        // 实际项目中 token 解析通常在拦截器里完成，这里简化演示
        String token = authorization.replace("Bearer ", "");
        UserVO user = userService.getByToken(token);
        return Result.success(user);
    }
}
```

## 6. 常见坑

**坑 1：GET 请求用 @RequestBody 接参数。**

错误写法：`@GetMapping` + `@RequestBody StoreQueryParam param`。GET 请求按 HTTP 规范没有 body（axios 的 `params` 会拼到 URL 上），Spring 解析不到 body 内容，参数全是 null。正确做法：GET 请求的查询参数用对象直接接收（不加注解，Spring 按字段名绑定 query string）或逐个 `@RequestParam`。`@RequestBody` 只用于 POST / PUT / PATCH 的 JSON body。

**坑 2：@RequestParam 默认 required=true，可选参数没加 required=false。**

错误写法：`@RequestParam String keyword`。前端不传 keyword 时（用户没搜索），Spring 认为缺少必填参数，直接返回 400。正确做法：可选参数加 `@RequestParam(required = false) String keyword`，或给默认值 `@RequestParam(defaultValue = "") String keyword`。判断标准：前端不一定会传的参数，都是可选的。

**坑 3：@PathVariable 名称和路径占位符不一致。**

错误写法：`@GetMapping("/{storeId}")` 配合 `@PathVariable("id") Long id`。路径里是 `{storeId}`，注解里写的是 `"id"`，Spring 找不到对应关系，启动时直接报错。正确做法：保持一致——要么 `@PathVariable Long storeId`（变量名和占位符同名，可省略 value），要么 `@PathVariable("storeId") Long id`（显式指定）。

**坑 4：用对象接收查询参数时，字段类型用了 int 而不是 Integer。**

错误写法：`private int regionId;`。前端不传 regionId 时，Spring 无法把 null 赋给基本类型 int，抛出类型转换异常。正确做法：可选字段用包装类型 `Integer`、`Long`（可以为 null），必填字段可以用基本类型（配合 `@RequestParam` 的 required=true 保证一定有值）。

**坑 5：@RequestBody 和 @RequestParam 同时出现在 POST 方法上，前端不知道参数该放哪。**

错误写法：`@PostMapping` 方法里既有 `@RequestParam Long id` 又有 `@RequestBody StoreDTO dto`。前端困惑：id 是放 URL query 里还是 body 里？正确做法：POST 请求的参数尽量统一放在 body 里（DTO 里加一个 id 字段），或者 id 放路径 `@PostMapping("/{id}")` + `@PathVariable`。不要混用让前端猜。

## 7. 和之前知识的连接

- **第 23 篇「状态码设计」**：今天 `detail` 方法里门店不存在时返回 `Result.fail(ErrorCode.STORE_NOT_FOUND)`，这个 `STORE_NOT_FOUND(50100)` 就是上一篇定义的门店模块错误码。参数接收是"入口"，状态码是"出口"，一入一出构成完整的接口契约。

- **第 22 篇「统一返回结构」**：今天所有 Controller 方法都返回 `Result<T>`，这是上一篇定义的全局规范。不管用哪种参数接收方式，返回格式永远一致——前端拦截器不需要关心参数怎么传的，只需要关心 `code` 和 `data`。

- **第 21 篇「请求参数校验」**：今天 `create` 方法里的 `@RequestBody @Valid StoreCreateDTO dto`，`@Valid` 触发校验是第 21 篇的内容。参数接收解决"怎么拿到数据"，参数校验解决"拿到的数据合不合规"，两者配合才能保证进入 Service 层的数据既完整又合法。

- **第 20 篇「RESTful 接口设计」**：今天的 `@GetMapping("/{id}")`、`@PostMapping`、`@PutMapping("/{id}/status")`、`@DeleteMapping("/{id}")` 就是上一篇设计的 RESTful 路由。RESTful 管"URL 怎么设计"，参数接收管"URL 里的数据怎么取出来"，是同一件事的两面。

## 8. 面试 / 工作中常见问题

### 问题 1：@RequestParam 和 @PathVariable 有什么区别？什么时候用哪个？

参考答案：`@PathVariable` 从 URL 路径中取值（`/stores/{id}` 里的 id），表达"操作哪个资源"；`@RequestParam` 从查询字符串中取值（`?pageNum=1&size=20`），表达"筛选/分页/排序条件"。设计原则：资源标识用路径参数（RESTful 风格），过滤条件用查询参数。`/stores/10086` 表示" id 为 10086 的门店"，`/stores?regionId=110105` 表示"朝阳区的所有门店"。

### 问题 2：GET 请求的参数太多，用 @RequestParam 逐个写很冗长怎么办？

参考答案：定义一个查询参数对象（如 `StoreQueryParam`），Controller 方法参数直接写对象类型、不加任何注解。Spring MVC 会自动把 query string 中同名字段绑定到对象属性上。字段名和参数名一致即可自动映射，不需要逐个 `@RequestParam`。对象里可以给默认值（`private int pageNum = 1`），可选字段用包装类型（`Integer`、`Long`）允许为 null。参数超过 3 个就建议用对象接收。

### 问题 3：前端传了参数但后端接收到 null，可能是什么原因？

参考答案：按概率排序：一是位置不对——前端放在 query 里，后端用 `@RequestBody` 接（或反过来）；二是名称不一致——前端传 `page_num`（下划线），后端字段是 `pageNum`（驼峰），Spring 默认按精确名称绑定，不会自动转驼峰；三是 GET 请求用了 `@RequestBody`——GET 没有 body，自然接不到；四是 Content-Type 不对——前端发 JSON 但没设 `Content-Type: application/json`，Spring 不知道按 JSON 解析。排查方法：浏览器 Network 面板看请求实际长什么样，再对照 Controller 方法签名逐个检查。

## 9. 今日小结

- HTTP 请求参数有四个位置：路径、查询字符串、请求体、请求头——后端用 `@PathVariable`、`@RequestParam`（或对象）、`@RequestBody`、`@RequestHeader` 分别对应。
- 前端把数据放在哪，后端就用对应注解去哪接，放错位置就是 null 或 400。
- GET 请求参数用对象接收最整洁（不加注解，Spring 按字段名自动绑定），POST/PUT 的 JSON body 用 `@RequestBody`。
- 可选参数必须 `required = false` 或用包装类型，否则前端不传时直接报错。
- 看 Controller 方法签名就能知道前端该怎么传参——这是 Java 注解驱动的优势，方法签名即文档。

## 10. 明日预告

明天建议学习：`接口幂等性`

原因：今天搞清楚了前端数据怎么传到后端，接口"能跑通"了。但真实业务里还有一个高频问题：用户双击了提交按钮、网络超时后前端自动重试、用户刷新页面导致表单重复提交——同一个请求被发了两次，后端会不会创建两个门店、扣两次库存？这就是接口幂等性要解决的问题。它和今天的参数接收直接相关：幂等方案往往需要在请求参数里加一个唯一标识（幂等 key），后端根据这个 key 判断"这个请求是不是已经处理过了"。
