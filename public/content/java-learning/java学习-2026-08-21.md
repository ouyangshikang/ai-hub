# Java 学习：数据脱敏

> 系列第 37 篇 · 第四阶段：精度、安全与稳定性
> 衔接上一篇「权限校验」：昨天解决了"谁能看"——客服有权限打开会员详情页。但紧接着还有个问题：有权限也不该看到全部，完整手机号、身份证号不能直接给出去；接口管住了，日志和导出文件里的敏感字段照样会漏。权限管入口，脱敏管出口，今天讲 Java 里怎么优雅地做脱敏，而不是在每个接口里手写 `substring`。

## 1. 今天学什么

上一篇的权限校验回答了"这个页面你能不能打开"，但答案有个后续：打开之后，你能看到多少？客服系统里，客服查会员信息是他的本职工作，权限上完全合法，可完整展示手机号、身份证号、家庭住址既没必要也很危险——任何一个客服截图外发，或者任何一次数据导出，都是数据安全事故。个人信息保护相关法律对敏感个人信息的展示有明确要求，这不是"讲究"，是合规底线。

数据脱敏就是解决"看到多少"的技术：敏感数据在离开后端之前，把可识别的部分替换成 `*`，做到"可辨识、不可还原"——客服知道这是尾号 5678 的手机号，但拿不到完整号码。脱敏的核心就两件事：**规则收敛**（手机号保前三后四、身份证保前三后四，全公司一份规则）；**出口收敛**（在后端数据出门的统一位置处理，而不是在前端展示层）。

## 2. 前端工程师视角理解

你一定写过这样的代码：

```js
// 前端展示脱敏
const maskedPhone = phone.replace(/^(\d{3})\d{4}(\d{4})$/, "$1****$2");
```

看起来没毛病，但先说结论：**前端脱敏是自欺**。前端能 `replace` 的前提，是接口已经把完整手机号发到了浏览器——打开 DevTools 的 Network 面板，明文一览无余。前端格式化的只是"屏幕上显示什么"，不是"用户能拿到什么"。数据在返回那一刻就已经漏了，前端挡得住普通用户的眼睛，挡不住有心人的手。

所以脱敏的正确位置是后端出口：数据从 Java 对象序列化成 JSON 响应的那一刻，它就已经是 `138****5678`。前端拿到什么就展示什么，连见到原值的机会都没有。这和上一篇权限校验是同一个逻辑：**前端管体验，后端管安全**。前端展示层的打码只是体验兜底（屏幕上显示占位），后端出口的脱敏才是安全边界。

## 3. 和 JavaScript / TypeScript 的对比

**脱敏的位置在两个技术栈里完全不同。** JS 里脱敏逻辑通常写在"展示层"：formatter、filter、组件渲染函数——因为前端控制不了接口返回什么，只能在最后一公里加工。Java 里脱敏写在"序列化层"：数据从对象转成 JSON 由 Jackson（Spring Boot 默认的序列化库）完成，在这一步动手，所有流出去的字节都已经是脱敏后的。一个是下游拦截，一个是源头管控，差别就在于明文有没有上过网络。

**实现机制上，Java 注解对应 TS 的装饰器。** NestJS 里你可能用 class-transformer 的 `@Transform` 在 DTO 转换时加工字段；Java 里用自定义注解 `@Sensitive` + Jackson 自定义序列化器做同样的事：规则写一次，字段上打注解，所有返回这个 VO 的接口自动脱敏。而且注解是静态的、可检索的——安全团队做合规审查，只要扫一遍代码里哪些敏感字段没打 `@Sensitive`；JS 里靠散落各处的手写 replace 调用，这种审查几乎做不了。

**一个必须厘清的观念：脱敏 ≠ 加密。** 脱敏是不可逆的有损处理，`*` 替换掉的原值就永远没了，它只服务于"展示"。加密是可逆的，密文配合密钥能还原原值，它服务于"存储和传输"。把两者搞混的典型事故，就是下面要讲的场景。

## 4. 真实业务场景

**场景：连锁门店系统的客服工作台，客服导出了完整身份证号。**

业务背景：客服需要按手机号查询会员资料和订单记录，这是正常工作流。最初的实现里，接口直接返回了 Member 实体：完整手机号、身份证号（会员实名认证）、收货地址；前端在页面上做了展示打码，看起来一切正常。

事故有两层：安全团队例行扫描接口流量，发现响应里是明文身份证号，直接定级高危漏洞；随后一位客服把"会员活动名单"导出成 Excel 发到外部群，里面是几十条完整手机号和地址——数据泄露事件，公司被监管约谈。两个问题的根因完全相同：**脱敏只做了前端展示层，后端出口一条都没处理**。页面打了码，网络流量、导出文件里全是明文。

修复分两步：会员详情 VO 的敏感字段加脱敏注解，接口层面明文不再出门；导出场景同样脱敏，并且加上审批流程和审计日志——导出这个出口比接口更危险，因为它一次带走一整批数据。

## 5. Java 示例代码

```java
// 第一步：定义敏感类型 + 注解，规则声明在 VO 字段上
public enum SensitiveType {
    PHONE,      // 手机号：138****5678
    ID_CARD,    // 身份证号：110***********1234
    ADDRESS     // 地址：只保留省市
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@JacksonAnnotationsInside                           // 让这个注解被 Jackson 识别
@JsonSerialize(using = SensitiveSerializer.class)   // 绑定自定义序列化器
public @interface Sensitive {
    SensitiveType value();
}
```

```java
// 第二步：自定义序列化器——VO 转 JSON 时 Jackson 自动调用它
public class SensitiveSerializer extends JsonSerializer<String>
        implements ContextualSerializer {

    private SensitiveType type;

    @Override
    public void serialize(String value, JsonGenerator gen,
                          SerializerProvider provider) throws IOException {
        if (value == null) {
            gen.writeString("");
            return;
        }
        // 按类型替换：保头保尾，中间打码
        switch (type) {
            case PHONE -> gen.writeString(maskPhone(value));
            case ID_CARD -> gen.writeString(maskIdCard(value));
            case ADDRESS -> gen.writeString(maskAddress(value));
            default -> gen.writeString(value);
        }
    }

    // Jackson 处理每个字段前调用：读字段上的注解，拿到敏感类型
    @Override
    public JsonSerializer<?> createContextual(SerializerProvider provider,
                                              BeanProperty property) {
        if (property != null) {
            Sensitive anno = property.getAnnotation(Sensitive.class);
            if (anno != null) {
                SensitiveSerializer s = new SensitiveSerializer();
                s.type = anno.value();
                return s;
            }
        }
        return this;
    }

    private static String maskPhone(String v) {
        return v.length() == 11 ? v.substring(0, 3) + "****" + v.substring(7) : v;
    }
    // maskIdCard / maskAddress 同理：保留首尾，中间打码
}
```

```java
// 第三步：VO 上打注解，Controller 一行处理代码都不用写
public class MemberDetailVO {
    private Long memberId;
    private String nickname;

    @Sensitive(SensitiveType.PHONE)
    private String phone;      // 前端收到 138****5678

    @Sensitive(SensitiveType.ID_CARD)
    private String idCard;     // 前端收到 110***********1234

    @Sensitive(SensitiveType.ADDRESS)
    private String address;
}
```

```java
// 反例：在每个 Service 里手写脱敏，是最常见的坏味道
public MemberDetailVO getMember(Long id) {
    Member m = memberMapper.selectById(id);
    MemberDetailVO vo = convert(m);
    // 手写规则第一处
    vo.setPhone(m.getPhone().substring(0, 3) + "****" + m.getPhone().substring(7));
    // 过段时间另一个接口里，同事写成 replaceAll("(\\d{3})\\d{4}", "$1****")——规则第二处
    // 哪天合规要求变了，全仓库搜一遍逐个改，必然漏
}
```

## 6. 常见坑

**坑 1：前端打码，接口全量返回。** 错误理解："页面上已经格式化了，用户看不到。"问题：接口响应在网络上是明文，DevTools 一眼看到原值，爬虫脚本连页面都不用看。正确做法：脱敏放后端序列化出口，前端展示处理只是体验兜底。

**坑 2：把脱敏后的数据存进数据库。** 错误写法：`member.setPhone(maskPhone(phone))` 然后 insert。问题：脱敏不可逆，存进去之后真实手机号就永远丢了——后面任何要"发短信、打电话、按手机号匹配"的业务全部瘫痪。正确做法：库里存原值（安全等级要求高就加密存储），脱敏只发生在展示出口。记住一句话：**脱敏是给人看的，加密是用于存的**。

**坑 3：只脱了接口，漏了日志和导出。** 错误理解："VO 上加了注解就安全了。"问题：注解只在 Jackson 序列化这条路上生效——`log.info("用户手机号: {}", user.getPhone())` 打出去的是明文；导出 Excel 走的是 EasyExcel 另一条序列化路径，注解不生效。正确做法：枚举数据出口（接口、日志、导出、短信通知），每个出口都接同一份脱敏规则。

**坑 4：手写 replace 到处散落，规则漂移。** 错误写法：每个接口各写各的 substring。问题：两个接口两套脱敏规则，改规则时全仓库搜索逐个改，必漏。正确做法：规则收敛到一处（注解 + 序列化器，或统一的 MaskUtil 工具类），业务代码只引用它。

**坑 5：拿脱敏结果做业务逻辑。** 错误写法：用列表页展示的 `138****5678` 去调"按手机号查询"，或后端拿脱敏号码做模糊匹配。问题：脱敏值是展示数据，不是查询条件，拿它匹配永远查不到。正确做法：查询走独立的输入参数（用户重新输入的完整手机号、会员 ID），脱敏字段只展示、不参与任何逻辑。

## 7. 和之前知识的连接

- **第 36 篇「权限校验」（上一篇）**：昨天管住入口——谁能打开这个页面；今天管住出口——打开之后能看到多少。权限 + 脱敏合起来才是完整的数据安全，只有权限没有脱敏，就是今天场景里被约谈的原因。
- **第 2 篇「DTO / VO / Entity 的区别」和 Controller 出口规范**：`@Sensitive` 注解能生效，前提是接口返回 VO——这正是前面反复强调"Controller 出口永远是 VO，不是 Entity 也不是 Map"的又一个回报。直接返回 Entity，敏感字段没地方挂注解，只能裸奔出门。
- **第 34 篇「日志规范」**：日志是另一个数据出口。那篇讲日志要带业务主键方便检索，今天要补一条：手机号、身份证这类敏感值要么不打，要么打脱敏后的值——日志系统往往权限比接口更宽，反而是最容易漏的出口。

## 8. 面试 / 工作中常见问题

### 问题 1：你们项目里脱敏是怎么统一实现的？

参考答案：定义 `@Sensitive` 注解 + 敏感类型枚举，打在 VO 字段上；配合 Jackson 自定义序列化器（实现 `ContextualSerializer`），序列化时读取字段注解、按类型规则替换。好处是规则收敛在一处，接口代码零处理，合规审查只需扫注解覆盖情况。日志和导出走同一份 MaskUtil，保证所有出口规则一致。

### 问题 2：脱敏和加密的区别？各自什么时候用？

参考答案：脱敏是不可逆的有损处理，`*` 替换掉的原值就没了，服务于"展示给人看"——接口响应、页面、日志；加密是可逆的，密文配密钥能还原，服务于"存住数据"——数据库存储、系统间传输。典型组合是存储层加密、展示出口脱敏。混淆两者的事故就是把数据脱敏后才存库，结果真实数据永久丢失。

### 问题 3：安全扫描发现某接口返回了完整身份证号，你怎么排查和整改？

参考答案：先定位出口：找到这个接口的 Controller，看它返回的是什么——十有八九是直接返回了 Entity 或 Map，绕过了展示层规范。短期整改：换成 VO 并给敏感字段加脱敏注解，验证后上线。长期整改：把"Controller 出口禁止返回 Entity"纳入代码规范或静态检查，对全量接口做一次敏感字段扫描（手机号、身份证、地址字段是否都有 `@Sensitive`），同时把日志和导出两个出口一并排查。

## 9. 今日小结

- 权限校验管入口（谁能打开），脱敏管出口（能看到多少），两者合起来才是数据安全。
- 前端脱敏是自欺：明文已经到了浏览器；真正的脱敏必须发生在后端序列化出口。
- 脱敏 ≠ 加密：脱敏不可逆、服务于展示；加密可逆、服务于存储。脱敏后存库等于毁数据。
- 规则收敛到一个注解 + 序列化器；到处手写 substring 是规则漂移和漏改的开端。
- 出口不止接口：日志、导出、短信通知，每一条都要接同一套脱敏规则。
