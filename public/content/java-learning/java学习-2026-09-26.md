# Java 学习：分库分表与在线扩容

> 系列第 66 篇 · 第八阶段：数据架构进阶（第 2 篇）
> 衔接上一篇「读写分离与主从延迟」：读写分离解决"读多"，解决不了"写入瓶颈与单表过大"。今天讲那一步——水平分片。
> **与第 63 / 18 篇的分工**：第 63 篇讲的"垂直拆分"是**按业务拆**（拆出服务与独立库）；今天讲**水平分片**：同一张表按分片键散到多个库表。第 18 篇讲单库内的深分页，今天讲跨库分页为什么更贵。

## 1. 今天学什么

分库分表是"**最难回头的一步**"：一旦上线，所有查询路径都要带分片键、跨库 JOIN 与事务都要重新设计、扩容要搬迁数据。所以它是一门**先想清楚再动手**的功夫。

四块内容：① **分片键怎么选**——高频查询必须能带上它、分布要均匀、**绝不能是会变的字段**；② **跨库的三个硬约束**——JOIN 要变组装、分页要归并、事务要缩到单分片内；③ **全局唯一 ID**——自增主键在分片下会撞车，雪花与号段怎么选；④ **在线扩容路径**——预分片、双写回填、灰度切读、回滚预案这套流程，和第 26 篇的接口兼容、第 57 篇的回滚纪律是同一套工程方法。

一句话定位：分片的本质不是"技术升级"，而是**把数据库的分布式问题提前设计进业务模型**。

## 2. 前端工程师视角理解

最贴切的类比是**跨接口分页**。你在前端遇到过这种需求：要展示"全站最新的订单"，但数据在三个接口里（各自的列表），你要么让后端合并，要么前端同时请求三方、自己按时间归并、再在内存里切页——**页码、总数、去重全靠自己算**。跨库分页就是这个尴尬的服务端版本，而且数据量大到不能全拉回来。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端分片 |
|---|---|---|
| 数据散开 | 多接口/多来源聚合 | 同一张表按分片键散到多库多表 |
| 分片键 | 无（聚合靠约定） | 业务字段，一旦选定极难更改 |
| 排序分页 | 前端归并 + 内存切页 | 多库查询后归并，深分页代价翻倍 |
| 事务 | 无跨接口事务（用状态机兜） | 跨库事务不可用 → 必须缩进单分片 |
| 唯一标识 | UUID / 时间戳 | 雪花 / 号段（自增会撞车） |
| 扩容 | 加接口、换数据源 | 双写回填 + 灰度切路由（可回滚） |

**最需要建立的新观念：分片键是一份"数据契约"，改它等于迁移整个库。** 前端接口字段改名还能靠兼容层扛一版；分片键变了，意味着**这条数据要跨库搬家，且所有按旧键定位的查询全部失效**。所以选键的第一标准不是"查询方便"，而是"**它永远不变，且能覆盖 90% 以上的高频查询**"。

## 4. 真实业务场景

**场景：订单表 8 亿行，分片上线三个月后，运营发现"看不到最新订单"。**

业务背景：订单表按 `order_id % 16` 分成 16 个库。为了"让写入分散"，`order_id` 用的是**随机生成的 UUID 数字**。三个月后三类问题同时出现：

- **门店后台查不到最新订单**：后台按 `store_id` 查（这是门店的高频查询），但分片键是 `order_id`——**查询带不上分片键**，只能广播到 16 个库、合并结果、再排序。延时从 20ms 涨到 2.3 秒；
- **跨库分页更痛**：订单列表要"第 3 页、每页 20 条"，每个库都要取 `OFFSET 40 LIMIT 20` 再归并去重，翻到第 10 页时每库要扫 200 行，16 个库合计 3200 行（第 18 篇的深分页问题在跨库下被放大 16 倍）；
- **订单与明细不在同一库**：明细表按 `detail_id` 分片，同一笔订单的两张表落到不同库，**本地事务失效**，只能改成最终一致（第 61 篇那套），复杂度陡增。

修复没有捷径——**重新选分片键并迁移**：改成按 `store_id` 分片（门店是最高频查询维度，且永不变更），并让订单与明细**共用同一分片键**（`store_id`）从而回到单库单事务；扩容路径按第 5 节的四步走：预分片 64 个逻辑分片、双写回填、按门店灰度切读、保留旧路由可回滚。整个过程花了六周，而如果最初就选对键，成本是零。

**用错的代价**：不是"查询慢一点"，而是**把业务模型逼上分布式一致性的绝路**——本来一个本地事务能解决的下单，被迫拆成事件 + 对账 + 补偿。

## 5. Java 示例代码

**分片键要让"同一聚合内的表"落在一起；跨库查询用批量组装，不要 N+1。**

```java
@Mapper
public interface OrderMapper {

    /**
     * 按分片键（store_id）查询：能路由到单库，这是分片设计的目标形态。
     * ★ 表名只能用 ${}（#{} 会被预编译成占位符，表名拼不进去），所以分片号必须由代码算出的 int，
     *  绝不允许来自用户输入（第 13 篇讲过 #{} 与 ${} 的区别，这里是 ${} 唯一合理的用法）。
     */
    @Select("SELECT * FROM order_${shard} WHERE store_id = #{storeId} AND id = #{orderId}")
    OrderEntity selectByShard(@Param("shard") int shard, @Param("storeId") long storeId,
                              @Param("orderId") long orderId);

    /** 订单明细也用 store_id 分片：与订单同库，才能留在同一个本地事务里（第 39 篇） */
    @Select("SELECT * FROM order_detail_${shard} WHERE store_id = #{storeId} AND order_id = #{orderId}")
    List<DetailEntity> selectDetails(@Param("shard") int shard, @Param("storeId") long storeId,
                                     @Param("orderId") long orderId);

    /** 全局唯一 ID 用雪花/号段，绝不能用分片表上的 AUTO_INCREMENT（会重复） */
    // long id = IdUtil.getSnowflakeNextId();    // Hutool；或 MyBatis-Plus 的 IdWorker.getId()
}
```

**在线扩容的骨架：预分片 + 双写 + 灰度切读，任何阶段都能切回。**

```java
/** 预分片的关键：路由到"逻辑分片"，物理库只是逻辑分片的容器 —— 扩容只搬逻辑分片，不重算全量数据 */
public int route(long storeId) {
    long logicalShard = storeId % 64;        // 一开始就分 64 个逻辑分片，物理上先放 4 个库
    return (int) (logicalShard % CURRENT_DB_COUNT);   // 扩库时只改这一行映射
}

/**
 * 迁移期双写：新库为主、旧库兜底。
 * ★ 注意：跨库双写不能被一个 @Transactional 包住——本地事务只覆盖一个数据源，
 *   两者要么各自独立提交、要么上分布式事务（第 63 篇说过：尽量别上）。
 *   这里选择"新库为准 + 旧库尽力写 + 差异留给对账"（第 61 篇那套）。
 */
public void createOrder(OrderCmd cmd) {
    OrderEntity order = build(cmd);
    orderMapper.insert(order);               // ① 新分片：唯一真相，必须成功
    try {
        legacyOrderMapper.insert(order);     // ② 旧库：尽力写，失败只记录不抛错
    } catch (DataAccessException e) {
        log.warn("旧库双写失败，待对账补齐 orderId={}", order.getId(), e);   // ③ 由对账任务兜底
    }
}
```

## 6. 常见坑

**坑 1：分片键选"会变的字段"或"查询用不上的字段"。** 错误做法：为了"写入均匀"用随机 ID，或选一个业务上可修改的字段（如所属门店可转移）。问题：前者让高频查询无法路由、只能广播（延时翻十倍）；后者改一次字段要跨库搬数据，还要处理历史引用失效。正确做法：**选永不变更 + 覆盖绝大多数高频查询的维度**（用户/门店/租户），先统计线上查询分布再定，而不是拍脑袋。

**坑 2：以为分片后还能像单库一样写 SQL。** 错误做法：写跨库 JOIN、跨库事务、`ORDER BY` 全表排序。问题：跨库 JOIN 要么被中间件拒绝、要么退化成拉全量数据在内存拼（第 19 篇 N+1 的放大版）；跨库事务只能靠最终一致，成本和风险陡增。正确做法：**同一聚合共用分片键**（订单与明细同键，回到本地事务）；跨库关联改成应用层批量组装（收集 ID 一次 `IN` 查回）；统计报表走离线数仓或旁路，不在分片库上跑。

**坑 3：扩容靠"停机搬数据"或直接改模数。** 错误做法：把 `% 16` 改成 `% 32` 然后停服导出导入。问题：取模变更会让**几乎所有数据都要迁移**，停机窗口不可控，失败还无法回滚。正确做法：**预分片**（逻辑分片远多于物理库）+ 双写回填 + 按维度灰度切读 + 保留旧路由随时切回，整个过程和接口变更一样要有回滚预案（第 26 / 57 篇）。

## 8. 面试 / 工作中常见问题

### 问题 1：分片键怎么选？

参考答案：三个条件同时满足：**高频查询能带上它**（否则广播查询）、**分布足够均匀**（避免热点，参考第 60 篇的分桶思路）、**永不或极少变更**。通常选用户 ID / 门店 ID / 租户 ID 这类天然维度；如果业务有多个高频维度（如同时按用户和按商品查），要做"一份数据 + 冗余表（异构索引）"或走 ES 旁路，而不是指望一个键全满足。选之前先拉线上查询清单统计占比，别拍脑袋。

### 问题 2：跨库分页怎么处理？

参考答案：优先设计成"不跨库"——查询一定要带分片键，把分页约束在单库内。确实需要全局分页时：小规模用归并（每库取 `offset + limit` 再合并排序去重）；大页码场景改用**游标分页**（带上一次的排序键继续往后取，避免深 `OFFSET`，第 18 篇）；数据量大且查询维度多，就把列表需求交给 ES 或离线宽表，分片库只服务按分片键的精确查询。

### 问题 3：正在跑的库要扩容，怎么做才安全？

参考答案：四步走。① **预分片**是从第一天就该做的（逻辑分片远多于物理库），扩容只是搬逻辑分片；② **双写 + 回填**：新库承接增量、历史数据分批回填，并用对账比对差异（第 61 篇）；③ **灰度切读**：按用户/门店维度小比例切，观察延迟与错误率；④ **回滚预案**：旧库保留读写能力，出问题切回。整个过程要有容量与延迟指标护航（第 64 篇），并把窗口安排到低峰。

## 9. 今日小结

- 分片键是一份**数据契约**：选"永不变更 + 覆盖高频查询 + 分布均匀"的维度，选错就是六周迁移。
- 同一聚合（订单与明细）**共用分片键**，是把跨库事务压回本地事务的唯一设计手段。
- 跨库三件事必须重新设计：JOIN 改批量组装、分页改游标或归并、统计走数仓/ES 旁路。
- 分片后自增主键会撞车（用雪花或号段）；扩容的完整动作是**预分片 + 双写 + 灰度切读 + 可回滚**，且扩展顺序始终是 SQL 治理 → 缓存 → 读写分离 → 分片。

明天建议学习：`冷热分离与数据生命周期`

原因：分片解决"数据放不下"，但还有个更省钱的角度——**很多数据根本不该待在昂贵的在线库里**。三年前的历史订单几乎没人查，却和今天的订单一样占索引、占备份、拖慢 DDL 与扩容（第 52 / 66 篇的代价都与表大小正相关）。明天讲冷热分离：热表边界怎么定（时间 + 状态）、归档任务怎么设计成可重放（第 61 篇）、冷存储怎么选（归档表 / 对象存储 / 数仓），以及数据保留期在合规与成本之间怎么平衡。
