# Java 学习：Optional 是否应该使用

> 系列第 31 篇 · 第四阶段：精度、安全与稳定性
> 昨天建立了一套手写判空的防线，但防线全靠 `if (x != null)`，写多了又啰嗦又容易漏。Java 8 给出的官方答案是 `Optional`：把"这里可能没有值"写进返回类型。可它并不是万能钥匙——官方定位和阿里开发规范一直强调"克制使用"。今天讲清楚：Optional 是什么、怎么用，更重要的是哪些地方不该用。

## 1. 今天学什么

`Optional<T>` 是 Java 8 引入的容器类，用来包装一个"可能有、也可能没有"的值。方法返回 `Optional<User>` 时，签名本身就在告诉调用方：这次查询可能查不到，别默认有值。这等于把 null 的隐患从实现内部提到了类型签名上，逼着每个调用方显式处理"空"的情况。

今天主题的关键词是"是否应该"。Optional 的设计者 Brian Goetz 在设计文档里说得很直白：它只为**方法返回值**设计，不该用来做字段、不该做方法参数、更不该装进集合。阿里 Java 开发手册也是同样口径。用错地方的 Optional 不会让代码更优雅，只会制造序列化事故和无谓的包装。学 Optional，一半是学用法，一半是学克制。

## 2. 前端工程师视角理解

可以把 Optional 理解成"给值额外套一个盒子，盒子上贴着标签：里面可能是空的"。

写 TS 时你会写 `function findManager(storeId: number): User | null`，返回类型里的 `| null` 就是类型契约，编译器会强制调用方收窄。Java 的类型系统表达不了"可空"，于是用一个真实对象来替代：`Optional<User>`。调用方拿到的不是 User，而是一个容器，必须显式拆盒（`orElse`、`map`、`ifPresent`……），拆的过程自然就思考了"空了怎么办"。

对照昨天学的手写判空：

```java
// 昨天的写法：拿到值，自己记得判空
User manager = userMapper.selectManagerByStore(storeId);
String name = (manager != null) ? manager.getName() : "未分配";

// 今天的写法：类型声明"可能为空"，链式处理
String name = storeService.findManager(storeId)
        .map(User::getName)   // 类似 ?.name
        .orElse("未分配");     // 类似 ?? '未分配'
```

Java 没有 `?.` 和 `??` 语法糖，Optional 的 API 就是方法版的等价物。至于"是否应该用"——服务层查询方法的返回值值得用，字段、参数、集合这些位置先想想是否必要。

## 3. 和 JavaScript / TypeScript 的对比

**表达载体不同。** TS 把可空性写在类型里（`User | null`），零运行时成本，编译器强制执行；Optional 是真实存在的运行时对象，有创建和方法调用开销。这正是 Java 社区对它吝啬的原因：可空的地方太多，每处都包一层成本扛不住，只值得用在最容易出事故的"方法返回值"这一个位置。

**约束力度不同。** TS 里写了 `User | null`，还有人用 `as User` 硬蒙混过关，契约靠编译器也靠自觉。Optional 更彻底：你拿到的就是容器，不拆盒根本当不了 User 用，语言层面逼你面对空分支。代价是调用处变啰嗦，每次取值都要经过方法调用。

**JS 里没有对应物。** JS 没有 option 类型（亲戚是 Rust 的 `Option`、Haskell 的 `Maybe`），可空全靠 `?.` 和 `??` 兜底。所以不要在 JS 世界里找 Optional 的对应物，把它理解成"TS 联合类型被装进了运行时对象"即可。

**序列化行为不同，这一条对前后端协作最关键。** TS 的 `User | null` 序列化成 JSON，null 就是 null；Java 的 Optional 是个普通对象——把它放进 DTO 字段，Jackson 会序列化出 `{"present":false,"empty":true}` 之类的怪异结构，甚至直接报错。这是 Optional 不能进 DTO 的第一理由。

## 4. 真实业务场景

**场景：门店详情页的"区域负责人"字段，有的门店还没分配负责人。**

业务背景：运营后台的门店详情页要展示"区域负责人"。真实业务里新开门店经常还没分配负责人，"没有负责人"是正常业务状态，不是错误。StoreService 提供 `findManager(storeId)`，它有好几个调用方：详情页接口、月度报表导出任务、门店交接流程。

按昨天的写法返回 User，调用方各自记得判空。结果三个调用方总有一个漏判，线上一查就是 NPE，且只在"没分配负责人的店"上复现。今天把返回值改成 `Optional<User>`，"可能为空"被提到方法签名上，任何新调用方看到类型就知道要处理空分支，不靠记性靠类型。

误用则是另一头的事故。有同学觉得"这么好用，VO 字段也安排上"，在 StoreDetailVO 里写 `private Optional<String> managerName;`。前端联调时收到的不是 `managerName: null`，而是 `managerName: {"present":false,"empty":true}`，页面上直接展示出一串对象文本。类型设计的好意变成前后端联调事故——这正是今天主题叫"是否应该使用"而不是"怎么使用"的原因。

## 5. Java 示例代码

```java
// StoreService：返回值用 Optional，签名明确写着"可能查不到"
public Optional<User> findManager(Long storeId) {
    // MyBatis Mapper 返回值仍是普通类型，Service 层包一层
    User manager = userMapper.selectManagerByStore(storeId);
    return Optional.ofNullable(manager); // null 转成 Optional.empty()，非 null 正常包装
}
```

```java
// 调用方：三种拆盒方式，对应三种业务语义
// 1) map + orElse ≈ JS 的 manager?.name ?? '未分配'
String managerName = storeService.findManager(storeId)
        .map(User::getName)         // 为空直接跳过，有值则取字段
        .orElse("未分配");

// 2) orElseThrow："查不到"本身是数据异常，抛带错误码的业务异常
Order paidOrder = orderService.findLatestPaidOrder(storeId)
        .orElseThrow(() -> new BizException(ErrorCode.ORDER_NOT_FOUND, "该门店不存在已支付订单"));

// 3) ifPresent：有值才做一件事，等价于 if (manager != null) {...}
storeService.findManager(storeId)
        .ifPresent(manager -> vo.setManagerPhone(manager.getPhone()));
```

```java
// orElse 与 orElseGet 的区别在默认值的求值时机，容易踩
// orElse：参数先求值——即使容器里有值，这行也会执行
vo.setRemark(opt.orElse(buildDefaultRemark()));        // buildDefaultRemark() 总会跑
// orElseGet：lambda 只在空时才执行；默认值需要查库或昂贵计算时必须用它
vo.setRemark(opt.orElseGet(() -> configService.getDefaultRemark()));
```

```java
// 三个反面例子，都是代码评审里真实会遇到的：
// ❌ Optional 做 DTO 字段：序列化出怪异 JSON，前端没法消费
public class StoreDetailVO {
    private Optional<String> managerName; // 错，DTO 字段用普通类型
}
// ❌ Optional 做方法参数：调用方被迫包一层，负担大于收益
public void audit(Long storeId, Optional<String> reason) { ... } // 错
// ❌ 不检查直接 get() 拆盒：把 NPE 换成 NoSuchElementException 而已
User u = storeService.findManager(storeId).get(); // 错
```

## 6. 常见坑

**坑 1：不检查直接 `.get()`。** 错误理解："get() 比 orElse 直接"。问题：值为空时抛 `NoSuchElementException`，本质是换了马甲的 NPE，用 Optional 的意义全丢了。正确做法：一律用 `orElse / orElseGet / orElseThrow / map` 拆盒；真要用 get() 也得先 `isPresent()` 检查，但更推荐 orElseThrow，能把错误信息带出来。

**坑 2：把 Optional 放进 DTO / Entity 字段。** 错误写法：`private Optional<String> managerName;`。问题：Jackson 把 Optional 当普通对象序列化，出 `{"present":false,...}` 这种结构或直接报错；且 DTO 是给前端的序列化契约，不该携带实现细节。正确做法：VO 字段用普通类型，空就是 null，配合统一返回结构向前端交代。

**坑 3：Optional 当方法参数。** 问题：每个调用方都被迫 `Optional.of(x)` / `Optional.empty()` 包一层，签名负担大，而官方设计意图只针对返回值。正确做法：参数用普通类型加校验注解（呼应第 21 篇请求参数校验），需要区分"可以不传"就提供方法重载。

**坑 4：给集合包一层 `Optional<List<T>>`。** 问题：多此一举——空结果本来就该用空集合表达，调用方拿到直接循环。正确做法：一律返回 `Collections.emptyList()` 而不是 null，这条规则在昨天坑 5 已经立过，Optional 不该推翻它。

**坑 5：默认值有计算成本时用了 orElse。** 错误写法：`opt.orElse(queryDefaultFromDb())`。问题：orElse 的参数先求值，即使容器里有值，那次数据库查询也白白执行了。正确做法：换 `orElseGet(() -> queryDefaultFromDb())`，lambda 只在空时执行。

## 7. 和之前知识的连接

- **第 30 篇「null 与空指针」**：今天是昨天防御战术的升级——把"调用方自觉判空"变成"返回类型主动声明"。昨天月报例子里 `latestOrder` 的两层判空，用今天的 `Optional.map().orElse()` 重写就是一行表达式。
- **第 15 篇「selectOne / selectList 的区别」**：selectOne 查无记录返回 null，正是 Optional 的主场。注意 MyBatis Mapper 接口返回的还是普通类型，要在 Service 层包一层，别指望 Mapper 直接返回 Optional。
- **第 10 篇「DTO / VO / Entity 的区别」**：DTO/VO 是给前端的序列化契约，直接推出今天"Optional 不能进 VO 字段"的结论——哪一层用什么对象承载数据，这个分层思想一直在起作用。
- **第 23 篇「状态码设计」**：今天 `orElseThrow` 抛出的 `BizException(ErrorCode.ORDER_NOT_FOUND, ...)` 正是状态码体系的延续——空值不只有"给默认值"一条路，还有"带错误码抛错"这一档。

## 8. 面试 / 工作中常见问题

### 问题 1：Optional 是为了解决什么问题？为什么不推荐当字段和参数？

参考答案：Optional 为方法返回值设计，目的是把"可能没有值"表达在类型上，让调用方显式处理空。不当字段：一是 DTO/Entity 要序列化，Jackson 对 Optional 支持很差；二是给对象平添存储和包装开销。不当参数：调用方被迫包一层，可读性反而不如方法重载或普通类型加校验注解。一句话：Optional 是"出口"约定，不是"入口"和"存储"约定。

### 问题 2：orElse 和 orElseGet 的区别？什么时候会出问题？

参考答案：orElse 接收一个已经算好的值，即使容器有值，默认值表达式也会被求值；orElseGet 接收 lambda，只在空时才执行。默认值是常量时两者无差别；但默认值来自查库、RPC 或昂贵构造时，误用 orElse 每次调用都多一次无谓求值，可能造成重复查询甚至重复生成幂等键之类的副作用。凡是默认值有成本或副作用，一律 orElseGet。

### 问题 3：查询可能查不到数据时，接口层该返回 Optional 吗？REST 接口怎么处理？

参考答案：分两层看。Service 层查询方法返回 Optional 是合适的，能强制调用方处理空；但 Optional 不该出现在 Controller 返回值或 DTO 字段里，前端收到的必须是普通 JSON。REST 层面："查不到"是正常业务态就在统一返回结构里给默认值或 null 字段；"查不到"属于异常，就用 orElseThrow 抛业务异常，由全局异常处理器转成状态码和错误信息——全局异常处理是后面的主题，这条链路很快会闭环。

## 9. 今日小结

- Optional 是 Java 8 的容器类，把"可能没有值"写进返回类型；定位只有方法返回值。
- `map` ≈ `?.`，`orElse` ≈ `??`，`orElseThrow` ≈ "取不到就带错误码抛错"；这是 Java 没有可选链语法时的替代方案。
- 三不做：不当 DTO 字段（序列化炸）、不当方法参数（调用方受罪）、不包集合（用空集合）。
- orElse 先求值、orElseGet 懒执行，默认值有成本必须用后者。
- 直接 `get()` 拆盒是变相 NPE，拆盒永远走有兜底语义的方法。
