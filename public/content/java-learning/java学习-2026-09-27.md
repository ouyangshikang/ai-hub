# Java 学习：冷热分离与数据生命周期

> 系列第 67 篇 · 第八阶段：数据架构进阶（第 3 篇）
> 衔接上一篇「分库分表与在线扩容」：分片解决"数据放不下"，但更省钱的思路是——**很多数据根本不该待在昂贵的在线库里**。
> **与第 66 / 52 篇的分工**：那两篇处理"表太大怎么办"（分片、DDL、慢 SQL），今天处理"**表里不该留的数据怎么请出去**"：热表边界、归档任务的工程形态、冷存储选型与保留期。

## 1. 今天学什么

冷热分离的本质是一次**成本与可用性的再平衡**：在线库的价格买的是"按主键 / 分片键的高速精确查询"（第 66 篇的结论），而三年前的历史订单既不需要这个速度，也很少被查——它们却和今天的订单一样占索引、占备份、拖慢 DDL 与扩容。

今天讲四块：① **热表边界怎么定**——时间 + 状态 + 业务查询分布，三者缺一不可；② **归档任务怎么设计**——分批、限速、幂等可重放、先校验后删除（这套纪律和第 61 篇的消息投递是同源的）；③ **冷存储怎么选**——归档表、只读库、对象存储、数仓各适合什么查询；④ **保留期与合规**——法定保留、删除权、销毁可审计，这三件事决定了归档不是"能删就删"。

一句话定位：**数据生命周期管理是把"存储成本"从线性增长变成可控工程**的唯一手段。

## 2. 前端工程师视角理解

你早就在用冷热分层，只是没意识到：Chrome 的请求会依次经过 **memory cache → disk cache → 网络（回源）**——最近用过的在最快的一层，老的要么降级到磁盘、要么直接淘汰。后端的冷热分离是同一个分层：**在线库 = memory cache，归档库 = disk cache，对象存储 = 冷备份**，而"淘汰策略"就是你今天要设计的归档任务。

第二个类比是**前端埋点上报**：事件先写本地缓冲，攒够了批量上报，超过保留期的本地数据直接丢弃——你从不会把三个月的日志全塞在 localStorage 里。后端归档任务就是服务端版本的"批量上报 + 定期清理"，两者都要面对同样的问题：**中断了怎么办（断点续传）、重复了怎么办（幂等）、搬完怎么确认没丢（校验）**。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 分层结构 | memory → disk cache → 回源 | 热表 → 归档库 → 对象存储 / 数仓 |
| 淘汰策略 | LRU / TTL 自动 | 归档任务按"时间 + 状态"显式搬运 |
| 搬运动作 | 缓存回填、脏数据丢弃 | 先复制、再校验、后删除（不能反过来） |
| 幂等要求 | 重复上报去重 | 归档任务必须可重放（同批次号只搬一次） |
| 失败处理 | 丢弃 + 监控上报失败率 | 跳过坏数据、记录差异、对账兜底 |
| 合规约束 | 本地不存敏感数据 | 保留期、删除权、销毁审计 |

**最需要建立的新直觉：删除是唯一不可逆的操作，所以它必须排在最后。** 前端清缓存无所谓——源站还在；后端删了热库的行，如果归档时静默漏了几百条，就**真的没有第二份**了。所以顺序永远是：写冷 → 校验行数与校验和 → 才删热（第 61 篇对账思路的直接复用）。

## 4. 真实业务场景

**场景：一次"清理历史订单"的操作，让售后查不到三个月前的订单。**

业务背景：订单表 12 亿行，运维按"创建时间超过 90 天"批量删除，SQL 写得很干脆：`DELETE FROM orders WHERE created_at < NOW() - INTERVAL 90 DAY LIMIT 100000`，循环执行。当晚出三件事：① **一次删 10 万行的大事务**，锁范围大、主从延迟飙到 8 分钟（第 52 / 65 篇的老问题），下单接口超时；② **售后打不开三个月前的订单**——原来"90 天"是拍脑袋定的，而客诉追溯期是 6 个月，业务规则与归档条件脱节；③ 更糟的是**已取消但未退款的订单也被删了**，财务对账时缺了依据，只能人工翻备份恢复。

修复后的方案把三件事分开：**边界重定**——时间改 180 天，并且**只归档终态订单**（已完成、已关闭、已退款），任何"进行中"的状态一律不许动（这是铁律）；**归档任务重写**——按主键范围分批（每批 2000 行）、每批限速、只搬不删、搬完校验行数与校验和、确认后才删热，整个批次记录在归档表里（幂等可重放、可断点续传、可随时暂停）；**冷存储分层**——180 天以上进归档表（还支持按订单号点查，售后够用），两年以上导出 Parquet 到对象存储（只用于审计），保留期由法务确认。

**用错的代价**：不是"空间省了一点"，而是**用一次不可逆的删除，把业务的可追溯能力打掉**——数据还能从备份捞回来的算幸运，捞不回来就是合规事故。

## 5. Java 示例代码

```java
/** 归档任务：分批 + 限速 + 幂等批次记录 + 先搬后校验再删 */
@Component
@RequiredArgsConstructor
@Slf4j
public class OrderArchiveJob {

    private static final int BATCH = 2000;

    private final OrderMapper orderMapper;
    private final ArchiveMapper archiveMapper;
    private final ArchiveBatchMapper batchMapper;      // 批次表：记录进度，保证可重放

    /** 一键停开关（第 49 篇）：归档出问题时先停任务，再排查，不要靠改代码发版 */
    @Value("${store.archive.enabled:true}")
    private boolean archiveEnabled;

    @Scheduled(cron = "0 0 3 * * *")                   // 低峰执行（第 44 篇的定时任务纪律）
    public void archive() {
        if (!archiveEnabled) return;                   // 配置开关：出问题一键停（第 49 篇）

        long lastId = batchMapper.loadLastArchivedId();
        while (true) {
            // 只搬终态订单：任何进行中的状态都不许动，这是不可协商的前提
            List<OrderEntity> batch = orderMapper.selectArchivable(lastId, BATCH);

            for (OrderEntity o : batch) {
                int rows = archiveMapper.insertFromOrder(o.getId());   // 先复制到冷库
                if (rows == 0) {
                    log.warn("归档复制未生效，跳过并记录 orderId={}", o.getId());   // 坏数据隔离
                    continue;
                }
                // 校验通过才删热库；校验失败保留热数据，交给人工核对
                if (archiveMapper.checksumEquals(o)) {
                    orderMapper.deleteByIdIfTerminal(o.getId());       // 条件删除：状态又变了就不删
                }
                lastId = o.getId();
            }
            batchMapper.saveProgress(lastId);          // 记录进度：任务可暂停、可续跑、可重放
            if (batch.size() < BATCH) break;
        }
    }
}
```

```sql
-- 保险一：热库侧的条件删除（状态在归档期间被改回"进行中"就不删）
DELETE FROM orders WHERE id = #{id} AND status IN ('FINISHED','CLOSED','REFUNDED');

-- 保险二：搬完做一次总量校验（逐批比行数，必要时比 CHECKSUM TABLE / 字段哈希）
SELECT COUNT(*) FROM orders WHERE id BETWEEN #{from} AND #{to};
SELECT COUNT(*) FROM orders_archive WHERE id BETWEEN #{from} AND #{to};
```

## 6. 常见坑

**坑 1：归档条件没排除"进行中"的状态。** 错误做法：只按时间删（`created_at < 180 天`）。问题：一张跨不了几个月的长流程订单（分期、争议、退货中）会被归档甚至删除，用户和客服都查不到，还会击穿财务对账。正确做法：**时间 + 状态双条件**，且状态白名单要纳入业务与法务评审；归档期间状态可能变化，所以删除必须带条件（`AND status IN (...)`），不能只按 id。

**坑 2：用大事务一批删光。** 错误做法：一条 `DELETE ... LIMIT 1000000` 循环跑，或归档与删除在同一事务里。问题：大事务制造长锁与主从延迟（第 52 / 65 篇），拖垮在线业务；事务太大还会把 undo 撑爆。正确做法：**小批次 + 每批独立提交 + 限速（必要时 sleep）+ 低峰执行**；"复制到冷库"和"删除热库"分两步提交，中间隔一步校验，去掉这个依赖反而更安全。

**坑 3：只搬不校验，或者搬完就"以为对了"。** 错误做法：删之前不比对行数，或者在应用层凭"插入没报错"就认为成功。问题：静默失败（影响行数为 0、字段截断、编码问题）在归档里是"丢了就永远丢了"，第 34 篇那句"没抛异常不代表没问题"在这里代价最大。正确做法：**每批校验行数与关键字段校验和**，差异进清单人工处理；搬完保留一段"双读期"（热库数据先软标记，确认冷库可查后再物理删）。

## 7. 和之前知识的连接

- **第 66 篇「分库分表与在线扩容」**：分片与冷热分离是同一笔账的两个方向——一个把数据摊开，一个把数据请出去；两者都指向同一句原则：在线库只服务按主键 / 分片键的高频查询。
- **第 61 篇「消息可靠性与最终一致性」**：归档任务与 Outbox 投递器共享同一套纪律——分批、幂等、可重放、对账兜底；今天的批次表就是那篇 `outbox` 表思想在数据搬迁上的复用。
- **第 52 / 65 篇「慢 SQL / 主从延迟」**：大事务是这两篇里反复出现的元凶，归档是它最容易复发的场景，所以"小批次 + 限速 + 低峰"是硬要求。

## 8. 面试 / 工作中常见问题

### 问题 1：热表边界怎么定？

参考答案：三个输入一起定：**时间**（按业务追溯期，而不是"看着差不多"）、**状态**（只归档终态，进行中一律不动）、**查询分布**（老数据若仍在被高频查，说明还不能归档，而是该建索引或做分区）。边界还要有业务与法务的可解释性：客诉追溯期、财务对账周期、监管保留期，哪条更长就以哪条为准。

### 问题 2：归档任务怎么写才安全？

参考答案：把它当成一次"数据搬迁工程"：**先复制后删除**（顺序不能反）、**小批次 + 独立提交 + 限速 + 低峰**、**每批校验行数与校验和后再删**、**批次进度落表**（幂等、可断点续传、可随时暂停）、**删除带状态条件**（防止归档期间状态回退）、**差异清单人工兜底**。上线时先只搬不删跑一段时间（双读期），确认冷库能查到、查到的是对的，再开启删除。

### 问题 3：冷数据还能被查询吗？怎么设计？

参考答案：按**查询形态**设计：如果只有"按订单号点查"的需求（售后最常见），就用归档表（同构、可加索引、成本低）；如果只是审计导出，用对象存储放 Parquet / CSV，按需批量取；如果要做分析聚合，进数仓；如果是模糊检索，进 ES。关键是**保留一条可用的点查入口**（应用层先查热库、未命中查归档，或提供专门的"历史查询"接口），否则用户会认为数据"丢了"。同时把合规考虑进去：删除请求要能穿透到冷存储，销毁过程要留审计记录。

## 9. 今日小结

- 冷热分离的收益是"把存储成本从线性增长变成可控工程"，前提是边界有业务与法务依据。
- 边界 = **时间 + 状态 + 查询分布**；进行中的状态绝不许归档，这是不可协商的前提。
- 归档任务的纪律：**先复制、再校验、后删除**，小批次、限速、低峰、批次可续跑（第 61 / 52 篇的同一套）。
- 冷存储按查询形态选（点查用归档表、审计用对象存储、分析用数仓、检索用 ES）；删除是唯一不可逆的操作——先跑通双读期再物理删除，并给保留期与删除权留出合规出口。
