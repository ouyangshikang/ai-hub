# Java 学习：消息队列基础

> 系列第 47 篇 · 第五阶段：事务与架构进阶（本阶段收尾）
> 衔接上一篇「Redis 基础」：昨天 Redis 解决"多个实例共享一份状态"，但它管不了**跨服务的异步通知与削峰**——支付成功后要通知库存、发券、门店、财务四个下游，任何一个抖动都不该阻断已经收钱的主流程。今天讲 MQ 的定位、消息在哪里丢、重复怎么防、顺序为什么贵。

## 1. 今天学什么

消息队列（MQ）是**服务之间的缓冲区**：生产者把消息丢进队列就返回，消费者按自己的节奏取。它解决三件事——**解耦**（下单服务不认识下游）、**异步**（非核心链路挪出主流程）、**削峰**（用队列吸收瞬时流量）。今天讲四块：① 什么时候该用 MQ、什么时候是过度设计；② 一条消息从产生到消费完，三个环节各自会在哪里丢；③ "至少投递一次"带来的重复消费与幂等；④ 顺序消息为什么贵、积压了怎么办。

## 2. 前端工程师视角理解

最贴的类比是**事件总线**。`emitter.emit('order:paid', payload)` 之后，组件 A、B、C 各自订阅处理，发消息的人**不认识也不需要认识**消费的人——这就是解耦。但请注意异步化带来的连带变化：`POST /order` 返回 200，不代表订单真的处理完了，它只代表"已受理"，真实结果要靠轮询或推送。很多前端"提交成功却查不到数据"的困惑，根源就在这里。

**决定性差异在于消息的分量。** 前端丢一个事件无所谓，页面刷新一下又回来了；后端的消息代表**一次业务事实**——"用户已经付了 38 元"。这条消息丢了，用户付了钱却没发货，是实打实的资损。所以在后端，MQ 的第一工程指标不是吞吐量，而是**可靠性**：能不能保证不丢、不重、不乱。

第二个差异是**它有物理形态**。EventEmitter 在内存里，进程结束就没了；MQ 要落盘、会积压、能重投，于是多出"积压怎么办""重投导致重复怎么办""顺序错了怎么办"这三座山——前端事件模型里根本不存在这些。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 EventEmitter / 回调 | 后端 MQ |
|---|---|---|
| 投递保证 | 触发一次，丢了就丢 | 默认 **at-least-once**：失败重投，消费方必须幂等 |
| 失败处理 | 冒泡到 `window.onerror` | 重试 + 退避 + **死信队列（DLQ）**，需人工兜底 |
| 作用域 | 同进程内同步执行 | 跨进程跨服务，秒到分钟级延迟 |
| 背压 | 事件队列无上限，打爆内存 | 磁盘积压可控，但积压拖垮下游时效 |
| 广播语义 | 一个事件所有监听器都收到 | **同组内竞争消费，不同组各得全量** |

最后一行是需要专门理解的新概念：**Topic + ConsumerGroup**。四个下游各是一个独立 group，每群收全量；库存服务自己的 4 个实例同属一个 group，一条消息只被其中 1 个实例消费。也就是说，MQ 用**订阅方分组**同时给出了"广播"和"负载均衡"，而前端事件模型只有前者。

另一个习惯差异：TS 能给事件 payload 定义类型，MQ 消息本质是 JSON 文本，**跨服务演进只能靠约定**——加字段可以、改语义不行，这是第 26 篇接口兼容性在消息上的翻版。

## 4. 真实业务场景

**场景：门店小程序支付成功后的四条下游链路。**

业务背景：用户支付成功后要做四件事——扣库存、发券、通知门店出杯、财务记账。同步做法是下单服务依次 RPC 调这四个下游。

问题很直接：四段耗时相加，下单接口从 80ms 涨到 900ms；财务服务发布重启的 30 秒里所有下单全部失败——**而用户钱已经付了**。这才是必须上 MQ 的理由：不是"看起来更高级"，是**不能因为一个非核心下游挂掉就阻断主链路**。

再看削峰：大促开抢瞬间下单 QPS 3 万，订单库只扛得住 2000/s。MQ 把请求接进来排队，消费端按 2000/s 匀速写库。代价是用户订单可能"处理中"停留几秒，接口必须返回"已受理"语义（第 23 篇），前端要能展示排队态并轮询结果。

**用错的代价：** 消费端没做幂等，网络超时重投一次就多发一张券；没有死信队列，一条格式错误的消息反复重试，把整个消费组卡死；下游依赖了消息到达顺序，"退款"消息比"支付"消息先到，状态机直接错乱。

## 5. Java 示例代码

**生产端：事务提交后再发，用本地消息表兜底。**

```java
@Service
@RequiredArgsConstructor
public class PayServiceImpl {

    private final OrderMapper orderMapper;
    private final OutboxMsgMapper outboxMapper;      // 本地消息表
    private final RabbitTemplate rabbit;

    /**
     * 支付成功处理：更新订单 + 登记待发消息，在同一个 DB 事务内完成。
     * 不在事务里直接发 MQ——否则消息发出去了、事务却回滚，下游会收到一个不存在的事实。
     */
    @Transactional(rollbackFor = Exception.class)
    public void onPaySuccess(PayCallback cb) {
        orderMapper.markPaid(cb.getOrderNo(), cb.getPayTime());
        outboxMapper.insert(OutboxMsg.of("order-paid", cb.getOrderNo(),   // 消息号 = 业务号，供消费端幂等
                JSON.toJson(cb), Status.TODO));
    }

    /** 由定时任务（第 44 篇）扫描 TODO 记录投递：发送失败下轮重试，保证「库有消息就一定发出去过」 */
    public void flushOutbox() {
        outboxMapper.selectTodo(200).forEach(m -> {
            try {
                rabbit.convertAndSend("order-exchange", "order-paid", m.getBody());
                outboxMapper.markSent(m.getId());
            } catch (Exception e) {
                log.error("消息投递失败，等待重试 msgId={}", m.getId(), e);   // 不抛：留 TODO 下轮再来
            }
        });
    }
}
```

**消费端：业务成功之后再手动 ack，靠唯一索引去重。**

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class OrderPaidConsumer {

    private final ConsumeLogMapper consumeLogMapper;

    /**
     * 手动确认模式：只有业务真的处理成功才提交 offset。
     * 若在处理前 ack，一旦后面抛异常，消息已被认领、再也不会重投 —— 等于丢消息。
     */
    @RabbitListener(queues = "stock-order-paid", containerFactory = "manualAckFactory")
    public void onMessage(OrderPaidMsg msg, Channel channel,
                          @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            // ★ 幂等：msgId 建唯一索引，插入冲突说明这条已处理过，直接 ack 丢弃
            consumeLogMapper.insertConsumed(msg.msgId(), msg.orderNo());
            stockService.deduct(msg.orderNo());
            channel.basicAck(tag, false);                    // 业务成功才确认
        } catch (DuplicateKeyException dup) {
            channel.basicAck(tag, false);                    // 重复消息：确认掉，不算失败
        } catch (Exception e) {
            log.error("消费失败 orderNo={}", msg.orderNo(), e);
            // 第三个参数 requeue=false：不重回队列，交给重试策略/死信队列，避免热循环
            channel.basicNack(tag, false, false);
        }
    }
}
```

上面的 `manualAckFactory` 需要自己声明——Spring Boot 默认的容器工厂是自动确认，不改就没有手动 ack 的能力：

```java
@Configuration
public class MqConfig {

    /** AcknowledgeMode.MANUAL：把确认时机交回业务代码，坑 1 才有解 */
    @Bean
    public SimpleRabbitListenerContainerFactory manualAckFactory(ConnectionFactory cf) {
        SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
        factory.setConnectionFactory(cf);
        factory.setAcknowledgeMode(AcknowledgeMode.MANUAL);
        return factory;
    }
}
```

## 6. 常见坑

**坑 1：先 ack 再处理，或用自动提交。** 错误做法：`ack-mode: auto`（方法返回即确认），或进方法就 `basicAck`。问题：确认等于告诉 Broker"这条我收下了别重发"，之后业务抛异常消息就永久丢了。正确做法：**手动 ack，且只在业务成功之后确认**；Kafka 侧对应关闭 `enable.auto.commit`、处理完再提交 offset。

**坑 2：把 MQ 当"只投一次"用，消费端不幂等。** 错误理解：网络正常时一条消息只会来一次。问题：只要有重试和 rebalance，重复投递就是**必然**而非偶发；at-least-once 下不幂等等于资损。正确做法：每条消息带**业务唯一号**，消费端用唯一索引或状态机去重（第 25 篇那套），别用"先查后插"两步判断。

**坑 3：在数据库事务里同步发 MQ。** 现象：偶发"订单没支付成功，库存却扣了"。问题：`@Transactional` 方法内发消息时事务尚未提交，一旦回滚消息收不回；发消息本身的网络耗时还会拉长事务、拖住连接。正确做法：**事务内只写本地消息表，提交后再投**；或直接采用 RocketMQ 事务消息这类现成方案。

**坑 4：失败无限重回队列。** 错误做法：catch 里 `requeue=true`。问题：一条脏消息被无限重试，队列原地打转、CPU 打满，正常消息全被堵住。正确做法：`requeue=false` + 限制重试次数 + 指数退避，超过阈值进**死信队列**并告警，交人工或补偿任务处理。

**坑 5：上线后不看消费积压。** 现象：lag 一直涨，用户侧表现为"下单十分钟后还没拿到取餐码"。问题：积压说明消费能力不足或下游被拖垮，没有监控就只能等投诉。正确做法：把 **lag 和消费耗时**接进告警；积压时先扩消费者实例（**不能超过队列/分区数**，否则加了也不消费），再考虑临时降级非核心消费。

## 7. 和之前知识的连接

- **第 25 篇「接口幂等性」**：那篇的结论在 MQ 里从"最好有"变成"必须有"——重试使重复投递成为常态，唯一索引是消费端的入场券。
- **第 38～41 篇「事务」**：DB 事务和 MQ 发送不在同一边界内，一个 `@Transactional` 包不住，才有本地消息表与事务消息；跨服务只能做**最终一致**。
- **第 46 篇「Redis 基础」**：Redis 锁只能在同一套 Redis 内防并发，撑不起跨服务的"同一事实只处理一次"；用它做队列也不可靠，逐出或重启就没了。
- **第 22 / 23 篇「统一返回结构与状态码」**：链路一旦异步化，接口返回的就是"已受理"而不是"完成"，这套语义必须前后端共同约定。

## 8. 面试 / 工作中常见问题

### 问题 1：你怎么保证消息不丢？

参考答案：三段分头保证。**生产端**要拿到 Broker 确认（RabbitMQ publisher confirm、Kafka `acks=all`），更稳的是本地消息表或事务消息，把"业务成功"和"消息已登记"绑进同一个 DB 事务；**Broker 端**靠副本与持久化，单节点裸奔谈不上可靠；**消费端**手动确认，业务成功再 ack。最容易出问题的恰恰是最后一段——很多人默认框架会重投，其实是自己的 ack 时机把消息丢了。

### 问题 2：重复消费怎么解决？

参考答案：不指望 MQ 不重复，而是让消费**幂等**。按可靠性排序：① 消费记录表 + 业务唯一号唯一索引，冲突即视为已处理；② 状态机推进，重复消息落到"已处理"自然无效；③ Redis `SETNX` 去重只当辅助，它会逐出、会重启丢失，扛不住资金场景。最忌讳"先查后插"——两条并发消息会同时通过检查。

### 问题 3：需要保证顺序消息怎么做，代价是什么？

参考答案：MQ 只保证**分区内有序**，全局有序等于放弃并发。做法是让同类消息用同一个 key 路由到同一队列/分区——同一订单号的变更都进分区 1 由单消费者串行处理，不同订单仍并行。三个代价要认：单分区吞吐被封死、该分区成热点时无法横向扩容、消费者重启触发 rebalance 期间仍可能乱序。所以更稳的选择往往是：**不要求消息有序，消费端用版本号/时间戳自己判断该不该应用**。

## 9. 今日小结

- MQ 的三个真实价值：**解耦**（不认识下游）、**异步**（非核心链路别拖主流程）、**削峰**（用积压换 DB 存活），缺一个就别引入。
- 可靠性入场券是**手动 ack**：业务成功再确认；先确认再处理等于自己把消息丢了。
- at-least-once 意味着**重复投递是常态**，消费端必须幂等（唯一索引或状态机）；同理，顺序也别指望 MQ——用版本号在消费端判序更便宜。
- DB 事务里不要直接发消息：**事务内写本地消息表、提交后再投、失败重试**，这是最朴素也最难被推翻的方案。
