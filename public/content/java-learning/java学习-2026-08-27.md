# Java 学习：事务失效场景

> 系列第 40 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「Spring 事务注解」：上一篇的坑 5 留了个钩子——注解打了，却压根没生效，这比参数写错更隐蔽。今天把这份"失效清单"完整展开：为什么同类内部调用会绕过事务、为什么 private 方法上打注解等于白打、为什么 catch 吞了异常就不回滚，每一条都给出排查方法和代码修正。读完这一篇，你才算真正看懂"@Transactional 是靠代理生效的"这句话。

## 1. 今天学什么

上一篇讲清了 @Transactional 每个参数怎么写，但还有一类比参数写错更憋屈的问题：代码看起来完全正确——注解在、参数对、异常也抛了——事务却根本不存在，半截数据照常被提交，出了事故才发现这个注解从头到尾没起过作用。这类问题的共同根源是：**Spring 的事务不是靠注解直接生效的，而是靠代理对象生效的**。今天把失效场景逐条列出来：同类自调用、private / final / static 方法、异常被 catch 吞掉、新线程里执行、对象不是 Spring 管理的……每条都讲清"为什么失效、怎么排查、怎么修"。学完今天，线上再出"半截提交"的事故，你能照着清单在几分钟内定位到原因。

## 2. 前端工程师视角理解

理解今天内容只需要抓住一句话：**别的代码拿到的那个"你"，不是你本人**。

Spring 启动时，不会把你写的 OrderService 原样塞给调用方，而是生成一个**代理对象**（基于 CGLIB 的动态子类）注入进去。这个代理重写了带 @Transactional 的方法：方法执行前开启事务，正常返回后提交，抛异常就回滚。Controller 和其他 Service 注入到的，全是这个"加工过"的代理。

前端工程师可以类比 axios 拦截器：你给实例挂了 `api.interceptors.request.use(...)`，统一加 token、记日志——前提是请求真的走了这个实例。哪个组件绕开 apiClient 直接用了原生 `fetch()`，拦截器就完全不知情。同类自调用就是这种情况：方法内部的 `this` 指向原始对象，`this.otherMethod()` 是裸调用，不经过代理，前后自然没有开事务、提交、回滚这些动作——等于绕开实例直接 fetch。

再给一个同构的例子：Vue 3 的 `reactive()` 返回的是 Proxy，只有通过代理改属性才触发视图更新；你如果在哪里留了一份原始对象的引用直接改，界面纹丝不动。Spring 世界里，"不走代理"同样什么都不会发生。记住这句就够了：**注解贴在方法上，事务却长在代理上，谁绕过代理，谁就没有事务**。

## 3. 和 JavaScript / TypeScript 的对比

**TS 装饰器世界里几乎没有"自调用失效"，因为包装的位置不同。** TS / NestJS 的装饰器是在类定义时包裹**方法本身**——方法已经被替换成新函数了，之后无论谁调用、哪怕是类内部 `this.method()`，执行的都是包装后的版本。Spring 走的是**对象级**包装：方法还是原方法，运行时另造一个代理对象挡在入口。一个包方法（任何入口调都生效），一个包对象（只有通过代理调才生效）。这是两个生态的底层差异，也是前端工程师初遇事务失效时最困惑的地方——"我在 NestJS 里从没遇到过这种问题"。

**排查手段上，Java 反而比 JS 有"框架级线索"。** 事务有没有生效，Java 里有个非常直观的检查：打印注入的 bean 的类名，被代理过的对象形如 `com.xxx.StocktakeService$$SpringCGLIB$$0`，没被代理的就是干干净净的原类名。JS 里拦截器没执行，可没有这种一眼可辨的痕迹，只能靠 console.log 一步步追。所以排查 Java 事务问题的第一步往往就是"确认对象是不是代理"，成本比想象的低得多。

**"吞掉异常保平安"的前端肌肉记忆在这里是反模式。** 前端代码习惯 `try/catch` 加一行 console.error 兜底，免得一个报错白屏。这个习惯带进后端会出大事：Spring 判断回滚的依据是"异常是否抛出了方法外"，你自己 catch 掉，Spring 眼里这个方法就是成功的。异常在事务机制里是**信号**，吞信号等于拔电话线。

## 4. 真实业务场景

**场景：门店打烊盘点，"已完成"的盘点单只调了一半库存。**

业务背景：门店每天打烊后盘点，店员录入实物数量，店长点"完成盘点"，后端 finishStocktake 方法做三件事：① 计算每个 SKU 的差异数（实物 − 账面）；② 把盘点单状态更新为"已完成"；③ 按差异批量修正库存表。三步必须同生共死——库存只调了一半，第二天门店就会按错误的库存接单、备料。

开发同学是这么写的：submit(sheetId) 作为统一入口，负责参数校验，然后调用 this.finishStocktake(sheetId)；@Transactional(rollbackFor = Exception.class) 端端正正打在 finishStocktake 上。代码评审没有任何人提出异议。

事故经过：某天某门店提交盘点，第 ③ 步批量改库存时，一条库存行恰好被一笔进行中的订单并发更新，抛出乐观锁异常。按预期应该整体回滚，结果却是：盘点单状态已提交为"已完成"，库存改了一半、另一半没动。总部对账时发现账面和盘点结果对不上，最后靠工程师拿着盘点单明细手工补数。

排查结论：finishStocktake 的注解和参数全对，问题出在调用入口——submit 和它在同一个类里，`this.finishStocktake()` 是原始对象调用，没经过代理，这个方法全程在"裸奔"，压根没有事务。

## 5. Java 示例代码

错误写法（事故版本）：

```java
@Service
public class StocktakeService {

    // 统一入口：没有事务注解，只做校验
    public void submit(Long sheetId) {
        validate(sheetId);
        // 危险：this 指向原始对象，这次调用不经过 Spring 代理，
        // finishStocktake 上的 @Transactional 完全失效
        this.finishStocktake(sheetId);
    }

    @Transactional(rollbackFor = Exception.class)
    public void finishStocktake(Long sheetId) {
        // ① 算差异 ② 更新盘点单状态 ③ 批量调库存
        // ...
    }
}
```

修正一（推荐）：把事务方法抽到独立 Bean，跨对象调用必然经过代理：

```java
@Service
public class StocktakeService {

    @Resource
    private StocktakeTxService stocktakeTxService; // 注入另一个 Bean

    public void submit(Long sheetId) {
        validate(sheetId);
        // 跨对象调用会经过 Spring 代理，事务注解正常生效
        stocktakeTxService.finishStocktake(sheetId);
    }
}

@Service
public class StocktakeTxService {

    @Transactional(rollbackFor = Exception.class)
    public void finishStocktake(Long sheetId) {
        // ① 算差异 ② 更新盘点单状态 ③ 批量调库存
        // ...
    }
}
```

修正二（不想拆类时）：自注入，把自己的代理对象注入给自己：

```java
@Service
public class StocktakeService {

    // 注入自己的代理对象；@Lazy 避免启动时报循环依赖
    @Lazy
    @Resource
    private StocktakeService self;

    public void submit(Long sheetId) {
        validate(sheetId);
        // 通过代理调用，事务生效，等价于"调别人"
        self.finishStocktake(sheetId);
    }
}
```

再补一个高频手法——catch 了异常，仍想让事务回滚：

```java
@Transactional(rollbackFor = Exception.class)
public void importRows(List<Row> rows) {
    try {
        doImport(rows);
    } catch (Exception e) {
        log.error("导入失败", e);
        // 异常被吞掉后 Spring 看不见了，必须手动把当前事务标记为回滚，
        // 否则方法正常返回，Spring 会当成功处理、照常提交
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    }
}
```

## 6. 常见坑

**坑 1：同类自调用（出现频率最高）。** 错误形态：Service 里方法 A 调 this.B()，事务注解打在 B 上。问题：this 是原始对象，绕过代理，B 的事务形同虚设。正确做法：拆成两个 Bean，或自注入用 self.B()；评审时见到"调用带事务注解的 this 方法"直接亮红灯。

**坑 2：注解打在 private 方法上，或对象是 new 出来的。** 错误形态：为了"收敛入口"把 @Transactional 打在 private 方法上，或图省事 `new OrderService()` 绕开容器。问题：CGLIB 代理是生成子类，无法覆盖 private 方法；手动 new 的对象不经过 Spring 容器，根本没有代理。正确做法：事务注解只打在 Spring 管理的 Bean 的 public 方法上，final、static 方法同样无法被代理，一并避开。

**坑 3：catch 吞异常，Spring 以为成功了。** 错误形态：事务方法里 try/catch 住异常，只打一行 log.error，方法继续正常返回。问题：Spring 以"异常是否抛出方法外"为回滚依据，吞掉就照常提交半截数据。正确做法：catch 后要么重新抛出，要么调 setRollbackOnly() 手动标记回滚。这是上一篇「事务是什么」坑 1 的正式入册，今天有了配套救急手法。

**坑 4：新线程里执行事务逻辑。** 错误形态：在事务方法里为了提速，new Thread(...) 或丢线程池执行另一段带 @Transactional 的写库逻辑。问题：数据库连接是绑定在线程上的，新线程拿的是新连接，和主线程的事务完全不共享，回滚也够不着它。正确做法：必须同生共死的写操作不要放异步线程；确需异步处理的部分，挪到事务提交之后用消息队列做。

**坑 5：受检异常不回滚（老熟人，但永远排排查清单第一位）。** 上一篇刚讲过：不写 rollbackFor，受检异常默认照常提交。它在"看起来有、实际没有"的事故里占比最高、检查成本又最低，所以每次排查都先看它。

## 8. 面试 / 工作中常见问题

### 问题 1：@Transactional 打了，线上数据还是一半成功一半失败，你按什么顺序排查？

参考答案：按失效清单从高频到低频查：① 是否没写 rollbackFor 而抛的是受检异常；② 异常是不是被方法内部 catch 吞掉了；③ 调用入口是不是同类自调用；④ 方法是不是 private / final / static，或对象是 new 出来的、不受 Spring 管理；⑤ 是不是在异步线程里执行的；⑥ 数据库引擎是否支持事务（MySQL 的 MyISAM 不支持）。快速验证手段：打印 bean 的类名，看有没有 `$$SpringCGLIB$$` 后缀，一眼判断代理是否存在。

### 问题 2：为什么同类自调用事务不生效？有哪些修法？

参考答案：Spring 事务由为 Bean 生成的代理对象实现，开事务、提交、回滚都发生在代理这一层，只有经过代理的调用才有事务。类内部 `this.method()` 用的是原始对象，直接绕过了代理。修法三种：把事务方法抽到另一个 Bean 注入调用（最清晰，推荐）；用 @Lazy 自注入自己的代理再调用；或用 AopContext.currentProxy() 获取代理（需开启 exposeProxy，侵入性最强，一般不推荐）。

### 问题 3：事务方法里我 catch 了异常想走兜底逻辑，但又想让事务回滚，怎么办？

参考答案：异常被吞掉后，Spring 看不到任何异常，方法正常返回就会照常提交。这时要手动把当前事务标记为回滚：`TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。更推荐的习惯是：catch 后包装成业务异常重新抛出，交给全局异常处理器统一转响应——回滚由框架自动完成，代码里不留手动控制。只有在"确实要吞掉异常继续执行"的少数场景，才用手动标记。

## 9. 今日小结

- Spring 事务不是靠注解直接生效，而是靠代理对象：不经过代理，就没有事务。
- 同类自调用是失效头号原因，修法：拆 Bean 或 @Lazy 自注入。
- private / final / static 方法、手动 new 的对象、异步线程，都承载不了事务；注解只打在 Spring Bean 的 public 方法上。
- 回滚的判定依据是"异常抛出方法外"：吞了就要么重抛，要么 setRollbackOnly()。
- 排查第一步：打印 bean 类名看有没有 `$$SpringCGLIB$$` 后缀，确认代理是否存在。
