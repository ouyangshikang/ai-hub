# Java 学习：日志规范

> 系列第 34 篇 · 第四阶段：精度、安全与稳定性
> 昨天全局异常处理的兜底逻辑全靠一行 `log.error("系统异常", e)` 留线索，但"会打日志"和"打出凌晨三点能救命的日志"是两回事。今天讲日志规范：级别怎么分、占位符怎么写、该带哪些字段、怎么把一个请求的日志串起来。

## 1. 今天学什么

后端服务跑在服务器上，没有浏览器 DevTools，出了事故你唯一能依赖的就是日志。但"打了"不等于"有用"：新人的日志通常两种废稿——`System.out.println("进来了")`，没上下文没级别，线上根本收集不到；或者 `log.error("报错了")`，看着有模有样，排查时才发现既没订单号也没用户 id，几万行里等于没写。

日志规范就是把日志从"开发期的 printf 调试"升级成"生产环境的可检索证据"，具体四件事：用对级别（debug/info/warn/error 各管什么）、用对写法（占位符而非字符串拼接）、带全字段（业务主键必须出现）、串起链路（一个请求的日志能用一个 id 捞出）。这四件事决定了事故发生时你是十分钟定位，还是通宵翻代码。

## 2. 前端工程师视角理解

前端打日志基本是 `console.log` 走天下。这套习惯背后是个现实：前端日志散落在千万个用户的浏览器里，你默认拿不到，所以打日志更多是"给本地调试的自己看"。

后端完全反过来。所有日志集中在你自己的服务器上，由采集管道收进 Elasticsearch 这类系统，出事时按关键词全文检索。**后端日志的第一读者不是写代码的你，而是凌晨被告警叫醒、对这块代码一无所知的值班同事。** 所以后端日志天然要求有级别（能快速过滤严重程度）、有上下文（能定位到具体哪笔数据）、有时间（能对齐监控曲线）。

你其实接触过类似的东西——Sentry。前端报错上报 Sentry 时会带 breadcrumbs、用户信息，因为光有一句 `TypeError` 什么都查不出来。后端日志规范就是同一思想的服务器版：每条关键日志自带足够的面包屑。

## 3. 和 JavaScript / TypeScript 的对比

**Java 日志是"门面 + 实现"两层，JS 没有这个概念。** 业务代码写的是 SLF4J 接口，真正输出的是 Logback 实现，换实现不用改业务代码。JS 里接近的是 pino / winston，但多数前端项目还是裸用 console。

**占位符 vs 模板字符串，动机不同。** JS 写 `` log(`订单 ${orderId} 已支付`) ``，拼接成本可忽略；Java 要求 `log.info("订单 {} 已支付", orderId)`——延迟拼接：如果当前级别不输出 info，连拼接都不执行。每秒几万条日志的服务里这是实打实的 CPU 开销。更关键的是异常参数：`log.error("支付失败, orderId={}", orderId, e)` 里的 `e` 会被 SLF4J 特殊识别并打印完整堆栈，字符串拼接做不到。

**级别体系两边都有，执行力度不同。** console 也有 debug/info/warn/error，但浏览器里全打到同一个地方，没人真用它分级。Java 后端靠级别做两件硬事：配置里控制输出（生产只出 info 以上）、告警按级别订阅（error 触发告警）。级别打错，告警就乱，这不是风格问题。

**输出归宿不同。** console.log 打进浏览器控制台，关页面就没了；Java 日志滚动写入文件（按天切割、保留 N 天）再进检索系统。所以 Java 项目几乎从不直接用 `System.out.println`——它进不了日志文件，等于没写。Node 服务化后弃 console 改用 pino 输出结构化日志，走的是同一条演进路径。

## 4. 真实业务场景

**场景：运营反馈"有笔订单支付成功了但一直显示待支付"，要你排查。**

业务背景：门店订单服务，支付回调接口收到通知后要把订单状态从"待支付"改成"已支付"。某天运营甩来一个订单号：用户付了钱，页面却显示待支付。

没有日志规范时的排查现场：代码里只有 `log.info("收到回调")` 和 `log.error("处理失败")`。搜"收到回调"出几千条——全国门店每秒都在收回调，不知道哪条是这笔订单的；搜"处理失败"一条没有。只能本地复现、逐行加日志重新发版，一下午才定位到：回调里的订单号字段名和约定不一致，解析出 null，更新语句没匹配到任何行，静默成功。**"静默成功"是日志缺失时最贵的一种失败。**

按规范写完日志的排查现场：入口一条 `log.info("收到支付回调, orderNo={}, tradeNo={}", ...)`；更新后检查影响行数，为 0 时 `log.warn("支付回调未匹配到订单, orderNo={}", ...)`。用订单号一搜，三秒看到那条 warn，顺着 traceId 捞出整条链路，十分钟定位。同样的事故，一下午变十分钟——差距不在代码能力，在日志里有没有留订单号这个检索锚点。

## 5. Java 示例代码

```java
// Service 里的标准日志写法：Lombok 的 @Slf4j 自动生成 log 字段
@Slf4j
@Service
public class OrderService {

    public void handlePayCallback(PayCallbackDTO callback) {
        // 1) 入口日志：info 级别 + 业务主键，"谁来过"一搜便知
        log.info("收到支付回调, orderNo={}, tradeNo={}",
                callback.getOrderNo(), callback.getTradeNo());

        Order order = orderMapper.selectByOrderNo(callback.getOrderNo());

        // 2) 业务异常走 warn：预期内的失败，别污染 error 告警
        //    （呼应昨天：业务异常 warn、未知异常 error）
        if (order == null) {
            log.warn("支付回调未匹配到订单, orderNo={}", callback.getOrderNo());
            throw new BizException(ErrorCode.ORDER_NOT_FOUND, "订单不存在");
        }

        int rows = orderMapper.markPaid(order.getId(), callback.getTradeNo());
        if (rows == 0) {
            // 3) "静默失败"必须显式记日志：没抛异常不代表没问题
            log.warn("订单状态更新影响行数为0, orderId={}, orderNo={}",
                    order.getId(), order.getOrderNo());
        }
    }

    public void refund(Long orderId) {
        try {
            payGateway.refund(orderId);
        } catch (IOException e) {
            // 4) 异常日志：e 必须放最后一个参数，堆栈才完整
            //    错误写法 log.error("退款失败: " + e.getMessage()) 会丢堆栈
            log.error("调用退款接口失败, orderId={}", orderId, e);
            throw new BizException(ErrorCode.PAY_CHANNEL_ERROR, "退款渠道暂不可用");
        }
    }
}
```

## 6. 常见坑

**坑 1：用 `System.out.println` 打日志。** 问题：标准输出不进日志文件，采集系统收不到，也没级别和时间戳，生产环境等于没写。正确做法：一律用 `@Slf4j` 的 log 对象，评审见到 println 直接打回。

**坑 2：字符串拼接代替占位符。** 错误写法：`log.info("订单" + orderId + "状态" + status)`。问题：无论级别是否输出，拼接都会执行，高并发下白耗 CPU；参数为 null 还会拼出 "null" 字符串误导排查。正确做法：`log.info("订单{}状态{}", orderId, status)`，延迟求值，null 如实显示。

**坑 3：记异常时丢了堆栈。** 错误写法：`log.error("退款失败: " + e.getMessage())`。问题：拼进字符串后 `e` 不在最后一个参数位置，SLF4J 不会打堆栈，根因全部消失——这是第 32 篇"丢 cause"问题在日志层的翻版。正确做法：业务参数在前，异常对象永远放最后。

**坑 4：日志不带业务主键。** 错误写法：`log.error("更新失败")`。问题：哪个订单？哪个门店？高流量下这类日志和噪音无异。正确做法：业务操作日志必须携带订单号、门店 id、用户 id 中至少一个可检索主键，写之前先问自己"出事后拿什么搜到这一行"。

**坑 5：日志里打印敏感信息。** 错误写法：把登录请求整个打进日志，密码、手机号、token 全部落盘。问题：日志会被收集、归档、给很多人检索，等于把敏感数据扩散到第二套存储。正确做法：密码密钥绝不落日志，手机号等脱敏后再打（脱敏是第四阶段后面的主题）。

## 7. 和之前知识的连接

- **第 33 篇「全局异常处理」**：昨天兜底处理器那行 `log.error("系统异常", e)` 是排查的唯一入口，今天讲的正是"这行日志怎么写才有用"——异常对象放最后、堆栈完整落盘、前端只见安全文案。日志规范是全局异常处理真正发挥作用的另一半。
- **第 32 篇「异常处理」**：那篇坑 1 说过 `e.printStackTrace()` 不能用，原因今天补齐：printStackTrace 打到标准输出，生产日志系统收集不到。"包装异常别丢 cause"和今天"记日志别丢堆栈"是同一原则的两面。
- **第 22 篇「统一返回结构」**：响应体和日志是同一件事的两个出口——前端拿到克制的 `{ code, message }`，细节全在日志里。哪边信息多、哪边信息少，这条边界写每行日志时都要想清楚。
- **第 7 篇「application.yml 配置」**：日志级别就是通过它按环境配置的，配置文件是日志策略的总开关。

## 8. 面试 / 工作中常见问题

### 问题 1：SLF4J 和 Logback 是什么关系？为什么不直接用 Logback？

参考答案：SLF4J 是日志门面（接口），Logback 是实现。业务代码只依赖 SLF4J 的 API，运行时由 Logback 输出，替换实现只需换依赖和配置，业务代码一行不改。这是 Java 生态的典型思路——门面与实现分离，和 JDBC 驱动、Spring 数据源抽象同一套路。

### 问题 2：线上一个接口报错，你怎么快速找到对应日志？

参考答案：两步。先用业务主键检索：日志按规范带了订单号/用户 id，直接在日志系统里搜，命中报错那行；再用 traceId 串链路：过滤器通过 MDC 给每次请求打了 traceId，拿任意一行日志的 traceId 再搜，就能捞出这次请求的所有日志。这也解释了为什么规范要求"必带主键"——它就是检索锚点。

### 问题 3：error 和 warn 怎么分？业务失败算 error 吗？

参考答案：判断标准不是"失败没失败"，而是"要不要叫醒人"。error 代表需要人工介入的故障：数据库连不上、第三方挂了、意料之外的异常，它应该触发告警；warn 是预期内的异常态：库存不足、数据没匹配到、降级兜底。业务失败记 error 的后果是告警天天响、值班人麻木，真故障反被淹没——这正是昨天"业务异常 warn、未知异常 error"的原因。

## 9. 今日小结

- 后端日志的第一读者是事故现场的值班同事：有级别、有主键、有时间，才可检索。
- 占位符 `log.info("x={}", x)` 替代字符串拼接：省 CPU、防 null 误导、给堆栈留位置。
- 记异常时 `e` 永远放最后一个参数，否则堆栈消失等于没记。
- 级别即告警语义：error 叫醒人，warn 进报表，业务失败别刷 error。
- 日志必带业务主键 + traceId（MDC），前者是检索锚点，后者串起链路。
