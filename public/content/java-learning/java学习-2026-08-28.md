# Java 学习：AOP 是什么

> 系列第 42 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「事务传播机制」：前面四篇从「事务是什么」一路讲到「传播机制」，有一个词反复出现却始终没展开——「代理」。事务靠代理生效、传播靠代理协调、失效是因为绕过了代理。这个"在方法前后自动插入逻辑"的能力，名字就叫 AOP。今天把它彻底讲透：它是什么、动态代理怎么实现、以及怎么自己写一个 `@Log` 注解自动打印入参。学完这篇，回看这几天所有事务原理会一次性通透。

## 1. 今天学什么

AOP（Aspect-Oriented Programming，面向切面编程）解决的是一个非常具体的工程问题：有一段逻辑（开事务、记日志、鉴权、埋点）需要在**很多方法前后都执行**，但你不想在每个方法里复制粘贴一遍。Spring 的做法是——把这些"横切"逻辑抽出来，在运行时用**代理对象**自动织入到目标方法前后。今天讲三件事：① AOP 到底在解决什么问题、和 OOP 的分工；② 两种动态代理（JDK 动态代理 vs CGLIB）的区别，以及为什么 Spring Boot 默认用后者；③ 用一个 `@Log` 注解 + 切面的完整示例，让你亲手写一次"不改业务代码就给一堆方法加日志"。前几篇事务的所有"魔法"，本质都是今天这套机制。

## 2. 前端工程师视角理解

其实你天天在用 AOP，只是没这个名字。

最直接的类比是 **axios 拦截器**：`api.interceptors.request.use(cfg => { cfg.headers.token = getToken(); return cfg })`。你没有在每个 `api.get()`、`api.post()` 里手写加 token，而是在"请求发出前"这个横切点上统一插了一段逻辑。AOP 干的是同一件事，只不过它的"请求"换成了"任意一个方法调用"。

再类比 **Express / NestJS 中间件和 Guard**：`app.use(logger)`、`@UseGuards(AuthGuard)`，都是"不碰业务 handler，却能拦在 handler 前后做检查、打日志"。NestJS 的 `@Injectable()` 装饰器 + 拦截器（Interceptor）几乎就是 Spring AOP 的 TS 翻版。

关键差异在于**拦截的粒度**：前端中间件大多拦在"HTTP 请求"这一层（进 Controller 之前）。而 Spring AOP 能拦在"任意 Spring Bean 的任意 public 方法"这一层—— Service 方法、Mapper 方法都行，触发条件是你自定义的（比如"凡是带 @Log 注解的方法"）。这个"注解当标记 + 切面按标记织入"的组合，就是 AOP 的核心手感。

## 3. 和 JavaScript / TypeScript 的对比

**TS 装饰器"改方法"，Spring AOP"造代理对象"。** 这是和前几篇反复呼应的那个根因。TS / NestJS 的装饰器在类定义阶段直接**包装方法本身**——方法被替换成了新函数，之后谁调都生效。Spring AOP 默认**不改原对象**，而是在运行时另造一个代理对象挡在前面：`proxy.method()` 先执行切面逻辑，再转调 `target.method()`。正因如此，Spring AOP 才会出现"同类 `this.method()` 自调用绕过代理、切面不生效"的问题——和第 40 篇「事务失效场景」的失效根因**一模一样**。理解了 AOP，你就理解了事务为什么会失效，它们是同一套机制的两个应用。

**JS 里等价的"代理"是 `Proxy`。** MDN 的 `new Proxy(target, handler)` 让你拦截对对象的属性读写、函数调用。Spring 的动态代理在概念上非常接近：代理对象 = `new Proxy(target, { get(target, prop) { return (...args) => { before(); const r = target[prop](...args); after(); return r } } })`。区别是 JS Proxy 能拦截所有操作，Java 动态代理只能拦截**方法调用**，且需要框架在编译/运行期帮你生成这个代理类。

**编译期 vs 运行期。** AspectJ 是另一个 Java AOP 实现，它在编译期就把逻辑织进字节码，能拦 private、能拦自调用，功能更强但配置重；Spring AOP 只在运行期用代理，简单、够用，代价就是"只能拦经过代理的 public 方法"。前端没有这种权衡，因为 JS 是动态语言，包一层函数随手就来。

## 4. 真实业务场景

**场景：后台管理系统——给所有写操作自动记审计日志，不改一行业务代码。**

业务背景：企业内部系统有个硬要求——凡是"改数据"的接口（改价格、改库存、改权限）都必须留下审计记录：谁、什么时候、调了哪个方法、传了什么参数，出事好追溯。第一版实现是每个 Service 方法开头手写一段 `auditService.record(...)`。

问题很快暴露：① 几十个方法，复制粘贴几十遍，漏了就是合规风险；② 审计逻辑（取当前登录用户、序列化参数、算耗时）和业务逻辑搅在一起，方法越来越长、越来越难测；③ 某天要把审计从"写数据库"改成"发消息队列"，全项目搜索替换。

用 AOP 重构后：定义一个 `@Audit` 注解当"标记"，写一个切面统一实现"凡是打了 @Audit 的方法，执行前后自动记日志、算耗时、捕获异常也照记"。业务方法只需要 `@Audit` 一个注解，审计逻辑和业务代码彻底解耦。这正是 Spring 官方用同样机制实现 `@Transactional` 的方式——你现在写的切面，和框架写事务用的是同一套 API。

## 5. Java 示例代码

先用**自定义注解**标记"哪些方法要被拦截"：

```java
@Target(ElementType.METHOD)   // 只能打在方法上
@Retention(RetentionPolicy.RUNTIME) // 运行时可读——切面靠反射读它，必须 RUNTIME
public @interface Audit {
    String value() default ""; // 可选：业务动作描述，如 "修改商品价格"
}
```

再写**切面**，把审计逻辑集中在这里：

```java
@Aspect          // 声明这是一个切面
@Component       // 交给 Spring 容器管理
@Slf4j
public class AuditAspect {

    // 切入点(pointcut)：凡是打了 @Audit 注解的方法
    @Around("@annotation(audit)")
    public Object around(ProceedingJoinPoint pjp, Audit audit) throws Throwable {
        long start = System.currentTimeMillis();
        String method = pjp.getSignature().toShortString();
        Object[] args = pjp.getArgs();               // 入参数组
        String user = SecurityContextHolder.currentUser(); // 当前登录人

        try {
            Object result = pjp.proceed();           // ★ 执行真正的业务方法
            log.info("[审计] user={} method={} action={} 耗时={}ms 成功",
                     user, method, audit.value(), System.currentTimeMillis() - start);
            return result;
        } catch (Throwable e) {
            // 业务方法抛异常也要留痕，但不能吞掉——原样抛出，
            // 否则外层 @Transactional 就看不见异常、不会回滚了
            log.error("[审计] user={} method={} 失败: {}", user, method, e.toString());
            throw e;
        }
    }
}
```

业务方法只需打注解，一行业务代码都不用为审计而改：

```java
@Service
public class PriceService {

    @Audit("修改商品价格")
    @Transactional(rollbackFor = Exception.class)
    public void updatePrice(Long skuId, BigDecimal newPrice) {
        // 纯业务逻辑；进入方法前、离开方法后的审计动作，由 AuditAspect 自动织入
        priceMapper.update(skuId, newPrice);
    }
}
```

`@Around` 里那句 `pjp.proceed()` 就是"调用真实方法"，它前后可插入前置逻辑、后可插入后置逻辑——这正是前几篇里 `@Transactional` 自动"开事务 → proceed → 提交/回滚"的同一个结构。

## 6. 常见坑

**坑 1：以为 AOP 能拦一切。** 错误理解："切面配好了，所有方法都能被增强。"问题：Spring AOP 只对**经过代理的、public 方法**生效。同类自调用、private / final / static 方法、非 Spring 管理的对象，全都拦不到——和第 40 篇事务失效清单完全重合。正确做法：需要被增强的方法一定要"从别的 Bean 调用进来"。

**坑 2：切面里 catch 了异常没往外抛。** 错误形态：`try { pjp.proceed() } catch(e){ log.error(...) }` 就结束了。问题：异常被切面吞掉，外层 `@Transactional` 看不见异常就不会回滚（回滚判定依据是"异常抛出方法外"，第 40 篇坑 3）。正确做法：记完日志一定 `throw e` 原样抛出。

**坑 3：注解 `@Retention` 忘了写 RUNTIME。** 错误形态：默认是 CLASS，运行时反射读不到。问题：切面的 `@annotation(audit)` 匹配不上，切面永远不触发，还没报错。正确做法：给要被切面读取的注解显式标 `@Retention(RetentionPolicy.RUNTIME)`。

**坑 4：JDK 动态代理 vs CGLIB 搞混导致注入报错。** 现象：用 JDK 动态代理时，代理对象实现的是**接口**，如果你 `@Resource private OrderServiceImpl svc;` 注入具体实现类，会报"没有这个 bean"。问题：JDK 代理生成的是接口的实现，不是目标类的子类。正确做法：按接口类型注入（`OrderService`）；Spring Boot 默认用 CGLIB（生成目标类的子类），可直接注入实现类，一般不用你操心，但面试和排查老项目时这个区别仍会出现。

**坑 5：切面顺序不受控。** 现象：既有事务切面又有你自己的审计切面，两者都想"最先执行"。问题：你的日志切面若在事务之前 proceed，异常回滚后你可能已经记了"成功"。正确做法：用 `@Order` 显式指定切面优先级（数字越小优先级越高），事务通常应更靠外。

## 7. 和之前知识的连接

- **第 41 篇「事务传播机制」**：三种传播行为（REQUIRED / REQUIRES_NEW / NESTED）的"挂起事务、开新事务、设 savepoint"全部是 AOP 代理在 `proceed()` 前后自动做的——今天的 `pjp.proceed()` 结构和它们完全同构。
- **第 40 篇「事务失效场景」**：那篇的核心结论"事务靠代理生效、绕过代理就失效"，本质就是今天 AOP 的机制；今天从原理上解释了**为什么**自调用会失效：因为自调用没经过代理对象。
- **第 39 篇「Spring 事务注解」**：当时说"NestJS 装饰器看着像但深度不同，背后是 AOP 能力，后续专门讲"——今天正是那笔账的兑现。
- **第 8 篇「Controller / Service / Mapper 分层」**：Service 层是 @Transactional 的宿主，也是今天这类切面最常增强的层，AOP 是分层之外给方法"平行加一层能力"的手段。

## 8. 面试 / 工作中常见问题

### 问题 1：AOP 和 OOP 有什么区别，什么时候该用 AOP？

参考答案：OOP 是纵向分层（Controller→Service→Mapper），解决"是什么"；AOP 是横向切面，把散落在各层、重复出现的横切关注点（事务、日志、鉴权、埋点）抽到一处统一处理，解决"每层都要做但和业务无关"。判据：如果一段逻辑要在几十个不相关方法前后执行、且和业务本身无关，就该用 AOP 而不是到处复制。

### 问题 2：JDK 动态代理和 CGLIB 的区别，Spring 用哪个？

参考答案：JDK 动态代理基于**接口**，运行时生成实现目标接口的代理类，要求目标类必须实现接口；CGLIB 基于**继承**，运行时生成目标类的子类并覆盖方法，不需要接口，但无法代理 final 类/final 方法。Spring Boot 2.x 起默认用 CGLIB（`proxyTargetClass=true`），因为它更省事、可直接注入实现类；老项目或显式配置时可能退回 JDK 代理，表现为"只能按接口注入"。

### 问题 3：为什么我写的切面在某个方法上没触发？

参考答案：从代理角度排查：① 该方法是不是被同类方法用 `this.xxx()` 内部调用（绕过代理）；② 方法是不是 private / final / static（代理无法覆盖）；③ 对象是不是 Spring 管理的 Bean（手动 new 的没有代理）；④ 自定义注解有没有 `@Retention(RUNTIME)`；⑤ 切面类本身有没有 `@Component`、有没有开 `@EnableAspectJAutoProxy`。前四条和事务失效原因是同一套。

## 9. 今日小结

- AOP = 把"在很多方法前后都要执行"的横切逻辑（事务/日志/鉴权）抽出来，用代理对象自动织入，业务代码零改动。
- 前端类比：axios 拦截器、NestJS Guard/Interceptor 就是同一思想；Spring AOP 的粒度是"任意 Bean 的任意 public 方法"。
- 两种动态代理：JDK 基于接口、CGLIB 基于继承；Spring Boot 默认 CGLIB。
- AOP 只对"经过代理的 public 方法"生效——这正是前几篇事务会失效的根本原因，一篇打通四条。
- 手写切面三件套：自定义注解（RUNTIME）+ `@Aspect` 切面 + `pjp.proceed()` 前后插逻辑，和 @Transactional 用的是同一套 API。

原因：今天 AOP 让你在"方法层"做横切拦截，但后端还有两个更靠外、拦在"HTTP 请求层"的机制——Filter（过滤器）和 Interceptor（拦截器）。它们和 AOP 是同一类思想（在真正处理前插一段逻辑）作用在不同位置：Filter 在 Servlet 容器层、Interceptor 在 Spring MVC 层、AOP 在方法层。明天讲清三者的执行顺序、各自适合做什么（如 Filter 做跨域/CORS、Interceptor 做登录鉴权、AOP 做方法审计），并串成一条"一个请求进来到返回，到底路过了几层拦截"的完整链路。
