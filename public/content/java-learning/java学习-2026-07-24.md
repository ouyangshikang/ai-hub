# Java 学习：RESTful 接口设计

> 系列第 20 篇 · 第三阶段：接口与规范（开篇）  
> 第二阶段我们解决了"后端怎么和数据库打交道"的全部问题。从今天开始进入第三阶段——后端怎么对外提供稳定、规范的 HTTP 接口。你在前端调了无数接口，今天换到后端视角，搞清楚那些接口是怎么设计出来的。

## 1. 今天学什么

RESTful 不是一门新技术，而是一种接口设计的约定和风格。它规定了 URL 怎么命名、HTTP 方法怎么选、资源路径怎么组织、状态码怎么返回。一个团队如果不遵守统一风格，每个人设计出来的接口就会形态各异——有人用 `/getOrderList`，有人用 `/order/list`，有人用 `/queryOrder`，前端对接时每个接口都要重新理解语义。

RESTful 的核心思想是"面向资源"：URL 代表资源（名词），HTTP 方法代表操作（动词）。GET 是查、POST 是增、PUT 是改、DELETE 是删。URL 里不出现动词，操作语义全部交给 HTTP 方法表达。这不是强制标准，但它是行业里最广泛接受的接口设计公约，Spring Boot 的注解体系（`@GetMapping`、`@PostMapping`）天然就是为 RESTful 设计的。

## 2. 前端工程师视角理解

你在前端写 API 请求时，一定见过这两种风格的接口：

```typescript
// 风格 A：动词在 URL 里（非 RESTful）
fetch('/api/getOrderList?storeId=10086')
fetch('/api/deleteOrder?id=123')
fetch('/api/updateOrderStatus', { method: 'POST', body: ... })

// 风格 B：资源 + HTTP 方法（RESTful）
fetch('/api/orders?storeId=10086')           // GET 查列表
fetch('/api/orders/123', { method: 'DELETE' }) // DELETE 删除
fetch('/api/orders/123/status', { method: 'PUT', body: ... }) // PUT 更新
```

风格 A 每个接口都是"自定义动词"，看 URL 才知道干什么；风格 B 看 URL 就知道操作什么资源，看 HTTP 方法就知道做什么操作。你在前端用 axios 封装请求时，风格 B 天然适合按资源模块组织代码——`orderApi.get()`、`orderApi.delete(id)`，而风格 A 只能按函数名一个个罗列。

后端设计接口的思路完全一样：RESTful 让接口"自解释"，新人看 URL 结构就能猜出接口语义，不需要翻文档。

## 3. 和 JavaScript / TypeScript 的对比

### 路由设计：Express vs Spring Boot

```typescript
// Express（Node.js）的路由设计
app.get('/api/orders', listOrders);        // GET 查列表
app.get('/api/orders/:id', getOrder);      // GET 查详情
app.post('/api/orders', createOrder);      // POST 新增
app.put('/api/orders/:id', updateOrder);   // PUT 全量更新
app.delete('/api/orders/:id', deleteOrder); // DELETE 删除
```

```java
// Spring Boot 的 Controller（完全对应的写法）
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @GetMapping
    public Result<PageResult<OrderVO>> list(OrderQueryParam param) { ... }

    @GetMapping("/{id}")
    public Result<OrderVO> detail(@PathVariable Long id) { ... }

    @PostMapping
    public Result<Long> create(@RequestBody OrderCreateDTO dto) { ... }

    @PutMapping("/{id}")
    public Result<Void> update(@PathVariable Long id, @RequestBody OrderUpdateDTO dto) { ... }

    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) { ... }
}
```

两者的设计哲学完全一致：URL 是资源路径，HTTP 方法是操作类型。Spring Boot 用注解（`@GetMapping`、`@PathVariable`）表达的东西，Express 用 `app.get('/api/orders/:id')` 表达——只是语法不同，思想相同。

### PUT vs PATCH：前端容易忽略的区别

```typescript
// PUT：全量替换——前端必须传完整对象
await fetch('/api/orders/123', {
  method: 'PUT',
  body: JSON.stringify({ status: 'shipped', remark: '加急', amount: 99.9 })
});

// PATCH：局部更新——只传要改的字段
await fetch('/api/orders/123', {
  method: 'PATCH',
  body: JSON.stringify({ status: 'shipped' })
});
```

前端经常混用 PUT 和 PATCH，但语义不同：PUT 是"用你传的内容完整替换这个资源"，没传的字段会被置空；PATCH 是"只改你传的字段"。后端如果严格区分，前端传错方法可能导致数据被意外清空。

### 为什么 Java 后端更强调 RESTful 规范

前端项目里，路由和 API 调用通常一个人或一个小团队就能统一风格。后端项目往往是多人协作、多期迭代，如果没有统一规范，三个月后接口就会变成"考古现场"。RESTful 是团队层面的公约——不是技术上必须，而是协作上必须。

## 4. 真实业务场景

门店管理系统里，运营需要管理门店信息：查看门店列表、查看门店详情、新增门店、修改门店营业状态、删除门店。

如果不用 RESTful 风格，五个接口可能长这样：`/getStoreList`、`/getStoreDetail`、`/addStore`、`/modifyStoreStatus`、`/removeStore`。每个接口都是独立的"动词短语"，没有统一的资源路径前缀，前端封装时只能逐个硬编码。

用 RESTful 风格：`GET /api/stores`、`GET /api/stores/{id}`、`POST /api/stores`、`PATCH /api/stores/{id}/status`、`DELETE /api/stores/{id}`。所有接口围绕 `/api/stores` 这个资源路径展开，语义一目了然。

如果用错会怎样？最典型的问题是"一个 POST 打天下"——所有操作都用 POST，URL 里塞动词。短期看不出问题，但当接口数量膨胀到上百个时，前端无法按资源模块组织 API 层代码，后端也无法通过 URL 前缀做统一的权限控制（比如"运营角色只能访问 `/api/stores` 下的 GET 接口"）。

## 5. Java 示例代码

```java
/**
 * 门店管理 Controller —— RESTful 风格
 * URL 是资源（名词），HTTP 方法是操作（动词）
 */
@RestController
@RequestMapping("/api/stores")
public class StoreController {

    @Autowired
    private StoreService storeService;

    // GET /api/stores?city=上海&pageNum=1&pageSize=20
    // 查询条件通过 Query Param 传递，不放在路径里
    @GetMapping
    public Result<PageResult<StoreVO>> list(StoreQueryParam param) {
        return Result.success(storeService.queryStores(param));
    }

    // GET /api/stores/10086
    // 路径参数：定位到具体某一个资源
    @GetMapping("/{id}")
    public Result<StoreVO> detail(@PathVariable Long id) {
        return Result.success(storeService.getStoreById(id));
    }

    // POST /api/stores
    // 新增资源，请求体传完整数据
    @PostMapping
    public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) {
        Long storeId = storeService.createStore(dto);
        return Result.success(storeId);
    }

    // PATCH /api/stores/10086/status
    // 局部更新：只改状态这一个子资源
    @PatchMapping("/{id}/status")
    public Result<Void> updateStatus(@PathVariable Long id,
                                     @RequestBody @Valid StatusUpdateDTO dto) {
        storeService.updateStatus(id, dto.getStatus());
        return Result.success(null);
    }

    // DELETE /api/stores/10086
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) {
        storeService.deleteStore(id);
        return Result.success(null);
    }
}
```

注意几个设计细节：URL 里全是名词（`stores`、`status`），没有 `get`、`add`、`delete` 这些动词；查询条件放 Query Param（`?city=上海`），不放路径里；路径参数（`/{id}`）用于定位单个资源；子资源操作用路径嵌套（`/{id}/status`）。

## 6. 常见坑

### 坑 1：URL 里塞动词

```java
// ❌ 非 RESTful：URL 是动词短语
@GetMapping("/api/getStoreList")
@PostMapping("/api/deleteStore")
```

URL 应该是名词（资源），操作由 HTTP 方法表达。`/api/getStoreList` 的问题是：如果以后要加"按区域查门店列表"，你是写 `/api/getStoreListByRegion` 还是 `/api/getRegionStoreList`？动词一多，命名就开始混乱。正确做法：`GET /api/stores?region=华东`，筛选条件放 Query Param。

### 坑 2：所有接口都用 POST

```java
// ❌ 查询、新增、删除全是 POST
@PostMapping("/api/order/list")
@PostMapping("/api/order/create")
@PostMapping("/api/order/delete")
```

"POST 一把梭"在内部系统里很常见，短期省事，长期灾难：无法通过 HTTP 方法做统一的权限拦截（比如"只读角色只允许 GET"）、无法利用 HTTP 缓存（GET 请求可以被 CDN / 浏览器缓存，POST 不行）、接口语义完全依赖 URL 字符串约定。正确做法：查询用 GET，新增用 POST，更新用 PUT/PATCH，删除用 DELETE。

### 坑 3：路径参数和 Query Param 混用定位资源

```java
// ❌ 同一个资源，有时用路径参数，有时用 Query Param
@GetMapping("/api/stores/{id}")       // 详情用路径参数
@GetMapping("/api/stores?id=10086")   // 又用 Query Param？
```

团队内必须统一：定位单个资源用路径参数（`/{id}`），筛选/分页/排序用 Query Param（`?city=上海&pageNum=1`）。混用会让前端封装 API 时不知道参数该放哪里。

### 坑 4：URL 层级设计过深

```java
// ❌ 嵌套太深，维护成本高
@GetMapping("/api/regions/{regionId}/cities/{cityId}/stores/{storeId}/orders/{orderId}")
```

超过 3 层嵌套就该考虑拆分。上面的接口可以简化为 `GET /api/orders/{orderId}`，因为 orderId 本身就能唯一定位订单，不需要从 region 一路嵌套下来。RESTful 的嵌套表达的是"归属关系"，不是"查询路径"。

## 7. 和之前知识的连接

- **第 8 篇「Controller / Service / Mapper 分层」**：今天的 `StoreController` 就是那篇讲的 Controller 层。RESTful 规范约束的正是 Controller 层的 URL 设计和 HTTP 方法选择——Controller 是后端对外的"门面"，接口风格在这一层定型。

- **第 10 篇「DTO / VO / Entity 的区别」**：注意今天代码里，`create` 方法接收的是 `StoreCreateDTO`（前端传入的数据结构），返回的是 `StoreVO`（给前端展示的数据结构）。RESTful 规范管的是 URL 和方法，而 DTO / VO 管的是"数据长什么样"——两者配合，接口才既规范又清晰。

- **第 19 篇「N+1 查询问题」**：`GET /api/stores?city=上海&pageNum=1` 这个列表接口，后端实现时仍然要面对 N+1 问题（查门店列表后关联查区域名、负责人等）。RESTful 管的是接口"对外长什么样"，N+1 管的是接口"内部怎么查"——外层规范和内层性能是两件事，都要做好。

## 8. 面试 / 工作中常见问题

### 问题 1：RESTful 里 PUT 和 PATCH 有什么区别？你们项目里怎么选的？

参考答案：PUT 是全量替换——客户端必须传资源的完整表示，没传的字段会被置为默认值或 null；PATCH 是局部更新——只修改客户端传了的字段。实际项目里，如果更新操作涉及的字段少（比如只改状态），用 PATCH 语义更准确；如果前端表单本身就是全量提交（编辑页回显所有字段、用户改完整体提交），用 PUT 更自然。很多团队为了简化，统一用 PUT 做更新，但要在文档里说明"未传字段保持不变"还是"未传字段置空"，避免前端踩坑。

### 问题 2：查询条件应该放在 URL 路径里还是 Query Param 里？

参考答案：定位唯一资源用路径参数（`/api/orders/123`），筛选、分页、排序等条件用 Query Param（`/api/orders?status=paid&pageNum=1&sortBy=createTime`）。判断标准：这个参数是不是在"定位哪个资源"？是的话放路径（`/{id}`）；不是的话放 Query Param。不要把筛选条件塞进路径（`/api/orders/status/paid/page/1`），否则 URL 组合爆炸、难以维护。

### 问题 3：你们项目的接口 URL 是怎么设计的？有没有统一的规范？

参考答案：以资源名词为核心，复数形式（`/api/stores`、`/api/orders`）；路径参数定位单个资源（`/{id}`）；子资源用路径嵌套但不超过 3 层（`/api/stores/{id}/orders`）；操作语义由 HTTP 方法表达，URL 里不出现动词；筛选、分页、排序全部走 Query Param；统一前缀 `/api` 方便网关做路由和鉴权。团队在接口设计评审时对照这份规范 check，新接口不符合规范的不允许合入。

## 9. 今日小结

- RESTful 的核心：URL 是资源（名词），HTTP 方法是操作（动词），接口"自解释"。
- Spring Boot 的 `@GetMapping`、`@PostMapping`、`@PathVariable`、`@RequestBody` 天然为 RESTful 设计，和 Express 路由思想一致。
- 路径参数定位资源，Query Param 传筛选条件，两者不混用。
- PUT 全量替换、PATCH 局部更新，团队要统一选择并写进文档。
- RESTful 不是技术强制而是团队公约——多人协作、多期迭代时，统一风格比"能跑就行"重要得多。

## 10. 明日预告

明天建议学习：`请求参数校验`

原因：今天设计了 RESTful 接口，`@RequestBody StoreCreateDTO dto` 接收前端传来的数据。但前端传过来的数据能直接信任吗？门店名能不能为空？手机号格式对不对？金额能不能是负数？如果不在后端做校验，脏数据直接写进数据库，线上就会出各种诡异问题。明天讲 Spring Boot 的参数校验体系——`@Valid`、`@NotNull`、`@Size`、自定义校验注解，把"前端传什么后端都照收"变成"不合规的请求在 Controller 层就被拦下"。
