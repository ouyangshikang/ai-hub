# Java 学习：定时任务

> 系列第 44 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「拦截器与过滤器」：前 43 篇处理的都是**被动**流量——有人发请求，才走 Filter → Interceptor → Controller → Service。但后端还有一半工作是**主动**发起的：凌晨跑门店对账、每分钟同步库存、月初生成结算单。今天讲 Spring 的 `@Scheduled`，重点不在注解怎么写，而在**为什么单机版定时任务不能直接上生产**。

## 1. 今天学什么

定时任务就是"不需要用户触发、到点自己跑"的代码。Spring Boot 里它极简：`@EnableScheduling` + `@Scheduled` 两个注解，三种触发方式——`cron`（按日历时间）、`fixedRate`（固定间隔开始时间）、`fixedDelay`（固定间隔结束时间）。今天讲四件事：① 三种触发方式怎么选；② cron 怎么写，尤其它和 JS 的 cron **位数不一样**；③ `@Scheduled` 默认跑在**单线程**调度池，一个任务卡住会让全部任务静默失踪；④ 生产的多实例问题——3 个副本同一分钟各跑一遍，工资发三次。第四点才是这篇真正的重点。

## 2. 前端工程师视角理解

你在 Node 里一定写过 `setInterval(() => syncData(), 60_000)`，或用 `node-cron` 写 `cron.schedule('0 2 * * *', ...)` 每天凌晨跑个脚本。Java 的 `@Scheduled` 就是这件事的工程化版本：跑在 Spring 容器里，能直接注入任何 Bean，不用单独起进程。

**但有一个决定性差异：部署模型。** 前端 BFF 或 Node 服务常常单实例，`setInterval` 只有一份，没人管也跑得对。Java 后端是**多副本对等部署**——线上同一应用通常 3~10 个实例，每个都加载了同一份代码、都注册了同一个 `@Scheduled`。于是**到点那一刻，3 个实例同时认为"该我跑了"**。这是定时任务在生产环境的核心问题，在你的单机 Node 经验里完全不存在。

第二个差异是**线程模型**。Node 单事件循环，回调慢了会阻塞整个进程，但不会出现"任务被别的任务占着线程不跑"；Java 的 `@Scheduled` 默认由一根线程的调度池执行，5 个任务共用它排队跑。其中一个查库卡了 10 分钟，另外 4 个这 10 分钟里一个都不会触发——日志里还没有错误，纯粹是"到点没跑"。

## 3. 和 JavaScript / TypeScript 的对比

**第一处差异：cron 位数。**

```js
// node-cron：5 位（分 时 日 月 周）
cron.schedule('0 2 * * *', task);          // 每天 02:00
```

```java
// Spring：6 位（秒 分 时 日 月 周），多了最前面的「秒」
@Scheduled(cron = "0 0 2 * * *")           // 每天 02:00:00
```

前端手写 Java cron 最常犯的错，就是把 5 位表达式直接粘过来。好在 Spring 会解析失败并在**启动时**抛异常，不让你带到线上——这比 JS 友好，`cron.schedule` 格式传错往往只是静默不跑。

**第二处差异：`fixedRate` / `fixedDelay` 在 JS 里没有对应物，只有 `setInterval`。** 差别就是"上一次还没跑完时，下一次算不算准时"：

- `fixedRate` ≈ `setInterval`：以上次**开始**时间为基准。任务耗时 70s、间隔 60s，第 2 次本该在 60s 触发，但线程被占着，只能等它跑完立刻补上——节奏会漂。
- `fixedDelay`：以上次**结束**时间为基准，保证两次之间一定有 60s 空闲。**同步类任务优先用这个**。

**第三处差异：注解的值必须是编译期常量。** `@Scheduled(fixedDelay = someVariable)` 写不了，只能硬编码或用 `fixedDelayString = "${job.xxx.interval-ms:60000}"` 从配置读——Java 靠**占位符 + 默认值**把写死的值变成可配置的引用，也就是第 7 篇讲的配置注入。

**第四处差异：时区。** 两边都默认用服务器 / JVM 时区，而容器里的 JVM 常常是 UTC——"凌晨 2 点的对账"就会在北京时间上午 10 点跑，正好撞在业务高峰。Spring 的解法是 `zone` 参数，生产建议**永远写死**。

## 4. 真实业务场景

**场景：门店系统——每天凌晨的营业日对账 + 每分钟库存同步。**

业务背景：连锁门店每天 0 点切一个"营业日"，凌晨 2:00 要把前一天订单金额和第三方支付流水（微信、支付宝、银行卡）逐门店对账，差异超阈值生成异常单给财务；同时每分钟从 ERP 同步一次库存，供 C 端小程序判断"是否可售"。

**为什么会踩到今天的知识点：** 这个服务线上跑 4 个实例做高可用。对账任务一部署，凌晨 2:00 四个实例同时开跑——四份结果写进同一张表，同一笔差异生成 4 张异常单，财务看到 4 倍差异金额；下游"自动补货"被执行 4 次，部分库存直接翻倍。库存同步则是四个实例同时抢 ERP 接口，配额打满被限流，反而不如单实例快。

**代价分三层：** 重复执行 → 数据和钱出错；单线程池被长任务卡住 → 库存同步静默失踪，用户在小程序看到有货、下单才发现没货；异常不 catch 只打一行 error → 第二天没人知道对账压根没跑完。

## 5. Java 示例代码

```java
@SpringBootApplication
@EnableScheduling        // ★ 必须显式开启，漏了这个注解 @Scheduled 静默不生效
public class StoreApplication { }
```

```java
@Component
@Slf4j
public class StoreDailyJob {

    @Resource private ReconcileService reconcileService;
    @Resource private JobLockService jobLockService;

    /**
     * 每天凌晨 2:00（北京时间）跑前一营业日门店对账。
     * 6 位 cron：秒 分 时 日 月 周；zone 必须显式写，别赌容器的系统时区。
     */
    @Scheduled(cron = "0 0 2 * * *", zone = "Asia/Shanghai")
    public void reconcileYesterday() {
        LocalDate bizDate = LocalDate.now().minusDays(1);   // 第 29 篇：用 LocalDate，不用 Date
        String traceId = "job-reconcile-" + UUID.randomUUID().toString().replace("-", "");
        MDC.put("traceId", traceId);                        // 第 43 篇：HTTP 有 Filter 打 traceId，
                                                            // 定时任务没有请求上下文，得自己造
        try {
            // ★ 抢锁：4 个实例只有 1 个能成功，其余直接退出
            if (!jobLockService.tryLock("dailyReconcile", bizDate, Duration.ofMinutes(30))) {
                log.info("对账已由其他实例执行，跳过 bizDate={}", bizDate);
                return;
            }
            reconcileService.run(bizDate, traceId);
        } catch (Exception e) {
            // 异常兜底：定时任务没人给你返回 500，不 catch 就等于没有失败信号
            log.error("门店对账任务失败 bizDate={} traceId={}", bizDate, traceId, e);
        } finally {
            MDC.remove("traceId");                          // 线程池复用，必须清理
        }
    }

    /**
     * 每分钟同步库存：用 fixedDelay，跑完再等 60s，不会重叠堆积。
     * 间隔外置到 yml，运维可调，不用改代码重新发版。
     */
    @Scheduled(fixedDelayString = "${job.stock-sync.interval-ms:60000}",
               initialDelayString = "${job.stock-sync.initial-delay-ms:10000}")
    public void syncStock() {
        if (!jobLockService.tryLock("stockSync", Duration.ofSeconds(50))) return;
        reconcileService.syncStock();
    }
}
```

锁的实现——本质就是 Redis 的 `SET NX PX`：

```java
@Service
public class JobLockService {

    @Resource private StringRedisTemplate redis;

    /** key 带上业务日期：同一天只有第一个实例能设置成功 */
    public boolean tryLock(String jobCode, LocalDate bizDate, Duration ttl) {
        String key = "job:lock:%s:%s".formatted(jobCode, bizDate);
        return Boolean.TRUE.equals(redis.opsForValue().setIfAbsent(key, "1", ttl));
    }

    public boolean tryLock(String jobCode, Duration ttl) {
        return tryLock(jobCode, LocalDate.now(), ttl);
    }
}
```

线程池必须显式调大（默认只有 1 根线程）：

```yaml
spring:
  task:
    scheduling:
      pool:
        size: 4          # ★ 默认 1！多个定时任务共用一根线程 = 互相阻塞
      thread-name-prefix: store-job-   # 排查线上堆栈时能一眼认出是定时任务线程
```

**但 `tryLock` 只解决"同一时刻只有一个在跑"，不解决"跑过一遍还会长出第二遍"。** 真正的兜底是幂等记录表：`(job_code, biz_date)` 建唯一索引，任务开始前先插入，冲突即返回。这套锁 + 唯一索引的组合，和第 25 篇「接口幂等性」是**同一套思路**，只是触发方从"用户重复点击"换成了"多实例 + 失败重试"。

## 6. 常见坑

**坑 1：cron 里"日"和"周"同时指定，任务变成"或"关系。** 错误写法：`@Scheduled(cron = "0 0 2 1 * MON")`，本意"每月 1 号且是周一才跑"。问题：day-of-month 和 day-of-week 同时限制时，Spring/Quartz 按**或**处理，结果每周一和每月 1 号都跑。正确做法：其中一个写 `?` 表示"不指定"——`0 0 2 1 * ?`（每月 1 号）或 `0 0 2 ? * MON`（每周一）。

**坑 2：默认单线程池，一个慢任务让所有任务集体失踪。** 现象：定时任务偶发不跑，日志无任何报错。问题：`@Scheduled` 共用一个 size=1 的调度线程，任务 A 卡死 → B/C/D 全部排队等待，且超时不会自己恢复。正确做法：`spring.task.scheduling.pool.size` 调大；长任务加 `@Async` 并配独立线程池，别占调度线程。

**坑 3：靠"部署时只开一台"来避免重复执行。** 问题：滚动发布期间新老版本必然并存，重启、扩缩容、故障转移也会让两个实例同时在线。正确做法：分布式锁（ShedLock 给 `@Scheduled` 方法加 `@SchedulerLock`）+ 幂等记录表；调度精度和任务量要求更高时，直接上 XXL-JOB、ElasticJob 这类调度中心，由它决定"这一轮派给哪个实例"。

**坑 4：锁的 TTL 比任务实际耗时短。** 现象：任务预计 5 分钟、锁设了 3 分钟，第 4 分钟锁过期，另一个实例拿到锁又跑一遍。正确做法：TTL 按 P99 耗时留足余量，或让看门狗自动续期；但更根本的是**别指望锁保证正确性**——锁只省算力，正确性交给 `(job_code, biz_date)` 唯一索引。

**坑 5：任务里 `@Transactional` 不生效。** 现象：对账写了一半，失败后前面插入的数据留下了。问题：Job 类天然是"外层调度 + 内层业务"结构，同类内部调用绕过代理（第 40 篇的失效场景）。正确做法：事务方法放独立的 `ReconcileService` Bean，由 Job 注入调用——Job 只管"什么时候跑、跑不跑"，Service 管"怎么跑、跑砸了怎么回滚"。

## 7. 和之前知识的连接

- **第 43 篇「拦截器与过滤器」**：HTTP 的 traceId 由 Filter 自动注入，定时任务不经过 Filter，MDC 必须自己塞、自己在 finally 清——同一条规范在两个入口的两种落法。
- **第 25 篇「接口幂等性」**：唯一索引幂等在今天原样复现，只是重复来源从"用户双击 / 网络重试"变成"多实例并发 + 失败重试"。幂等在后端从来不是体验问题，而是**资金安全问题**。
- **第 40 / 41 篇「事务失效场景」与「事务传播机制」**：Job 类同类自调用概率比 Controller 更高，事务更易失效；"逐门店处理、单条失败不整批回滚"正是 `REQUIRES_NEW` 的标准用例。
- **第 34 篇「日志规范」**：定时任务无人可感知，出错全靠日志——开始、结束、跳过原因（"锁被占用"）、条数与耗时，一条不能省，否则无法区分"没跑"和"跑太快没打日志"。

## 8. 面试 / 工作中常见问题

### 问题 1：`@Scheduled` 的 cron 和 fixedDelay 有什么区别，什么时候用哪个？

参考答案：cron 按**日历时间**触发，适合"必须发生在某个时刻"的任务——凌晨对账、月初结算。fixedDelay 按**上次结束的相对时间**触发，适合"保证每 60 秒跑一次就行"的任务——库存同步、消息补偿。判据就一句：这个任务晚跑 10 分钟有没有业务问题？有 → cron；没有 → fixedDelay（它天然避免任务重叠）。fixedRate 以上次开始时间为基准，耗时超过间隔时会串行追赶，实际用得比 fixedDelay 少。

### 问题 2：项目部署了多个实例，定时任务怎么避免重复执行？

参考答案：两层。防并发用**分布式锁**：手写 Redis `SET NX PX`，或直接用 ShedLock 给方法加 `@SchedulerLock`；要求更高就交给 XXL-JOB / ElasticJob 这类调度中心统一派发并分片。防重复用**幂等表**：`(job_code, biz_date)` 唯一索引，先插执行记录，冲突即返回。面试要点是那句判断：锁只能防同时，防不住先后，涉及钱的场景必须有唯一索引兜底；"只部署一台跑定时任务"不算方案，滚动发布窗口照样漏。

### 问题 3：线上反馈某个定时任务"今天早上没跑"，你怎么排查？

参考答案：按序四点。① 日志里有没有执行记录，先区分"真没跑"和"跑了但报错被吞"。② `jstack` 看 `scheduling-1` 这根线程在干什么——默认调度池只有一根线程，大概率被别的长任务卡住。③ 核对时区，容器是 UTC 时 `0 0 2` 实际跑在 10:00。④ 检查 cron 的"日"和"周"是否都写了具体值，导致语义变成"或"、任务在别的时间点提前跑掉。顺带确认 `@EnableScheduling` 在启动类上、Bean 确实被组件扫描扫进了容器。

## 9. 今日小结

- 三件套：启动类 `@EnableScheduling`、方法 `@Scheduled`、调度池 `spring.task.scheduling.pool.size`（默认 1，必须改）。
- 触发方式：**必须几点跑用 cron，只需保证间隔用 fixedDelay**；cron 是 6 位（比 node-cron 多"秒"），"日"和"周"同时指定是**或**关系、另一个要写 `?`，且**永远显式写 `zone`**。
- 难点不在注解而在**多副本对等部署**：4 个实例就跑 4 遍。防线是"分布式锁防并发 + 唯一索引防重复"，锁只省算力，索引才保正确。
- 定时任务没有 HTTP 上下文，第 43 篇 Filter 自动做的 traceId、第 33 篇全局异常统一做的错误响应，这里都得**自己补一遍**。
