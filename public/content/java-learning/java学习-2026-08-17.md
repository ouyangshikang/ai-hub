# Java 学习：全局异常处理

> 系列第 33 篇 · 第四阶段：精度、安全与稳定性
> 昨天把 `BizException` 抛出来了，但抛出之后谁来接？默认情况下异常一路冒到框架边界，变成一个裸的 500 和默认错误页，堆栈信息直接暴露。今天讲 `@RestControllerAdvice` + `@ExceptionHandler`：给所有异常安排一个统一出口——业务异常转成带错误码的统一返回体，参数校验异常提取具体字段错误，未知异常兜底成"系统繁忙"。昨天抛出的每个异常，今天都有体面的归宿。

## 1. 今天学什么

一个后端项目有几十上百个接口，每个接口都可能抛异常。如果每个 Controller 方法都自己写 try-catch，会有两个必然的问题：一是总有人忘写，漏网之鱼变成裸 500；二是每个人 catch 之后返回的格式五花八门，前端没法统一处理。

Spring MVC 给出的答案是全局异常处理：写一个标注了 `@RestControllerAdvice` 的类，里面用 `@ExceptionHandler` 按异常类型声明若干处理方法。之后任何 Controller 抛出的异常，都会被 Spring 在请求处理的最外层自动拦截，按异常类型路由到对应的处理方法，由它决定返回什么。异常处理从"每个接口各自为战"变成"一个类集中收口"，返回格式也就天然统一了。

它解决的核心问题是：**异常的"抛出"和"转响应"这两件事要解耦**。Service 层只管抛（昨天学的），怎么变成前端能理解的 JSON，统一交给边界上的这一个类。

## 2. 前端工程师视角理解

你在 Node.js 里一定写过类似的东西——Express 的全局错误中间件：

```javascript
// Express：所有路由的错误最终都流到这里
app.use((err, req, res, next) => {
  if (err instanceof BizError) {
    return res.json({ code: err.code, message: err.message, data: null });
  }
  console.error(err);
  res.json({ code: 50000, message: '系统繁忙，请稍后重试', data: null });
});
```

路由里不用管错误怎么返回，抛出去（或 `next(err)`）就行，格式统一由这个中间件决定。Spring 的全局异常处理器就是同一个角色，只不过写法是声明式的：你不用把错误"转发"到某个中间件，Spring 自动把异常送过来。

也可以类比你天天写的 axios 响应拦截器：拦截器能统一处理成功和失败，前提是后端所有接口的错误格式一致。全局异常处理器正是站在后端这一侧的"拦截器"——它是 `{ code, message, data }` 这个契约的最后一道保障，连 500 级别的意外也包成同样的信封。

## 3. 和 JavaScript / TypeScript 的对比

**错误的汇聚方式不同。** Express 里错误要汇聚到错误中间件，得靠你手动 `next(err)`，async 函数里的 rejection 还得靠包装库或 `express 5` 才能自动捕获，漏了就石沉大海。Spring MVC 是同步调用链模型，Controller 方法（及其调用链）里抛出的任何异常都会被 DispatcherServlet 自动捕获并交给异常解析器，不需要任何"转发"动作，想漏都难。

**匹配规则不同。** Express 错误中间件按注册顺序匹配，第一个接住就完事；Spring 是按异常类型的继承关系选"最精确"的处理器——抛 `BizException` 就命中 `BizException` 的处理器，没有专门的才落到 `Exception` 兜底。所以你不用关心声明顺序，只关心类型划分。

**NestJS 几乎是照抄。** 如果你用过 NestJS，它的 `@Catch()` + `ExceptionFilter` 就是这套机制的直系后代（Nest 本身深受 Spring 影响）。写法几乎一一对应，理解成本为零。

**一个关键差异：覆盖范围。** Express 的错误中间件覆盖整个进程内所有路由请求；Spring 的 `@RestControllerAdvice` 只覆盖走 DispatcherServlet 的那条请求链路。`@Async` 异步任务、`@Scheduled` 定时任务、MQ 消费线程里抛的异常不经过这里——这是后端新人最常有的误解，后面常见坑里细说。

## 4. 真实业务场景

**场景：门店系统的下单接口和运营后台的"创建优惠券"接口。**

业务背景：下单接口在库存不足时抛 `BizException(STOCK_NOT_ENOUGH)`；创建优惠券接口用 `@Valid` 校验入参（优惠券名称不能为空、折扣必须在 0 到 1 之间）；此外任何接口都可能有意想不到的 bug，比如某个字段没判空引发 NPE。

没有全局异常处理时的典型事故：新同事写接口忘了 try-catch，库存不足时前端收到一个 500，响应体里还带着 Java 堆栈和内部类名——安全扫描直接报漏洞，前端也只能弹一个看不懂的"Network Error"。另一个接口自己 catch 了但返回 `{ error: '库存不足' }`，和别的接口格式都不一样，axios 拦截器判断不了，每个页面各自写兜底逻辑。

上了全局异常处理之后：业务异常自动转成 `{ code: 4xxxx, message: '库存不足，剩余 3', data: null }`，前端拦截器按错误码弹提示；未知异常返回统一的"系统繁忙"，真实堆栈只进日志。所有接口的失败响应从此长得一模一样。

## 5. Java 示例代码

```java
// 全局异常处理器：整个项目只有这一个，放在统一的 web/exception 包下
@Slf4j
@RestControllerAdvice  // = @ControllerAdvice + @ResponseBody，返回值直接序列化成 JSON
public class GlobalExceptionHandler {

    // 1) 业务异常：转成带错误码的统一返回体
    // BizException 和 ErrorCode 来自第 32 篇、第 23 篇
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBizException(BizException e) {
        // 业务异常是"预期内的失败"，warn 级别足够，别触发 error 告警
        log.warn("业务异常: code={}, message={}", e.getErrorCode(), e.getMessage());
        return Result.fail(e.getErrorCode().getCode(), e.getMessage());
    }

    // 2) @Valid 参数校验失败：提取具体是哪个字段、什么问题
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidException(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(err -> err.getField() + err.getDefaultMessage())
                .collect(Collectors.joining("；"));
        // 例如输出："couponName 不能为空；discount 必须在0到1之间"
        return Result.fail(ErrorCode.PARAM_ERROR.getCode(), msg);
    }

    // 3) 兜底：任何没被上面接住的异常
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        // 完整堆栈进日志，这是排查问题的唯一线索
        log.error("系统异常", e);
        // 前端只拿到安全提示，绝不返回 e.getMessage()
        return Result.fail(ErrorCode.SYSTEM_ERROR.getCode(), "系统繁忙，请稍后重试");
    }
}
```

```java
// ErrorCode 枚举补一个系统错误码（在第 23 篇的枚举上追加）
SYSTEM_ERROR(50000, "系统繁忙，请稍后重试");
```

注意匹配是自动的：抛 `BizException` 命中第 1 个方法，抛 `MethodArgumentNotValidException` 命中第 2 个，其余全部落到第 3 个兜底。Controller 里一行 try-catch 都不用写。

## 6. 常见坑

**坑 1：以为全局异常处理器无所不能。** 错误理解：只要加了 `@RestControllerAdvice`，项目里任何异常都会被接住。问题：它只覆盖 HTTP 请求处理链路。`@Async` 方法、`@Scheduled` 定时任务、MQ 消息监听器都在独立线程里跑，抛出的异常根本不到这儿，线程静默挂掉，什么响应也没有。正确做法：异步任务、定时任务内部自己 try-catch 记日志，或配置专门的 `AsyncUncaughtExceptionHandler`。

**坑 2：兜底处理器把 `e.getMessage()` 直接返回给前端。** 错误写法：`Result.fail(50000, e.getMessage())`。问题：未知异常的 message 里可能带着 SQL 语句、表名、内部文件路径，等于把系统内部结构透露给外部。正确做法：前端永远只收到"系统繁忙，请稍后重试"这类安全文案，细节只进日志。

**坑 3：Controller 里自己 try-catch，全局处理器失效。** 错误写法：Controller 方法里 `try { ... } catch (Exception e) { return Result.fail(...); }`。问题：异常被你接住了就传不到全局处理器，而且每个人 catch 后返回的内容各不相同，统一格式形同虚设。正确做法：Controller 不写 try-catch，让异常自然抛到边界；只有"需要补偿处理"（比如调第三方失败要降级）时才局部 catch。

**坑 4：忘了处理参数校验异常。** 错误写法：只写了 BizException 和 Exception 两个处理器。问题：`@Valid` 校验失败抛的是 `MethodArgumentNotValidException`，会落进 Exception 兜底——用户填错一个字段，却收到"系统繁忙"，error 日志里还多出一条假"系统故障"。正确做法：给校验异常单独写处理器，把字段级错误信息提取出来返回。

**坑 5：业务异常也用 error 级别记日志。** 错误写法：在 `handleBizException` 里 `log.error(..., e)`。问题：库存不足、余额不够这类业务失败每天发生成百上千次，error 日志被刷爆，告警天天响，真正的故障反而被淹没。正确做法：业务异常 warn，未知异常 error——日志级别本身就是在表达"这事严不严重"。

## 7. 和之前知识的连接

- **第 32 篇「异常处理」**：昨天定义的 `BizException`（继承 RuntimeException、携带 ErrorCode）是今天的主角。昨天只管"怎么抛"，今天解决"抛出后在哪被接住、变成什么响应"，两篇连起来就是异常从出生到终点的完整链路。
- **第 22 篇「统一返回结构」**：今天所有处理器返回的都是那篇定义的 `Result<T>` 信封。成功时由 Controller 返回 `Result.success(data)`，失败时由全局异常处理器返回 `Result.fail(...)`，两条路径殊途同归，前端拦截器才能一套逻辑通吃。
- **第 23 篇「状态码设计」**：`ErrorCode` 枚举今天是错误的"货物"，全局异常处理器是"打包发货"的地方。兜底用的 `SYSTEM_ERROR(50000)` 就是在那篇的码表上追加的。
- **第 21 篇「请求参数校验」**：`@Valid` 校验失败的产物 `MethodArgumentNotValidException`，正是今天第 2 个处理器专门接住的对象——校验只管"发现问题"，怎么把问题体面地告诉前端，是今天的活。

## 8. 面试 / 工作中常见问题

### 问题 1：@RestControllerAdvice 为什么能捕获所有 Controller 的异常？原理是什么？

参考答案：Controller 方法由 DispatcherServlet 统一调度执行，执行中抛出的异常会交给异常解析器链（HandlerExceptionResolver），其中 `ExceptionHandlerExceptionResolver` 负责查找 `@ControllerAdvice` 类里与异常类型匹配的 `@ExceptionHandler` 方法，按继承关系选最精确的那个执行。`@RestControllerAdvice` 相当于 `@ControllerAdvice + @ResponseBody`，处理方法的返回值直接序列化为响应体。本质是"请求入口统一，所以异常出口也能统一"。

### 问题 2：为什么 @Async 方法或定时任务里的异常，全局异常处理器捕获不到？该怎么处理？

参考答案：`@RestControllerAdvice` 的覆盖范围是 DispatcherServlet 的请求处理链路。异步方法和定时任务运行在独立线程池里，不经过这条链路，异常抛出后不会有任何 HTTP 响应可言。正确做法：在任务方法内部 try-catch 并记日志（必要时落库标记失败），异步任务还可以实现 `AsyncUncaughtExceptionHandler` 统一兜底；MQ 消费失败则交给消费重试和死信机制。

### 问题 3：线上用户反馈接口返回"系统繁忙，请稍后重试"，你怎么排查？

参考答案：这句话说明未知异常落进了兜底处理器，前端拿到的信息被刻意抹掉了，真相只在日志里。排查路径：按时间点 + 接口路径去日志系统搜对应的 `log.error("系统异常", e)`，堆栈就在里面。如果系统接入了链路追踪（traceId），响应头里带上 traceId，用一个 id 就能串起整条调用链。这也解释了为什么兜底方法必须先记完整日志再返回——那个 log 是排查的唯一入口。

## 9. 今日小结

- `@RestControllerAdvice` + `@ExceptionHandler` = 全局异常处理器，所有 Controller 异常转响应的统一出口。
- 三层结构：业务异常转错误码响应、校验异常提取字段错误、未知异常兜底"系统繁忙"。
- 日志与响应分离：堆栈进日志，前端只拿安全文案，`e.getMessage()` 绝不外泄。
- 业务异常记 warn、系统异常记 error，别让"库存不足"触发故障告警。
- 覆盖范围仅限 HTTP 请求链路，异步任务和定时任务的异常要自己兜。
