## 1. 今天学什么

Redis 是**进程外的键值内存存储**——所有应用实例共享同一份数据，这是它和本地缓存最根本的区别。Java 后端用它主要做四件事：缓存、分布式锁、计数与限流、排行与去重，分别对应 String、String/Set、String、ZSet 几种结构。今天讲三块：① 五种数据结构各自解决什么问题；② key 命名与过期规范，以及 `RedisTemplate` 的序列化陷阱；③ **分布式锁的正确实现**——`SET NX PX` 只是开始，误删、锁过期、不可靠这三件事都必须处理。

## 2. 前端工程师视角理解

最接近的类比是 `localStorage`：字符串 key、只能存序列化后的值、没有类型。但**作用域完全不同**——`localStorage` 每个用户一份，Redis 是**整个后端集群共享一份**。所以 Redis 的 key 设计不是给一个用户用的命名，而是**给全公司所有服务定的公共契约**，一旦上线就很难改。

**最有用的一个对应：Redis 执行命令是单线程的，和 JS 事件循环同构。** 你在 JS 里写一段同步死循环会卡住整个页面；在 Redis 里执行一条 `KEYS *` 或读一个几 MB 的大 key，会卡住**所有客户端的所有请求**。这个心智模型一旦建立，"禁止慢命令""禁止大 key"就不是背诵的规范，而是显然的结论。

**第二个对应是原子性。** JS 里 `count = count + 1` 在并发下不安全，Redis 的 `INCR key` 因为单线程串行执行，天然就是原子的——这解决了后端一个高频难题：多实例同时对一个数字做加减（库存、限流计数、点赞数）怎么不加错。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | JS / TS | Redis（Java 侧） | 迁移要点 |
|---|---|---|---|
| 存对象 | `JSON.stringify` 手动 | `RedisTemplate` 默认 **JDK 序列化**，存进去是二进制乱码 | 一律显式用 `StringRedisTemplate` + Jackson，让 redis-cli 里人可读 |
| 数据结构 | Object / Array / Map / Set | String / Hash / List / Set / ZSet | Hash≈对象、Set≈Set、ZSet≈带分数的可排序 Map，概念可直接迁移 |
| 并发计数 | 需自己加锁 | `INCR` / `HINCRBY` 服务端原子 | 分布式计数的首选，别用"读—改—写"三步 |
| 过期 | 无原生 TTL | 有 `EXPIRE`，但惰性删除 + 定期采样 | 设了 TTL 不等于准时释放内存（昨天坑 5 同源） |
| 类型安全 | 运行时才知道 | 泛型只到编译期，取回仍是 `byte[]` 解码 | `RedisTemplate<String, VO>` 的泛型骗不了运行期 |

一个反直觉的设计：**Redis 没有"字段级 schema"**。Hash 可以每个 entry 字段不同，Java 侧取出来直接映射成对象就会缺字段。所以工程上更常见的做法不是狂用 Hash，而是**一个聚合根一个 String key、value 存 JSON**——因为你的读取单位通常是整个对象，而运维排查时一行 JSON 比十个散字段好懂得多。

## 4. 真实业务场景

**场景：门店小程序——详情页缓存、活动限流、优惠券防超发、门店销售榜。**

- **详情页缓存（String + JSON）**：昨天方案的落地形态，`store:info:1024` → JSON 字符串，TTL 10 分钟。
- **活动限流（String 原子自增）**：大促开始瞬间，小程序首页 QPS 上万，后端要挡住"同一用户 1 秒内重复领券"。用 `INCR` 计数 + 首次请求设 `EXPIRE`，比查数据库快两个数量级。
- **优惠券防超发**：券库存 1 万张，用 `DECR` 原子扣减，扣到负数说明抢完。注意这**不违背昨天"库存绝不进缓存"的结论**——这里的 Redis 是**削峰的计数器**，DB 里的发放记录才是事实；Redis 扣了但落库失败要回补，两边差异靠对账收敛（第 44 篇）。
- **门店销售榜（ZSet）**：`ZINCRBY` 累加每家门店的分数，`ZREVRANGE` 取 Top 50，省掉每次 `ORDER BY` 全表扫描（第 16 篇）。

**用错的代价：** 用 `KEYS product:*` 排查线上问题，一次让 Redis 阻塞两秒，全服务超时；领券判断写成"先 GET 再判断再 SET"，超发几万张券；锁的 value 不记持有者，超时后删掉了别人的锁。

## 5. Java 示例代码

**分布式锁工具——`SET NX PX` + 持有者标识 + Lua 原子释放：**

```java
@Component
@RequiredArgsConstructor
public class RedisLockHelper {

    private final StringRedisTemplate redis;
    /** 释放必须是"比对再删"，两步分开就可能在比对后删掉别人的锁，故用 Lua 保证原子 */
    private static final RedisScript<Long> UNLOCK_SCRIPT = RedisScript.of(
            "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
            Long.class);

    /**
     * 尝试加锁：SET key value NX PX ttl —— NX 只在不存在时写入，PX 强制带过期防死锁。
     * value 存本线程唯一标识，确保只有持有者能释放。
     */
    public boolean tryLock(String key, String token, Duration ttl) {
        return Boolean.TRUE.equals(redis.opsForValue().setIfAbsent(key, token, ttl));
    }

    /** 解锁：Lua 内比对 token，不匹配则什么都不删 */
    public void unlock(String key, String token) {
        redis.execute(UNLOCK_SCRIPT, List.of(key), token);
    }
}
```

**限流计数与原子扣减：**

```java
/** 用户级限流：同一用户 1 秒内最多 1 次领券。INCR 原子，返回值即当前计数 */
public boolean allow(String userId) {
    String key = "rate:coupon:" + userId + ":" + (System.currentTimeMillis() / 1000);
    Long count = redis.opsForValue().increment(key);          // 原子自增，非读改写
    if (count != null && count == 1L) {
        // key 已按秒分桶，这里设 TTL 只是兜底回收，且只由首个请求设置，避免被反复续期
        redis.expire(key, 2, TimeUnit.SECONDS);
    }
    return count != null && count <= 1L;
}

/** 券库存扣减：DECR 原子减，负数说明已抢完，立即回加并返回失败 */
public boolean takeCoupon(String activityId) {
    String key = "stock:coupon:" + activityId;
    Long left = redis.opsForValue().decrement(key);
    if (left != null && left < 0) {
        redis.opsForValue().increment(key);                   // 回补，防止库存被多扣
        return false;
    }
    return true;
}
```

序列化统一走 JSON（Spring Boot 默认已提供 `StringRedisTemplate`，无需额外配置）：

## 6. 常见坑

**坑 1：生产用 `KEYS`。** 错误做法：`KEYS store:*` 排查问题。问题：Redis 单线程执行命令，`KEYS` 是 O(N) 全库扫描，百万 key 直接阻塞数秒，等于自己制造一次故障。正确做法：用 `SCAN` 游标分批遍历；排查时在只读从库或管理平台上做。

**坑 2：默认 `RedisTemplate` 的 JDK 序列化。** 现象：redis-cli 里 key 前带 `\xac\xed`，value 是不可读二进制，别的语言也读不了。正确做法：统一用 `StringRedisTemplate`，value 自己 `objectMapper.writeValueAsString()`；需要对象直存再单独配 `GenericJackson2JsonRedisSerializer`。

**坑 3：锁没设过期，或释放时删了别人的锁。** 前者：进程崩在锁中间 → key 永久存在 → 全局死锁；后者：A 执行超过 TTL 锁自动释放、B 拿到锁，A 结束时把 B 的锁删了。正确做法：`SET NX PX` 一步完成（不要分成 `SETNX` + `EXPIRE`，中间崩了就永久持锁）、value 存唯一 token、Lua 比对后删；生产直接用 Redisson 的 `tryLock(waitTime, leaseTime, unit)`。

**坑 4：把 Redis 当数据库。** 现象：内存到顶触发逐出（`allkeys-lru` 会随手删 key），或实例重启后数据丢失。正确做法：明确 Redis 只承载"丢了可重建"的数据；需要可靠的消息投递、幂等记录、资金流水，一律落 DB。

## 8. 面试 / 工作中常见问题

### 问题 1：RedisTemplate 和 StringRedisTemplate 有什么区别？为什么我存的值在 redis-cli 里是乱码？

参考答案：两者 API 相同，只是默认序列化器不同。`RedisTemplate` 默认用 JDK 序列化，key 和 value 都写成二进制，所以出现 `\xac\xed` 前缀，别的语言读不了、人也不能直接排查。`StringRedisTemplate` 是 `RedisTemplate<String, String>` 且用字符串序列化，key/value 在 Redis 里就是明文。工程结论：绝大多数场景从 `StringRedisTemplate` 起步，value 自己存 JSON。

### 问题 2：用 Redis 实现分布式锁要注意什么？

参考答案：四点。① 加锁必须是 `SET key value NX PX ttl` **一条命令**，拆成 `SETNX` + `EXPIRE` 就有"设完过期前进程挂了"的死锁窗口；② value 要存持有者唯一标识（UUID + 线程 ID），否则释放时无法判断锁还是不是自己的；③ 释放要"比对再删"，必须用 Lua 保证原子；④ TTL 要大于任务最长耗时，或者用 Redisson 看门狗自动续期。最后一条判断标准是：**Redis 锁只能防并发，不能保正确性**，涉及资金和发放的动作仍要有 DB 唯一索引兜底。

### 问题 3：Redis 单线程为什么还这么快？什么操作会毁掉它？

参考答案：快主要因为纯内存操作、单线程避免锁竞争和线程切换、 epoll 多路复用处理连接。"单线程"指命令执行，网络 I/O 在 6.0 后是多线程的。毁掉它的是一类 O(N) 大命令：`KEYS`、大集合的 `SMEMBERS` / `HGETALL`、读写几 MB 的大 key、以及 `DEL` 一个大集合——它们独占命令线程，表现为全服务超时。所以规范是禁 `KEYS`、控大 key、集合类用 `SCAN` 或拆分。

## 9. 今日小结

- Redis 是**全实例共享的一份数据**，key 设计是跨服务契约，不是本地变量。
- 记两个心智模型：**它和 JS 一样单线程执行命令**（慢命令 = 全站卡）；**`INCR` / `DECR` 是原子的**（分布式计数与扣减的正确解法）。
- 序列化只有一条规矩：**`StringRedisTemplate` + JSON**，让 key 在 redis-cli 里人可读、跨语言可读。
- 分布式锁四件套：`SET NX PX` 一条命令、token 标识持有者、Lua 比对释放、TTL 大于任务耗时；并且**锁防并发不保正确**，DB 唯一索引才是底线。
