> 衔接上一篇「线程池与并发」：那篇的故障停在"队列涨到百万级、Full GC 从 2 秒变 40 秒、最后 OOM"。今天把这三句话里的每个数字都拆开看。

## 1. 今天学什么

JVM 与内存解决的是"**进程还能不能被信任地跑到明天**"。功能 bug 影响一次请求，内存问题影响整台机器：一次 Full GC 停顿 40 秒，等于所有接口同时不可用，而 CPU 看起来还很闲。

四块内容：① 堆的分区（新生代/老年代、G1 的 region）与"对象为什么会长到老年代"，这是 Full GC 变长的因果起点；② 收集器怎么选（G1 与 ZGC 的适用边界）；③ 容器里内存怎么配——`-Xmx` 只是预算的一部分，**堆外、元空间、线程栈都要算，否则会被 OOMKilled**；④ 排查工具箱：`jstat` 看趋势、GC 日志看原因、堆 dump + MAT 支配树看元凶，以及"被杀 ≠ OOM"这个最容易被误判的分叉。

它是第 58 篇的下半场：上一篇告诉你无界队列会堆内存，这一篇告诉你堆内存之后会发生什么。

## 2. 前端工程师视角理解

好消息是你有一个几乎完全对口的经验：**DevTools 的 Memory 面板。** 前端排查内存泄漏的标准动作是——进进出出同一个页面几次，拍三次堆快照，看保留大小（Retained Size）是不是每次都在涨；Detached DOM trees 就是"你以为释放了、其实还被引用着"。后端是同一套方法论，只是工具换成 `jstat`（看趋势）和 MAT（看快照的支配树 Dominator Tree，Retained Heap 概念一模一样）。

第二个直觉是 **GC 其实一直都在，只是 V8 帮你藏得很好**。V8 也有新生代（Scavenge）和老年代（Mark-Sweep），只是浏览器页面生命周期短、你很少观察它。后端进程要跑几个月，GC 的每一分代价都会暴露出来：**GC 停顿是"所有应用线程一起停"的**，这就是为什么停顿期间接口集体超时、而 CPU 却不忙。你只需要把前端那条经验放大来看：一个页面卡 200ms 你嫌卡，服务卡 40 秒就是事故。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | JVM |
|---|---|---|
| 堆分区 | V8 新生代 / 老年代（你一般看不见） | 显式可查：Eden / Survivor / Old，G1 按 region 动态划 |
| 停顿 | 主线程 GC 停顿表现为掉帧 | STW 期间**所有业务线程停**，体现为接口集体超时 |
| 上限 | 页面刷新即归零；Node 用 `--max-old-space-size` | 长期运行，`-Xmx` / 容器 limit 双约束 |
| 诊断 | Memory 快照 + Retained Size | `jstat` 趋势 + GC 日志 + MAT 支配树 |
| 死亡方式 | 标签页被系统回收 | `OutOfMemoryError`（Java 层）**或** OOMKilled（内核层） |
| 内存对象 | 引用/闭包 Detached DOM | 静态集合、线程池队列、`ThreadLocal`、连接缓冲 |

**最关键的一条因果：Full GC 变长，通常不是 GC 变慢了，而是"活着的东西变多了"。** GC 的工作量与**存活对象数量**成正比：Minor GC 只扫新生代，便宜；而一旦对象活得够久被晋升（age 阈值）到老年代，或者一次性分配超大对象（G1 里叫 humongous），清理就要动用 Full GC，停顿随存活集大小线性上升。所以第 58 篇那条链在 JVM 视角是这样闭合的：无界队列 → 任务对象在每次 Minor GC 里都活着 → 年龄涨满被晋升 → 老年代只涨不降 → Full GC 越来越长、越来越频繁。**监控上表现为一对特征组合：老年代 GC 后基线抬高 + Full GC 频率上升**，看到这对组合就该抓 dump，而不是等它炸。

## 4. 真实业务场景

**场景：门店订单异步化上线第 3 天，两台实例先后"无声死亡"。**

业务背景：就是第 58 篇那套代码——`Executors.newFixedThreadPool(10)` 的无界队列。上线当天没出事，因为大促流量才刚开始爬坡：每天存活对象缓慢变多，队列在夜里也没排空。

第三天 02:40，一台实例的接口开始大面积超时 5 秒（RT 曲线整齐地跳一个台阶，错误码是网关超时），K8s 探针判定失败把流量切走；02:47 容器被杀，`kubectl describe pod` 显示 **`OOMKilled`，退出码 137**。诡异的是：**应用日志里没有任何 `OutOfMemoryError`，也没有 heap dump**，看起来像"进程凭空消失"。

复盘时两条线索拼起来：① `jstat -gcutil` 的历史采样显示老年代（O 列）在两天内从 40% 爬到 96%，每次 Full GC 后只降 2 个百分点——**基线持续抬升就是泄漏级堆积，不是抖动**；② 容器 limit 是 2GB，而 JVM 配了 `-Xmx1600m`，加上 Metaspace、每根线程约 1MB 的栈（当时线程数 400+）、Netty/驱动的直接内存，RSS 早就顶到 2GB 了——**Java 层的堆还没喊饿，内核先动手了**。这也解释了为什么没有 `OutOfMemoryError`：被 SIGKILL 的进程没有机会抛异常。

修复分三层：队列改有界 + 拒绝策略（第 58 篇）、堆上限按容器 limit 重新算并留 25% 余量、加上"死前留尸检"的参数（下一节）。

**用错的代价**：不是"重启一下就好"，而是**故障被伪装成基础设施问题**——没有异常、没有日志、没有 dump，团队会去怀疑节点、网络和 K8s，而真正的原因是三天前那次"内存多点无所谓"的写法。

## 5. Java 示例代码

**容器里的 JVM 参数：预算、尸检、可观测，三件都要。**

```bash
# 堆按容器内存的百分比取，而不是按宿主机（cgroup 感知，JDK 8u191+/10+）
-XX:MaxRAMPercentage=70.0                # 留 30% 给元空间、线程栈、直接内存与 RSS 开销
-Xms512m                                 # 起始堆不必等于上限，避免启动即占满
-XX:MaxMetaspaceSize=256m                # 元空间也要有上限，否则类加载泄漏同样撑爆容器

# ★ 死前留证据：OOM 时自动 dump，并让进程退出交给编排系统重启（别让它半死不活地僵在那）
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs/
-XX:+ExitOnOutOfMemoryError

# GC 日志（JDK 9+ 统一日志）：排查"为什么这次停顿 8 秒"全靠它的原因行
-Xlog:gc*,gc+age=trace,safepoint:file=/data/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=50m

-Xss512k                                 # 线程栈预算：400 根线程 × 1MB ≈ 400MB，是压垮容器的隐形项（第 58 篇）
```

**应用侧自检：把"老年代基线是否抬升"变成一条日志/指标。**

```java
/**
 * 定期打印各内存池的使用与已提交量：老年代 GC 后不回落，就是堆积/泄漏的最早信号。
 * 生产上更常见的是接 Micrometer 的 MemoryMetrics（JVM 指标默认就有），这里给一份不依赖监控的兜底。
 */
@Component
@Slf4j
class MemoryProbe {

    @Scheduled(fixedDelay = 60_000)          // 第 44 篇：定时任务，注意别在本地环境也跑起来
    void probe() {
        for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans()) {
            if (pool.getType() != MemoryType.HEAP) continue;
            MemoryUsage u = pool.getUsage();                    // getUsed/getCommitted/getMax 单位字节
            if (u == null || u.getMax() < 0) continue;           // 部分池无上限，跳过
            long usedMb = u.getUsed() / 1024 / 1024;
            long maxMb = u.getMax() / 1024 / 1024;
            // 名字里含 Old 的池就是老年代：它若长期 >85%，比告警更早提示你要出事
            log.info("mem pool={} used={}MB max={}MB ratio={}", pool.getName(), usedMb, maxMb,
                    String.format("%.2f", (double) usedMb / maxMb));
        }
    }
}
```

## 6. 常见坑

**坑 1：以为进程内存不足一定会有 `OutOfMemoryError`。** 错误判断："日志里没有 OOM，说明不是内存问题。" 问题：容器里 RSS 触到 limit 会被内核直接 `SIGKILL`（K8s 显示 `OOMKilled`、退出码 137），进程没有机会抛异常、也没有堆栈；Java 层的堆 OOM 和容器层的 OOMKilled 是**两套完全不同的死法**。正确做法：排查时先看 `kubectl describe pod` 的 Last State / 退出码，再看节点 `dmesg` 的 oom-kill 记录；把堆上限按容器 limit 留出 25~30% 余量，并把 `-XX:+ExitOnOutOfMemoryError` 配上，让"死得体面"变成可观测事件。

**坑 2：把 Full GC 当病因去调参。** 错误做法：看到停顿长，就去搜"JVM 调优参数"，改一堆 `-XX:` 数字。问题：GC 的工作量由**存活对象集**决定，停顿变长是结果；如果真实原因是队列堆积、静态集合只增不减、缓存无上限，调参只是把 OOM 推后几分钟，还会掩盖现场。正确做法：先用 `jstat` 确认"GC 后老年代基线是否抬升"，再抓两次 dump 做差集；**基线平稳 + 单次大对象分配**才是容量问题，**基线持续抬升**就是泄漏或无上限堆积，改代码不改参数。

**坑 3：不做任何"死前留证"配置，事故后无从下手。** 错误做法：生产只给 `-Xmx`，其余全默认。问题：真出事时既没有 dump、也没有 GC 日志，只能重启观察，等于每轮故障都从零猜；反过来"随时可 dump"也有代价——几百 MB 到几 GB 的堆 dump 会拉长停顿、占满磁盘。正确做法：**上线前就固定三件事**——`HeapDumpOnOutOfMemoryError` + 落盘目录有配额、GC 日志轮转（`filecount/filesize`）、JVM 指标进监控；排查期再临时打开额外的 dump 开关。

## 8. 面试 / 工作中常见问题

### 问题 1：怎么区分"内存泄漏"和"就是需要这么多内存"？

参考答案：看 **GC 之后的基线**，不看峰值。泄漏的特征是每次 Full GC 后老年代都降不回原水位、曲线持续抬升；容量不足则是 GC 后基线平稳，但业务量一上来就顶到上限。工程做法：抓两个时间间隔足够长的 dump 做**差集**（同一类实例数量单调增长、且支配树指向静态集合/队列/`ThreadLocal`），就是泄漏；否则调大堆并加限流即可。

### 问题 2：容器里 2GB 内存，JVM 参数怎么给？

参考答案：先算总账，堆只是其中一项：堆 + 元空间 + 线程数×栈大小 + 直接内存（Netty/NIO）+ 代码缓存与 GC 结构 + JIT 的开销。2GB 通常给堆 1.2~1.4GB（用 `-XX:MaxRAMPercentage=60~70` 表达，随 limit 自适应），`MaxMetaspaceSize` 设上限、`-Xss` 按线程数校准。最后一定要看真实 RSS 峰值是否留有 25% 余量，否则 `OOMKilled` 会替你收场，而且不留 Java 层日志。

### 问题 3：线上 Full GC 频繁，你第一步看什么？

参考答案：先看 GC 日志的**原因行**（哪一列触发：Allocation Failure / Metadata GC Threshold / System.gc / Humongous Allocation），它能立刻把问题分流——元空间满就去查类加载，频繁 humongous 就是大数组/大结果集，出现 `System.gc()` 要查是不是某个库在调。第二步 `jstat -gcutil` 看晋升速率与老年代基线，确认是"堆不够"还是"东西不该活着"。只有需要定位到具体对象时才抓 dump，因为 dump 本身有停顿和磁盘代价。

## 9. 今日小结

- GC 的工作量取决于**存活对象集**：停顿变长几乎总是"活着的东西变多了"，先怀疑堆积，再怀疑参数。
- 老年代 **GC 后基线是否抬升**是判别泄漏与容量的唯一硬指标，趋势看 `jstat`，元凶看 MAT 支配树（Retained Size）。
- 容器里要同时防两种死法：`OutOfMemoryError`（Java 层，有日志有 dump）与 `OOMKilled` 137（内核层，什么都不留）；堆只是预算一项，元空间、线程栈、直接内存都要算，`MaxRAMPercentage` + 留 25% 余量是基本姿势。
- 上线前就该配好"尸检三件套"：heap dump on OOM、GC 日志轮转、JVM 指标进监控。
