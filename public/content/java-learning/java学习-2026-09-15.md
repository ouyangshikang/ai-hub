# Java 学习：代码分层规范

> 系列第 55 篇 · 第六阶段：工程化
> 衔接上一篇「集成测试」：昨天说到有一类问题测试永远测不出来——**结构**。今天就把"依赖方向"变成一条会红的测试。
> **与第 8 篇的分工**：第 8 篇讲三层**各自该干什么**（职责与调用方向）；今天讲**怎么让这个约定不被破坏**——包结构为什么等于可见性、Entity/VO 的转换点放在哪、`common` 层怎么防止长成垃圾场，以及用 ArchUnit 把规则钉进 CI。

## 1. 今天学什么

代码分层规范的目的是：**把架构从"评审时靠人记"变成"提交时机器判"。** 大多数项目的分层只写在 README 里，于是三年后 Controller 直接 new Mapper、`util` 里藏着业务规则、数据库实体被原样返回给前端——每一步都不违反编译器规则，却一步步让改动成本上升。

今天讲四件事：① 包结构与依赖方向的定义（谁能 import 谁，为什么违规要付出代价）；② Entity / DTO / VO 的**转换点**该固定在哪一层；③ 公共层（`common` / `util`）的边界，它一旦无序就会造成隐式循环；④ 用 ArchUnit 写三条规则，让新违规在 CI 里直接失败，并用"冻结历史违规"的方式给老项目渐进落地。

它是工程化主题：规范本身不难，难的是**在没有人力持续监督的情况下也不腐化**。

## 2. 前端工程师视角理解

你其实有过同样的挫败。前端项目里"组件不能直接调 API，要走 `services/`"这条规矩，写在文档里时没人遵守，直到 ESLint 配上 `import/no-restricted-paths` 或 eslint-plugin-boundaries，违规才在 lint 阶段变红——**能被机器执行的约定才会被执行，剩下的都只是愿望。** 今天 ArchUnit 扮演的就是这个角色，区别只是它检查的是 Java 的类依赖而不是 import 路径。

第二个直觉是**可见性差异**。ESM 里一个模块不 `export`，别人就拿不到，**默认是封闭的**；Java 里一个 `public class` 只要在同一条 classpath 上，任何包都能 import，**默认是敞开的**。Java 唯一的天然屏障是"包级私有"（不写修饰符 = 同包可见），它挡得住隔壁包的乱引用，但也因此逼你把内部实现拆到不同包。这条差异解释了为什么 Java 项目必须自建架构检查工具：**编译器根本不关心你的分层。**

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 默认可见性 | 不 `export` 即私有 | `public` 即全 classpath 可用，包级私有才受控 |
| 违规成本 | 编译器不管，靠 lint 规则 | 编译器也不管，靠 ArchUnit / 评审 |
| 环依赖 | 打包能过但行为诡异（模块循环） | Spring 启动直接失败（Boot 2.6 起默认禁止） |
| 循环的修法 | 提取共享模块、依赖倒置 | 提取下层服务、事件解耦（第 8 篇）；`@Lazy` 是止痛药（第 40 篇） |
| 组织方式 | 按类型目录 → 按 feature 目录 | 按层分包 → 按模块分包 + 层内再分 |
| 强制手段 | ESLint boundaries 插件 | ArchUnit `layeredArchitecture()` 规则 |

**为什么后端把这件事看得更重？** 因为运行时的耦合更硬。前端两个组件互相引用，最坏是 bundle 里多一份代码；后端两个 Service 互相依赖，**Spring 直接起不来**——循环依赖在依赖注入阶段就无法收敛（第 6 篇的第五步）。这个"启动即失败"的特性其实是礼物：它逼你在设计阶段就把方向理顺。而更隐蔽的风险是**间接环**：A→B→C→A 这种三个类跨模块的环，Spring 靠字段注入还能侥幸启动，但已经没人能安全改动其中任何一个——所以今天要写的规则之一是"模块之间不得成环"，它比"不许有环"更现实。

## 4. 真实业务场景

**场景：券模块三年腐化后，一次满减规则改动要动 7 个地方。**

业务背景：门店中台的优惠券最早只有"满减"，后来加了折扣券、赠品券、企业专享券。项目最初严格按第 8 篇的三层写，但每次赶工期都会漏一点：

- 有人为了少写一次转换，把 `CouponEntity` 直接放进接口返回（第 10 篇明确禁止过）——于是数据库列 `internal_cost_rate`（内部成本率）被前端拿到过，第 37 篇讲的脱敏边界被从结构上击穿；
- 券状态判断被复制了三份：一份在 `CouponService`，一份在 `OrderService` 里"顺手写的"，一份在导出报表的 `common/CouponUtils`；
- `common` 包越堆越大，最后 `CouponUtils` import 了 `OrderService`、`OrderService` 又 import `CouponUtils`——**包级循环，Spring 靠字段注入侥幸启动**，但没人敢动它们。

结果：一次"企业券不参与满减"的规则改动，需要同时改三处状态判断（漏一处就是线上口径不一致），并且因为 Entity 被前端直接消费，字段改名变成前后端联调级别的破坏性变更（第 26 篇讲过的兼容性代价）。

治理动作分两步：先把规则写成 ArchUnit 测试（下面 3 条），**跑一次红了 214 处违规**——这个数字本身就是腐化程度；然后用"冻结历史违规"的方式只拦新增，再按迭代逐步还债。

**用错的代价**：不是"代码不好看"，而是**每一次改动都要靠人记住全部历史例外**——规范衰减速度只要快于团队扩张速度，改一个需求的风险就会持续上升。

## 5. Java 示例代码

```java
/** 架构规则也是一种测试：不起容器、不连 DB，秒级跑完且不会 flaky */
@AnalyzeClasses(packages = "com.example.store",
        importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureRulesTest {

    /** 规则 1：分层方向。Controller 只被框架访问，Service 只允许 Controller 调用 */
    @ArchTest
    static final ArchRule layerDependencyDirection = layeredArchitecture()
            .consideringAllDependencies()
            .layer("Controller").definedBy("..api..")
            .layer("Service").definedBy("..service..")
            .layer("Mapper").definedBy("..mapper..")
            .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
            .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
            .whereLayer("Mapper").mayOnlyBeAccessedByLayers("Service");

    /** 规则 2：接口层与 VO 都不许依赖 Entity —— 这才真正阻止了"Controller 返回 Entity" */
    @ArchTest
    static final ArchRule entityNeverLeavesServiceLayer = noClasses()
            .that().resideInAnyPackage("..api..", "..vo..")
            .should().dependOnClassesThat().resideInAPackage("..domain.entity..")
            .because("Entity 结构一变就同时影响 SQL 与前端契约，必须在 Service 出口转成 VO");

    /** 规则 3：业务模块之间不得成环（含经由 common 形成的间接环） */
    @ArchTest
    static final ArchRule noCyclesBetweenPackages = slices()
            .matching("com.example.store.(*)..").should().beFreeOfCycles();

    /** 规则 4：common/util 里不许有业务 */
    @ArchTest
    static final ArchRule commonLayerHasNoBusinessLogic = noClasses()
            .that().resideInAnyPackage("..common..", "..util..")
            .should().dependOnClassesThat().resideInAnyPackage("..service..", "..mapper..")
            .because("工具类一旦依赖业务，就同时变成调用方和被调用方，隐式环从这里开始");
}
```

老项目一次性全红怎么办？用 ArchUnit 的冻结规则——把当前违规基线存进仓库，**只有新增违规才让 CI 失败**：

```java
@ArchTest
static final ArchRule onlyBlockNewViolations = FreezingArchRule.freeze(layerDependencyDirection);
```

依赖放 test scope：`com.tngtech.archunit:archunit-junit5:1.2.1`；它跑在 surefire 里，所以第 53 篇的 `mvn test` 就是执行门禁的地方。

## 6. 常见坑

**坑 1：规范只写在文档和 Wiki 里。** 错误做法：新人入职发一份《分层规范》，靠 code review 守。问题：评审是最先被工期牺牲的环节，且评审者并不知道全量历史例外；三个月后文档和代码就不一致了。正确做法：每条能机器检查的规则都要有对应测试（依赖方向、Entity 不外泄、包不成环），**并在 CI 上是硬门禁**；文档只留"为什么这样定"。

**坑 2：Entity 一路穿透到接口层。** 错误做法：为了少写转换，Controller 直接返回 `CouponEntity`。问题：数据库字段成为对外契约（改列名 = 破坏性变更），敏感列（成本率、内部备注）被顺带暴露，而且 `LocalDateTime`、`BigDecimal` 的序列化格式前端无法控制（第 27 篇的字段命名与格式约定同时失控）。正确做法：**转换点固定在 Service 出口**，接口层签名里只允许 `VO`；入参只允许 `DTO`。实在嫌重复，用 MapStruct 生成转换代码，也别把 Entity 交出去。

**坑 3：`common` 层长成隐式枢纽。** 错误做法：不知道放哪的代码就放 `util`，最后工具类 import 业务 Service、业务又 import 工具类。问题：编译期看不出错，但模块之间通过 `common` 完成了事实上的双向依赖，谁也拆不出来。正确做法：`common` 只放**无业务语义**的东西（时间格式化、加解密、分页包装），并用规则 3、4 双向锁死；带业务的"公共逻辑"要么下沉成独立领域模块，要么按第 8 篇的做法抽出一个更下层的聚合服务。

## 7. 和之前知识的连接

- **第 8 篇「Controller / Service / Mapper 分层」**：那篇定义了三层职责和"用聚合服务打破 Service 循环"；今天给它补上强制手段——把同一件事写成 ArchUnit 规则。
- **第 10 篇「DTO / VO / Entity 的区别」**：那篇回答"用哪个对象"，今天回答"在**哪一层**转换、怎么用测试保证没人偷懒把 Entity 递到接口层"。
- **第 54 篇「集成测试」**：ArchUnit 规则本质是一类特殊测试——只读字节码、不启容器、不碰数据，因此它不会 flaky，适合放进 PR 的秒级门禁。

## 8. 面试 / 工作中常见问题

### 问题 1：接手一个没有分层的老项目，怎么落地规则而不是一上来红 500 条？

参考答案：分三步。① 先只加**最便宜、最有共识**的一条（Entity 不得依赖接口层），让它红并当场冻结成基线，这样规则立刻存在且只拦新增；② 再逐条加依赖方向与包环，每加一条都走"冻结 + 建还债任务"；③ 每轮迭代顺手解一批历史违规，冻结基线会自然缩小。切忌第一次就把十条规则全设成硬门禁——那只会让团队把它整体关掉。

### 问题 2：Spring 报循环依赖了，你怎么拆？

参考答案：先确认是"包设计问题"还是"职责划分问题"。① 最常见是 A、B 两个 Service 互相注入，把共同逻辑抽到第三方的下层服务（第 8 篇的做法），或把其中一侧改成**事件驱动**（本地事件 / MQ，第 47 篇）解耦；② 若只是两个方法级的小引用，`@Lazy` 能止痛但不解决问题，会留下一个没人敢动的环；③ 结构性原因是模块边界切错，就按业务模块重切，用 ArchUnit 保证新边界不被打穿。

### 问题 3：为什么不直接按功能建包，还保留 controller/service/mapper 分层？

参考答案：两者不是替代关系，是**两个轴**。中大项目通常先按业务模块分（`coupon/`、`order/`），模块内部再分层（`coupon/api`、`coupon/service`、`coupon/mapper`）——这样"改券"只动一个子树，同时依赖方向仍然清晰。小项目只按层分足够；关键是选定后由规则锁定（模块间只准引用彼此的 `api` 包），否则两种切法会混成一团。

## 9. 今日小结

- 能机器执行的约定才会被执行：分层规范的价值取决于它是不是 CI 上的一条红色失败。
- Java 的可见性默认是敞开的（`public` 即可被 import），这和 ESM"不 export 就拿不到"相反，所以架构约束必须自己写。
- 先钉两条最便宜的规则：**接口层不依赖 Entity**（转换点固定在 Service 出口）、**`common` 只被依赖不依赖业务**——后者是隐式环的源头。
- 老项目用冻结基线渐进收敛：先让规则存在并只拦新增，再让违规数随迭代下降，别一次上十条硬门禁。

## 10. 明日预告

明天建议学习：`代码可维护性`

原因：今天解决的是"**谁能动谁**"，把依赖方向锁死。但结构合规之后还有一类问题 ArchUnit 测不出来——**看不看得懂**：一个 300 行的 `if` 嵌套、一个 `handleData()` 这样的命名、一段没有注释的优惠叠加顺序。第六阶段第 9 项「代码可维护性」讲的就是这一层：命名与包名的一致性约定、圈复杂度与长方法的拆分手法、注释该写"为什么"而不是复述代码、常见坏味道清单与安全重构。顺序上正好互补：拆方法会改动依赖，方向对不对由今天的门禁兜住。
