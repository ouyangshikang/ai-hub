# Java 学习：分布式锁与幂等

> 系列第 60 篇 · 第七阶段：分布式一致性与容错（第 1 篇）
> 衔接上一篇「JVM 与内存」：那篇的 GC 停顿不只是"接口变慢"，它还会**让分布式锁失效**——今天就来收这个账。
> **与第 25 / 46 篇的分工**：第 25 篇讲"重复请求怎么挡"（幂等 key + SETNX + 唯一索引），第 46 篇讲"锁怎么写才不误删"（`SET NX PX` + 持有者标识 + Lua 释放）。今天讲**挡住之后仍然出错怎么办**：正确性该由谁保证、锁在什么情况下会失效、以及"只生效一次"的完整模型。

## 1. 今天学什么

多副本部署（第 48 篇）之后，"同时发生"跨了进程，单机时代的三样保证全部失效：`synchronized` 只管本进程，事务只管单库，`check-then-act` 的两个动作之间能被别的实例插进来。

今天讲四件事：① **正确性来源的优先级**——能用唯一约束和条件更新（CAS）解决的，不要用分布式锁；锁的位置应该是"实在无法用一条语句表达"的地方；② 锁的**失效模型**：超时时间小于业务耗时、GC 停顿（第 59 篇）、主从切换丢锁，以及唯一能救回"旧持有者迟到写入"的办法——**fencing token**；③ **条件更新与乐观锁**：`WHERE quantity >= n` 和 `version` 列怎么把判断和写合并成一步；④ 幂等表的**三态与结果复用**：重复请求不该只返回"失败"，网关重试要拿到第一次的结果。

一句话概括：**锁降低冲突概率，约束和 CAS 保证正确性。** 把正确性寄托在锁上，是所有超卖事故的共同起手式。

## 2. 前端工程师视角理解

先说一个你完全没有的经验：**前端不存在这个问题。** 一个页面一个 JS 运行时，两个 `onClick` 不可能同时改同一个变量——事件循环替你做掉了互斥。所以你会本能地觉得"我先查一下库存再扣减"是对的，因为在浏览器里它确实是对的。后端这两个动作之间，另一个实例可以插进来，这叫 **check-then-act 竞态**：读到的值在做决定时已经过期了。

那"锁"这个概念从哪儿理解最好？其实你在浏览器里做过一模一样的事——**提交按钮点下去立刻置 loading 并禁用**。那是个客户端锁：能挡住双击，挡不住两个标签页各点一次（不同 JS 上下文）。后端的 `synchronized` 就是这个按钮：**只对同一个进程有效**，三个实例就是三个按钮。Redis 锁相当于把 loading 状态挪到服务端共享，能跨标签页了——但它会"卡死"（进程崩了没解锁）、会"提前解锁"（超时了业务还没跑完），这就是今天第 3、4 节要处理的失效。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 多副本 |
|---|---|---|
| 互斥范围 | 天然单线程，无竞争 | `synchronized` 只覆盖本进程，跨进程无效 |
| 共享状态 | 全服共享一份，但更新要自己排队 | Redis / DB 是共享的，写入要显式仲裁 |
| 乐观并发 | ETag / `If-Match`、`version` 字段冲突则 412 | 同一思路：`UPDATE ... WHERE version = ?` |
| 去重 | 按钮 loading、请求 cancel | 幂等键 + 唯一索引 + 三态记录 |
| 失败模式 | UI 卡住、重复发请求 | 超卖、重复发券、脏数据（不可回滚） |

**Java 里"共享可变状态"的规模比 Node 大得多**，因为 Node 的共享只有 Redis 一层，而后端把数据库当共享内存用。于是有一个非常关键的差别：数据库**能替你原子地做"判断 + 写入"**，而 Redis 锁不能。

```sql
-- 判断和扣减合并成一步，多副本同时执行也只会成功 N 次（N = 库存数）
UPDATE store_stock SET quantity = quantity - #{n}
 WHERE store_id = #{s} AND sku_id = #{k} AND quantity >= #{n};
```

这条语句没有锁、没有 `SELECT`、没有 if，却是三者里唯一**在任何并发时序下都成立**的写法。第 46 篇那套 Redis 锁的完整实现，正确性也不如它——这就是"能 CAS 就别上锁"的由来。锁真正的用武之地是**跨表跨系统**、无法压缩成一条语句的动作（比如"查余额 → 调第三方 → 记流水"）。

## 4. 真实业务场景

**场景：门店库存超卖 12 杯，Redis 锁明明"加了"。**

业务背景：到店自取的限量商品，库存 30，三个实例接大促流量。开发在扣减前加了 `synchronized`，压测没问题（**单实例压测**，第 51 篇讲过的坑）；上线后发现超卖，于是改成第 46 篇那套 Redis 锁：`SET stock:lock:1024 NX PX 3000`。仍然超卖。

三个原因叠加，每一个都单独致命：

1. **锁内做了"查 + 改"两步**：拿到锁后 `SELECT quantity` 再 `UPDATE ... SET quantity = 计算值`，扣减用的是内存里读到的数——锁过期时这一步尤其致命；
2. **锁的 3 秒小于业务最坏耗时**：一次 Full GC 停顿 6 秒（第 59 篇），锁在停顿中过期，另一实例合法拿到锁，两者先后写入同一个库存行；
3. **释放时没校验持有者**：实例 A 超时后自己的 `finally` 执行删除，删掉了实例 B 正持有的锁，冲突窗口瞬间扩大到所有请求。

治理分三层落地：**正确性交给数据库**——上面的 CAS 语句 + 影响行数为 0 时抛业务异常（第 34 篇的 warn 留证）；**热点拆开**——库存按 10 段分桶存，`store_stock` 变成 10 行，同一商品的行锁竞争降一个量级（第 55 篇那个 `handleData` 式的集中式写法在这里也一并被拆掉）；**锁降级为效率手段**——只用来减少无效争抢，且 `finally` 用 Lua 比较持有者再删。同一天还查出另一件事：网关超时重试（前端用户其实只点了一次）造成 5 笔重复下单——幂等表当时只有"存在即拒绝"，改成了三态 + 结果复用。

**用错的代价**：超卖不能靠回滚，只能事后打电话补货或赔付；而第 3 个原因让"加了锁"变成了"故障被放大"。

## 5. Java 示例代码

```java
@Mapper
public interface StockMapper {

    /**
     * ★ 正确性来源：判断、扣减、拒收旧令牌三件事在同一条语句里完成，多副本天然安全。
     * last_token 放在被保护的资源行上——分开两张表校验就会留窗口：校验通过后仍可被覆盖。
     */
    @Update("UPDATE store_stock SET quantity = quantity - #{n}, last_token = #{token} " +
            "WHERE store_id = #{storeId} AND sku_id = #{skuId} " +
            "  AND quantity >= #{n} AND last_token < #{token}")
    int deduct(@Param("storeId") long storeId, @Param("skuId") long skuId,
               @Param("n") int n, @Param("token") long token);
}

@Service
@RequiredArgsConstructor
@Slf4j
public class StockService {

    private final StockMapper stockMapper;      // 世代号由加锁层（拿锁成功后 INCR 锁键世代）传入，这里只负责拒收旧值

    /**
     * token 取自"每次成功拿到分布式锁时"的 INCR 结果 —— 它是锁的世代号（generation），
     * 不是每次业务调用自增：一个请求一号就退化成请求顺序，挡不住 GC 停顿后迟到的旧持有者。
     */
    public void deduct(long storeId, long skuId, int n, long lockGeneration) {
        if (stockMapper.deduct(storeId, skuId, n, lockGeneration) == 0) {
            // 影响行数 0 有两种原因，必须留证据区分（第 34 篇）：库存不足 vs 被更新的世代拒绝
            log.warn("库存扣减未生效 storeId={} skuId={} n={} token={}", storeId, skuId, n, lockGeneration);
            throw new BizException(ErrorCode.STOCK_NOT_ENOUGH, "库存不足");
        }
    }
}
```

```java
/** 幂等表三态：重复请求不是简单拒绝，而是复用第一次的结果（网关重试要看到成功） */
@Service
@RequiredArgsConstructor
@Slf4j
public class IdempotentOrderService {

    private final IdempotentRecordMapper recordMapper;

    public OrderVO submit(IdempotentCmd cmd) {
        try {
            // 占位：biz_key 上建唯一索引，"判断有没有"和"插入"必须是同一步
            recordMapper.insert(new IdempotentRecord(cmd.key(), IdempotentStatus.PROCESSING, null));
        } catch (DuplicateKeyException dup) {
            IdempotentRecord exist = recordMapper.selectByBizKey(cmd.key());
            if (exist.status() == IdempotentStatus.SUCCESS) {
                // ★ 结果复用：cachedResult 就是把结果列（JSON 字符串）反序列化，不是框架自带能力
                return exist.cachedResult(OrderVO.class);
            }
            if (exist.status() == IdempotentStatus.PROCESSING) {
                throw new BizException(ErrorCode.REQUEST_PROCESSING, "请求处理中，请稍后查询");
            }
            recordMapper.markRetrying(cmd.key());   // FAIL：允许同一 key 重试，第 25 篇的"删掉记录"会丢结果
        }
        try {
            OrderVO result = doCreate(cmd);
            recordMapper.markSuccess(cmd.key(), result);    // 存结果，供后续重试复用
            return result;
        } catch (RuntimeException e) {
            recordMapper.markFail(cmd.key(), e.getMessage());  // 别删记录：留下可审计的失败态
            throw e;
        }
    }
}
```

## 6. 常见坑

**坑 1：把正确性寄托在锁上。** 错误做法：拿锁 → `SELECT` → 内存计算 → `UPDATE set x=算出的值`。问题：写的是"我读到的那一刻的值"，锁只要过期一次就丢更新；而锁一定会过期（GC 停顿、下游抖动、时钟漂移、主从切换丢锁）。正确做法：**写"相对变化"和"带条件的变化"**（`quantity = quantity - n`、`WHERE quantity >= n`），把判断交给数据库；锁只用来减少无效争抢和串行化跨系统步骤，并用 fencing token 拒收迟到的旧持有者。

**坑 2：幂等只做"存在即拒绝"。** 错误做法：查到幂等记录就直接返回"重复请求"错误码。问题：调用方分不清是"我的请求失败了"还是"早就成功了"——网关重试会把一次正常请求判成失败，用户看到"下单失败"但其实已经下单（比超卖更容易被投诉）。正确做法：幂等记录带**三态**，`SUCCESS` 时返回首次结果，`PROCESSING` 时返回"处理中 + 查询入口"，只有 `FAIL` 才允许重投；异步场景（MQ 重投，第 47 篇）则应直接跳过并 ack。

**坑 3：锁的超时时间按平均耗时设。** 错误做法：业务平均 200ms，就把 lease 设 500ms。问题：超时是**为最坏情况准备的**，一次 Full GC 就可能 6 秒（第 59 篇），500ms 必然被击穿；反过来把 lease 拉到几分钟，又会让进程崩溃后长时间无人接管。正确做法：用 Redisson 的看门狗自动续期（默认 30s、每 10s 续一次），或按 P999 之上设 lease；同时清楚**续期也救不了长时间停顿**，正确性仍由 CAS 兜底。

## 8. 面试 / 工作中常见问题

### 问题 1：Redis 分布式锁可靠吗？能当正确性保证用吗？

参考答案：不能当唯一保证。它至少会在四种情况下失效：lease 到期而业务未完（含 GC 停顿）、Redis 主从异步切换丢锁、进程被 kill 后锁悬空、集群模式下锁不互斥（同一 key 在不同分片）。工程定位是**降冲突、提效率**；数据正确性由数据库唯一约束、条件更新或状态机 CAS 兜底。Redlock 想解决多节点共识，但学界（Kleppmann 那篇著名批评）指出它仍受时钟跳变影响，所以生产上很少把它当强一致依据。

### 问题 2：多实例部署的定时任务怎么只跑一次？

参考答案：两个方向。① **加锁**：用 ShedLock 这类库（在 DB/Redis 上记一条带过期时间的执行记录），或自己写 `INSERT ... 唯一(任务名+批次号)` ——注意后者其实就是幂等表，天然防重复；② **分片**：把任务按 `instanceId % totalInstances` 拆成互不相交的数据切片（第 44 篇的多副本问题就是这个解法），调度中心（XXL-JOB 式）能直接给分片参数。锁保证"不重复"，分片保证"跑得快"，两者常一起用；实例数变化时还要考虑重平衡。

### 问题 3：热点商品库存怎么扛住并发扣减？

参考答案：先让单条 SQL 承担正确性（CAS 扣减），再解决"同一行的锁排队"：**分段库存**把一个 SKU 的库存拆成 N 行（或 N 个桶），请求按 hash 落段，段内不足时再借还；或把扣减前置到 Redis 用 Lua 原子预扣，DB 侧异步落账（第 45/46 篇）。代价是**可读性和一致性变差**——分桶后的余量要对账、预扣要和实际扣减对账，必须有兜底任务与监控，否则只是把超卖从"卖多"变成"卖少"。

## 9. 今日小结

- 正确性优先级：**唯一约束 / 条件更新（CAS）> 锁**；锁一定会失效（GC、超时、主从切换、进程被杀），迟到的旧持有者只有 **fencing token** 能挡住。
- `quantity = quantity - n WHERE quantity >= n` 一句抵得上"加锁 + 查询 + 计算 + 更新"四步，且对多副本天然安全。
- 幂等要做三态 + 结果复用：`SUCCESS` 返回首次结果，`PROCESSING` 给查询入口，`FAIL` 才允许重试。
- 热点行的终局是分桶或预扣，但必须先有对账兜底，否则只是换一种错法。
