# Java 学习：微服务边界与拆分

> 系列第 63 篇 · 第七阶段：分布式一致性与容错（收尾篇）
> 衔接上一篇「超时、重试与熔断」：这一阶段后半段处理的锁、消息、对账、超时、熔断，**全都是"服务被拆开之后"才存在的成本**。今天回到源头：为什么要拆、拆错了长什么样、怎么给已拆开的系统兜底。
> **与第 55 / 26 篇的分工**：第 55 篇讲**进程内**的包与依赖方向；第 26 篇讲接口的版本兼容。今天讲**进程之间**：拆分判据、数据归属、分布式单体的识别。

## 1. 今天学什么

微服务不是架构目标，而是**组织与规模的解法**：它买来独立部署、独立扩缩容、故障隔离、团队自治，代价是网络不可靠、事务变最终一致、跨进程调试、跨服务版本兼容。

四块内容：① **拆的判据**——独立扩缩容 / 独立团队 / 独立发布节奏 / 数据归属，至少一条真实成立才值得拆；② **怎么切**——按业务能力与数据归属，而不是按技术层次；③ **分布式单体的识别**——拆了一堆服务却每次一起发版、共享库表；④ **边界兜底**——防腐层、跨服务一致性阶梯、对账。

结论先行：**能用一个服务解决的问题，不要用两个。** 这六篇分布式技巧，都是"拆"的账单。

## 2. 前端工程师视角理解

你经历过同一道选择题：**monorepo 还是多仓库？** 多仓库换来独立发布与清晰依赖，代价是跨包改动要发多个版本、联调要 link 一堆包。后端拆服务是同一个权衡，只是把"跨包引用"换成"网络调用"、"版本不兼容"换成"老实例还在跑旧接口"。于是你会看到一个很熟的现象：**拆了 5 个 repo 但每次上线要同时发，那和 monorepo 相比只剩麻烦**——这就是分布式单体在前端的对应物。

第二个类比是微前端（Module Federation）。社区吵了很多年的结论是：**它主要解决的不是技术问题，而是组织问题**（多团队要不要共享发布节奏），技术复杂度（运行时隔离、依赖版本、通信）反而是代价。微服务同理——它最硬的前提是**有多个能独立负责的团队**。这条判据能让你在评审会上直接问一句："拆开之后，谁独立负责它？"

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 拆分收益 | 独立发布、依赖隔离 | 独立部署与扩缩容、故障隔离、团队自治 |
| 拆分代价 | 跨包改动、link 联调、版本漂移 | 网络不可靠、最终一致、跨进程调试、版本兼容 |
| 组织映射 | 微前端 ≈ 多团队共享发布节奏 | 康威定律：系统结构映射组织沟通结构 |
| 拆错形态 | 拆了 repo 但要一起发 | 分布式单体：一起发版、共享库表 |
| 边界表达 | package exports / 版本号 | API 契约、事件、独占数据库 |

**最需要建立的新观念：边界的第一载体是数据库，不是代码。** 前端拆包时边界体现在 `exports` 上；后端拆服务时，**只要两个服务还在读写同一张表，它们在业务上就是一个服务**——代码分开了，"边界"是假的。所以数据归属（谁写、谁读、谁能改）是拆分时唯一不能含糊的东西，比接口怎么设计重要得多。

## 4. 真实业务场景

**场景：拆了 6 个服务的"门店中台"，一次改价要发 4 次版。**

业务背景：两年前按"技术层次"拆——用户、商品、库存、订单、支付、报表六个服务。问题在业务演进中暴露：

- **一次"会员价"需求**要同时改用户（等级）、商品（价格）、订单（计价）、支付（实收），且必须**同一晚上按顺序发布**：先发商品（新字段）、再发订单（读新字段）、最后发支付；漏一个就出金额错误——直接违背了拆服务的第一收益（独立部署）；
- **共享库表**：库存与订单都直连 `store_stock`（为了"避免跨服务调用"），加个索引要协调两个团队；
- **同步调用成环**：订单 → 库存 → 商品 → 订单，任一节点抖动全站都慢（第 62 篇的放大在这里更容易发生）；
- **联调要起 6 个服务**，新人第一周全花在环境上。

根因不是"拆得不够细"，而是**边界切错**：按技术层次切，把同一个业务能力（定价）拆到四个服务里，变更必然跨服务。修复不是继续拆，而是按业务能力重画：定价（价格、等级、优惠）合成"计价"服务并独占价格数据；订单只持有订单数据，订阅价格变更事件（第 61 篇的 Outbox）；库存独占 `store_stock`；那个环改成"订单 →（事件）→ 计价 →（事件）→ 订单"的异步闭环。

**用错的代价**：拆错的微服务不会以"服务挂了"报警，它只是让**每次业务变更都更慢、更贵、更危险**，团队用加班消化它，直到某次发布顺序错了才看见账单。

## 5. Java 示例代码

**第一道防线：防腐层——只依赖对方的 api 包，并把对方模型翻译成本地模型。**

```java
/**
 * 防腐层（ACL）：对方模型 StockApiDTO 只允许出现在 api 包（可用第 55 篇的 ArchUnit 规则强制）。
 * 价值：对方改字段/换语义时只需改这一层转换，不会污染本地领域模型。
 */
@Component
@RequiredArgsConstructor
public class StockAcl {

    private final StockApiClient stockApiClient;   // 只认对方 api 包的契约

    public LocalStock toLocal(StockApiDTO dto) {
        if (dto == null || dto.getAvailable() == null) {
            return LocalStock.unknown(dto == null ? null : dto.getSkuId());   // 语义不明时显式建模
        }
        return new LocalStock(dto.getSkuId(), dto.getAvailable(), dto.getVersion());
    }
}
```

**第二道防线：跨服务一致性按代价阶梯选，别默认上分布式事务。**

```java
@Service
@RequiredArgsConstructor
public class PriceChangeService {

    private final PriceMapper priceMapper;         // 价格数据只属于本服务（独占库）
    private final OutboxMapper outboxMapper;       // 第 61 篇的本地消息表

    /**
     * 阶梯：① 单库单事务（能用就用）→ ② 同库多表事务 → ③ 跨服务最终一致（本地事务 + Outbox 事件，
     * 下游订阅并维护读模型）→ ④ 分布式事务（2PC/Saga）：协调者单点、锁持有时间长，只在极少数场景慎用。
     */
    @Transactional
    public void changePrice(PriceCmd cmd) {
        priceMapper.update(cmd);                                              // 本地事务：价格落库
        outboxMapper.insert(OutboxMsg.of("price-changed", cmd.skuId(), cmd));  // 同事务写事件
        // 订单/支付不再同步调用本服务取价，而是订阅 price-changed，各自更新读模型
    }
}
```

## 6. 常见坑

**坑 1：按技术层次拆服务。** 错误做法：拆成用户、商品、订单、报表服务——每个对应"一类数据"而非"一个业务能力"。问题：任何需求都横跨 3~5 个服务，变更成本随服务数上升，独立性收益归零。正确做法：**按业务能力与数据归属切**（定价、下单、履约、结算），一个能力一个主人，数据只有主人能写；分不开的先留在同一服务里，用第 55 篇的包结构在进程内约束。

**坑 2：共享数据库，却自称微服务。** 错误做法：几个服务连同一个库甚至同一张表，理由是"避免跨服务调用"。问题：表结构成为隐式契约（改列 = 全量破坏性变更，第 26 篇的问题在库层重演），DDL 要跨团队协调，服务间通过数据事实咬死——**分布式单体最典型的特征**。正确做法：**每个服务独占自己的库/表**，跨服务只走 API 或事件；共享数据用事件同步副本，接受最终一致 + 对账，而不是两边连同一张表。

**坑 3：拆错了就继续拆更细。** 错误做法：发现不独立就引入更多服务。问题：服务数增长会**线性放大**所有代价（网络、一致性、版本、联调），而根因通常是边界切错，不是粒度不够。正确做法：先**合并**——把共享数据的服务合回去，契约重画在业务能力上；只有当"独立扩缩容/团队/发布节奏/数据归属"至少一条真实成立，才重新拆。

## 8. 面试 / 工作中常见问题

### 问题 1：什么时候该拆服务？

参考答案：先问四个问题，至少一个明确为"是"才拆：**是否需要独立扩缩容**（报表服务吃内存不该拖累下单）、**是否有独立团队负责**（康威定律）、**是否要独立发布节奏**（一方一天十次、一方一周一次）、**数据归属是否清晰**（能否独占）。四个都答不上来，说明现在拆只是把复杂度提前付掉——用包结构与 ArchUnit 在进程内保持整洁，条件成熟再拆。

### 问题 2：跨服务的强一致场景怎么做？

参考答案：按代价阶梯逐档试：优先把数据放到同一个服务里用单库事务解决；确实跨服务时用"本地事务 + Outbox 事件 + 下游幂等 + 对账"（第 61 篇），牺牲实时性换可靠与简单；需要业务级回滚的用 Saga，每步配幂等与补偿；**2PC 尽量不用**（协调者单点、锁持有时间长）。判据是不一致窗口能否被业务接受、差异能否被对账发现和修复。

### 问题 3：怎么判断我们拆出的是微服务还是分布式单体？

参考答案：看四个信号：① 每次发版是否需要多个服务同时上线；② 是否有服务间共享库表或直连对方数据库；③ 服务间是否有同步调用成环；④ 联调是否必须起全量服务。命中两条以上基本就是分布式单体——处理方式是按业务能力与数据归属重画边界，必要时先合并回单体再重拆。

## 9. 今日小结

- 微服务是**组织与规模的解法**，不是架构目标；收益与代价都要摆在桌面上算。
- 拆前先问四个"是否独立"（扩缩容、团队、发布节奏、数据归属），一个都不成立就先别拆。
- **边界的第一载体是数据库**：共享库表的服务在业务上就是同一个服务。
- 按**业务能力与数据归属**切，不按技术层次；切错了先合并重画，而不是继续拆细。
- 兜底三件套：api 包 + 防腐层、Outbox + 事件 + 对账、契约与灰度。
