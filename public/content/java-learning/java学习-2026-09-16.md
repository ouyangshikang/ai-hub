# Java 学习：代码可维护性

> 系列第 56 篇 · 第六阶段：工程化
> 衔接上一篇「代码分层规范」：昨天锁住的是"**谁能动谁**"，今天管的是另一半——**接手的人看不看得懂**。ArchUnit 能测出 `api` 包引用了 `entity`，却测不出一个 500 行的 `calc()`。
> **连续剧提示**：场景还是券模块，第 54、55 篇的券核销与券模块腐化是同一件事的三个层面——SQL、结构、代码。

## 1. 今天学什么

代码可维护性只有一个判据：**改这段代码的人，需不需要问原作者、或者翻 git 记录才敢下手。** 需要，就说明代码只在"能被执行"，没在"能被理解"。

今天讲四件事：① 怎么量化"读不懂"——圈复杂度、认知复杂度、方法长度这些指标各自说明什么、阈值定在哪合理；② 长方法怎么安全拆开（卫语句、抽取方法、参数对象、把 `if` 链换成策略）；③ 注释该写什么——为什么这样写，而不是复述代码在干什么；④ 重构怎么做才不出事：**一次提交只改一件事**，纯重构与行为变更必须分开。

它排在分层规范之后很自然：结构对了，还要每个方法自己也对得起下一个读它的人。

## 2. 前端工程师视角理解

你早就有这套判断力，只是词汇不同。一个 500 行、塞了 6 个 `useEffect` 的 React 组件，你知道该拆——判据不是行数，而是"**你能不能用一句话说清这个组件做什么**"。说不清，就是它的名字和边界都错了。后端长方法完全同理：一个方法里同时在校验参数、算折扣、发 MQ、写日志，它其实不是一个方法，是四个模块挤在了一起。

第二个直觉来自 **ESLint 的 `complexity` 和 `max-lines-per-function`**。它们会把"分支太多"变成 lint 报错——这就是后端 PMD / Checkstyle 的 `CyclomaticComplexity` 在做的事，只是后端更常放在 SonarQube 的**认知复杂度**（Cognitive Complexity）里看：它不只数分支，还对嵌套深度加罚，所以 `if` 里再套三层 `try` 的写法分特别难看。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 复杂度指标 | ESLint `complexity`、`max-lines-per-function` | PMD / Checkstyle `CyclomaticComplexity`、Sonar 认知复杂度 |
| 分支消解 | 判别联合 + `switch` 穷尽（漏分支编译报错） | 枚举 + 策略 `Map`（漏配运行期才报）或 `switch` 表达式（漏枚举值编译期就报错） |
| 长参数 | 对象字面量（天然随意） | 参数 > 3 个就该收 `record` 参数对象 |
| 注释 | JSDoc 面向公共 API | JavaDoc 面向公共 API；方法内注释只写"为什么" |
| 重构安全网 | 类型 + 测试 + 快照 | 类型 + 测试 + 编译器（改签名会炸一片调用点） |

**Java 在两点上更容易变坏，也更容易被救。** 更容易变坏：`Optional`、受检异常和 getter/setter 模板代码会让一个方法天然变长，而且 `if (type == 1) ... else if (type == 2)` 这类链可以无限长、漏掉任何分支都不报错——**普通的 `if` 链上，编译器不会提醒你**。唯一例外是 `switch` 表达式：它要求对枚举穷尽，新增枚举值忘了处理会编译失败，这才是 TS 判别联合的对应物。更容易被救：Java 的重命名是跨全工程改引用（前端 re-export 满天飞时反而不敢改），拆方法、提取参数对象由 IDE 代劳，改签名会立刻在所有调用点报错。所以后端的实践顺序是：**先用 IDE 做机械重构，再用测试确认行为没变**——工具链给了底气，但"行为没变"这件事仍然只有测试能证明（第 53 篇的判据在这儿复用）。

## 4. 真实业务场景

**场景：券价格计算 500 行，一次"企业券不叠加满减"改成了全员折扣。**

业务背景：`CouponPriceService.calc()` 是三年前一次大促前赶出来的，签名是 `calc(List<OrderItem>, int, String, long, boolean, int, Map)`，方法体 500 行、最深嵌套 5 层，里面有 `0.85`、`3000`、`type == 4` 这样的裸值，注释只有一行"// 特殊处理"。第 55 篇说"改一个规则要动 7 处"，那 7 处里最难的就是这个方法。

新需求是"**企业专享券不参与满减**"。改动的人看不出 `type == 4` 就是企业券（这个映射只存在于原作者脑子里），于是他在"会员折扣"那段加了判断——结果所有会员的满减都没了。测试也没覆盖"企业券 + 满减同时命中"这条组合（第 53 篇讲过的组合爆炸），线上跑了 6 小时才发现，期间产生 2000 多单错误折扣，只能整批退款。

重构分四步走，**第一步不加任何功能**：把 500 行拆成 6 个私有方法（名字就是原来注释里该说的话）、裸值换成命名常量、`type == 4` 换成 `CouponType.CORPORATE`；跑一遍已有的参数化测试确认全绿。第二步才把 `if` 链换成策略表。第三步给新需求加一个测试 case，改完策略的分支。**四步分三个提交**，第二个提交 diff 里一行行为都没变，评审也只需回答一个问题："这真的只是搬家吗？"

**用错的代价**：可读性债务不像慢 SQL 会立刻报警——它以"每次改动多花两小时、每次事故多一个误判"的方式持续收利息，而且没人能为它负责。

```java
/** 参数超过 3 个就打包：签名自解释，调用点也能用命名赋值（JDK 16+） */
public record CalcContext(List<OrderItem> items, MemberLevel level,
                          CouponType type, DeliveryType delivery) {}

/** 策略接口：新增券型 = 新增实现类，不改这段链 —— 结构上杜绝"改一处错全处" */
public interface CouponStrategy {
    BigDecimal apply(BigDecimal base, CalcContext ctx);
}
```

```java

    private static final BigDecimal STAFF_DISCOUNT = new BigDecimal("0.85");   // 企业员工 85 折
```

## 6. 常见坑

**坑 1：重构和业务改动混在同一个提交。** 错误做法：一个 PR 里既拆了 500 行方法，又改了折扣规则。问题：评审者无法判断"红了是搬家搬坏了还是规则改错了"，回滚会连带撤掉功能；这也是事故最常见的入口。正确做法：**先提一个纯重构的提交**（diff 里不许有任何行为变化，靠已有测试证明等价），再提功能提交。评审者只需回答一个问题："这次真的只是搬家吗？"

**坑 2：为消除重复而过早抽象。** 错误做法：看到三处相似 `if` 就抽一个 `boolean check(x, flag1, flag2, mode)`，参数越加越多，最后没人敢调。问题：三处相似常常只是**现在**长得像，语义完全不同（第 55 篇说的隐式耦合），错误的通用抽象会把两种业务焊死在一起，比重复更难拆。正确做法：**先让重复暴露出差异**，确认它们真的同源再抽象；参数里出现三个以上布尔开关，就是抽象走错方向的信号。

**坑 3：用注释补偿差命名。** 错误做法：字段叫 `flag`、方法叫 `handleData()`，后面补一句 `// 表示是否为企业券且未叠加满减`。问题：注释会和代码漂移（没人改注释），而真正需要读的人得同时相信两份信息；魔法值也一样，`if (channel != 3)` 的正确修复是 `DeliveryType.THIRD_PARTY`，不是在其上方加一行注释。正确做法：**先改名、再删注释**；只有"为什么这样决定"（业务口径、历史兼容、性能权衡）才写进注释；公共 API 的职责与约束用 JavaDoc 写，方法体内不逐行复述代码。

## 7. 和之前知识的连接

- **第 55 篇「代码分层规范」**：那篇的 ArchUnit 守的是包与包的边界，今天守的是方法内部；两者都是"能被机器检查的规范"，只是检查器不同（ArchUnit 看依赖，PMD/Sonar 看复杂度）。
- **第 53 篇「单元测试」**：那篇说单测的产出是**重构安全网**——今天四步重构里"确认行为没变"这一步，靠的就是它；没有测试的重构不叫重构，叫第二次开发。
- **第 35 篇「参数边界」**：卫语句（先挡非法输入再写主干逻辑）是那篇入口校验在方法内部的延续，也是把 5 层嵌套压平最直接的手法。

## 8. 面试 / 工作中常见问题

### 问题 1：你怎么判断一段代码该重构了？

参考答案：不看行数，看三个信号：改它时要不要问原作者；同一个概念在项目里有几种叫法（`storeId` / `shopId` 混用）；加一个需求要同时改 5 个 `if`。指标上做辅助——单方法认知复杂度持续偏高、一个类同时负责校验和计算和发送。最硬的信号其实是**改动成本在上升**：同样的小需求，上个月一小时、这个月一天。

### 问题 2：圈复杂度和认知复杂度有什么区别，阈值怎么定？

参考答案：圈复杂度数的是独立路径数（分支、循环、`&&` 都算），只看结构；认知复杂度在此基础上**给嵌套和控制流跳跃加罚**，更贴近"人读起来的吃力程度"。阈值不要一刀切：常见做法是给新方法设上限、对存量代码设"只降不升"的基线，核心计费/风控包从严，DTO 转换与测试代码放宽。指标是用来发现趋势的，一旦当成 KPI 压给个人，人会立刻学会把方法拆成 5 个都叫 `step1..step5`。

### 问题 3：一长串 `if/else` 的券规则，你会怎么改？

参考答案：先问这些分支是不是**同一件事的不同取值**——是的话用枚举 + 策略表（`Map<CouponType, CouponStrategy>`）替掉，新增类型加实现类而不是改链；只是浅层的参数校验就用卫语句拍平嵌套，不必上设计模式；如果已经用 TS 风格的可辨识联合写过 Java 版，可以用 `switch` 表达式配合枚举穷尽，让编译器帮忙提示漏分支。别一上来就套模式：分支只有两处且稳定，`if` 比五个类更好读。

## 9. 今日小结

- 判据只有一条：**接手的人不问原作者能不能安全改**——能读懂，才改得动。
- 长方法不是"太长"的问题，是"一个方法承担了多个职责"的问题：先按职责拆，再按行数看。
- 魔法值、布尔长参数、三处相似都不该用注释或提前抽象来糊：正确解依次是**命名类型 / `record` 参数对象 / 先让差异暴露再合并**。
- 重构与行为变更必须分两次提交，靠测试证明第一次没改行为——这是第 53 篇安全网最典型的用法。
