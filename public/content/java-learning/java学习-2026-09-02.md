# Java 学习：缓存基础

> 系列第 45 篇 · 第五阶段：事务与架构进阶
> 衔接上一篇「定时任务」：昨天用"每分钟同步一次库存"换准实时，本质是**定时轮询**——没人访问也在跑，一跑就扫全表。今天换思路：这些数据能不能"查一次、用很久"。缓存的语法只有几个注解，真正的难度全在决策。

## 1. 今天学什么

缓存就是把"又慢又贵的查询结果"存在"又快又便宜的地方"复用。Java 后端两个常见位置：**进程内**（Caffeine，纳秒级）和**进程外**（Redis，毫秒级但要走网络）。今天讲四件事：① 本地缓存和分布式缓存怎么选；② 失效策略——TTL 被动过期 vs 主动删除，以及"先更新库还是先删缓存"；③ 三个高频故障：**穿透**（查不存在的 key）、**击穿**（热点 key 到期瞬间被打穿）、**雪崩**（一批 key 同时到期）；④ 什么数据绝对不能缓存。Spring 的 `@Cacheable` 把这一切声明化了，但**它只是语法糖，决策错了注解救不了你**。

## 2. 前端工程师视角理解

这件事你其实做得比谁都熟，只是换个名字。

**React Query 的 `staleTime` + `gcTime` 就是 TTL + 缓存淘汰；`invalidateQueries` 就是"主动删缓存"。** 你为了"进详情页别重复请求"配 `staleTime: 5 * 60_000`，和后端给门店信息配 5 分钟 TTL，是**完全同一个决策**：这份数据五分钟内不新鲜，业务上能接受吗？

**CDN 缓存接口返回 = 服务端缓存查询结果。** 你在 CDN 上配过 `max-age`，然后被"源站改了、边缘还发旧的"坑过一次——后端缓存一模一样：DB 改了，缓存还是旧值。CDN 的解法是刷新的同时改版本号，后端的解法是**更新库之后删缓存**，让下一次读自然回填。

**但有两个决定性差异。** 一是**影响半径**：前端缓存错了只是一个用户看到旧数据，刷新就好；后端缓存是**所有用户共享的一份**，价格缓存错了就是全站错价、真金白银的资损。二是**归属**：前端缓存在用户设备上，你已经管不到它了；后端缓存在自己的进程或 Redis 集群里，过期策略、驱逐策略、内存上限全要自己设计并负责。

## 3. 和 JavaScript / TypeScript 的对比

**手搓 vs 内置。** JS 里做 LRU 要引 `lru-cache` 或自己写；Caffeine 是 Java 生态的事实标准，`maximumSize` / `expireAfterWrite` / 命中率统计全部内置。差异来源是：后端缓存是**基础设施**，必须可观测——运维要能说出"命中率 92%、逐出 3 万条"，前端的缓存没人考核。

**过期语义不一样。** `setTimeout` 到点一定触发；Caffeine 是**惰性过期**——读的时候才发现过期并丢弃，所以"设了 1 分钟 TTL"不等于"1 分钟后内存就释放"。高 QPS 下无妨，低峰期可能留一批僵尸 entry。

**命中缓存要反序列化。** Redis 存的是字节，取回来必须解码：Java 里泛型集合常取回变成 `List<LinkedHashMap>` 强转失败，这和你在前端 `JSON.parse` 丢方法、`Date` 变字符串是同一类问题。工程做法也一样——**缓存值用明确结构（JSON 字符串 + 显式类型），别把内存对象直接扔进去**。

**声明式有代理陷阱，null 语义要自己约定。** `@Cacheable` 由 AOP（第 42 篇）织入，同类内部自调用同样不生效，和第 40 篇事务失效是**同一个根因**。另外 JS 的 `undefined` 与 Java 的 `null` 都分不清"没查过"还是"查过且为空"，所以空值必须显式设计：真存 null，还是用 `EMPTY` 哨兵。

## 4. 真实业务场景

**场景：小程序门店详情页——门店信息、商品价格、运营报表三级数据。**

业务背景：详情页一次渲染要拿门店基础信息、在售商品及价格、可用券；区域经理的后台还要看按天的门店销售报表。大促期间详情页 QPS 是平时的 20 倍，DB 直接扛不住。

按数据分级：

| 数据 | 读写特征 | 缓存决策 |
|---|---|---|
| 门店基础信息（名称、地址、营业时间） | 低频改、高频读 | 缓存 10 分钟，后台改完主动删 |
| 商品列表 | 中频读、单次查询重 | 缓存 5 分钟，可按 TTL 自然过期 |
| 商品价格 | 改价由运营发起，错了是资损 | 极短 TTL 或不缓存，下单前必须回源 |
| 门店销售报表 | 一次查询 8 秒、结果按天固定 | 按 `(区域, 门店, 日期)` 缓存 30 分钟 |
| **库存** | 决定能否下单 | **绝不缓存**，见下 |

**用错的代价：** 报表缓存 30 分钟，只要页面写清"数据延迟 30 分钟"就能接受；价格缓存 30 分钟，运营改价后半小时内用户全按旧价下单，这些订单会在第 44 篇的凌晨对账里集体暴露成差异单。**库存**最特殊——它要求绝对正确，缓存里"有货"而 DB 已扣完就是超卖，用户到店取不到商品。这条边界必须记住：**缓存只能承载"可容忍短暂陈旧"的数据，正确性要求高的必须回源。**

## 5. Java 示例代码

声明式版本——适合"规则统一、不值得手写"的读：

```java
@EnableCaching          // 启动类上开启，和 @EnableScheduling 一样容易漏
```

```java
@Service
@Slf4j
public class StoreInfoServiceImpl {

    @Resource private StoreInfoMapper storeInfoMapper;

    /**
     * key 只放 storeId，别把整个查询对象当 key（会带上不可控字段，命中率归零）。
     * sync = true：未命中时只放一个线程去查库回填，其余等待 —— 这就是防「击穿」。
     */
    @Cacheable(cacheNames = "store:info", key = "#storeId", sync = true)
    public StoreInfoVO getStoreInfo(Long storeId) {
        return storeInfoMapper.selectByStoreId(storeId);
    }

    /** 改完库之后删缓存：@CacheEvict 保证删的动作和写逻辑绑在一起，不会漏写 */
    @CacheEvict(cacheNames = "store:info", key = "#storeId")
    public void updateStoreInfo(Long storeId, StoreInfoUpdateReq req) {
        storeInfoMapper.update(storeId, toEntity(req));
    }
}
```

手写 Cache-Aside 版本——需要精细控制 TTL、空值和大 key 时用：

```java
public StoreProductVO getProduct(Long storeId, Long spuId) {
    String key = "product:" + storeId + ":" + spuId;
    StoreProductVO cached = redis.opsForValue().get(key);
    if (cached != null) return cached;                      // 命中，不打 DB

    StoreProduct product = productMapper.selectByStoreAndSpu(storeId, spuId);
    if (product == null) {
        // ★ 防穿透：不存在的商品也缓存一个空哨兵，但只给 60s，避免脏数据长期占位
        redis.opsForValue().set(key, StoreProductVO.EMPTY, Duration.ofSeconds(60));
        return null;
    }
    StoreProductVO vo = toVO(product);
    // ★ 防雪崩：基础 30 分钟 + 随机 0~5 分钟，避免同批 key 同一秒集体失效
    redis.opsForValue().set(key, vo,
            Duration.ofMinutes(30).plusMinutes(ThreadLocalRandom.current().nextInt(5)));
    return vo;
}
```

## 6. 常见坑

**坑 1：更新缓存而不是删除缓存。** 错误做法：改价后把新价格 `set` 进缓存。问题：A、B 并发改价时，读→改→写的先后无法保证，慢的那个会用旧值覆盖新值，而且**在 TTL 到期前没有任何机制能纠正**。正确做法：**更新库 + 删缓存**，让下一次读自然回填；一致性要求更高时再加"延迟双删"或用 binlog 订阅异步失效。

**坑 2：缓存 key 设计不当，命中率低到个位数。** 错误写法：`key = "#req"` 把整个请求对象当 key（里面带着时间戳、页码、操作人 ID）。问题：任何一个易变字段都会让 key 分裂，缓存等于没加。正确做法：key 只放**真正决定结果**的维度，并显式命名带业务前缀（`store:info:1024`），便于在 Redis 里按前缀排查和清理。

**坑 3：本地缓存在多实例下必然不一致。** 现象：运营改了门店公告，部分用户看到新内容、部分一直看到旧的，刷新也没用。问题：Caffeine 是**每个实例一份**，删缓存的请求只落到一个实例（第 44 篇多副本问题的缓存版）。正确做法：要跨实例一致就换 Redis；想保留本地缓存的速度，就用"Redis 主 + 本地二级 + 发布订阅广播失效"，或把本地 TTL 压到秒级、明确接受短暂陈旧。

**坑 4：大 key。** 现象：某次请求偶发 3 秒超时，Redis 监控出现网络尖刺。问题：把"全部门店列表"塞进一个 key，序列化后几 MB——读它占满网卡、拖慢主从同步，删它阻塞 Redis 主线程（单线程）。正确做法：列表按页或按维度拆 key，集合类用 hash 分字段，单个 value 控制在 KB 级。

**坑 5：把缓存当存储用。** 现象：Redis 重启或被逐出后数据消失。问题：`maxmemory-policy` 为 `allkeys-lru` 时内存写满会逐出任一 key，定时任务的中间结果、幂等记录、券库存都可能被顺手清掉。正确做法：**丢了能重查的才配进缓存**；幂等表（第 25 篇）这类丢了就无法恢复的状态留在 DB。

## 7. 和之前知识的连接

- **第 44 篇「定时任务」**：轮询和缓存是"减少重复开销"的两条路——轮询主动拉、缓存被动等；昨天的"4 个实例都跑一遍"，今天变成"4 个实例各有一份本地缓存"，**多副本这个变量在每一层都会重演**。
- **第 16 篇「数据库查询性能基础」+ 第 19 篇「N+1」**：那两篇让查询变快，缓存把查询**彻底省掉**。顺序不能反——先优化 SQL 和索引，再上缓存，否则缓存只是在掩盖慢查询。
- **第 10 篇「DTO / VO / Entity」**：缓存里存 Entity 还是 VO 是真问题——VO 一改字段，旧缓存反序列化就出错，所以通常缓存**贴近存储层的结构**，返回前再组装 VO。
- **第 42 篇「AOP」+ 第 40 篇「事务失效」**：`@Cacheable` 与 `@Transactional` 是同一套代理机制，失效场景完全复用。

## 8. 面试 / 工作中常见问题

### 问题 1：更新数据时，是删缓存还是改缓存？先删还是先更新库？

参考答案：**改库 + 删缓存**，不是改缓存。理由：并发写会互相覆盖，删除让下一次读自然回源、天然收敛；且缓存值常是多查询拼出来的，改一次重算一次不划算。顺序上"先更新库、再删缓存"优于反向，反向会留下"缓存已删、库未改，另一个读把旧值填回去"的窗口。删失败要兜底——重试队列或靠 TTL 过期，所以 TTL **绝不能设成无限期**。

### 问题 2：缓存穿透、击穿、雪崩分别怎么解决？

参考答案：三个词对应三种失效。**穿透**＝查根本不存在的数据，缓存永不命中、每次都打 DB → 空值缓存（短 TTL）或布隆过滤器提前挡掉。**击穿**＝热点 key 到期瞬间大量并发同时回源 → `sync = true` / 互斥锁让单线程回填其余等待，或改逻辑过期、由后台异步刷新。**雪崩**＝大批 key 同一时刻集体过期 → TTL 加随机抖动，架构上再做多级缓存与 Redis 高可用。

### 问题 3：本地缓存和 Redis 怎么选？能不能一起用？

参考答案：看两点——**要不要跨实例一致**、**能不能接受序列化与网络开销**。单实例、量小、纯计算结果用 Caffeine；多实例共享、数据量超过单机内存用 Redis。生产上更常见**两级**：Caffeine 挡热点（秒级）、Redis 做共享层（分钟级）、DB 兜底。代价是不一致窗口变长，所以价格、库存要么不走本地缓存，要么把本地 TTL 压到极短。

## 9. 今日小结

- 缓存两个位置：**Caffeine 在进程内、每个实例一份；Redis 在进程外、全实例共享**——选型第一个变量永远是"多副本"。
- 写路径一句话：**改库 + 删缓存**，不是改库 + 改缓存；删能避开并发覆盖，但保证不了顺序，所以 TTL 是最后的兜底。
- 三个故障按成因记：**穿透=查不存在（空值 / 布隆）、击穿=热点到期（互斥 / 逻辑过期）、雪崩=批量到期（TTL 加随机）**。
- 缓存只承载"**可容忍短暂陈旧**"的数据：报表可以，价格谨慎，库存绝对不行。
- `@Cacheable` 只是 AOP 的语法糖，同类自调用照样失效——注解写对了，不等于策略想对了。
