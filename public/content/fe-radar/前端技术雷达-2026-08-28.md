## 2. 本周值得关注的 6 个变化

### 变化 1：Next.js 8/25 安全发布落地——2 个 Critical RCE（AVIF 图片优化 + Windows），补丁 16.3.3 / 15.5.24

* 分类：框架生态 / 安全
* 雷达评级：**采用**（立即打补丁并验收）
* 来源：[August 2026 Security Release（2026-08-25，官方）](https://nextjs.org/blog/august-2026-security-release) | [Update: August Next.js Security Release（提前到 8/25，官方）](https://nextjs.org/blog/nextjs-security-release-august-2026-update) | [GHSA-2xp9-vwfh-vxw4（AVIF）](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4) | [CVE-2026-75604 / GHSA-p293-qw3h-jr36（Windows）](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36)
* 发生了什么：上期预告的"8/26 一个 Critical"在 8/25 落地时升级为**两个 Critical**，官方为此把发布日提前了一天。两项均为**未授权远程代码执行（Unauthenticated RCE）**：（1）**Image Optimization API 处理攻击者构造的 AVIF 图片时的 RCE**，根因在 `sharp` 依赖的底层 `libheif` 库（GHSA-2xp9-vwfh-vxw4，另关联 libheif 侧 GHSA-g89c-p67h-r497）——补丁的做法是**在修复传播到上游前直接禁用 AVIF 优化**；（2）**Windows 承载服务器上的 RCE**（CVE-2026-75604），触发条件是应用同时使用 Pages Router 与 App Router 且未启用 Cache Components、且 Next.js 服务跑在 Windows 文件系统上，**Linux 与 macOS 不受影响，且受影响应用无规避方案**。补丁版本为 **v16.3.3（Active LTS）** 与 **v15.5.24（Maintenance LTS）**。
* 为什么值得关注：这是连续第二周由上期雷达预告、本周真正落地的 Next.js 安全事件，而且量级从"1 Critical"跳到"2 Critical"、还都是 RCE（比 7 月那批 HIGH 更高）——严重度直接命中了上期"预留窗口、当天响应"的假设。值得注意的是官方对 AVIF 选择"先禁用、后随上游修复"这一保守策略：说明根因不在 Next.js 自身、短期无法彻底根治，团队要预判"升级到 16.3.3 后 AVIF 优化会失效"这一行为变化。
* 对前端工程师的影响：所有 Next.js App Router 项目都是潜在暴露面。凡走 `next/image` 优化 AVIF 的项目，升级后 AVIF 会退回原图/其他格式（性能与体积可能变化，需回归）；**Windows 上自托管 Next.js 且混用 Pages + App Router 的项目是本批次最高危人群**，且不能靠配置规避，只能升级。
* 对现有项目的影响：高。具体取决于是否用 AVIF 优化、是否 Windows 承载。
* 建议动作：**本周核心动作是验收——确认上期设想的升级真的发生**：`pnpm ls next --recursive` 核对每个项目已到 16.3.3 / 15.5.24；对用 AVIF 的项目做一次图片显示与 LCP 回归；盘点是否有 Windows 自托管实例，有则视为最高优先级、不留到下个迭代。

### 变化 2：pnpm 12.0 正式版发布——Rust 重写的包管理器转正（8/26）

* 分类：工程化与团队实践 / 构建工具
* 雷达评级：**试点**（预演不切换；延续上期"等正式版 + 2 周验证"的判断）
* 来源：[pnpm 12.0 官方发布（2026-08-26）](https://pnpm.io/blog/releases/12.0) | [What's different in pnpm 12](https://pnpm.io/blog/whats-different-in-pnpm-12) | [pnpm/pnpm Releases（v12.0.0，8/26）](https://github.com/pnpm/pnpm/releases)
* 发生了什么：pnpm 于 8/26 宣布 **v12.0.0 正式版**，官方定性"**pnpm 12 is stable. It is a rewrite of pnpm in Rust**"。关键设计是"**deliberately not a migration**"——11 的命令、flag、设置与 **lockfile 格式全部沿用**，`--frozen-lockfile` 原样消费旧锁文件，官方称安装**快 2–3 倍、内存省约 25%、锁文件显著更小**，且重排 importer/依赖、重复安装都产出**字节一致的确定性锁文件**。官方列出 **5 处行为差异**：Git 依赖按仓库规范 HTTPS 地址归一识别、`pnpm-workspace.yaml` 中未识别设置会显式报错（`ERR_PNPM_UNRECOGNIZED_WORKSPACE_SETTINGS`）、循环依赖的 peer 解析被归一化、Linux 导入 `auto` 先试硬链接、`engineStrict` 跟随"边"而非"子树"（经普通 `dependencies` 边触达不兼容包时安装直接失败）。另有值得留意的新能力：**pnpm 现在能替你安装/管理 npm、Yarn、Bun 等其他包管理器**、全局 bin 跟随项目锁定的运行时、远程拒绝在 `sudo` 下运行全局命令。**重要提醒：npm 上的 `latest` 仍指向 pnpm 11 线，12 需 `pnpm self-update next-12` 显式安装。**
* 为什么值得关注：这是上期把 pnpm 12 列为"观察、等正式版 + 2 周社区验证"后的兑现——正式版 8/26 才落地，本周恰好是"2 周验证窗口"的起点，而不是"该切换"的信号。但从趋势看它是标志性一步：继 Rolldown、Oxc、Bun 1.4 之后，**连包管理器都完成了 Rust 化并转正**，"基础设施层全面 Rust 化"从上期的"判断"变成"事实"。pnpm 主动把 `latest` 留在 11、要求 `next-12` 显式安装，本身就是官方给出的"先别急着上生产"的谨慎信号，值得团队照做。
* 对前端工程师的影响：本地/实验环境可用 `pnpm self-update next-12` 尝鲜；`engineStrict` 行为和 `workspace.yaml` 未识别设置报错这两条差异，可能在迁移时第一次让 CI 变红，需要提前知道。
* 对现有项目的影响：低（前提是保持 11 线不动）。11.x 本周也有 v11.24.0（8/24）维护版继续跟进安全与修复，留在 11 是安全的。
* 建议动作：在**一个实验分支**里 `pnpm self-update next-12 && pnpm install --frozen-lockfile` 做一次预演，重点观察三点：确定性锁文件是否改变你的 diff 噪音、`engineStrict`/未识别设置两条差异会不会让你现有 CI 报错、锁文件是否被重写。**主 CI 与生产仍留在 11.24。**

### 变化 3：Chrome 152 全量 Stable + 153 提前通道 + 一批 LTS 吞下 28 个 CVE

* 分类：浏览器 / Web 平台 / 安全
* 雷达评级：**采用**（受管环境跟进）/ **观察**（153 新特性）
* 来源：[Chrome Releases Blog · 2026-08](https://chromereleases.googleblog.com/2026/08/)
* 发生了什么：本周是 Chrome 多通道密集推进的一周。桌面 **Stable 于 8/25 推进到 152.0.7977.64/.65**（即上期的 Early Stable 特性正式全量），Android 于 8/26 跟进 152.0.7977.64；**153 于 8/26 进入 Early Stable/Beta（153.0.8010.12）**、**154 于 8/27 上 Dev（154.0.8025.0）**。真正值得工程侧单独确认的是 **8/27 的 LTS 通道一次性发布了 28 个安全修复**，绝大多数为 High（含 CORS 实现不当 CVE-2026-76033、Media/WebGL/FileSystem/Extensions/HTML/UI 等多处 use-after-free、V8/Network 缓冲区溢出等）。这些修复面向**长期支持/受管与合规部署**，不随个人 Chrome 自动更新路径覆盖同一批版本。
* 为什么值得关注：152 全量意味着上期列的那批能力（媒体状态伪类 `:playing/:paused`、CSS `alpha()` 相对颜色、CPU Performance API、`::backdrop` 可编程等）现在从"可提前验证"转为"生产可用"。而单批 28 个 CVE 延续了上周 8/20 Chrome 151 紧急安全更新的节奏——**浏览器补丁已进入"一周多版、Critical/High 常态化"**，风险不在功能而在"受管环境有没有真的拿到这些版本"。
* 对前端工程师的影响：日常开发无代码影响；有自定义音视频播放器的项目可正式采用媒体状态伪类，动效密集页面可用 CPU Performance API 做设备分级降级。CI 中固定版本浏览器（Playwright/Puppeteer channel）需按节奏更新。
* 对现有项目的影响：低——152 均为渐进增强，无破坏性变化；影响点在运行环境而非项目代码。
* 建议动作：企业受管 / EDR / 锁定版本的测试环境确认更新到 152 stable 与最新 LTS；把 152 的媒体状态伪类、CPU Performance API 从"上期观察"转为"可试点"。

* 分类：框架生态
* 雷达评级：**采用**（3.5.42 常规升级）/ **观察**（3.6）

### 变化 5：create-vite@9.2.0（8/24）新增对 Nub 包管理器支持——"反 Bun"式 Rust 工具链开始渗透脚手架

* 分类：构建工具 / 工程化
* 雷达评级：**观察**
* 来源：[vitejs/vite Releases（create-vite@9.2.0，8/24）](https://github.com/vitejs/vite/releases) | [Introducing Nub（nubjs.com 官方博客）](https://nubjs.com/blog/introducing-nub) | [Show HN: Nub – A Bun-like all-in-one toolkit for Node.js](https://news.ycombinator.com/item?id=48660267)
* 发生了什么：**本周真正的新信号是 create-vite@9.2.0（8/24）在 changelog 里"add nub package manager support"**——即官方脚手架现在能识别/选用 Nub。需要澄清时间线：**Nub 本体并非本周发布**，其 Hacker News "Show HN" 帖约在 63 天前（≈ 6 月底）就已出现，因此它不算"本周新动态"，此处仅收录"被 Vite 脚手架集成"这一本周事件。就 Nub 本身：它是**一个 Rust 编写的单文件 CLI / 一体化 Node.js 工具链**（TypeScript 免构建直跑、脚本 runner、bin runner、watch、Node 版本管理、完整包管理器），**关键差异是"没有 Nub 运行时、就用真实 Node"**——走的是"增强 Node"而非"替代 Node"路线；其引擎由 **jdx（mise 的作者）** 打造。对比 Bun 的"整体替换运行时"，社区把它读作"the anti-Bun"。
* 为什么值得关注：单独看这是一次很小的脚手架维护改动，但它透露两件事：一是**工具链层的"一体化 Rust 工具"赛道正在拥挤**（Bun、Rolldown、Oxc、Nub），二是"增强 Node 而非重造运行时"这条路线拿到了 mise 作者这样有口碑的维护者背书，且被 Vite 官方脚手架接纳——**兼容性风险更低**的那条路可能才是团队更该关注的方向。
* 对前端工程师的影响：本周无任何必须动作；新脚手架项目初始化时你可能第一次看到 Nub 这个选项。
* 对现有项目的影响：无——纯 opt-in，且尚未在真实生产项目验证。
* 建议动作：列入技术观察清单。若要做工具链选型调研，把 Nub 作为"增强 Node"路线的代表与 Bun 的"替换运行时"路线做一次对照测试（安装速度、TS 直跑、脚本并行），但不进任何现有项目。

## 4. 可以引入团队的实践

### 实践 1：在实验分支做一次 pnpm 12 迁移预演（非破坏性）

* 适合场景：所有 pnpm 11.x 项目，尤其 monorepo 与 CI 安装偏慢的仓库
* 引入成本：低
* 预期收益：提前量化 pnpm 12 声称的 2–3 倍安装提速与更小的确定性锁文件，暴露 `engineStrict`、workspace 未识别设置这两条差异对现有流水线的影响，为"2 周验证窗口"结束后的正式切换决策积累数据
* 建议试点方式：单独开一个分支，`pnpm self-update next-12 && pnpm install --frozen-lockfile`，记录：耗时对比、锁文件是否被重写、`git diff pnpm-lock.yaml` 噪音、CI 是否变红。**主 CI 与生产全程留在 11.24，验证通过前不合并。**

* 引入成本：低

## 6. 本周可以落地的小动作

### 小动作：给上周的 Next.js Critical 收尾验收 + 顺手开一个 pnpm 12 预演分支

* 目标：用 15–20 分钟，先闭环本周最高危的安全项（确认 Next.js 补丁真的装上了），再低成本为下周期的 pnpm 12 切换攒一份数据。
* 操作步骤：

  1. **验收 Next.js 补丁**（约 8 分钟）：

     ```bash
     pnpm ls next --recursive
     ```

     核对每个项目是否 ≥ 16.3.3（16.x 线）/ ≥ 15.5.24（15.5 线）。凡是 Windows 自托管、或用了 `next/image` 优化 AVIF 的项目单独标记——前者最高优先，后者升级后要做一次图片显示与 LCP 回归（补丁禁用了 AVIF 优化）。没升的当场 `pnpm add next@16.3.3` / `next@15.5.24` 补上。

  2. **开 pnpm 12 预演分支**（约 10 分钟）：

     ```bash
     git switch -c spike/pnpm12-preview
     pnpm self-update next-12
     pnpm install --frozen-lockfile
     git diff pnpm-lock.yaml | head
     ```

     只看三件事：安装耗时对比、锁文件是否被重写（diff 噪音）、有没有触发 `ERR_PNPM_UNRECOGNIZED_WORKSPACE_SETTINGS` 或 `engineStrict` 失败。**看完即弃，不合并，主流程仍是 11.24。**

* 预期收益：把 8/25 两个 Critical RCE 的风险敞口在当天/本周内确认关闭；同时用极低成本量化 pnpm 12 迁移的真实阻力，为两周后的正式评估提供一手数据。
* 验收标准：产出一张"项目 → Next.js 版本是否达标 → 是否用 AVIF / 是否 Windows 承载"的清单，缺口全部补齐；pnpm 12 预演分支留下耗时、锁文件 diff、CI 是否变红三条记录（或明确"本团队暂不做预演"的决定）。
