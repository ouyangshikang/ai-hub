# Java 学习：接口幂等性

> 系列第 25 篇 · 第三阶段：接口与规范  
> 上一篇我们搞清楚了前端数据怎么传到后端——`@PathVariable`、`@RequestParam`、`@RequestBody` 各就各位，接口"能跑通"了。但真实业务里还有一个高频问题：用户双击了提交按钮、网络超时后 axios 自动重试、用户刷新页面导致表单重复提交——同一个请求被发了两次，后端会不会创建两个门店、扣两次库存？这就是今天的主角：接口幂等性。

## 1. 今天学什么

幂等（Idempotent）这个词来自数学：一个操作执行一次和执行多次，结果完全相同。HTTP 协议里，GET、PUT、DELETE 天然幂等——你查一次和查一百次，数据不会变；你把一个资源的状态改成"已关闭"，改一次和改十次结果一样。但 POST 不幂等——每次 POST 都可能创建一条新记录。

问题在于：前端无法保证请求只到达后端一次。网络抖动、用户手抖、浏览器重试，都可能导致同一个"创建门店"请求被发送两次。如果后端不做任何防护，数据库里就会出现两条一模一样的门店记录。接口幂等性就是后端保证"即使同一个请求被重复发送，业务结果也只生效一次"的能力。

这不是锦上添花，而是涉及钱和库存的接口的刚需。支付扣款、库存扣减、优惠券发放——这些操作如果因为重复请求被执行了两次，就是线上事故。

## 2. 前端工程师视角理解

你在前端一定做过类似的防护：

```typescript
// 提交按钮加 loading，防止双击
const submitLoading = ref(false)

async function handleSubmit() {
  if (submitLoading.value) return // 前端防抖
  submitLoading.value = true
  try {
    await axios.post('/api/stores', formData)
    ElMessage.success('创建成功')
  } finally {
    submitLoading.value = false
  }
}
```

这个 `loading` 锁能防住用户双击，但防不住以下场景：请求已经发出去了，响应还没回来时用户刷新了页面；或者 nginx 超时后自动重试；或者移动端弱网环境下 TCP 层重传。这些情况下，前端根本不知道请求到底有没有成功，只能"再发一次试试"。

所以前端的防抖只是第一道防线，后端必须有独立的幂等保障。你在前端能做的配合是：每次提交时生成一个唯一的请求标识（幂等 key），跟着请求一起发给后端。后端根据这个 key 判断"这个请求是不是已经处理过了"——处理过就直接返回上次的结果，没处理过才真正执行业务逻辑。

```typescript
// 前端生成幂等 key
import { v4 as uuidv4 } from 'uuid'

async function handleSubmit() {
  const idempotentKey = uuidv4() // 每次"用户意图提交"生成一个
  await axios.post('/api/stores', formData, {
    headers: { 'X-Idempotent-Key': idempotentKey }
  })
}
```

关键点：这个 key 在"用户的一次提交意图"内保持不变。如果用户点了一次按钮，网络超时后前端自动重试，重试用的是同一个 key——后端识别出是重复请求，不会重复创建。但如果用户关掉弹窗重新打开、填了新数据再次提交，那是一次新的提交意图，应该生成新的 key。

## 3. 和 JavaScript / TypeScript 的对比

### 防重复提交：前端锁 vs 后端幂等

```typescript
// Node.js + Express：用内存 Map 做简单幂等
const processedKeys = new Map<string, any>()

app.post('/api/stores', (req, res) => {
  const key = req.headers['x-idempotent-key'] as string
  if (processedKeys.has(key)) {
    // 已处理过，直接返回上次的结果
    return res.json(processedKeys.get(key))
  }
  // 首次处理
  const result = createStore(req.body)
  processedKeys.set(key, result)
  res.json(result)
})
```

```java
// Spring Boot：用 Redis 做分布式幂等（生产级写法）
@PostMapping
public Result<Long> create(
        @RequestHeader("X-Idempotent-Key") String idempotentKey,
        @RequestBody @Valid StoreCreateDTO dto) {
    // setIfAbsent = Redis 的 SETNX，原子操作
    boolean isFirst = redisTemplate.opsForValue()
        .setIfAbsent("idempotent:" + idempotentKey, "processing", 10, TimeUnit.MINUTES);
    if (!isFirst) {
        // 重复请求，直接返回（或返回上次的结果）
        return Result.fail(ErrorCode.DUPLICATE_SUBMIT);
    }
    Long storeId = storeService.createStore(dto);
    return Result.success(storeId);
}
```

Node.js 的内存 Map 在单进程下能工作，但 Java 后端通常部署多个实例（负载均衡），请求可能打到不同机器上——A 机器处理了第一次请求，B 机器收到重试时内存里没有这个 key，就会重复执行。所以 Java 后端用 Redis 做幂等存储：所有实例共享同一个 Redis，无论请求打到哪台机器，幂等判断结果一致。

### 幂等 vs 防抖：设计哲学差异

前端防抖（debounce / loading 锁）是"尽量不让重复请求发出去"，属于客户端优化。后端幂等是"即使重复请求到了，也保证结果正确"，属于服务端保障。两者不是替代关系，而是纵深防御——前端减少无意义的重复请求（降低服务端压力），后端兜底保证数据正确性（不依赖前端的可靠性）。

### 为什么 Java 后端更重视幂等

前端项目通常是单用户视角——你自己的浏览器、你自己的操作。后端是多用户、多实例、多入口的——同一个用户可能从 App 和 H5 同时操作，同一个请求可能经过网关重试、MQ 重复投递。Java 后端把幂等当作基础设施来建设（Redis + 数据库唯一索引 + 状态机），而不是依赖调用方"保证不重复调用"。

## 4. 真实业务场景

**场景：门店管理后台的"新增门店"接口。**

业务背景：运营人员在后台录入新门店信息（名称、地址、联系电话），点击"提交"按钮。

为什么会遇到幂等问题？

一是用户双击。运营录完信息快速点了两下"提交"按钮，两个 POST 请求间隔 50ms 发出。如果后端不做幂等，数据库里出现两条一模一样的门店记录，后续门店编号、区域统计全部错乱。

二是网络超时重试。运营在公司内网提交，请求经过 nginx 代理。后端处理耗时 3 秒（要校验区域编码、查重、写数据库），nginx 的 proxy_read_timeout 设了 2 秒，超时后 nginx 自动重试了一次。后端实际收到了两个相同请求。

三是前端 axios 重试配置。项目里配了 `axios-retry` 插件，网络错误时自动重试 3 次。如果第一次请求其实已经到达后端并执行成功，只是响应在回程时丢了，axios 会再发两次——后端执行了三次创建。

如果幂等方案缺失，后果是：门店表出现重复数据、运营看到"创建成功"但列表里有两条一样的记录、删除一条后另一条还在、客服接到投诉。更严重的场景是支付和库存——扣了两次钱、发了两张优惠券，那就是资损事故。

## 5. Java 示例代码

```java
/**
 * 幂等注解：标记在 Controller 方法上，声明该接口需要幂等保护
 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    /** 幂等 key 的过期时间（秒），默认 10 分钟 */
    int expireSeconds() default 600;
    /** 重复请求时的提示信息 */
    String message() default "请勿重复提交";
}
```

```java
/**
 * 幂等拦截器：基于 AOP 实现，在方法执行前检查 Redis
 * 这里用注解 + 拦截器的方式，业务代码无侵入
 */
@Aspect
@Component
public class IdempotentAspect {

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Around("@annotation(idempotent)")
    public Object check(ProceedingJoinPoint joinPoint, Idempotent idempotent) throws Throwable {
        // 从请求头中取幂等 key
        HttpServletRequest request = ((ServletRequestAttributes)
            RequestContextHolder.getRequestAttributes()).getRequest();
        String key = request.getHeader("X-Idempotent-Key");

        if (key == null || key.isBlank()) {
            throw new BizException(ErrorCode.PARAM_ERROR, "缺少幂等标识");
        }

        String redisKey = "idempotent:" + key;
        // SETNX：原子操作，只有 key 不存在时才设置成功
        Boolean isFirst = redisTemplate.opsForValue()
            .setIfAbsent(redisKey, "1", idempotent.expireSeconds(), TimeUnit.SECONDS);

        if (Boolean.FALSE.equals(isFirst)) {
            // 重复请求，拒绝执行
            throw new BizException(ErrorCode.DUPLICATE_SUBMIT, idempotent.message());
        }

        try {
            return joinPoint.proceed(); // 首次请求，正常执行业务
        } catch (Exception e) {
            // 业务执行失败，删除幂等 key，允许前端重试
            redisTemplate.delete(redisKey);
            throw e;
        }
    }
}
```

```java
/**
 * Controller 中使用：加一个注解即可获得幂等保护
 */
@RestController
@RequestMapping("/api/stores")
public class StoreController {

    @Autowired
    private StoreService storeService;

    @Idempotent(expireSeconds = 600, message = "门店正在创建中，请勿重复提交")
    @PostMapping
    public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) {
        Long storeId = storeService.createStore(dto);
        return Result.success(storeId);
    }
}
```

```typescript
// 前端配合：生成幂等 key 并在重试时保持不变
import { v4 as uuidv4 } from 'uuid'

function useIdempotentSubmit() {
  // 每次"打开表单"时生成一个 key，整个提交生命周期内不变
  const idempotentKey = ref(uuidv4())

  async function submit(url: string, data: any) {
    return axios.post(url, data, {
      headers: { 'X-Idempotent-Key': idempotentKey.value }
    })
  }

  // 提交成功后重置（下次新提交用新 key）
  function reset() {
    idempotentKey.value = uuidv4()
  }

  return { submit, reset }
}
```

## 6. 常见坑

**坑 1：用业务字段做幂等判断，而不是独立的幂等 key。**

错误写法：后端根据"门店名称 + 区域"判断是否重复。问题：用户确实想在不同时间创建同名门店（比如"星巴克望京店"关了又开），业务字段相同不代表是重复请求。正确做法：用前端生成的 UUID 作为幂等 key，它标识的是"一次提交意图"而不是"一条业务数据"。业务唯一性用数据库唯一索引保障，请求幂等用独立的 key 保障，两者职责不同。

**坑 2：幂等 key 的过期时间设太短。**

错误写法：`expireSeconds = 5`。问题：后端处理一个复杂创建逻辑可能要 3 秒，加上网络延迟，前端 5 秒后重试时 key 已过期，幂等保护失效。正确做法：过期时间要大于"接口最大处理时间 + 前端重试间隔"，一般设 5-10 分钟。太短防不住，太长浪费 Redis 内存，按业务场景权衡。

**坑 3：业务执行失败后没有清除幂等 key。**

错误写法：SETNX 成功后直接执行业务，业务抛异常了但 key 还在。问题：用户收到"创建失败"，想修改参数重新提交，但前端用的还是同一个 key（因为是同一次提交意图），后端判断为重复请求直接拒绝——用户怎么试都提交不了。正确做法：业务执行失败时 `catch` 里删除 Redis key（如上面代码所示），允许前端用同一个 key 重试。

**坑 4：只靠 Redis 做幂等，没有数据库兜底。**

错误理解：有了 Redis SETNX 就万无一失了。问题：Redis 主从切换时可能丢数据（异步复制），或者 Redis 集群故障时降级跳过了幂等检查。正确做法：Redis 是第一道防线（快速拦截），数据库唯一索引是最后一道防线（绝对保障）。两层配合：Redis 挡住 99.9% 的重复请求，唯一索引兜住剩下 0.1% 的极端情况。

**坑 5：GET 请求也加幂等拦截。**

错误写法：给查询接口也加 `@Idempotent`。问题：GET 天然幂等（查一次和查一百次结果一样），加幂等拦截只会增加 Redis 压力、拖慢响应速度，没有任何收益。正确做法：只有写操作（POST 创建、涉及状态变更的 PUT）才需要幂等保护。纯查询接口不需要。

## 7. 和之前知识的连接

- **第 24 篇「Controller 参数接收」**：今天幂等 key 通过 `@RequestHeader("X-Idempotent-Key")` 从请求头获取，这正是上一篇讲的第四种参数接收方式。上一篇解决了"数据怎么传进来"，今天在此基础上解决"传进来的请求是不是重复的"。

- **第 23 篇「状态码设计」**：今天重复提交时返回的 `ErrorCode.DUPLICATE_SUBMIT(40901)` 就是上一篇定义的"业务冲突段"错误码。前端收到 40901 后弹提示"请勿重复提交"，而不是弹一个通用的"操作失败"——状态码体系让幂等拒绝也有了精确的前端处理路径。

- **第 21 篇「请求参数校验」**：幂等检查和参数校验的执行顺序有讲究——应该先做幂等判断（重复请求直接拒绝，不需要再校验参数），再做参数校验。如果反过来，重复请求还会走一遍校验逻辑，浪费资源。在 Spring 中，拦截器（幂等）先于 `@Valid`（校验）执行，天然满足这个顺序。

## 8. 面试 / 工作中常见问题

### 问题 1：你们项目的接口幂等是怎么实现的？

参考答案：三层方案。第一层前端防抖：提交按钮加 loading 锁，防止用户双击。第二层 Redis SETNX：前端每次提交意图生成 UUID 放在请求头 `X-Idempotent-Key`，后端用 AOP 拦截器在方法执行前做 SETNX 判断，重复请求直接返回 40901。第三层数据库唯一索引：业务表的关键字段加联合唯一索引，即使 Redis 失效也不会产生脏数据。三层纵深防御，任何一层失效都有下一层兜底。

### 问题 2：如果前端没有传幂等 key 怎么办？

参考答案：分两种策略。对于核心写接口（支付、库存），缺少幂等 key 直接拒绝（返回参数错误），强制前端配合。对于普通写接口（创建门店、编辑信息），可以降级为"基于业务字段的短时去重"——比如同一个用户 5 秒内提交了完全相同的门店名称和地址，视为重复。但这是降级方案，长期还是要求前端统一接入幂等 key。

### 问题 3：幂等和事务是什么关系？会不会冲突？

参考答案：不冲突，但要注意执行顺序。幂等判断在事务开启之前（拦截器先于 Service 方法执行），它决定的是"要不要执行这段业务逻辑"。事务管的是"业务逻辑内部的多个数据库操作要么全成功要么全回滚"。一个在门外拦人，一个在门内保障一致性。需要注意的是：如果业务执行失败事务回滚了，但 Redis 里的幂等 key 没清除，用户就无法重试——所以 catch 里必须删 key。

## 9. 今日小结

- 幂等 = 同一请求执行一次和多次，业务结果完全相同。POST 创建类接口天然不幂等，必须人工保障。
- 前端防抖只是辅助，后端必须有独立的幂等机制——因为你无法保证请求只到达一次。
- 生产级方案：前端生成 UUID 幂等 key → 后端 Redis SETNX 拦截 → 数据库唯一索引兜底，三层纵深防御。
- 幂等 key 标识的是"一次提交意图"，不是"一条业务数据"——过期时间要覆盖接口最大处理时间。
- 业务失败必须清除幂等 key，否则用户无法重试；GET 查询不需要幂等保护。

## 10. 明日预告

明天建议学习：`接口兼容性`

原因：今天解决了"重复请求"的问题，保证接口在并发和重试下行为正确。但接口上线后还面临另一个长期挑战：前端有多个版本同时在线（App 用户不一定升级、H5 有缓存、小程序有审核周期），后端接口改了字段名、删了参数、调了返回结构，老版本前端会不会直接崩？接口兼容性讲的就是：如何在迭代中保证新老版本前端都能正常工作，不出现"后端一上线，老用户全白屏"的事故。它和今天的幂等性同属"接口稳定性"范畴——幂等防的是重复调用，兼容性防的是版本差异。
