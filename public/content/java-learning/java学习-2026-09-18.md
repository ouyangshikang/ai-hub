# Java 学习：线程池与并发

> 系列第 58 篇 · 第七阶段：并发与性能（开篇）

> **与前几篇的分工**：第 51 篇从**容量**看池（Little's Law、拐点、p99）；第 50 篇只解决了一件事（MDC 怎么跨线程传）。今天讲的是**编程模型本身**：参数怎么定、队列与拒绝策略怎么选、`CompletableFuture` 的池陷阱、以及 JS 里根本不存在的共享状态问题。

## 1. 今天学什么

线程池解决一件事：**线程是昂贵的资源，不能每来一个任务就开一根。** 它把"能同时干多少活"变成一个显式的、可监控的、可以拒绝的上限。

今天讲四块：① 一个任务提交进来后按什么顺序被处理（核心线程 → 队列 → 非核心线程 → 拒绝），这条流程决定了一切参数的含义；② 有界队列与四种拒绝策略怎么选，各自会把故障变成什么形状；③ `CompletableFuture` 不传线程池时会共用 `ForkJoinPool.commonPool()`，一个慢 IO 就能拖垮全服务的并行任务；④ 共享可变状态与 `ThreadLocal` 串号——线程复用带来的新问题。

它是第七阶段的第一篇，因为并发是后端与前端口感差异最大的一块：**从这里开始，你要为"同时发生"写代码。**

## 2. 前端工程师视角理解

先把最反直觉的一条说清：**JS 里没有真正的并行，所以你从来没有为"共享可变状态"写过防御代码。** 单线程事件循环意味着两个回调永远不会同时改同一个对象——这是白拿的保证。Java 一上线程池，这个保证消失了：同一个 `HashMap`、同一个 `SimpleDateFormat`、同一个实例字段，可能被两根线程同时读写，而且**大部分时候看起来是对的**（竞态窗口只有微秒）。后端要求"能不共享就不共享、要共享就用并发容器或不可变对象"，本质是在补这一课。

第二个锚点你其实天天在排队，只是没意识到：**浏览器对同一域名默认只有 6 个并发连接**，第 7 个请求会在队列里等；前端限流库 `p-limit(5)` 也是同一件事。所以"并发度 + 有界队列 + 超出怎么办"这套模型你完全熟——只是后端把这三样做成了显式参数，而且超出的处置方式（拒绝、丢弃、让调用方自己跑）会直接决定故障长什么样。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端 |
|---|---|---|
| 并发模型 | 单线程事件循环，等待不占资源 | 每任务一根线程，阻塞要占栈与调度 |
| 排队 | 浏览器 6 连接 / 自己 `p-limit` | 线程池 + 有界队列 + 拒绝策略 |
| 共享状态 | 天然无竞争 | 竞态、可见性、`ThreadLocal` 串号 |
| 并行聚合 | `Promise.all` + 手写超时 | `CompletableFuture` + `orTimeout`（但默认共用 `commonPool`） |
| 优雅关闭 | 进程退出即了结 | `shutdown()` 只停接收，任务还在跑，要等它 |

**为什么 Java 非用池不可？** 因为线程很贵：每根线程默认要 1MB 级栈内存、要进内核调度、还会成为 GC 的 root。Node 里挂 1 万个 `await` 只是 1 万个 Promise 对象；Java 里挂 1 万个阻塞任务，如果每个都占一根线程，光是栈就要 10GB 量级。池的意义是**把"同时在做"的数量压到一个能承受的值，多出来的排队或拒绝**——这也解释了第 51 篇那句"CPU 才 20% 但接口排成长队"：排队发生在池上，不在 CPU 上。

## 4. 真实业务场景

**场景：下单接口异步化之后，大促当晚 OOM，同时有门店收到别人家的券。**

业务背景：门店下单要顺带做三件事——发优惠券、发通知短信、写埋点。原本同步串在主链路里，接口 RT 300ms。开发为了提速改成异步：

```java
private static final ExecutorService POOL = Executors.newFixedThreadPool(10);  // ← 两个坑一起埋下
```

大促开始后两件事同时发生。**第一件**：`newFixedThreadPool` 用的是**无界队列**，任务生产速度（8000/s）远高于消费速度（10 线程 × 每任务 200ms = 50/s），队列一路涨到百万级，对象全在堆里活着，Full GC 从 2 秒变 40 秒，最后 OOM。而监控上 CPU 只有 30%——**堆积不体现在 CPU 上**。

**第二件**：发券逻辑里用 `ThreadLocal<ShopContext>` 存当前门店，取值时直接 `SHOP.get().shopId()`。线程是复用的，队列一深，某个任务读到的就是**上一个任务留下的门店上下文**，于是 A 店的券发到了 B 店。这不是新 bug——第 50 篇的 traceId 丢失是同一个根因的另一面：**线程复用会把上一手的残留带给下一手。**

还有一个后续雷：`@Async` 默认找容器里唯一的 `TaskExecutor`，而定时任务（第 44 篇）与异步方法共用同一根调度线程的经历，让一个卡住的短信重试把凌晨对账也拖没了。

**用错的代价**：从"接口不够快"变成"整台机器不可用 + 资金类数据错发"——异步化省下的 300ms，代价是两类全新故障。

## 5. Java 示例代码

```java
@Configuration
public class AsyncConfig {

    /**
     * 下单异步线程池：参数与队列全部显式，禁用 Executors 默认工厂。
     * 执行顺序固定为：核心线程 → 队列 → 临时线程 → 拒绝策略（不是"先扩线程再排队"）。
     */
    @Bean("orderExecutor")
    public ThreadPoolTaskExecutor orderExecutor(MeterRegistry registry) {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(16);                       // 常驻线程：按稳态并发定，参考第 51 篇
        ex.setMaxPoolSize(32);                        // 队列满后才允许扩到这里
        ex.setQueueCapacity(500);                     // ★ 必须有界：无界 = 把 OOM 换成"正常"
        ex.setKeepAliveSeconds(60);
        // 线程命名：线上 jstack 和日志靠它认人，pool-3-thread-7 这种名字等于自盲
        ex.setThreadFactory(new ThreadFactoryBuilder().setNameFormat("order-async-%d").build());
        // 满了让调用方线程自己跑：天然反压，但会拖慢 HTTP 线程 —— 只用于"绝不能丢"的任务
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setWaitForTasksToCompleteOnShutdown(true); // 关闭时跑完存量任务，不硬切
        ex.setAwaitTerminationSeconds(30);            // 最多等 30s，超时再中断（第 57 篇发布窗口）
        ex.initialize();
        registry.gauge("order.async.queue.size", ex, e -> e.getThreadPoolExecutor().getQueue().size());
        return ex;                                    // 队列长度必须有指标，否则堆积只能靠 OOM 发现
    }

    /** 带上下文传递的提交封装：把第 50 篇的 MDC 复制收进一处，避免每处手写漏掉 */
    public static Runnable withMdc(Runnable task) {
        Map<String, String> ctx = MDC.getCopyOfContextMap();
        return () -> {
            Map<String, String> old = MDC.getCopyOfContextMap();
            if (ctx != null) MDC.setContextMap(ctx);
            try { task.run(); } finally {
                if (old != null) MDC.setContextMap(old); else MDC.clear();   // ★ 还原，别留给下一手
            }
        };
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class OrderDetailLoader {

    private final ShopClient shopClient;
    private final ItemClient itemClient;
    private final CouponClient couponClient;
    /** 第 5 节定义的池。用 Lombok 时要在 lombok.config 里配 copyableAnnotations 才能带上 @Qualifier，
     *  否则老实写构造器注入更稳 */
    private final Executor orderExecutor;

    /** 并行查询三个下游：显式传自己的池 + 超时，不用默认 commonPool */
    public OrderDetail loadDetail(String orderNo) {
        CompletableFuture<Shop> shopF =
                CompletableFuture.supplyAsync(() -> shopClient.get(orderNo), orderExecutor);
        CompletableFuture<List<Item>> itemF =
                CompletableFuture.supplyAsync(() -> itemClient.list(orderNo), orderExecutor);
        CompletableFuture<Coupon> couponF =
                CompletableFuture.supplyAsync(() -> couponClient.best(orderNo), orderExecutor)
                        .completeOnTimeout(null, 200, TimeUnit.MILLISECONDS);   // 券拿不到就无券，不拖整体

        // 前两个是必需数据：任一失败整体失败（和 Promise.all 一样），超时也要有
        CompletableFuture.allOf(shopF, itemF).orTimeout(500, TimeUnit.MILLISECONDS).join();
        return new OrderDetail(shopF.join(), itemF.join(), couponF.join());
    }
}
```

## 6. 常见坑

**坑 1：用 `Executors` 的默认工厂建池。** 错误做法：`newFixedThreadPool` / `newCachedThreadPool` 一行搞定。问题：前者队列无界，堆积直接换来 OOM；后者最大线程数近乎无上限，线程数能飙到几千，栈内存与切换把机器打死（这也是《阿里 Java 开发手册》明确禁止这种写法、要求手写 `ThreadPoolTaskExecutor` 的原因）。正确做法：**核心数、最大数、有界队列、拒绝策略、线程名、关闭行为**六项全部显式，池只在一处定义、按业务隔离（下单的池不给导出报表用）。

**坑 2：拒绝策略选错，把故障换了个形状。** 错误理解："配个 `CallerRunsPolicy` 就不会丢任务了。" 问题：调用方线程往往是 Tomcat 的 HTTP 线程——它替池跑任务，等于把线程池的排队转嫁成 Web 层排队，接口 RT 集体上涨、可用线程更少，故障从"任务被拒"变成"全站变慢"；反过来 `DiscardPolicy` / `DiscardOldestPolicy` 静默丢弃，日志里什么都没有。正确做法：按任务性质分：**绝不能丢**的写本地消息表或落 DB 由定时任务重投（第 25、44 篇）后走 `AbortPolicy` 抛错报警；**可丢**的用 `DiscardOldestPolicy` 但必须打点计数；`CallerRuns` 只用于调用方本来就关心结果的场景，并且要给它单独的池。

**坑 3：`CompletableFuture` 不传 executor，`ThreadLocal` 不清理。** 问题有两层：① 两参数的 `supplyAsync` 会走全局 `ForkJoinPool.commonPool()`，它按 CPU 核数定大小、**为计算密集设计**，一个 300ms 的 IO 就能把它占满，于是全服务所有 `parallelStream` 和未指定池的 Future 一起变慢；② `ThreadLocal`（含 MDC）放在线程上，线程复用不自动清，就出现场景里"A 店券发给 B 店"这种串号。正确做法：**所有异步都显式传自己的池**；上下文只靠 `withMdc` 这类统一封装传递，`finally` 里必须还原或 `remove()`。

## 7. 和之前知识的连接

- **第 50 篇「日志排查」**：`TaskDecorator` / MDC 复制是同一个根因的用法之一——线程复用会带走上一手的上下文。今天的 `withMdc` 就是把那条规矩收进一处。
- **第 51 篇「接口压测」**：池参数不能凭手感。核心数看稳态并发（`并发 ≈ TPS × RT`），队列看能容忍多久的排队（队列 500 × RT 200ms ÷ 32 线程 ≈ 3 秒的等待上界），拒绝策略由压测验证——这三个数今天终于有了来源。
- **第 54 篇「集成测试」**：那篇说"测试线程的 `@Transactional` 回滚管不到真实 HTTP 触发的另一根线程"，根因就在这里：线程不同，绑在线程上的事务上下文与连接也就不同。

## 8. 面试 / 工作中常见问题

### 问题 1：线程池参数怎么定，公式是什么？

参考答案：没有万能公式，只有两条约束。CPU 密集取"核数 + 1"左右；IO 密集按 `目标TPS × 单任务耗时`（Little's Law）估在途并发，再受下游与 DB 连接数上限约束——**连接池往往比线程池更早成为天花板**（第 51 篇那个默认 10）。队列长度按"能容忍多久的排队"倒推，而不是拍一个 1000。最后一定用压测验证：调大核心数同时要看 DB、下游限流扛不扛得住，否则只是把压力往下游搬。

### 问题 2：优雅下线时线程池怎么处理才不丢任务？

参考答案：先摘流量再停进程，顺序不能反。Spring 侧配 `setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(n)`，让容器关闭时先 `shutdown()`（不再接新任务、存量继续跑）并等待；n 必须小于发布平台的 kill 超时，否则等不到就被 `SIGKILL`。JVM 层可再加 `Runtime.addShutdownHook`。关键认知：`shutdown()` 不会中断正在跑的任务，`shutdownNow()` 才会——**硬切就是你没写完的那笔订单。**

### 问题 3：线上怀疑任务堆积，怎么确认和处置？

参考答案：先看三个指标：队列长度（没埋点就先加，见示例的 gauge）、活跃线程数、拒绝次数（配合告警）。再看线程栈：大量线程卡在同一个外部调用（`WAITING`/`TIMED_WAITING`）说明瓶颈在下游，堆栈里 `pool-N-thread-M` 这种无名线程只能靠猜——这就是命名线程工厂的价值。处置按代价排：给慢下游收紧超时并降级（第 57 篇的开关）、临时扩容池与实例、必要时拒绝非核心任务；**重启只是把队列清空，不解决生产速度大于消费速度这件事。**

## 9. 今日小结

- 任务的去处是**先入队、队满才扩线程**，不是"先扩线程再排队"——理解这条顺序，参数和拒绝策略才讲得通。
- 建池六项全部显式（核心数、最大数、**有界队列**、拒绝策略、线程名、关闭行为）并按业务隔离；`Executors` 默认工厂是 OOM 与线程爆炸的直通车，而拒绝策略是在选"故障长什么样"。
- `CompletableFuture` 必须显式传池，`ThreadLocal` 用完必须清——线程复用是把双刃剑。
- 池参数的答案在第 51 篇的压测里，不在博客的"核心数 = 2×CPU"里。
