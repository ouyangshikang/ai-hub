## 1. 本周摘要

本周的主线是「止血方案被真修复替换」。上期用关闭功能绕过的 Next.js AVIF 漏洞，在 8/31 随 16.3.4 与 15.5.25 重新开启，上游补丁到位才是这条链路的终点。同期 Chrome 桌面 Stable 在三天内滚了两次，共 38 个安全修复、含 2 个 Critical。

第二条线是「工具链开始为速度还债」。pnpm 12 在窗口内连发五版，其中两版是在修升级链自断的问题；Vite 8.3 beta 删掉 esbuild 插件路径，Rolldown 回改类型去对齐 Rollup。Rust 化红利仍在，但兼容性账单本周第一次集中出现。

第三条线是「可测的新基建与可管的工具同时到位」。Vitest 5.0 转正、Turbopack 首次把分块策略开放给业务配置、npm 支持单包多套 Trusted Publishing、Cursor 把 agent 执行搬进客户内网。整体判断：本周适合做测量与验收，不适合做切换。

## 3. 本周值得关注的 6 个变化

### 变化 1：Next.js 恢复 AVIF 图片优化

**评级 采用** · 分类 框架生态 / 安全 · 项目风险 中 · 发布 2026-08-31

**发生了什么**：8/31 Vercel 同步发布 16.3.4 与 15.5.25，官方措辞是重新启用 AVIF 图片优化。8/25 那批用「关掉 AVIF」止血的未认证 RCE，上游修复已随 sharp 0.35.4（libvips 8.18.6）到位。15.5.25 带前提条件：只有装了较新版本 sharp 才恢复。

**为什么值得关注**：它修正了上期「升级即安全」的结论。功能被禁用不是终点，恢复可用才是这条链路闭环的信号。

**对工程师的影响**：仍停在 16.3.3 或 15.5.24 的项目，图片体积与 LCP 还带着上期的降级损失。

**对现有项目的影响**：中。AVIF 恢复本身是行为变更，出图格式会变，需要一次回归；Windows 那一项的修复范围没有变化。

**建议动作**：把版本推进到 16.3.4 或 15.5.25，并按上期建议补一次实测出图确认，不要只核对版本号。

### 变化 2：Chrome 三天两次 Stable 安全滚动

**评级 采用** · 分类 浏览器 / 安全 · 项目风险 中 · 发布 2026-09-01

**发生了什么**：9/1 桌面 Stable 到 152.0.7977.75/.76，一次修 26 个漏洞，含 2 个 Critical（Shared Tab Groups 与 WebGL 的释放后使用）。9/3 再滚到 .82/.83，又修 12 个，全部 High。同周 153 于 9/3 进 Early Stable、154 于 9/2 进 Beta，Firefox 155.0 也在 9/1 发布。

**为什么值得关注**：三天 38 个修复延续了 8/20 Chrome 151 紧急更新与 8/27 一批 LTS 吞 28 个 CVE 的节奏，「一周一次补丁」的假设已经不成立。

**对工程师的影响**：业务代码无影响。固定浏览器版本的 CI 需要跟节奏，153 目前只是小比例灰度，不能按生产可用排期。

**对现有项目的影响**：中。风险在运行环境而不是代码，受管机器和内网测试环境最容易被漏掉。

**建议动作**：本周把桌面 Chrome 推到 .82/.83，并确认受管环境的更新策略允许这个频率；把 CI 里锁死的 channel 一并更新。

### 变化 3：Vitest 5.0 正式版发布

**评级 试点** · 分类 测试工程 · 项目风险 中 · 发布 2026-09-03

**发生了什么**：9/3 Vitest 5.0.0 转 stable，npm 的 `latest` 已指向它。运行门槛是 Node `^22.12.0 || ^24.0.0 || >=26.0.0`，Vite peer 收窄到 6.4、7、8 三条线。默认值与断言语义一起收紧：`clearMocks` 默认 true、未 await 的异步断言直接失败、locator 默认严格匹配。

**为什么值得关注**：它同时改默认值和 CI 时长，官方称依赖密集型项目最高快 53%，来自 VM pool 重写。这类「版本号只进一位、行为改得很硬」的升级最容易让流水线整片变红。

**对工程师的影响**：顶层 `bench` 与 `test.sequential` 被移除，Vue 与 Svelte 的 browser mode 里 `render` 变成异步，存量用例要动。

**对现有项目的影响**：中。多数红点其实是在补上过去漏掉的校验，要先判定是真 bug 还是旧依赖在兜底。

**建议动作**：挑一条非关键仓库升一次并跑全量测试，把失败清单当作测试债台账来用，不要直接在主干上做。

### 变化 4：Turbopack 分块策略首次可调

**评级 试点** · 分类 性能优化 / 框架 · 项目风险 低 · 发布 2026-09-03

**发生了什么**：Vercel 9/3 发文明确 Turbopack 的分块取舍逻辑，并开放 `experimental.turbopackChunking` 下的 `generateComponentChunks`、`firstPageLoadPriority`（默认 0.67）、`priorityRoutes`、`clusters`。另有 `experimental.turbopackCjsTreeShaking` 与 `experimental.turbopackSharedRuntime` 两个开关。

**为什么值得关注**：官方在 nextjs.org 实测三档差异：不合并 561.6 KiB / 96 请求，默认配置 554.8 KiB / 38 请求，组内全合并 610.0 KiB / 15 请求。合并到极致会多传约一成代码。

**对工程师的影响**：可以把已知的跳出率填进 `firstPageLoadPriority`、把高频路径写进 `priorityRoutes`，首屏与二跳不再是二选一。

**对现有项目的影响**：低。全部在 experimental 命名空间，需要 Next 16.3 以上，官方声明其中两项后续会转为默认开启。

**建议动作**：本周只做测量不改策略：同一组路由分别按三档构建，记录请求数、传输体积与二跳耗时，再决定是否打开 `generateComponentChunks`。

**来源**

- [How Turbopack chunks your JavaScript](https://nextjs.org/blog/turbopack-chunking)（官方博客，2026-09-03）
- [turbopackChunking 配置项](https://nextjs.org/docs/app/api-reference/config/next-config-js/turbopackChunking)（官方文档）

### 变化 5：pnpm 12 九天五连发，两条升级链自断

**评级 观察** · 分类 包管理 / 工程化 · 项目风险 低 · 发布 2026-09-02

**发生了什么**：8/26 正式版之后，pnpm 在窗口内连发 12.2.0、12.2.1、12.3.0、12.3.1、12.3.2。其中 12.2.1 恢复被 12.2.0 弄坏的无扩展名 `pnpm` 可执行目标，该问题会让 12.1 及更早版本无法自升级；12.3.1 修掉全局 `node`、`npm`、`yarn` 启动失败并补了迁移。

**为什么值得关注**：12.3.0 把所有 context-aware 全局命令改成各平台原生可执行文件，Windows 上用 exe 取代 cmd 与 ps1 脚本 shim。这类只有真实升级路径才会暴露的问题，比新特性更能说明成熟度。

**对工程师的影响**：npm 的 `latest` 至今仍是 11.25.0，`latest-12` 是 12.3.1、`next-12` 已到 12.3.2，隐式安装不会拿到 12 线。

**对现有项目的影响**：低。留在 11 线的项目完全无感，主要暴露面是已经手动装上 12.0 至 12.2 的开发者机器。

**建议动作**：延续上期「预演不切换」，两周验证窗口到 9/9；已在 12 线的直接装 12.3.2，不要逐级自升级。到期评估时把结论维度从「能不能跑」换成「升级路径是否可靠」。

### 变化 6：发布链路与 AI 工具管控同时收紧

**评级 试点** · 分类 工程化 / AI 工具链 · 项目风险 低 · 发布 2026-09-03

**发生了什么**：npm 于 9/3 支持单个包配置多套 Trusted Publishing，正式版与预发布版可以分别绑定不同的 CI 工作流。GitHub 同日宣布弃用部分 Copilot 模型、重新开放 Business 与 Enterprise 注册，Copilot 的 Content exclusions 已在 9/2 转 GA。

**为什么值得关注**：这几件事都在「能不能用」之外解决「归谁管」。多套 Trusted Publishing 让预发布与正式发布的发布权限第一次能按工作流隔离，这是前端库最常见的供应链风险点。

**对工程师的影响**：Cursor 在 9/2 上线 Self-hosted machines，官方口径是工具执行完全留在客户自己的网络内，此前 agent 执行出域是企业侧最主要的阻力。

**对现有项目的影响**：低。都是能力增量，不改任何前端构建产物，也不影响现有兼容性。

**建议动作**：库作者本周给预发布流程单独配一条 Trusted Publishing；用 Copilot 的团队复查 Content exclusions 是否覆盖到内部仓库与敏感路径。

**来源**

- [Multiple trusted publishing configurations for npm](https://github.blog/changelog/2026-09-03-multiple-trusted-publishing-configurations-for-npm)（官方 Changelog，2026-09-03）
- [GitHub Changelog 列表](https://github.blog/changelog/)（官方 Changelog，2026-09-02 与 09-03）
- [Cursor Changelog](https://cursor.com/changelog)（官方 Changelog，2026-09-02）

**例行更新**：UnoCSS 66.9.0（9/1）新增官方包 `@unocss/processor-lightningcss`，把样式后处理交给 Lightning CSS，UnoCSS 用户可在下个迭代小范围试一次。PostCSS 8.5.27 与 8.5.28 同日两次，直接取 8.5.28。Rspack 2.2.2（9/1）以性能修复为主，vue-router 5.3.1（9/2）只修一个参数匹配问题，按常规跟版即可。

## 5. 可以引入团队的实践

### 实践 1：把 Vitest 5 放到一条非关键流水线

**成本** 低 · **适合** 已在 Vitest 4 且 Node 不低于 22.12 的仓库

**收益**：一次升级同时拿到更快的依赖密集型执行与更严的断言语义，暴露出来的红点大概率是真实存在的测试债，而不是新框架的锅。

**试点方式**：单独分支升级并跑全量测试，只保存失败清单、不改主干配置与共享 setup。分支不合即完全回退。

### 实践 2：给自己首页做一次三档分块测量

**成本** 低 · **适合** Next 16.3 以上的 C 端站点

**收益**：把「要不要合并 chunk」从经验判断变成有请求数与体积支撑的决策，同时量化 shared runtime 声称的每次导航省一个阻塞请求与约 10 KB。

**试点方式**：在预发布环境依次用不合并、默认、组内全合并三种配置各构建一次，跑同一组导航路径记数。实验开关都在 experimental 命名空间，删掉配置即回退。

### 实践 3：给 AI 编码工具补一份管控清单

**成本** 低 · **适合** 在用 Copilot 或 Cursor 的团队

**收益**：把选型问题从「模型有多强」换成四个可审计的问题，减少安全评审时的临时争论，也便于复用到新工具接入。

**试点方式**：把四问写进工具接入模板：代码是否出域、执行是否出域、排除规则覆盖哪些仓库、模型配额由谁审批。纯文档动作，随时可撤。

## 6. 只是噱头，暂时不用管

### 内容 1：本周把 pnpm 12 设为团队默认

**为什么不用急**：npm 的 `latest` 至今仍是 11.25.0，官方自己都没切；九天五版的节奏里有两版是在修升级链自断。两周验证窗口才走到一半，稳定性证据不足。

**后续观察点**：`latest` 何时指向 12，以及 9/9 之后有无集中的生产回归反馈。

### 内容 2：用远程构建产物缓存替代 CI 缓存

**为什么不用急**：pnpm 的这套 `remoteSideEffectsCache` 官方定性就是 proof of concept，配套 registry 仍在 alpha，且协议已明确服务端与客户端必须同版本，说明还在破坏性变更期。

**后续观察点**：该 registry 转 beta 的时间点，以及签名信任模型是否给出企业部署方案。

### 内容 3：把模型版本号更新当前端动态追

**为什么不用急**：本周模型侧的密集发布没有改变任何前端集成方式，调用协议与 SDK 形态都没动。真正影响日常的仍是能力边界与管控，例如 agent 执行能否留在内网。

**后续观察点**：模型更新是否带来客户端 SDK 或协议层的破坏性变化。

## 7. 本周可以落地的小动作

### 小动作：给 AVIF 回归做一次真出图验收

**目标**：确认上期被禁的 AVIF 优化已经真的回来，而不是只看版本号。约 20 分钟。

**步骤 1 · 核对框架与图片依赖版本**

```bash
pnpm ls next sharp --recursive
```

Next 要看是否已到 16.3.4（16.x 线）或 15.5.25（15.5 线）。15.5.25 的恢复带前提条件，也就是装了较新版本 sharp，所以 sharp 必须一起核。

**步骤 2 · 实测一次出图的响应类型**

```bash
curl -s -o /dev/null -w '%{content_type}\n' \
  -H 'Accept: image/avif,image/webp,*/*' \
  'http://localhost:3000/_next/image?url=%2Fhero.jpg&w=640&q=75'
```

返回 image/avif 说明优化已恢复；返回 image/jpeg 说明版本没到位或 sharp 过旧。请把 URL 换成项目里真实被优化过的图片路径。

**预期收益**：把上期「升级即安全」的假设换成有实测记录的结论，同时确认图片体积与 LCP 没有停在降级状态。

**验收标准**：每个 Next.js 项目留下一行记录，包含 Next 版本、sharp 版本、实测 Content-Type。三项不齐即视为未验收。

## 8. 和上期的连续观察

上期是 2026-08-28（第 8 期）。

**上期事项的落地结果**
