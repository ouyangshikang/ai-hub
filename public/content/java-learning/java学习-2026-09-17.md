# Java 学习：线上问题排查流程

> 系列第 57 篇 · 第六阶段：工程化（收官篇）
> 衔接上一篇「代码可维护性」：昨天管"看不看得懂"，今天管"凌晨告警响了，手往哪儿放"。
> **定位**：前面每一篇给了一个点——日志（第 50 篇）、压测（第 51 篇）、慢 SQL（第 52 篇）、测试（第 53 / 54 篇）、分层与可读性（第 55 / 56 篇）。今天是把它们串成一条**有顺序、有角色、有停手条件**的流水线。

## 1. 今天学什么

线上问题排查流程解决一件事：**把"恢复服务"和"找到根因"分成两段，并按正确顺序发生。** 大多数扩大化的故障不是查不出来，而是有人在止血之前先钻进 debug，或者反过来——凭直觉重启把现场抹掉了。

今天讲四段：① 接手（谁拍板、多久通报一次、时间线怎么记）；② **止血四板斧的优先级**（回滚 > 开关降级 > 扩容 > 切流限流）及各自前提；③ 定位的路径依赖（先看变更，再对指标拐点，最后用 traceId 二分）；④ 复盘要产出**机制**而不是责任人——测试、门禁、开关、Runbook，正好是前面九篇的用途。

一个后端值不值得信任，往往不看功能写得多快，而看他处理故障时有多克制。

## 2. 前端工程师视角理解

前端处置线上问题有条铁律：**先回滚，后调查。** CDN 版本秒级可退，所以"恢复优先"你天生就会。后端同样把回滚排第一，但有两个残酷差异：**发布慢**（镜像回滚 + 重启，分钟级还要排队），以及**数据库退不回去**——这次变更带了 DDL 或已经写脏数据，代码退回去也修不好，甚至旧代码不认识新列，直接起不来。

第二个需要重建的直觉是 feature flag 的**失败方向**。前端关掉一个 flag 只是少块展示；后端把风控开关关掉之后，业务是"跳过风控继续下单"还是"拒绝下单"？前者是资损，后者是可用性。这个取舍必须在平时写进代码并演练过，而不是留给凌晨三点的临场判断——这正是第 5 节的主角。也正因为如此，流程的第一条不是"谁懂谁看"，而是**先把责任人和通报节奏定下来**。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 | Java 后端 |
|---|---|---|
| 回滚成本 | CDN 切版本，秒级 | 镜像/包回滚 + 重启，分钟级，受发布排队 |
| 数据变更 | 基本无状态 | DDL 与已写数据**不可回滚**，需前向兼容设计 |
| 定位手段 | Source map + 会话回放 | traceId 全链路 + 指标拐点 + 多实例检索 |
| 降级 | flag 关展示 | 开关关能力，还要决定失败方向 |
| 现场保全 | 刷新十次慢慢复现 | 重启会丢内存态与线程栈，**先取证再重启** |
| 复盘产出 | 埋点 + lint + CI 体积门禁 | 测试 + ArchUnit + SQL 门禁 + Runbook |

**"现场"这个概念得重建。** 前端的状态在用户浏览器里，你可以复现十次；后端进程一旦重启，堆里的内存态、线程池的堆积、当时真正生效的配置值会全部消失——而重启往往就夹在止血动作里。所以流程要有一条硬规矩：**在不影响恢复的前提下先取证据**，三份就够：线程 dump、一次 `jcmd` 堆概况、当前生效配置（第 49 篇的 actuator 端点）。三条命令各十秒。于是顺序固定为：确认有回滚点 → 抓证据 → 止血 → 定位。

## 4. 真实业务场景

**场景：大促开始后 12 分钟，门店下单接口错误率从 0.1% 涨到 9%。**

当天 14:20 有一次配置变更——运营把风控超时从 800ms 调到 500ms。14:32 告警响起，群里三个方向同时开口：A 说回滚配置，B 说要先查数据库，C 已经准备重启实例"试试能不能好"。

这 12 分钟里做对两件事、做错一件：

- ✅ 第一句就指定了**指挥官**（谁拍板）和**通报人**（每 10 分钟同步），指挥者自己只读监控；
- ✅ 先在时间线上记下"14:20 有变更"，把指标拐点与变更时间**对齐**——只花 30 秒，却直接指向根因；
- ❌ C 的重启把现场抹了：堆积消失、错误率短暂回落，团队误判"已恢复"；14:50 再次恶化时已经没有线程栈可看，只能靠 actuator 回读配置反推超时值。

止血最终用了两斧：配置回滚到 800ms（错误率降到 1%）+ 风控临时降级为"放行并事后补查"。根因是风控大促期 P99 本来就在 950ms，500ms 把一半请求打成超时。**代价**：一次本可 15 分钟结束的故障拖成 70 分钟，而复盘写成"某人误重启"——因为没人把"重启前先取证"补进 Runbook，下次照样发生。

## 5. Java 示例代码

**让止血只需改一个开关：降级实现与失败方向都要显式。**

```java
/** 业务只依赖接口（第 48 篇的"面向能力编程"），开关才能真的改变行为 */
public interface RiskGateway {
    RiskResult check(Order order) throws RiskUnavailableException;
}

/** 正常实现：真实调风控 */
@Component
@RequiredArgsConstructor
@ConditionalOnProperty(name = "store.risk.enabled", havingValue = "true", matchIfMissing = true)
class HttpRiskGateway implements RiskGateway {

    private final RiskClient riskClient;         // 封装超时与连接池的 HTTP 客户端

    @Override
    public RiskResult check(Order order) throws RiskUnavailableException {
        // 超时阈值要由压测给出依据（第 51 篇），不要拍脑袋写 800ms
        return riskClient.evaluate(order, Duration.ofMillis(800));
    }
}

/**
 * 降级实现：开关关掉后走这里。
 * ★ 失败方向写在代码里而不是留给临场判断：
 *   这里选择放行 + 事后补查（可用性优先），并把决策记成可审计日志。
 */
@Component
@ConditionalOnProperty(name = "store.risk.enabled", havingValue = "false")
@Slf4j
class PassThroughRiskGateway implements RiskGateway {
    @Override
    public RiskResult check(Order order) {
        log.warn("风控降级放行 orderNo={} amount={}", order.getOrderNo(), order.getPayAmount());
        return RiskResult.passWithAudit();      // 补查由第 44 篇的定时任务兜底
    }
}
```

**数据库变更按"扩展—过渡—收缩"发布，回滚才真的回滚得动。**

```sql
-- 第 1 次发布（Expand）：只加列。旧代码不认识新列也不受影响，这次发布可回滚
ALTER TABLE promo_order ADD COLUMN risk_level TINYINT NULL COMMENT '风控等级，NULL=未评估';

-- 第 2 次发布（Migrate）：双写新列、仍读旧列，同时回填历史数据；依旧保留回滚能力
-- 第 3 次发布（Contract）：确认读路径全切到新列且无旧实例在跑，才删旧列与旧逻辑
--   ★ 收缩永远单独一次发布，且放在观察期之后——删列之后，上一版代码就起不来了
```

**Runbook 最小骨架**（没有它的团队，每次故障都在重新发明流程）：`现象与影响面（哪个接口 / 哪些门店）→ 最近变更清单（发布 / 配置 / 开关 / DDL）→ 证据采集（traceId、线程 dump、生效配置）→ 止血选项与代价 → 通报模板与节奏 → 恢复判定标准（指标回基线并持续 N 分钟）`。

## 6. 常见坑

**坑 1：为了找根因而不止血。** 错误做法：故障还在扩大，人还在读代码追调用链，想用一条命令证明"就是它"。问题：定位的收益属于下一次，而此刻的代价是用户正在持续失败，两者完全不对称。正确做法：**先恢复到已知的安全状态**，恢复判定写死（第 51 篇的指标回基线并持续 N 分钟）。查不清可以，别把故障拖着。

**坑 2：回滚代码时不看数据变更。** 错误做法：一句"回滚上一版"就把包退回去。问题：这次发布若带了 DDL（删列、改类型）或已写入新格式数据，旧代码可能直接起不来，回滚反而制造第二个故障。正确做法：**回滚前先确认三件事**——有没有 DDL、有没有不可逆的外部副作用（已发的券、已扣的库存）、数据是否仍兼容旧代码。不可逆时走补偿脚本，而不是硬退。

**坑 3：复盘停在"人"，没走到"机制"。** 错误做法：结论写"某某误操作，已批评教育"，Action 是"下次注意"。问题：下次一定还会发生，因为不出错的系统本身不存在。正确做法：**无责备复盘**，产出必须能留在仓库里——一条会红的测试（第 53 篇）、一条 ArchUnit 规则（第 55 篇）、一个降级开关（今天）、一条 Runbook 或一处告警阈值修正（第 34 篇的 error / warn 分级），每条带 owner 与截止日期。同类故障第二次发生，要改的是机制不是人。

## 8. 面试 / 工作中常见问题

### 问题 1：接到 P0 告警，你的前三步是什么？

参考答案：① 确认影响面与级别（哪个接口、多少门店、是否还在恶化），指定指挥官与通报人，记下第一个时间戳；② 查最近变更（发布、配置、开关、DDL），把变更时间与指标拐点对齐；③ 按代价选止血手段——回滚 > 降级 > 扩容 > 限流，动手前尽量留证据。**前三步里没有"找到根因"。**

### 问题 2：有人说"重启一下就好了"，你怎么判断？

参考答案：先分清这是"降级恢复"还是"修复"。重启确实常能恢复——它清空堆积、重建泄漏的连接、重置变味的本地缓存；但它同时销毁现场，而且根因若是内存泄漏或数据倾斜，重启只是把故障周期化（每 6 小时一次的规律重启就是明显信号）。合理动作：**重启前抓 dump，重启后立刻看趋势**，并把"为什么需要重启"变成待办而不是结论。

### 问题 3：怎么证明你们的故障处置是有效的？

参考答案：看三个数。MTTD（发现时长，是否告警先于用户投诉）、MTTR（接手到恢复判定的时长，取决于止血手段是否提前备好）、复发率（同类故障是否重复发生，直接反映复盘有没有产出机制）。判据很实用：复盘 Action 里如果全是"加强意识""补文档"，基本说明这次复盘没起作用。

## 9. 今日小结

- **顺序即纪律**：影响面 → 变更对齐 → 取证 → 止血 → 定位 → 复盘；根因排在恢复之后。
- 止血四板斧按代价排序：回滚最便宜（先确认 DDL 与不可逆副作用）、开关降级最快、扩容与限流最粗糙。
- 重启不是修复，它是"清空状态换时间"，而且会销毁现场——能取证再重启。
- 复盘只产出机制才算完成：测试、门禁、开关、Runbook、告警阈值，全部带 owner 与截止日期。
