> **与第 16 篇的分工**：第 16 篇讲**一条 SQL 为什么慢**（EXPLAIN、索引失效）；今天讲**整个服务能扛多少并发、瓶颈在哪一层**。第 16 篇是局部验尸，今天是全局压力实验。

## 1. 今天学什么

接口压测是用可控流量问三个问题：**能扛多少（容量红线）、在哪个并发度开始坏（拐点）、坏的时候先坏什么（瓶颈在哪一层）。** 它不是"跑个工具看看快不快"，而是一次有指标口径、数据准备和隔离方案的实验。

今天讲四件事：① 指标怎么看——TPS、RT 分位数、错误率、饱和度，以及平均 RT 为什么会骗人；② 数据怎么造才失真最小（参数化、预热、流量标记）；③ 拐点出现后怎么把瓶颈定位到线程池、连接池还是 SQL；④ 压测怎么隔离，才不把脏数据打进生产。

容量参数（超时、池大小、副本数）只有压过才有依据，否则它们只是从别人博客抄来的数字——这就是它排在工程化阶段的原因。

## 2. 前端工程师视角理解

你其实早就懂压测最反直觉的那一点：**为什么不能看平均值。** Core Web Vitals 的门槛是按**第 75 百分位**定的，不是平均——因为性能分布严重右偏，少数极慢的样本会被平均数抹平。LCP 平均值 1.2s 很可能意味着 p95 是 6s。后端 RT 完全同理：一个接口平均 40ms 但 p99 1.5s，用户体验就是"每 100 次有 1 次转圈"，而平均值什么也没告诉你。**前端用 p75，后端更常用 p99 / p999，因为后端一次慢请求会占住一个线程。**

第二个锚点是 **Performance 面板**。你抓一段火焰图看谁在长任务里吃时间，后端压测卡住时做的是同一件事：JFR 或 Arthas 出火焰图，看时间花在锁、GC 还是等连接池。差别只是前端瓶颈几乎总在渲染，后端瓶颈常常**不在 CPU**——线程都在"等"，CPU 才 20%，看着很健康，接口已经排成长队。顺带一个让人安心的事实：发压脚本可以是 JavaScript（下面的 k6 就用 JS 写阶梯与 `p(99)<200` 验收线），前端那套"性能预算"的思路直接复用，只是预算对象换成了 TPS 和线程池水位。

## 3. 和 JavaScript / TypeScript 的对比

| 维度 | 前端 / Node | Java 后端压测 |
|---|---|---|
| 核心指标 | LCP/INP 按 p75，性能预算 | TPS、RT 的 p99/p999、错误率、饱和度 |
| 并发模型 | 单事件循环，等待不占线程 | 每请求一线程，等待即占用（池上限=并发上限） |
| 隐性瓶颈 | 主线程长任务、瀑布请求 | 线程池、DB 连接池、锁、下游超时 |
| 火焰图 | Performance 面板 | JFR / Arthas `trace` |
| 脚本 | artillery / k6 | JMeter / Gatling / wrk，k6 也能用 |

**最关键的一个换算关系：Little's Law——并发数 ≈ TPS × RT。** 想要 1000 TPS、RT 稳定在 20ms，只需约 20 个并发在途；但 RT 一旦涨到 100ms，同样的 1000 TPS 就需要 100 个在途。Node 里"等待"很便宜（事件循环挂着就行），Java 里等待要占一个线程、一个数据库连接。所以后端压测经常看到的画面是：**CPU 没满、内存没满，但 Tomcat 线程池 200 个全在等下游，第 201 个请求开始排队**。这也是为什么 Java 必须显式配池——它把"能同时等多件事"变成了一个要设值的参数：默认 200 线程 × 下游 800ms 超时 ≈ 最坏情况下 1 秒只能过 250 个请求。

## 4. 真实业务场景

**场景：大促前给门店下单接口定容量，第一次压测就得出"能扛 3000 TPS"的错误结论。**

业务背景：门店小程序下单接口，8 个实例，大促预估峰值 1500 TPS。压测团队在预发跑了 JMeter，看到 TPS 冲到 3000、平均 RT 30ms，报告写着"容量充足"。

三个问题让这份结论不可信：① 脚本用**同一个门店、同一个商品**反复下单，第 2 分钟起缓存命中率接近 100%（第 45 篇），DB 几乎没压力，而线上几千家门店的真实命中率只有 85%；② 只看平均 RT，p99 已悄悄到 800ms；③ 支付和风控走的是 mock（第 48 篇），而真实链路上这两个下游才是主要耗时。

重做之后结论完全不同：参数化 5000 家门店随机取、风控接真实沙箱、并发从 50 阶梯加到 400，**拐点出现在约 900 TPS**——P99 从 90ms 陡升到 1.2s，错误率 0.3%。用昨天的方法定位：日志里"等连接池"那一段被拉长，`spring.datasource.hikari.maximum-pool-size` 还是**默认值 10**，每台只有 10 个连接抢 DB，慢 SQL 一多池子就被占满，后面的请求全在 `connectionTimeout` 上排队。池调到 30、热点查询加缓存、超时按真实 P99 重设后，拐点推到约 2100 TPS，1500 的峰值才真正有了余量。

**用错的代价**：容量评估虚高不是"数字难看"，而是**大促当天限流、降级、扩容的时间窗被提前用光**——你以为还有 3 倍余量，于是没人盯那个接口。

## 5. Java 示例代码

**容量参数集中声明，压测就是给这些值找证据。**

```yaml
server:
  tomcat:
    threads:
      max: 200               # 默认 200：一个请求占一线程，这里是第一道天花板
    accept-count: 200        # 队列上限，超了直接拒绝而不是无限排队
spring:
  datasource:
    hikari:
      maximum-pool-size: 30  # 默认只有 10！压测里最常撞的那堵墙就是它
      connection-timeout: 3000   # 拿不到连接 3s 就失败，别让它等 30s（默认值）
```

**给关键下游单独埋点，并用标签把压测流量和真实流量分开。**

```java
@Component
@RequiredArgsConstructor
public class RiskGateway {

    private final MeterRegistry registry;      // Micrometer：指标统一入口
    private final RiskHttpClient httpClient;   // 封装好的连接池化 HTTP 客户端

    /**
     * 记录风控调用的耗时分布；tags 里的 pressure 用来在监控上区分压测流量，
     * 否则压测数据会把线上真实曲线一起污染掉。
     */
    public RiskResult call(RiskReq req, boolean pressure) {
        long start = System.nanoTime();
        try {
            return httpClient.post(req);
        } finally {
            Duration cost = Duration.ofNanos(System.nanoTime() - start);
            registry.timer("risk.invoke.duration",
                    "pressure", String.valueOf(pressure)).record(cost);   // p99 由监控系统算
        }
    }
}
```

**发压侧用 k6：阶梯加压 + 把 p99 写成验收门槛。**

```js
export const options = {
  stages: [
    { duration: '2m', target: 50 },    // 预热：JIT、连接池、缓存都要先热起来
    { duration: '5m', target: 200 },   // 稳态：取基线
    { duration: '5m', target: 400 },   // 加压：找拐点
  ],
  thresholds: {
    http_req_duration: ['p(99)<200'],  // 验收线：不是平均值，是分位数
    http_req_failed: ['rate<0.001'],   // 错误率红线 0.1%
  },
};

export default function () {
  // ★ 参数化门店与商品：不参数化就是在压缓存，不是在压服务
  const storeId = __ENV.STORE_IDS.split(',')[Math.floor(Math.random() * 5000)];
  http.post(`${__ENV.BASE}/api/orders`, JSON.stringify({ storeId, skuId: 1001 }),
    { headers: { 'Content-Type': 'application/json', 'X-Pressure': 'true' } });
}
```

`X-Pressure: true` 是压测流量的**标记**：入口 Filter 识别后放进 MDC，一路随 HTTP 头和 MQ 消息头透传（第 50 篇那套传递机制正好复用），下游据此把数据写进影子表、并把第三方接口替换成 mock。

## 6. 常见坑

**坑 1：只看平均 RT。** 错误结论："平均 30ms，没问题。" 问题：分布右偏时平均值被大量快请求拉低，长尾全看不见，而后端恰恰是长尾吃线程。正确做法：**主看 p99 / p999 与错误率**，并同时看饱和度（线程池 active 与队列、连接池 pending、CPU）；容量红线取拐点的 70~80%，别按极限值排班。

**坑 2：脚本不参数化、不预热。** 错误做法：固定一个商品一个门店连打十分钟。问题：同一份数据会把缓存命中率推到失真的高位（第 45 篇），或让行锁排队；而 JIT、建连、缓存回填都需要预热时间。正确做法：门店、用户、商品、时间窗全部随机化并贴近真实分布；预热期数据单独看，拐点结论只取稳态之后的区间。

**坑 3：压测流量打进真实数据。** 错误做法：直接对生产接口加压。问题：真实下单会扣库存、发短信、写脏报表，还可能触发支付风控，把下游压挂等于自己造事故。正确做法：压测标记**全链路透传**、数据落影子表/影子库、第三方一律走沙箱，并关掉消费端与定时任务（第 44 篇），别让对账任务把压测数据统计进去。

## 7. 和之前知识的连接

- **第 50 篇「日志排查」**：拐点上不去时，是日志告诉你哪一段被拉长——场景里"等连接池"那一段就是靠 traceId 分段的耗时看到的；压测报告里的每个拐点都该能对应一条日志或指标。
- **第 48 篇「环境区分」**：压测的隔离方案（第三方沙箱、影子数据、按 profile 关掉消费者）就是那套环境边界的延伸，没有隔离的压测数据等于噪声。
- **第 39 篇「Spring 事务注解」**：连接是被事务占住的——事务里包含 RPC 调用，池上限就直接封顶 TPS。这是场景里默认池 10 会成为瓶颈的根本原因。

## 8. 面试 / 工作中常见问题

### 问题 1：给你一个接口让你压测，你怎么设计与交付？

参考答案：五步。① 定目标（要容量红线还是验证某个改动，峰值 TPS 从哪来）；② 准备隔离环境与参数化数据，分布贴近真实；③ 阶梯加压，同时盯服务端饱和度而不只看客户端 TPS；④ 找到拐点后定位瓶颈层（线程池 / 连接池 / SQL / GC / 下游）；⑤ 交付并发-TPS-RT 曲线、拐点、红线值与建议参数，并写清这个结论只在什么条件下成立。

### 问题 2：TPS 压不上去了，CPU 却只有 20%，接下来看什么？

参考答案：这是"等待型瓶颈"，看四样东西。① 线程状态：大量 `WAITING`/`TIMED_WAITING` 说明在等 IO，用 Arthas `thread` 或线程 dump 看卡在哪个方法；② 连接池水位（HikariCP 的 active/idle/pending），pending 不为 0 就是池太小或 SQL 太慢；③ 下游 RT 分位数与超时配置，一个 800ms 的同步调用能把吞吐按 Little's Law 直接封死；④ 锁与队列：`synchronized`、单线程池、MQ 单分区消费都会串行化。

### 问题 3：怎么判断该压到多少并发、要多大线程池？

参考答案：用 Little's Law 反推——在途并发 ≈ 目标 TPS × RT。目标 1000 TPS、RT 50ms，需要约 50 个在途；但这是稳态估算，要按**最坏下游 RT** 再算一遍下限。而且池不是越大越好：线程越多切换与内存开销越高，DB 侧连接数也另有上限，真正该做的是**缩短 RT、隔离慢依赖**（异步化、超时收紧、缓存），而不是一味放大池。

## 9. 今日小结

- 压测的产出不是一份"跑分"，而是**拐点 + 红线 + 瓶颈层**；指标要 TPS、错误率、饱和度一起看，**RT 主看 p99 / p999**——平均值会骗人，这条直觉前端 p75 早就给了。
- Little's Law（在途并发 ≈ TPS × RT）解释了为什么 Java 必须显式配线程池与连接池：等待是有成本的。
- 数据不参数化就是在压缓存，环境不等价就不能线性外推，压测流量不打标记就会污染生产。
- 默认值是最常见的瓶颈：HikariCP 默认 10 个连接、从别人博客抄来的 800ms 超时，都要靠压测给出证据。
