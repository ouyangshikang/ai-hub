# Java 学习：请求参数校验

> 系列第 21 篇 · 第三阶段：接口与规范  
> 上一篇我们设计了 RESTful 接口，`@RequestBody StoreCreateDTO dto` 接收前端传来的数据。但前端传过来的数据能直接信任吗？今天讲 Spring Boot 的参数校验体系——把"前端传什么后端都照收"变成"不合规的请求在 Controller 层就被拦下"。

## 1. 今天学什么

后端接口是系统的"入口大门"。前端可能因为 bug 传了空值、用户可能手动篡改请求传了负数金额、爬虫可能传了超长字符串试图撑爆数据库字段。如果后端不做校验，这些脏数据会一路穿透到数据库，轻则报错、重则产生脏数据影响业务统计。

Spring Boot 基于 JSR 380（Bean Validation 2.0）规范，提供了一套声明式校验体系：在 DTO 字段上加注解（`@NotNull`、`@Size`、`@Min`），Controller 方法参数加 `@Valid`，框架自动校验、自动返回错误信息。你不需要写一堆 `if (name == null || name.isEmpty())` 的防御代码，校验规则和数据定义放在一起，清晰且可维护。

## 2. 前端工程师视角理解

你在前端一定写过表单校验：

```typescript
// 前端表单校验（比如用 zod、yup 或手写）
const schema = z.object({
  storeName: z.string().min(1, '门店名不能为空').max(50, '最多50字'),
  phone: z.string().regex(/^1[3-9]\d{9}$/, '手机号格式不对'),
  capacity: z.number().min(1, '至少1个座位').max(999),
});

const result = schema.safeParse(formData);
if (!result.success) {
  showErrors(result.error.issues); // 提示用户
  return;
}
```

后端的参数校验和这个思路完全一样——定义规则、自动校验、不通过就拒绝。区别在于：前端校验是"用户体验层"的（让用户少等一次网络请求），后端校验是"安全层"的（防止绕过前端直接调接口）。两者缺一不可：前端校验不能替代后端校验，因为请求可以绕过前端直接发。

你在前端用 zod 写 schema 的体验，和后端在 DTO 上写 `@NotNull`、`@Size` 的体验几乎一致——都是"声明式定义规则，框架帮你执行"。

## 3. 和 JavaScript / TypeScript 的对比

### 声明式校验：zod vs Bean Validation

```typescript
// TypeScript + zod：声明式校验
const createStoreSchema = z.object({
  name: z.string().min(1).max(50),
  phone: z.string().regex(/^1[3-9]\d{9}$/),
  address: z.string().max(200),
  capacity: z.number().int().min(1).max(999),
});
```

```java
// Java + Bean Validation：声明式校验（写在 DTO 类上）
public class StoreCreateDTO {
    @NotBlank(message = "门店名不能为空")
    @Size(max = 50, message = "门店名最多50个字符")
    private String name;

    @NotBlank(message = "手机号不能为空")
    @Pattern(regexp = "^1[3-9]\\d{9}$", message = "手机号格式不正确")
    private String phone;

    @Size(max = 200, message = "地址最多200个字符")
    private String address;

    @NotNull(message = "座位数不能为空")
    @Min(value = 1, message = "座位数至少为1")
    @Max(value = 999, message = "座位数最多999")
    private Integer capacity;
}
```

两者的设计哲学一致：校验规则和数据定义放在一起，不需要在业务逻辑里写 if-else。zod 的 `z.string().min(1)` 对应 Java 的 `@NotBlank`；zod 的 `.max(50)` 对应 `@Size(max = 50)`；zod 的 `.regex(...)` 对应 `@Pattern(regexp = ...)`。

### 校验触发方式

```typescript
// 前端：手动调用 parse
const result = schema.safeParse(data);
```

```java
// 后端：Controller 参数加 @Valid，框架自动触发
@PostMapping
public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) {
    // 走到这里说明校验已通过，dto 里的数据是合规的
}
```

前端需要你主动调 `parse`，后端只要加了 `@Valid`，Spring MVC 在反序列化 JSON 为 DTO 之后、进入方法体之前自动执行校验。校验不通过直接抛 `MethodArgumentNotValidException`，不会进入你的业务代码。

### 为什么 Java 后端更依赖注解校验

前端校验失败了，用户看到提示、改完重新提交就行。后端校验失败了，脏数据可能已经写进数据库、影响了下游报表和结算。而且后端接口不只被一个前端调用——可能有 App、小程序、第三方系统、甚至 curl 直接调。没有统一的后端校验，每个调用方都可能传入不合规数据。注解校验是"一次定义、所有调用方统一拦截"。

## 4. 真实业务场景

门店管理系统里，运营新增门店时需要填写：门店名称、联系电话、地址、座位数、经度纬度。

如果不做后端校验会怎样？

一是空值穿透。前端表单虽然有必填校验，但有人用 Postman 直接调接口、或者前端代码有 bug 漏了校验，`name` 传了 null 进来。没有后端校验的话，null 直接写进数据库，列表页显示"null"，运营以为是数据录入问题，排查半天才发现是接口没拦。

二是边界越界。`capacity` 传了 -1 或 999999，写进数据库后，报表统计"总座位数"时出现负数或异常大的数字，影响运营决策。金额字段传了负数，可能导致退款逻辑异常。

三是超长字符串。`address` 字段数据库定义 varchar(200)，前端传了 500 个字符，没有校验的话直接触发数据库的 `Data too long` 异常，接口返回 500，前端只看到"服务器错误"，完全不知道是参数问题。

## 5. Java 示例代码

```java
/**
 * 新增门店的请求 DTO
 * 校验注解直接写在字段上，规则和数据定义在一起
 */
public class StoreCreateDTO {

    @NotBlank(message = "门店名称不能为空")
    @Size(max = 50, message = "门店名称最多50个字符")
    private String name;

    @NotBlank(message = "联系电话不能为空")
    @Pattern(regexp = "^1[3-9]\\d{9}$", message = "手机号格式不正确")
    private String phone;

    @Size(max = 200, message = "地址最多200个字符")
    private String address;

    @NotNull(message = "座位数不能为空")
    @Min(value = 1, message = "座位数至少为1")
    @Max(value = 999, message = "座位数最多999")
    private Integer capacity;

    // getter / setter 省略
}
```

```java
@RestController
@RequestMapping("/api/stores")
public class StoreController {

    @Autowired
    private StoreService storeService;

    /**
     * @Valid 触发自动校验
     * 校验不通过 → 抛 MethodArgumentNotValidException → 不会进入方法体
     * 校验通过 → dto 里的数据保证合规，业务代码不需要再判空
     */
    @PostMapping
    public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) {
        Long storeId = storeService.createStore(dto);
        return Result.success(storeId);
    }
}
```

```java
/**
 * 全局异常处理：把校验失败转成前端能理解的错误响应
 * （第六阶段会专门讲全局异常处理，这里先给一个基本写法）
 */
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidation(MethodArgumentNotValidException e) {
        // 取第一条校验失败的错误信息
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .findFirst()
                .orElse("参数校验失败");
        return Result.fail(400, message);
    }
}
```

前端收到的响应：`{ "code": 400, "message": "门店名称不能为空", "data": null }`。和你在前端用 zod 校验失败后展示错误提示是一个逻辑——只不过拦截点从浏览器换到了服务端。

## 6. 常见坑

### 坑 1：@NotNull、@NotEmpty、@NotBlank 分不清

```java
// @NotNull：不能为 null，但可以是空字符串 ""
// @NotEmpty：不能为 null，且不能为空（""、空集合、空数组都不行）
// @NotBlank：不能为 null，且去掉首尾空格后不能为空（专用于 String）

@NotNull   // "  " 能通过 ❌（纯空格字符串）
@NotEmpty  // "  " 能通过 ❌（不是空串，只是空格）
@NotBlank  // "  " 不通过 ✅（trim 后为空）
private String name;
```

字符串字段（名称、手机号）用 `@NotBlank`；集合字段（标签列表）用 `@NotEmpty`；对象字段（嵌套 DTO）用 `@NotNull`。用错了等于没校验。

### 坑 2：嵌套对象没加 @Valid，内层校验不生效

```java
public class StoreCreateDTO {
    @NotBlank
    private String name;

    @NotNull
    @Valid  // ← 不加这个，AddressDTO 里的校验注解全部失效！
    private AddressDTO address;
}

public class AddressDTO {
    @NotBlank(message = "省不能为空")
    private String province;
    @NotBlank(message = "市不能为空")
    private String city;
}
```

嵌套对象字段上必须同时加 `@NotNull`（保证对象本身不为 null）和 `@Valid`（触发内层字段的校验）。漏了 `@Valid`，内层注解形同虚设，脏数据照样穿透。

### 坑 3：@Valid 和 @Validated 混用

```java
// @Valid：JSR 380 标准注解，支持嵌套校验
// @Validated：Spring 扩展注解，支持分组校验，但不支持嵌套

// ❌ 用 @Validated 接收嵌套对象，内层校验不触发
public Result<Long> create(@RequestBody @Validated StoreCreateDTO dto)

// ✅ 需要嵌套校验时用 @Valid
public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto)
```

简单场景用 `@Valid` 就够了；需要分组校验（同一个 DTO 在新增和编辑时校验规则不同）时用 `@Validated`，但嵌套字段上仍然要加 `@Valid`。

### 坑 4：校验注解的 message 写得太技术化

```java
// ❌ 前端拿到这种错误信息，用户看不懂
@Size(min = 1, max = 50, message = "size must be between 1 and 50")

// ✅ 写业务语言，前端可以直接展示给用户
@Size(min = 1, max = 50, message = "门店名称长度为1-50个字符")
```

`message` 是最终返回给前端的错误提示，要写成用户能理解的业务语言，而不是框架默认的英文技术描述。

### 坑 5：只校验了 Controller 层，Service 层被其他入口绕过

```java
// Controller 有 @Valid 校验
@PostMapping
public Result<Long> create(@RequestBody @Valid StoreCreateDTO dto) { ... }

// 但定时任务、消息消费者直接调 Service，绕过了 Controller
@Scheduled(cron = "0 0 2 * * ?")
public void syncStores() {
    storeService.createStore(buildDtoFromExternalData()); // 没有校验！
}
```

`@Valid` 只在 Controller 层生效。如果 Service 方法还有其他调用入口（定时任务、MQ 消费者、内部 RPC），那些入口不会触发校验。关键业务逻辑的防御性检查，Service 层也要做。

## 7. 和之前知识的连接

- **第 20 篇「RESTful 接口设计」** 是今天的直接前置。上一篇 `@PostMapping` + `@RequestBody StoreCreateDTO dto` 接收前端数据，今天解决的是"接收之后、进入业务逻辑之前，怎么确认数据是合规的"。RESTful 管接口"长什么样"，参数校验管接口"收什么数据"。

- **第 10 篇「DTO / VO / Entity 的区别」**：校验注解写在 DTO 上，不写在 Entity 上。DTO 是"前端传入的数据结构"，是校验的天然载体；Entity 是"数据库的映射"，字段约束由数据库 DDL 保证。把 `@NotBlank` 写在 Entity 上会导致从数据库查出来的数据也触发校验（比如历史数据某个字段允许为空），产生莫名其妙的校验失败。

- **第 8 篇「Controller / Service / Mapper 分层」**：参数校验是 Controller 层的职责。Controller 负责"接收参数、校验参数、调用 Service、返回结果"，校验不通过就不该进入 Service 层。这是分层架构中"每层只管自己的事"的体现——Controller 管入口合法性，Service 管业务逻辑，Mapper 管数据存取。

## 8. 面试 / 工作中常见问题

### 问题 1：@NotNull、@NotEmpty、@NotBlank 有什么区别？

参考答案：`@NotNull` 只判断不为 null，空字符串 `""` 和纯空格 `"  "` 都能通过；`@NotEmpty` 判断不为 null 且不为空（`""`、空集合、空数组不通过），但纯空格字符串 `"  "` 能通过；`@NotBlank` 专用于 String，判断不为 null 且 trim 后不为空，纯空格也不通过。实际使用：字符串字段用 `@NotBlank`，集合/数组用 `@NotEmpty`，对象引用用 `@NotNull`。

### 问题 2：前端已经做了表单校验，后端还需要再校验吗？

参考答案：必须校验。前端校验是用户体验优化（减少无效网络请求），后端校验是安全防线。请求可以绕过前端直接发——Postman、curl、爬虫、篡改请求都能绕过前端校验。后端是数据的最后一道关卡，不校验就意味着脏数据可以直接写入数据库。两层校验的目的不同：前端为了体验，后端为了安全。

### 问题 3：校验失败的错误信息怎么返回给前端？你们项目怎么处理的？

参考答案：通过全局异常处理器（`@RestControllerAdvice` + `@ExceptionHandler(MethodArgumentNotValidException.class)`）统一捕获校验异常，从 `BindingResult` 中提取字段错误信息，封装成统一的错误响应结构（code + message）返回。不在每个 Controller 方法里单独处理校验失败，而是全局统一拦截、统一格式，前端只需要判断 `code != 200` 就展示 message。

## 9. 今日小结

- 参数校验是后端的安全底线：前端校验管体验，后端校验管安全，两者缺一不可。
- Bean Validation 是声明式校验——注解写在 DTO 字段上，`@Valid` 触发自动执行，不需要手写 if-else。
- 字符串用 `@NotBlank`，集合用 `@NotEmpty`，对象用 `@NotNull`，用错等于没校验。
- 嵌套对象必须加 `@Valid` 才能触发内层校验，漏了就是形同虚设。
- 校验是 Controller 层的职责，Service 层被其他入口调用时不会触发 `@Valid`，关键逻辑仍需防御性检查。

明天建议学习：`统一返回结构`

原因：今天校验失败时返回了 `{ "code": 400, "message": "门店名称不能为空" }`，成功时返回了 `{ "code": 200, "data": 10086 }`。这个 `code + message + data` 的结构就是"统一返回结构"。目前每个接口各自包装返回值，格式不统一、字段名不一致，前端每次对接都要猜"这个接口的成功标识是 code=200 还是 success=true"。明天讲怎么设计一套全局统一的响应结构，让所有接口的返回格式一致，前端只需要一套通用的响应拦截逻辑。
