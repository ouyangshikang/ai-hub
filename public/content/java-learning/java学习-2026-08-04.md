# Java 学习：前后端字段命名约定

> 系列第 27 篇 · 第三阶段：接口与规范（收口篇）  
> 上一篇我们讲了改名必须"新老双写过渡"，代价很高。但值得追问一句：为什么 `storeName` 和 `name` 这种命名分歧一开始就会出现？根源是前后端对字段命名没有统一约定——Java 习惯驼峰、数据库习惯下划线、前端有时又想要别的名字。今天把从数据库列名到前端 JSON 的完整命名链路讲清楚，让接口从第一天就不需要兼容性补救。这也是第三阶段的最后一篇。

## 1. 今天学什么

同一个"门店名称"，在系统里可能以三个名字活着：数据库列叫 `store_name`（下划线风格），Java 字段叫 `storeName`（小驼峰风格），接口 JSON 里可能叫 `storeName`、也可能被某个同事写成 `store_name`。这不是谁粗心，而是三个世界各有各的命名传统：数据库社区约定列名用小写下划线（MySQL 对大小写不敏感，驼峰在里面毫无意义）；Java 语言规范要求变量和字段用小驼峰；JSON 本身没有约定，但前端 JavaScript 的对象属性习惯也是小驼峰。

字段命名约定要解决的就是：**给整条链路定一个统一规则，让每个环节的转换都由框架自动完成，而不是靠人在 Service 层手动改名字**。规则定得好，`store_name` 从数据库到前端一路自动变成 `storeName`，没人需要手写转换；规则没定好，就会出现同一份数据三个名字、前端联调时对着一堆 `undefined` 猜谜。

这个问题放在第三阶段最后讲是有原因的：前面学的参数校验、统一返回、状态码、参数接收、幂等、兼容性，都是在接口已经存在的前提下做加固；而命名约定是"接口长什么样"的最底层决定——它如果一开始就乱，后面所有机制都要为它擦屁股。

## 2. 前端工程师视角理解

你对这个问题其实一点都不陌生。联调时最烦的事之一就是：接口文档写的是 `storeName`，实际返回的是 `store_name`，于是你的 `item.storeName` 全是 `undefined`，只能临时加一层转换：

```typescript
// 前端被迫做的"翻译"工作
const list = res.data.records.map((item: any) => ({
  storeName: item.store_name,
  monthGmv: item.month_gmv,
  createTime: item.create_time
}))
```

这种代码写多了你一定会问：后端就不能直接给我驼峰吗？答案是可以，而且 Java 生态的默认行为就是给你驼峰。真正的问题是：有些后端同事手动返回了 Map、有些老接口照抄了数据库列名、有些团队全局配了下划线策略但没同步前端。混乱不来自技术，来自约定缺失。

前端自己也有一套对应的机制来做同样的事。如果你们对接的是一个下划线风格的 API（比如 GitHub API 就是 snake_case），常见做法是在 axios 拦截器里统一转换：

```typescript
import { camelCase, snakeCase } from 'lodash-es'

// 请求时：前端驼峰 → 接口下划线
axios.interceptors.request.use(config => {
  config.data = deepMapKeys(config.data, snakeCase)
  return config
})
// 响应时：接口下划线 → 前端驼峰
axios.interceptors.response.use(res => {
  res.data = deepMapKeys(res.data, camelCase)
  return res
})
```

这个拦截器就是前端版的"命名策略"——和 Java 里 Jackson 的命名策略是同一个思想：**约定只定一次，转换交给统一的机制，业务代码永远只写自己习惯的风格**。

## 3. 和 JavaScript / TypeScript 的对比

### 为什么 Node.js 后端很少遇到这个问题，Java 却必须处理

如果你用 Node.js 写过后端，会发现几乎没有命名转换这回事——数据库驱动查出来的行对象、JS 变量、返回的 JSON，全在一个语言、一种风格里流动，列名是什么出来就是什么。而 Java 跨了三个世界：SQL 世界（下划线）、Java 语言世界（驼峰，这是语言规范强制的，你把字段写成 `store_name` IDE 都会给你标黄警告）、JSON 世界（自由但默认跟随 Java 字段）。跨的世界多，所以需要框架在每道边界上自动搬运。这也是 Java 生态"框架重"的一个正面例子：约定被编码进了工具里，而不是靠人记。

### TS 类型定义：命名混乱的第一受害者

命名不统一的代价在 TypeScript 项目里会被放大。你的接口类型得忠实反映 JSON 的实际字段名：

```typescript
// 如果接口风格混乱，类型定义就成了备忘录
interface StoreVO {
  storeName: string      // 驼峰
  month_gmv: number      // 这个接口却是下划线
  openTime: string       // 驼峰
  last_order_at: string  // 另一个同事写的接口，又是下划线
}
```

TS 编译器能检查你拼错字段名，但救不了"后端返回的风格和文档不一致"——类型是按文档写的，运行时的 JSON 却是另一个样子。所以命名约定的受益者首先是前端：风格统一后，接口类型可以机械地生成（比如从 Swagger 自动生成），不再需要人肉核对。

### ESLint 的命名规则 vs Java 的统一约定

前端会用 ESLint 的 `@typescript-eslint/naming-convention` 规则强制变量、属性用驼峰，本质是"把约定变成自动化检查"。Java 侧的对应物不是一个 linter，而是框架的默认行为：JavaBeans 规范决定了 getter/setter 和字段名都是驼峰，Jackson 序列化默认照搬字段名，MyBatis 提供开关完成下划线到驼峰的映射。也就是说 Java 不需要 lint 命名风格——语言规范已经替你选好了，真正需要团队显式约定的只有"JSON 出口用哪种风格"这一件事。

## 4. 真实业务场景

**场景：门店运营报表系统，两个后端同事先后开发，命名风格分裂。**

业务背景：门店系统有一张报表，展示每家门店的月度营业额。数据库表长这样：

```sql
CREATE TABLE store_month_report (
    id BIGINT PRIMARY KEY,
    store_name VARCHAR(64),    -- 下划线风格
    month_gmv DECIMAL(12,2),   -- 月度营业额
    create_time DATETIME
);
```

同事 A 开发了第一个报表接口，老实用 Java 里定义 VO 字段为 `storeName`、`monthGmv`，Jackson 默认序列化，前端拿到的是驼峰，皆大欢喜。

同事 B 后来加了一个"导出明细"接口，图省事直接返回了 MyBatis 查出来的 Map：

```java
// 同事 B 的写法：直接把查询结果（Map）返回
@GetMapping("/export-detail")
public Result<List<Map<String, Object>>> exportDetail(@RequestParam String month) {
    // MyBatis 返回 Map 时，key 就是数据库列名：store_name、month_gmv
    return Result.success(reportMapper.selectDetailByMonth(month));
}
```

前端收到的 JSON 突然变成了 `store_name` 和 `month_gmv`，和列表页的 `storeName`、`monthGmv` 风格完全不同。前端只能写两套解析逻辑，或者到处加转换。更糟的是三个月后要做字段调整（接上一篇的内容）：同一份数据在系统里有两套名字，改哪个都得双写过渡，兼容性成本直接翻倍。

问题的本质不是同事 B 技术差，而是团队没有一条写进规范的约定："所有接口 JSON 一律小驼峰，禁止直接返回 Map 或 Entity"。约定缺失时，每个人都会按自己最顺手的方式写。

## 5. Java 示例代码

**第一步：数据库 → Entity，MyBatis 自动转驼峰。**

```yaml
# application.yml：一个开关搞定下划线转驼峰
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true   # store_name 自动映射到 storeName
```

```java
// Entity 里只管写标准驼峰，不用关心数据库列长什么样
@Data
@TableName("store_month_report")
public class StoreMonthReport {
    private Long id;
    private String storeName;    // 自动对应 store_name 列
    private BigDecimal monthGmv; // 自动对应 month_gmv 列
    private LocalDateTime createTime;
}
```

**第二步：Entity → VO，Java 内部全程驼峰，无转换。**

```java
@Data
public class StoreReportVO {
    private Long id;
    private String storeName;
    private BigDecimal monthGmv;
    private String createTime; // 日期格式在第 4 阶段会专门讲
}
```

**第三步：VO → JSON，Jackson 默认输出驼峰，前端直接可用。**

```java
@GetMapping("/list")
public Result<List<StoreReportVO>> list(@RequestParam String month) {
    // 返回强类型 VO 而不是 Map：字段名可控、风格统一、有编译期检查
    return Result.success(reportService.queryByMonth(month));
}
// 前端收到：{ "code": 0, "data": [{ "storeName": "望京店", "monthGmv": 88000.50 }] }
```

**特殊情况的正规武器：`@JsonProperty` 单字段改名。**

```java
public class StoreReportVO {
    // 对接第三方老系统，对方只认下划线字段名
    // 只改这一个字段的 JSON 输出名，不影响其他字段和 Java 内部写法
    @JsonProperty("month_gmv")
    private BigDecimal monthGmv;
}
```

```java
// 反序列化方向：一个字段接受多种入参名字（上一篇兼容性的双写利器）
public class StoreQueryDTO {
    @JsonAlias({"store_name", "shopName"}) // 历史调用方传什么都接得住
    private String storeName;
}
```

**全局命名策略（慎用）：让整个项目的 JSON 都变下划线。**

```yaml
# application.yml：全局生效，所有接口 JSON 从驼峰变下划线
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```

这个配置适合从零开始、且团队明确要对齐下划线风格（比如对接 Python / Ruby 生态）的项目。但对已上线的项目改这一行，等于把所有接口的字段名一夜之间全改了——这是最典型的破坏性变更，直接违反上一篇的兼容性原则。

## 6. 常见坑

**坑 1：直接返回 Map 或 Entity，把数据库列名暴露给前端。**

错误写法：MyBatis 返回类型写 `List<Map<String, Object>>`，或者偷懒直接把 Entity 当返回值。问题：Map 的 key 是数据库列名（下划线），Entity 还可能带 `password`、`deleted` 这类不该给前端的字段。正确做法：Controller 出口永远是专门的 VO 对象，Entity 到 VO 的转换在 Service 层完成——这也是第 10 篇 DTO/VO/Entity 分工的直接应用。

**坑 2：在已有项目上改全局 Jackson 命名策略。**

错误写法：为了让新对接的某个外部系统舒服，把 `property-naming-strategy` 改成 `SNAKE_CASE`。问题：这是全局生效的破坏性变更，所有存量接口的字段名全部翻转，所有老版本前端瞬间拿到一堆 `undefined`。正确做法：全局策略只能在项目第一天定；存量项目有这种需求，要么单独为外部系统开一组新接口并用 `@JsonProperty` 标注，要么让对方做转换。

**坑 3：忘了开 `map-underscore-to-camel-case`，Entity 字段全是 null。**

错误现象：查询明明有数据，Entity 里除了 id 全是 null。问题：MyBatis 默认按"列名和字段名完全一致"去映射，`store_name` 找不到叫 `store_name` 的 Java 字段。正确做法：全局开启 `map-underscore-to-camel-case: true`；个别不匹配的列用第 14 篇学过的 resultMap 显式指定列和字段的对应关系。

**坑 4：`@JsonProperty` 到处乱用，团队内部风格再次分裂。**

错误写法：每个开发都按自己对接过的老系统习惯给字段加 `@JsonProperty`，项目里驼峰和下划线混飞。问题：单字段注解是"局部例外"的工具，用多了就变成了新的混乱源头，而且这类差异全局搜索很难发现。正确做法：`@JsonProperty` 只允许用于有明确外部原因的字段（对接第三方、兼容历史调用方），且必须写注释说明原因；团队内部的接口一律保持全局统一风格。

**坑 5：前端和后端各自做转换，转了两次。**

错误现象：后端已经配了全局 `SNAKE_CASE` 输出下划线，前端 axios 拦截器又配了"请求转下划线、响应转驼峰"；某天后端把某个接口改回驼峰输出，前端拦截器把它转成了 `store[name]` 这种怪东西。问题：转换策略必须全链路只存在一处。正确做法：联调前先对齐——接口出口是什么风格、前端拦截器按什么风格转，两边配置写在同一份联调约定里，改任何一边都要通知对方。

## 7. 和之前知识的连接

- **第 26 篇「接口兼容性」**：今天的主题就是上一篇问题的"治本方案"。改名要双写过渡，代价极高；而命名混乱正是改名的最大来源。约定统一后，字段从第一天就叫对名字，兼容性机制只需要留给真正的业务演进。反过来，今天讲的"全局策略不能在存量项目上改"，也正是上一篇"破坏性变更"原则的直接应用。

- **第 10 篇「DTO / VO / Entity 的区别」**：今天的命名链路完整走了一遍这三种对象的分工——Entity 承载数据库映射（靠 MyBatis 转驼峰）、DTO 承载入参（靠 `@JsonAlias` 兼容历史写法）、VO 承载出参（靠 Jackson 输出统一风格）。对象分层不只是"数据结构不同"，也是命名转换发生的位置。

- **第 14 篇「MyBatis 查询结果映射」**：当时讲的 resultMap 是"手动指定列和字段的对应关系"，今天的 `map-underscore-to-camel-case` 是把最常见的下划线转驼峰变成了全局默认。两者是同一机制的两个档位：默认规则覆盖 95% 的情况，resultMap 处理剩下 5% 的特殊列。

- **第 22 篇「统一返回结构」**：命名约定作用在 `Result<T>` 的 `data` 内部。外层信封 `{ code, message, data }` 是全局冻结的，内层字段的风格统一则依赖今天讲的规则——外层稳定加内层有序，接口契约才算完整。

## 8. 面试 / 工作中常见问题

### 问题 1：为什么数据库用下划线、Java 用驼峰？框架是怎么打通的？

参考答案：数据库列名传统上用小写下划线，因为 SQL 对大小写不敏感，驼峰没有表达力，而 `order`、`desc` 这类词还涉及关键字冲突；Java 字段用小驼峰是语言规范（JavaBeans）的强制约定。打通靠两道自动转换：MyBatis 的 `map-underscore-to-camel-case` 开关负责"数据库列 → Java 字段"，Jackson 序列化默认按 Java 字段名输出 JSON 负责"Java 字段 → 前端"。理想状态下开发者全程只写驼峰，转换全部由框架完成。

### 问题 2：前端要求接口返回下划线风格，你作为后端怎么回应？

参考答案：先分清是存量还是增量。新项目可以在第一天就配 Jackson 全局 `SNAKE_CASE` 策略，大家按约定开发。但如果是已上线的项目，改全局策略等于对所有接口做破坏性变更，应该拒绝；替代方案是要么前端在 axios 拦截器里统一做驼峰/下划线转换（前端一次性成本），要么为特定调用方单独开一组接口并用 `@JsonProperty` 标注。核心原则：命名风格只能在项目起点定一次，中途切换的代价由所有人分摊。

### 问题 3：联调时发现某个接口的字段风格和其他接口不一致，你怎么排查？

参考答案：按三个可能源头依次查。第一看 Controller 返回的是不是 VO——如果直接返回了 Map 或 Entity，字段名就会是数据库列名（下划线）。第二看 VO 类里有没有 `@JsonProperty` 或 `@JsonAlias` 注解改过单个字段的 JSON 名字。第三看项目里有没有全局 Jackson 命名策略配置，以及这个模块是否被单独覆盖过。实践中第一种（返回 Map）和第二种（有人随手加注解）占绝大多数，找到后按团队约定修正，并在规范里补上对应条目。

## 9. 今日小结

- 同一份数据在系统里有三次"换装"：数据库列（下划线）→ Java 字段（驼峰）→ JSON（团队约定，推荐驼峰）。混乱来自约定缺失，不来自技术。
- 两道框架开关打通全链路：MyBatis `map-underscore-to-camel-case` 管入库映射，Jackson 默认序列化管出口输出——开发者全程只写驼峰。
- `@JsonProperty` / `@JsonAlias` 是局部例外的正规武器，只用于有明确外部原因的字段；全局命名策略只能在项目第一天定，存量项目改它就是全员破坏性变更。
- Controller 出口永远是 VO，不是 Map 也不是 Entity——这既保证命名统一，也防止内部字段泄露。
- 前端侧的对应物是 axios 拦截器统一转换：风格约定全链路只存在一处，改任何一边都要同步对方。
